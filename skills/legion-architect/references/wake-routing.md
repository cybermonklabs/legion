# Wake routing

Read this when a wake reaches you. A wake about an issue reaches its own architect while that
architect holds its role, else the nearest one above that does. A `catch-up` reaches only the
architect of its own issue. A `child-status` or `child-closed`, and a `worker-died` or
`worker-stalled` about a child's own architect, reach the architect above the child. Your role
prompt describes each notice; this table says what to do. "Section N" is that section of
`skill://legion-architect`. Where a row says to ask a person, a child's own architect sends the
question to the architect above it.

| Wake | What to do |
| --- | --- |
| `catch-up` | Start or resume from it as your role prompt says. Accept each issue its `reason` names as waiting for you (section 6), a parent only after its last round. |
| `design-approved` | One gated step opened; `gatedSteps` in `read_record` says which. Once every step is `approved`, release the children (section 2). A task saying "this resume is your design-approved wake" is this wake. On a `handed_over` root, or a version a person's answer to a decision block wrote, start nothing. |
| `design-changes-requested` | Revise the document of the step whose `status` is `changes_requested` as the reason asks, run step 3's two reviews on the new version and resolve every finding, then request approval again ("The armed gate" in `skill://legion-architect/references/design-gate.md`) and end your turn. One for an older version came late: answer its reason if the latest version does not. |
| `carried-gate-opened` | The gate this root carried opened. Start nothing and release nothing for it. |
| `phase-finished` | The next phase already started. Read the finished handoff (`dispatch handoff-read --issue <issue> --phase <word>`). Where it leaves a gap (an `openQuestions` or `deviations` entry, or a `gapAnalysis` finding with no `answer`), tell the role now working the issue with `envoy_publish` to its role topic. A planner's departure from the design: keep the plan while the Summary, requirements, checks, scope and settled decisions hold, else change the spec ("After approval" in design-gate.md). On a child, read the same condition against the child's spec at the version its parent's review approved; when it does not hold, write a new version of the child's spec and have the architect above review it (`skill://legion-architect/references/decomposition.md`, "Reviewing a child's spec"). A reviewer's `CHANGES_REQUESTED` needs nothing from you: the daemon has returned the issue to `implementing` and started the implementer. A reviewer's `APPROVED`: section 6. A tester's `verdict: "fail"` has gone back to the implementer; never record that check's result from another role. A worker reporting that no surface reaches the changed path: build the surface in this tree, as a child after the red-team check in `skill://legion-architect/references/decomposition.md`, or, when the red team folds it, tell the waiting worker to move the issue back to `implementing` with `request_backward_move`, naming the surface. When it is a child, tell the waiting worker to continue with `envoy_publish` to its role topic once that child's `child-closed` arrives. That report is never a reason to advance the phase. |
| `pr-blocked` | The review round cap is reached: read `skill://legion-architect/references/wake-routing-capped-pull-request.md` and decide in this turn. |
| `checks-red` | The daemon asked the implementer to merge the base forward; the issue stays in the phase the notice names. Start nothing; in `accepting`, wait for the reviewer's approval of the new head ("A conflicting head" in `skill://legion-architect/references/acceptance.md`). |
| `review-stuck` | No review decides the round, or the approval is of other code: tell the reviewer on the notice's `topic` to approve the head or request changes; ask a person when it answers again with no review. GitHub will not merge the head: no `topic`, and its `reason` names the merge state, each check run with its conclusion and each commit status with its state; sort it as your role prompt says. |
| `pr-merged` | Merged, not closed: it waits to reach `merging`, or for the issues beneath it. Start nothing. |
| `pr-closed-unmerged` | Decide whether the work reopens, restarts (`park_child` then `rerun_child`) or ends, and give the reason. A child's own architect cannot park or rerun its own issue (`ISSUE_NOT_OWNED`), so it sends a restart of its issue to the architect above it. A phase worker makes the repository change. |
| `pull-request-missing` | Tell the implementer to open the pull request from the branch the reason names. |
| `child-status`, `child-closed`, `child-release-stalled`, `child-not-recorded` | Read `skill://legion-architect/references/wake-routing-children.md` when one of these reaches you. |
| `children-first` | Release every child that should run. Park a child only when a person asked for that move, or when the work is done, folded into another issue or no longer needed, and cite that reason in a comment on the child. A released child, a held one included, stays under the parent, because the parent's wait ends when that child leaves the workflow. Move out from under the parent only a child you have not released and that should not run now. Move it under another issue you own (the root's architect owns every issue of the tree, a child's architect its own issue and the issues under it) that has started a phase and has not reached `accepting`, and never under an issue it waits on. After the move, ask the person on the root (`dispatch ask`) when that child's work should run or stop: release it when they say to run it; when they say to stop it, close it, or move it to `icebox` under the rule when they say its work should wait, citing their answer. Until they answer, sign off neither the issue you moved it under nor any issue above it that you accept. Never give such a child the `legion` label, and never clear its parent while the tree is live: the daemon admits an orphan as a root of its own only when its tree is not live, so such a child would run nowhere. Where you own no issue to move the child under, ask the person. A `blocked_by` link up the parent chain: ask a person to remove it. |
| `worker-died`, `worker-stalled`, `worker-silent`, `worker-background-stalled`, `volume-near-full` | Read `skill://legion-architect/references/wake-routing-workers.md` when one of these reaches you. |
| `held` | No `reason`: answer the `worker-died` that comes with it. `reason: "escalated"`: the controller has it; start nothing. Your `retry` is not the only release: a `todo` written on a held root releases the hold the same way, whoever writes it, so an issue you left held may be working that phase again when you next read it. |
| `message-refused` | Post what a person still needs yourself. Where Dispatch refused the status itself, ask a person to set it. |
| `status-reasserted` | A session outside the tree wrote a status on the root, and the daemon set it back. Ask a person when it reads as a wish to stop the tree. |
| A reply on an ask you follow | Interpret the reply in the issue's design context. Answer in its thread (`dispatch comment --reply-to <comment id>`) when it carries a question, a disagreement, a correction or a fact you lack, and whenever you are unsure. Under an approval request you must revise or hand back, `--reply-to-ask <ask id> --turn agent`, since a default reply gives the turn to the person. An approval or a settled answer draws no reply. Then adjust the plan, or relay the reply with `envoy_publish` to the role topic of the worker whose work it changes or whose question it answers, even when it needs nothing from you. Scope and product decisions remain with you. |
