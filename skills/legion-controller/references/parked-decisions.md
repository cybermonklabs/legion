# Decisions on a parked tree

Read this on a `parked-decision` wake, and for the parked-root walk at every start and on each `tick`. A parked tree is a labelled root in `backlog` or `icebox` whose `issues.<KEY>.phase` is `done`. A park means "should not run now", and a parked root keeps its `legion` label. Its architect is gone, so nobody inside it hears a person's decision. The daemon sends you each one as `parked-decision` (`decision`, `root`, `ref`, `actor`, and a spec decision's `version` and `reason`); the walk finds those sent while no controller ran. Read `skill://legion-controller/references/parked-decisions-notice.md` when you need what a field of the notice holds. When the tree runs, its architect's start task, or the catch-up of a later launch, names each decision the daemon relayed, and both versions of an approved document when the approved one is not the current one, so you need not tell it.

A person's own approval of a parked root's primary document while no tree is live is no decision for you: the daemon sets the root `todo` itself. A carried approval, or one on a root that keeps a Dispatch parent, is a decision. A session's reply on a parked tree is none.

A held root is not a parked one: `todo` on a root at `phase: held` releases the hold at the same generation. A root that is parked or lingers takes `todo` alone, and that `todo` re-admits its tree: a root whose tree lingers or stands at `phase: done` is re-admitted at a new generation. A root still in the workflow whose architect stopped takes `backlog`, then `todo`, which re-admits the tree.

## Deciding

1. **Where the tree stands.** Read `issues.<root>`.
   - `phase` is not `done`: the tree runs. When its `architect.state` is `failed` or `retired`, nobody heard: judge it in steps 3 and 4. Re-admit a tree whose decision gives a next step with `backlog`, then `todo`, once the `worker-died` section of `skill://legion-controller/references/wakes.md` finds no cause or finds it gone; while the cause stays, the tree stays admitted under the park ask of `skill://legion-controller/references/park-asks.md`. Otherwise the tree heard it: do nothing.
   - `phase` is `done`: `dispatch read --issue <root>`. In `backlog` or `icebox`, go on. In any other status, set nothing and name `ref` in your summary.
2. **Who parked it.** Under the root's `Events:`, each `issue.created`, `issue.updated` and `issue.closed` line ends `status <status>`. The park is the oldest line of the newest unbroken run of those lines showing the current status; an event of another type between two of them does not break the run. It is your own hold only when that line is by `session legion-daemon:<PROJECT>` and, within 10 minutes after it, a session's comment begins `Parked by Legion while it waits on:`. Every other park is someone else's. `Events:` shows only the last 10 events: when the run reaches the oldest one shown, read `/api/v1/issues/<root>/events?limit=200` with the `curl` of `skill://legion-controller/references/session.md` ("Reading Dispatch's API"); when it still does, you cannot read who parked it, so judge only the events newer than the oldest you read. Name in your summary, as one you could not place, each older decision that no newer `Parked decision read:` comment has judged (an approval's or a changes request's two events as one, by its `ref`). When no event you read shows a status, the park is older than every one of them. A decision older than the park is no reason to run.
3. **Read once.** A `Parked decision read:` comment from any session, newer than the decision, on the root or the decision's issue, has judged it: do nothing.
4. **Judge the words, not the kind.** Read the decision: `dispatch read --ref <ref>` for an ask or a reply; for a request for changes, the notice's `reason` or the issue's `Spec approval:` line; for an approval, `issues.<root>.designGate` and `gatedSteps`. An approval or a request for changes is two events at one time, the approval request's `ask.answered` and `artifact.approved` or `artifact.changes_requested`: judge them as one decision, whose `ref` is the document's (`dispatch://<KEY>/spec` for the spec).
   - It gives the work a next step: an approval (every `gatedSteps` entry `approved`; an `approvedVersion` below `currentVersion` counts), a change request that says what to change, an answer that picks an option or supplies the fact, a reply that tells the agent to go on.
     - Your own hold: `set_status` the root to `todo`.
     - Another's park, or one you cannot read, whose words ask Legion to start the tree: `todo`.
     - Another's park, or one you cannot read, otherwise: set nothing, since a decision that only gives the work a next step is no request to start it.
   - It only questions the work: leave it parked, and answer the question in one reply.
   - Read `skill://legion-controller/references/parked-decisions-comments.md` before you post on a decision: it has each comment's text and where to post it.

## The walk

1. List the parked roots: `dispatch issues --project <PROJECT> --status backlog --label legion --all`, then with `--status icebox`. Keep those `read_state` records at `phase: done`.
2. Read each root, then each issue under it, level by level (`dispatch issues --project <PROJECT> --parent <KEY> --all`).
3. A decision is an event by a `user`, newer than the root's park and every `Parked decision read:` comment on the root or on the event's issue, of type `artifact.approved`, `artifact.changes_requested`, `ask.answered`, `ask.resolved` or `comment.created`. Skip an `artifact.approved` that is the person's own handover, and with it the approval request's `ask.answered` at the same time: the root's `parent` is `null`, the event's `payload.artifact_id` is the root's `primary_artifact_id` (the same `curl` of `/api/v1/issues/<root>`), and its `payload.reason` does not begin `Carried forward from the approval of version`. When that read fails, judge it. Find an ask or comment's id under `Open asks:` or with `dispatch search`: the id at the end of a hit's link (`/asks/<id>`, `?ask=<id>`, `#b-<block id>`, `/comments/<id>`, `?comment=<id>`) names it. `dispatch read --ref dispatch://<KEY>/ask/<id>` takes a block id too and prints the ask's own id as `Ask id:`; that id goes in `ref` and in `--reply-to-ask`. A comment's `ref` is `dispatch://<KEY>/comment/<id>`.
4. Decide each tree's decisions as [Deciding](#deciding) says.
5. For each root that is your own hold and had no decision this walk, check its wait. Its mark, the first line of the `Parked by Legion while it waits on:` comment that step 2 of [Deciding](#deciding) pairs with the park, names the cause or the event it waits on. When that comment cites an ask's answer, the root's `Asked whether to park:` comment that names that ask gives the wait's `<key>` on its second line (`skill://legion-controller/references/park-asks.md`). For an `event:` key, read what its reference names; for any other mark, judge the cause by step 3 of `skill://legion-controller/references/escalation.md#an-escalated-hold` (a missing `capabilities` row proves nothing, since a parked tree runs no session). When the event has happened or the cause is gone, `set_status` the root to `todo` with a comment that cites the mark and what you checked. Otherwise move nothing, and name the root and its wait in your summary.
