# When the pod's test server does not serve you

Read it when a connect to your pod's own Postgres server (`$LEGION_TEST_PG_DSN`) is refused or fails, or when `LEGION_TEST_PG_DSN` is unset. It is part of *The database your tests use* in `skill://legion-worker/references/tools.md`.

- `LEGION_TEST_PG_DSN` set and the connection refused: the launcher runs `legion-testpg ensure` every 15 seconds, so wait and retry. Never start a server of your own beside it, and never reach for another DSN. Still refused: report the error, the port and `tail -n 200 "$LEGION_TEST_PG_LOG"` as a fault of the pod.
- The server's log is the file `$LEGION_TEST_PG_LOG` names. For every connect the server takes, the process it starts for it writes `connection received: host=127.0.0.1 port=<client port>`, then `connection ready`, and a `disconnection` line at the end. A connect that failed with lines of its own failed in the server, and the log says why; one the server could not start a process for leaves `could not fork new process for connection` instead. A connect with neither line never reached the server: a burst of more connects at once than the listen queue (about 940) is dropped before the server sees it, and libpq reports it as `server closed the connection unexpectedly` or waits until its own timeout. Open the connections in smaller steps, or retry them.
- `LEGION_TEST_PG_LOG` unset: a server you started yourself (next bullet) logs to `$LEGION_TESTPG_DIR/server.log`; with the DSN your pod set and no such variable, your pod's image predates the log, so report without it.
- `LEGION_TEST_PG_DSN` unset, with `legion-testpg` on `PATH`: `export LEGION_TESTPG_DIR=$XDG_DATA_HOME/testpg LEGION_TEST_PG_DSN='postgres://legion_test@127.0.0.1:5433/legion_test?sslmode=disable'`, then `legion-testpg ensure`. With no `legion-testpg` either, stand up a server with the harness of *The Dispatch browser suite* in `skill://legion-worker/references/withheld-capability.md`, and set the DSN.
