# Legion Phase Worker

Your role prompt gives the workspace, the push, the handoff, `handoff_complete`, the waits and the pod release; this skill adds the rest. The architect your `Legion addressing` line names owns your issue. When an architect above it tells you that it takes your issue's work while your issue's own architect does not run, send to that architect instead.

## Every phase, in this order

1. **Read first.** Read the issue, then its `open-items.md` where one exists (`dispatch doc-read --issue <issue> --artifact open-items-md`), because the architect records decisions there that it does not message, then each handoff before your phase with `dispatch handoff-read --issue <issue> --phase <word>`, in order: `plan`, `implement`, `test`, `review` (a phase with no handoff answers `HANDOFF_NOT_FOUND`). Before you read another phase's results with `dispatch results --issue <issue>`, read `skill://legion-worker/references/pr-body.md#what-a-result-is`, which defines a check and a result. Read the handoff your task's `Handoff:` line names at its version, with the command that line quotes (`dispatch handoff-read --issue <issue> --phase <word> --version <n>`): that is the record the daemon accepted, and a record written to the phase since does not replace it. Where a record disagrees with your memory or a transcript, the record wins: it is the copy that survived. At each later assignment read them again, your own included, since other phases may have recorded since. After a `Your workspace was recreated…` message, anything unpushed is gone, and no file in the workspace says so; the handoffs on the Dispatch issue are kept. A release of an idle pod is the one exception for the workspace: the daemon saves the unpushed tracked work and the next pod restores it, and a message names whatever the restore could not bring back. That version rule holds for the `implement`, `test` and `review` records, which are one round's own and must not move under a reader. The plan is the exception to it, and the rest of this item is for the roles that work from the plan: the implementer, the tester and the reviewer. The plan is the issue's `plan.md` document, and its planner goes on writing that document after the planning phase ends, so your task's `Handoff: plan version <n>` line is the receipt for the record the daemon accepted rather than the plan. The plan you build from is `plan.md` at the newest version the plan review approved: the version that the `Approval:` line of `dispatch read --issue <issue> --artifact plan-md` names (`approved v<n>`, and `approved v<n> … changed since` names that same version). `dispatch doc-read --issue <issue> --artifact plan-md --version <n>` prints the text of one version, and with no `--version` the newest. A newer version that the `Approval:` line does not name is a revision the plan review has not approved: build from the approved version and not from that one, and tell the planner what the newer version means for your work with `envoy_publish` to its role topic (your own topic with the trailing `-<role>` replaced by `-planner`), going on with the approved version while you wait. Read `plan.md` again before each task of the plan you begin and before you write your handoff, because a version approved while you work is the plan now. When the issue has no `plan.md`, or `dispatch read` prints no `Approval:` line for it, the plan is the `plan` record the daemon accepted: the `legion` tool's `read_record` gives its version as `workers.planner.handoffRecord.version`, and `dispatch handoff-read --issue <issue> --phase plan --version <n>` reads it. When that line reads `changes requested on v<n>`, it is the newest review alone and an older approval may still stand, which no command lists: ask the planner on that same topic which approved version stands, build from the accepted `plan` record until it answers, and build from the version it names once it has.
2. **Commit only your phase's work**, with `jj -R "$LEGION_WORKSPACE" split -m "<message>" <paths…>`, each commit holding only your phase's paths, so the next phase sees what you changed.
3. **Put back what you copied in.** Before you write the handoff, run `jj -R "$LEGION_WORKSPACE" status` and remove or restore every file you copied or fetched in that is not your phase's work, such as another branch's test rig. With jj the working copy is the commit: the next role's first commit builds on what you left, and its push ships it.
4. **Read again what you record.** Every role writes the one workspace, so a file can change while your run reads it, and a script can change while it runs. Run from a copy where you can, a `git archive` of the head or a scratch clone under `$TMPDIR`: no sibling writes that path, so the copy removes both faults. Before you record a result, run `git diff --quiet <head> -- <each file the check reads>` and record at the head the content matches. A non-zero exit of a script in the shared workspace is not reportable until you run it again with `sha256sum <script>` just before and just after it, both lines kept beside the exit status: a changed hash is the race; an unchanged hash with a failure that comes again is a finding; an unchanged hash with a failure that does not come again is unclassifiable. Three limits hold. A file's `mtime` proves little, because a checkout or a workspace rebuild stamps every path at once: an `mtime` inside the run's window proves nothing, one outside it still rules out the race, and `.jj/legion-created`, written once when the workspace was made, tells such a stamp from a real write. A pod replacement takes the `mtime` evidence of every run before it. A run whose output you did not capture can be neither confirmed nor cleared, so it is unclassifiable.
5. **Record the handoff** your role prompt names with `dispatch handoff-write --issue <issue> --phase <word> --body-file - <<'EOF'`, its JSON on standard input, or with an absolute path a command printed. Never write it into the workspace, which jj snapshots into the working-copy commit, and never with the `write` tool to a path that starts with `$`: that tool expands no variable and makes a directory of that name in the workspace. A handoff is never a commit and never a result: what you ran is a result you record against one of the issue's checks with `dispatch result`, and `skill://legion-worker/references/pr-body.md#what-a-result-is` defines a check and a result. To change a handoff already recorded, read it with `dispatch handoff-read`, edit the body, and record it whole again: each `dispatch handoff-write` adds a version, and `handoff_complete` reports the newest.
   Every handoff body holds `head`, the 40-character lower-case commit the work it reports was done against — the commit the planner's workspace stood on, the commit the implementer pushed as `@-`, the commit the tester's recorded results name (the `--commit` it gave `dispatch result`), the `commit_id` of the review the reviewer submits — and your completion carries that head to the daemon, which takes a completion of an earlier entry of your phase only at the head the record holds. The tester and the reviewer never fill it with a read of the pull request's head made when they write the handoff: a push that landed while they worked names a head their work was not done against.
6. **Push any work, then complete**, as the push section below says. `handoff_complete` is your only way to end a phase: add no label, keep no status of your own and run no loop of your own, since the daemon owns the issue's state and the architect its decomposition and gates.

## Stop rules

- A refused completion is information, not a retry loop. Quote the answer verbatim to the architect, then do what `skill://legion-worker/references/handoff-and-completion.md` says for its code.
- The workspace is read-only for you from the moment your phase ends, however it ended: read `skill://legion-worker/references/handoff-and-completion.md#when-your-phase-ends` for what that stops and its one exception.
- Never start another Legion role: the daemon starts every phase worker.
- These waits stand rather than proceed, each ending the turn with a `WAITING` line naming what it waits on:
  - a planner on a decision the plan itself needs, because a plan completed around an open decision carries that gap into every later phase;
  - a reviewer on a half of the round that has no review, on a required check with no run at the head, or on the architect's rewrite of a check whose `run` is a whole test suite (`skill://legion-worker/references/merge-gate.md`);
  - retro on the architect's answer to a defect it reported;
  - a pushing role whose second push still did not carry the pull request onto its commit.
- Send any other decision someone else owns (product, scope, design, lifecycle, another phase's) to the owning architect with the issue, phase, verified observation, what you tried and the decision needed, then go on. A human-only to-do is a `dispatch ask`.
- No surface reaches the changed path: report it to the architect, never complete (`skill://legion-worker/references/pr-body.md#when-no-surface-reaches-the-changed-path`).
- A released pod is not a stop. Your session, phase and task are kept, and the next pod restores your unpushed tracked work; nothing else of the disk survives.
- When another role's topic answers 404, read its handoff with `dispatch handoff-read`.

## Pull request and merge gate

- No deferrals. A finding that changes behaviour, hides an error, or breaks a gate is fixed in this pull request. So is a wording nit, or any other fix in a file it touches that needs no one else's decision: a later round costs a CI pass and a review. `Fast-follow:` reads `none` or names cleanup in files the pull request does not touch.
- Before you open or comment on a pull request, write a GitHub issue, or change `gh`'s config, its aliases or its token variables: read `skill://legion-worker/references/pull-request.md`.
- The merger merges the head it read as `skill://legion-worker/references/merge-gate.md` says; read it before you merge.
