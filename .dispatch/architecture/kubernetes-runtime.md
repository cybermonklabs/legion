How Legion runs under `runtime: kubernetes`: the pods of the worker image `release-engineering` builds, pinned by digest, and the operator's controller configuration (`deploy/kubernetes/daemon/controller.yaml.example`). The TypeScript daemon refuses `runtime: kubernetes` and names the Go daemon, which runs it. The image's own Dockerfile lives under `packages/daemon`. LEGION-206 plans replacing this hand-rolled pod layer with the kubernetes-sigs Agent Sandbox CRD, as Stage 4 of the Go coordinator — the same subsystem evolving, not a new component.

`deploy/kubernetes/daemon/legion.yaml.example` documents the daemon's top-level `repository_renames` key, the repository pairs the daemon treats as one repository wherever it compares a name; `cmd/legion/config_example_test.go` holds the example to the loader, so a key documented wrongly there fails that test rather than an operator's `legion config check`.

A project's memory overlays (`projects.<KEY>.memory.config_files`) are files of the operator's mounts, as a role's own (`role_config_files`) are, and take part in everything those take part in: the loader's mount check, the image probe's per-role value (passed for every workflow role, never for the controller, which runs in no tree), the pod drift, reported `memory.config_files <file>`, which replaces every issue pod of the deployment and no controller pod, since any tree may be drawn into the memory group, and the filtering a launch that keeps a live pod does, so a memory-group role started into a pod built before the mount is told only the overlays that pod holds and starts rather than refusing. None of those reads the project's mode: a tree already drawn into the memory group names the overlays under any mode, so the runtime is handed them while the block names them and only removing them from the block takes them away. The project's `instructions` file is not a mount: the daemon reads it and the runtime inlines its text into the role's system prompt, since a pod reads no file of the daemon's. `deploy/kubernetes/daemon/legion.yaml.example` documents the `memory` block and the `operator-memory` volume and mount it points to, and `cmd/legion/config_example_test.go` uncomments all three and holds them to the loader, as it does `role_config_files`.

An arm's folder of texts (`projects.<KEY>.experiments.<NAME>.variants[].texts`) is read twice for each launch under this runtime, by the daemon at its spec build and by the role's launcher before the start, so it stands at one path in the daemon's own pod and in every issue pod: the loader holds it to a whole-volume mount of `runtime.kubernetes.pod.volume_mounts`, never a `sub_path` one, and boot holds the manifest and each file it lists to the items of a ConfigMap or Secret volume that projects items, since a key holds no `/` and a folder's tree mounts only through `items` with nested paths, the kubelet's `..data` layout that `texts.Read` follows (`internal/texts/testdata/volume-layout.txt`).
A launcher of this release says `checksTexts` in its hello; a start of a folder launch hands it the folder, the fingerprint the daemon read, the two plugin roots the agent loads and the root to build, `<role state home>/legion-texts/g<generation>` (`shimwire.TextsRoot`, on the issue's volume, which every role's container already mounts, and which `LauncherStart.Validate` holds the root to), and the start's argv names `--extension <root>` before both plugins (`agentArgv`) and its environment `LEGION_TEXTS_ROOT` (owned in every pod) and the root's `texts-settings.yml` last in `PI_CONFIG_FILES`.
Before it writes anything of the generation the launcher reads the folder (`texts.Read`), refuses one whose fingerprint is not the daemon's (`changed`), holds its agents and skills to the plugin files the start loads (`texts.CheckPlugins`), and only then refuses a root not under the issue's volume root `/legion` (`launcher.VolumeRoot`, a mount point no role can rename) and, through directory descriptors walked from that volume root that follow no link a role planted at the scratch, the state home or anywhere below, removes every earlier `g<N>` root of the role, builds the root (`texts.BuildRootAt`, `rolefile`) and writes the settings layer, its base read from the start's `PI_CONFIG_FILES`, the workspace and the profile where the launcher sees them, so a file under a mount role-init binds back under the home is read from `HomeMountsDir`, and absent there when that mount lacks it (`internal/launcher`'s `prepareTexts`, `homeView`); a refusal names the file and the cause, and the daemon sends the control's start under `start-<generation>-texts-fallback` in the same try.
A kept pod whose launcher predates the hello member gets the control's start alone (`launcher-cannot-check`), and so does a launch that still installs the plugin pair into a kept pod after its start (`installs-plugins`), since no check reads those plugins' texts before the agent loads them; a launch that replaces the pod installs nothing and runs the folder.
`deploy/kubernetes/daemon/legion.yaml.example` documents the key with a commented arm, `operator-texts` ConfigMap volume and mount, which `cmd/legion/config_example_test.go` uncomments and holds to the loader and to `legion config check`.
