The TypeScript half of this repository's one client of the secrets broker's RFC 8693 token exchange (`@legion/cipher-client`): a machine trades the platform identity it already holds, or the sign-in of a person who ran `agent-secrets login` on it, for a DPoP-bound access token, which Dispatch and the Envoy listener read back at the broker's introspection route. The Go half is `packages/envoy/internal/cipherclient`, and the two are held to one wire by the corpus in that package's `testdata/wire.json`, which both suites replay. Each suite asserts set equality, not containment, over the form posted, the proof's header and claim set and the fields read out of the answer, so a field either client sends or reads without an entry in that file fails its own test and a field added to that file fails the client that does not send it yet.

One module per thing, no barrel. `src/wire.ts` holds the names the exchange is spoken in (the Go side's `internal/cipher/oauthwire`), and `src/source.ts` the identity interface. The machine identities are `src/projected-token.ts`, a pod's projected Kubernetes service-account token read from its file at every trade (the kubelet rewrites it in place), `src/metadata-identity.ts`, a Compute Engine machine's Google identity token asked for with `format=full`, and `src/pool-identity.ts`, a Google identity token minted through a workload identity pool, a port of the Go client's `PoolIdentity` that asks Google's security token service and IAM Credentials with the bodies Go sends. `src/signins.ts` reads a person's sign-in records as the Go client's `SignInStore` reads them and never writes one, and `src/person-identity.ts` renews the person's Google identity token from the record's refresh token at every trade, with `openid-client`, at the issuer and with the client the deployment configures. `src/dpop.ts` is the proof signer, `src/token-client.ts` the exchange itself and its retry loop, `src/token-errors.ts` the errors a trade ends in and the one reading of them (`isFinalRefusal`), `src/refusal-text.ts` what a refusal prints, and `src/environment.ts` the variables a deployment writes, the same names the Go client reads: `AGENT_SECRETS_URL`, `AGENT_SECRETS_MACHINE_IDENTITY` of `kubernetes`, `metadata` or `pool`, `AGENT_SECRETS_MACHINE_TOKEN_FILE`, `AGENT_SECRETS_MACHINE_AUDIENCE`, `AGENT_SECRETS_POOL_AUDIENCE`, `AGENT_SECRETS_POOL_ACCOUNT` and `AGENT_SECRETS_SESSION`, and the sign-in's `AGENT_SECRETS_SIGNIN_DIR` (else `$XDG_STATE_HOME`, else `$HOME`, as Go reads it), `AGENT_SECRETS_PERSON`, `AGENT_SECRETS_SIGNIN_ISSUER`, `AGENT_SECRETS_SIGNIN_CLIENT_ID` and `AGENT_SECRETS_SIGNIN_CLIENT_SECRET_FILE`.

`brokerTokenClient` in `src/environment.ts` builds one of two clients. With no sign-in on the machine it is the machine's own client: the machine's identity is the subject, the key is made inside the process, and the trade declines the launcher credential (`launcher_credential=false`), since no TypeScript caller reads one. With a sign-in it trades the person: the person's identity token is the subject, the machine's is the actor, and the proof is signed with the sign-in's box key (`importDpopKey`), so the broker records one sign-in for the box and its revoke reaches the client. That trade leaves the launcher credential parameter out, because the broker refuses a person's trade that declines, and it asks under the caller's own session, else under `signin-<person>-<thumbprint>` (Go's `SessionFor`), never under `AGENT_SECRETS_SESSION`, which the machine trades under. Every error while it chooses, reads or builds the person's client is thrown: nothing answers the machine's client while a sign-in record is on the machine. A caller may ask for a read trade (`ReadTrade`): either client then asks for the scope `read` and the cut it names (`FORM_SCOPE`, `FORM_AS_OF`), and the token keeps the identity the same trade would have had and writes nothing. The person's read trade also makes a key of its own for the client (`holderKey`) and sends a second proof of each trade by it in the `DPoP-Holder` header. The broker binds the token to that key, which signs every proof presented beside the token, so the box key signs the trade alone. The machine's own client already proves a key it made, which holds no launcher credential, so it sends no holder key.

The one exception is `PERSON_SIGNIN_TRADE=off` (`PERSON_TRADE_VAR` in `src/signins.ts`), a setting of a process whose own credentials are a service's and never a person's: under it `chooseSignIn` answers no sign-in without reading the store, and the client trades the machine as where nobody signed in, even where a sign-in record is on the machine. Unset or blank, the person trade is on, and any other value is refused with an error that names the variable. `legion controller start` sets it in the controller's environment under every configuration (`controllerPersonTradeVar`, `packages/daemon/cmd/legion/controller.go`), so the controller's own Dispatch credential, and its Envoy credential where no bearer names one, trade the machine and never the sign-in its operator made with `agent-secrets login`. Only this client reads it, so the controller's `agent-secrets` secret reads are signed as they would be without it; its name lies outside `AGENT_SECRETS_*` because `agent-secrets NAME -- <cmd>` strips that prefix's variables from its child but for a few, so a `dispatch` command run that way keeps it.

`openid-client` makes the exchange request and validates the answer, and `src/dpop.ts` signs every proof with `node:crypto` (jose supplies only the `JWK` type there): `typ: dpop+jwt`, `alg: ES256`, the public JWK in the header, and `jti`, `htm`, `htu` and `iat` in the claims, with `nonce` only after the broker has sent one (the token endpoint's `use_dpop_nonce` retry lives here) and `ath` only on a request that presents an access token; a NATS connection's proof (`connectionProof`) is the same signer over `htm: CONNECT` and `htu: nats:connect`, signed synchronously because nats.js asks for it inside its own synchronous handshake. Each private half is a `node:crypto` `KeyObject` rather than a WebCrypto `CryptoKey`, since WebCrypto signs only asynchronously: the one a machine's client makes (`newDpopKey`) and a box key imported from its sign-in record's PKCS#8 PEM (`importDpopKey`) alike, each held in the closure that signs and handed to no caller, so only its public half can ever reach the wire. A box key that does not parse is refused in the package's own words with no cause, since the runtime's parse error can quote the bytes it read. `token_type` is the one member read from the answer's own body rather than from the library's result, because the library lowercases it (RFC 6749 Section 7.1) while the corpus names the spelling the broker wrote.

The metadata reader uses `node:http` with an agent of its own and never `fetch`: the metadata server's address is link-local, Bun's `fetch` honours `$HTTP_PROXY`, a Node host can install a proxying global dispatcher, and Node 24 proxies `node:http` through its global agent when `NODE_USE_ENV_PROXY` is set — any of which would hand whatever a proxy variable names this machine's identity token, fetched afresh before every renewal. The Go reader's bare transport exists for the same reason.

The grant issues no refresh token, so a renewal is a fresh subject token traded again: `token()` answers the token in hand until it is within five minutes of lapsing, and after that the answer of the client's one retry loop (`#run`), with nothing of the caller's restarted. No caller starts a second loop or cuts its wait short, so however many callers ask, the broker sees one trade per slot of the loop's schedule: gRPC's connection backoff, capped exponential backoff with equal jitter around a per-trade timeout of 30 s (`TRADE_ATTEMPT_MS`, the Go client's `callTimeout`). A caller is one of gRPC's two kinds (`TokenCallOptions`): fail-fast, the default, told at once with `TradeRetryingError` where the loop's last trade failed in a way it trades again on and no live token is in hand; or wait-for-ready, which waits through the retries until a token lands, a refusal ends the loop or its signal ends: the startup paths in envoy-client's NATS credential (a channel server's start for its life, an Oh My Pi start for at most 20 s, and a switch's follow within its bound). Either kind waits out a pod session not registered yet within its signal. A pod session the broker holds no registration for yet (`podSessionUnregistered`, `invalid_grant` whose description begins `pod_session_not_registered:`) is traded again 2 s later, doubling to 30 s (`PENDING_*`), so the trade after a registration lands is at most 30 s away (that trade has its own 30 s); no answer, no connection, a 5xx, the broker's 429 or a DPoP refusal, an answer that is not the grant's, or an identity source that could not be read, 15 s later, doubling to 5 minutes (`RETRY_*`, the Go client's schedule). A final refusal (`isFinalRefusal`) ends the loop and drops the token in hand at once: a `BrokerRefusedError` no retry cures, or a `SignInEndedError`, the issuer's `invalid_grant` for a sign-in the person or Google ended; a call before the next slot is told the same refusal with no trade. Once a renewal has failed, a call takes the token in hand at once while it is live, and a caller whose signal ends while a live token is in hand takes it. A caller whose signal ends with none gets `RegistrationPendingError`, naming the session, or `TradeRetryingError`, saying what the last trade came to; `TradeUnansweredError` where a trade is out and none has ended yet; or its signal's reason where no trade is out at all. One with no signal waits until a token lands, a refusal ends the loop or, failing fast, a trade fails. The loop's waits hold no process open, and `close()` ends it, a caller with nothing live in hand told `TokenClientClosedError`. It logs as the Go client does (where the caller passes no `log`, `console.warn` of each line through the held-secret scrub): a pending registration once, naming the session, again every 30 minutes while it lasts and once when it ends; every other failure at each wait, saying when it trades again. `drop()` forgets the token in hand, for a caller a server has told that the token is no longer live. The subject, actor and access tokens of each trade are held for the scrub until an hour past their lapse.

`packages/envoy-client`'s `src/broker-credential.ts` is its one caller: it makes one client for each session a process acts as (`CLIENTS`, dropped by `forgetBrokerSession` when the host leaves that session), which both that session's Dispatch client and its listener client present as `Authorization: DPoP <token>` with a proof of their own for each request. A Dispatch credential narrowed to reading (`DISPATCH_TOKEN_BROKER_READ`) gets a client of its own beside that one, keyed by its read trade and its cut too. It keeps a final refusal of a person's client against that sign-in (the person and the box key's thumbprint, the `signIn` the factory answers beside the client), as Go's `SignInAuthority` does, and refuses that sign-in again with no network call until the store holds another one. It keeps no factory that failed, so a store the person corrected is read again at the next call, and its `stale()` calls `drop()` when Dispatch answers `401 BROKER_TOKEN_NOT_ACTIVE`.
