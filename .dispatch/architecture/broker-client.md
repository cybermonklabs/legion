The TypeScript half of this repository's one client of the secrets broker's RFC 8693 token exchange (`@legion/cipher-client`): a machine trades the platform identity it already holds, or the sign-in of a person who ran `agent-secrets login` on it, for a DPoP-bound access token, which Dispatch and the Envoy listener read back at the broker's introspection route. The Go half is `packages/envoy/internal/cipherclient`, and the two are held to one wire by the corpus in that package's `testdata/wire.json`, which both suites replay. Each suite asserts set equality, not containment, over the form posted, the proof's header and claim set and the fields read out of the answer, so a field either client sends or reads without an entry in that file fails its own test and a field added to that file fails the client that does not send it yet.

One module per thing, no barrel. `src/wire.ts` holds the names the exchange is spoken in (the Go side's `internal/cipher/oauthwire`), and `src/source.ts` the identity interface. The machine identities are `src/projected-token.ts`, a pod's projected Kubernetes service-account token read from its file at every trade (the kubelet rewrites it in place), `src/metadata-identity.ts`, a Compute Engine machine's Google identity token asked for with `format=full`, `src/pool-identity.ts`, a Google identity token minted through a workload identity pool, a port of the Go client's `PoolIdentity` that asks Google's security token service and IAM Credentials with the bodies Go sends, and `src/device-login.ts`, a machine's device login at the broker's RFC 8628 device grant, which no Go client trades: `dispatch login --device` makes it, and a trade presents its access token. `src/signins.ts` reads a person's sign-in records as the Go client's `SignInStore` reads them and never writes one, and `src/person-identity.ts` renews the person's Google identity token from the record's refresh token at every trade, with `openid-client`, at the issuer and with the client the deployment configures. `src/dpop.ts` is the proof signer, `src/token-client.ts` the exchange itself and its retry loop, `src/broker-request.ts` how each request `openid-client` makes is sent, with a DPoP proof where it goes to the broker's token endpoint, and how a failed request to the broker is worded, `src/token-errors.ts` the errors a trade ends in and the one reading of them (`isFinalRefusal`), `src/refusal-text.ts` what a refusal prints, and `src/environment.ts` the variables a deployment writes, the same names the Go client reads: `AGENT_SECRETS_URL`, `AGENT_SECRETS_MACHINE_IDENTITY` of `kubernetes`, `metadata` or `pool` (and `device-login`, which only this client reads, with `AGENT_SECRETS_DEVICE_LOGIN_FILE`), `AGENT_SECRETS_MACHINE_TOKEN_FILE`, `AGENT_SECRETS_KEY_DIR`, `AGENT_SECRETS_MACHINE_AUDIENCE`, `AGENT_SECRETS_POOL_AUDIENCE`, `AGENT_SECRETS_POOL_ACCOUNT` and `AGENT_SECRETS_SESSION`, and the sign-in's `AGENT_SECRETS_SIGNIN_DIR` (else `$XDG_STATE_HOME`, else `$HOME`, as Go reads it), `AGENT_SECRETS_PERSON`, `AGENT_SECRETS_SIGNIN_ISSUER`, `AGENT_SECRETS_SIGNIN_CLIENT_ID` and `AGENT_SECRETS_SIGNIN_CLIENT_SECRET_FILE`.

`brokerTokenClient` in `src/environment.ts` builds one of three clients. With no sign-in on the machine it is the machine's own client: the machine's identity is the subject, the key is the one the next paragraph names, and the trade declines the launcher credential (`launcher_credential=false`), since no TypeScript caller reads one. With a sign-in it trades the person: the person's identity token is the subject, the machine's is the actor, and the proof is signed with the sign-in's box key (`importDpopKey`), so the broker records one sign-in for the box and its revoke reaches the client. That trade leaves the launcher credential parameter out, because the broker refuses a person's trade that declines, and it asks under the caller's own session, else under `signin-<person>-<thumbprint>` (Go's `SessionFor`), never under `AGENT_SECRETS_SESSION`, which the machine trades under. Every error while it chooses, reads or builds the person's client is thrown: nothing answers the machine's client while a sign-in record is on the machine. Under `device-login` no sign-in is read: the login's access token is the subject under RFC 8693's `access_token` type, with no actor, the key is the login's own (`dpopKeyOf`), since the broker binds a trade of a machine login's token to that token's key, and the session is the caller's own, else `AGENT_SECRETS_SESSION`, else `device-login-<thumbprint>`.
A caller may ask for a read trade (`ReadTrade`): each of the three clients then asks for the scope `read` and the cut it names (`FORM_SCOPE`, `FORM_AS_OF`), and the token keeps the identity the same trade would have had and writes nothing.
The person's client and the device login's prove a key that signs launcher proofs, the box key or the login's key, and a key that signs launcher proofs is bound to no read token, so each makes a key of its own for the client (`holderKey`) and sends a second proof of each trade by it in the `DPoP-Holder` header.
The broker binds the token to that key, which signs every proof presented beside the token, so the proof key signs the trade alone.
The machine's own client proves a key that holds no launcher credential, one it made or a pod role's agent-secrets key, which the broker enrolls as a session key and mints no launcher credential on, so it sends no holder key.
Every refresh revokes the access tokens the login answered before and a rotated refresh token presented again past its grace revokes the login, so each trade runs under the login's lock file (`withDeviceLoginLock`, through the source's `spend`), which holds from the read of the file through the refresh, when one is due, to the trade's answer; `src/device-login-lock.ts` holds the lock's protocol, its stale bound of half a trade's attempt and the one take-over a stale lock gets. A holder refreshes, and replaces the file with a refresh's answer, only while the lock is still its own; it refreshes at once a kept access token the broker refuses as one it no longer honours (`BrokerRefusedError.subjectNotHonoured`), never one refused for its session or projects, and a refusal after it lost the lock is one a later trade cures; it sends once more a refresh the broker did not answer. A trade whose attempt ran out while it waited for the lock is `LockHeldError`, which the lock itself throws, naming the lock and not the broker.
The file keeps the last access token, so a process refreshes when that token has under a minute left, or the broker refuses it as one it no longer honours.
A read trade refreshes first where that token has less left than its client's renewal window and a second (`leastLifeMs`, `EXPIRES_IN_STEP_MS`; `#trade` says why), capped at half the life the last refresh gave the token (`access_life_seconds` in the file, `leastAccessLifeMs`) and never under the minute, so a token fresh from a refresh that lives over a minute meets it, and the next refresh comes no sooner than half a life later wherever that half is over the minute.
A refresh at that bound ends the read tokens other processes traded from the access token it replaces.
Where such a process renews its read token at the window, the token can end up to a second before that renewal; where it renews at the token's half life, as a read token that lands with under two windows left does (every one, where the access token lives under two windows), the token can end before that renewal by up to the least life the refresh keeps (the cap, or the minute where that is larger) less half the token's own life.
So where the access token lives under two minutes, a read token can end up to 60 s less half its own life before its renewal.
At an access-token life of 302 s, read tokens were measured ending 20 s, 10 s and 5 s before their renewal.
Either way that process's next request is refused once with Dispatch's `401 BROKER_TOKEN_NOT_ACTIVE`: `brokerCredential` drops the token and trades again, and `DispatchClient`'s `#send` (`packages/envoy-client/src/dispatch-http.ts`) sends the read once more, so the caller meets no failure, at the cost of one more trade and one more request.
A file that keeps no life, which an older build wrote, takes the minute alone until the next refresh keeps one.
`dispatch login --device` makes and checks the login's directory before it asks for a code (`deviceLoginPlace`). A device login is refused under `PERSON_SIGNIN_TRADE=off` (below), since the broker mints its trade as the person who approved it; Go's `MachineIdentity` refuses `device-login` by name, since no Go tool trades one. `src/broker-request.ts`'s `brokerRefusal` words every broker failure, the trade's and the device login's alike, so an OAuth code shows only where it is a known one.

The machine's key follows one rule, the same in the Go client's `MachineKey` (`packages/envoy/internal/cipherclient/environment.go`). When `AGENT_SECRETS_MACHINE_IDENTITY` is `kubernetes` and `AGENT_SECRETS_KEY_DIR` is set, the machine trade proves the key in `$AGENT_SECRETS_KEY_DIR/key.pem`, the PKCS#8 P-256 key `agent-secrets keygen` writes, imported with `importDpopKey`: a role in a pod trades with its own agent-secrets key, because the broker refuses a pod session's exchange whose DPoP key is not the one its registration names, which is that key. A role always has the file, since its shim runs `keygen` before its first hello (`packages/daemon/internal/shim/agentsecrets.go`, `identity`), and reads its own and no sibling's, since role-init binds each role's own agent-secrets directory (`packages/daemon/internal/launcher/roleinit_linux.go`). When that file cannot be read, or is no P-256 key, the factory throws naming its path and makes no fresh key in its place, which the broker would refuse in words that name neither the file nor the key. In every other case the key is made inside the process, as before: a session pod that carries no `AGENT_SECRETS_KEY_DIR`, and a machine whose identity is `metadata` or `pool`. `AGENT_SECRETS_KEY_DIR` is one of `BROKER_VARIABLES`, so `packages/envoy-client`'s client cache, keyed by those variables, makes a client of its own for each directory.

The one exception is `PERSON_SIGNIN_TRADE=off` (`PERSON_TRADE_VAR` in `src/signins.ts`), a setting of a process whose own credentials are a service's and never a person's: under it `chooseSignIn` answers no sign-in without reading the store, and the client trades the machine as where nobody signed in, even where a sign-in record is on the machine. Unset or blank, the person trade is on, and any other value is refused with an error that names the variable. `legion controller start` sets it in the controller's environment under every configuration (`controllerPersonTradeVar`, `packages/daemon/cmd/legion/controller.go`), so the controller's own Dispatch credential, and its Envoy credential where no bearer names one, trade the machine and never the sign-in its operator made with `agent-secrets login`. Only this client reads it, so the controller's `agent-secrets` secret reads are signed as they would be without it; its name lies outside `AGENT_SECRETS_*` because `agent-secrets NAME -- <cmd>` strips that prefix's variables from its child but for a few, so a `dispatch` command run that way keeps it.

`openid-client` makes the exchange request and validates the answer, and `src/dpop.ts` signs every proof with `node:crypto` (jose supplies only the `JWK` type there): `typ: dpop+jwt`, `alg: ES256`, the public JWK in the header, and `jti`, `htm`, `htu` and `iat` in the claims, with `nonce` only after the broker has sent one (the token endpoint's `use_dpop_nonce` retry lives here) and `ath` only on a request that presents an access token; a NATS connection's proof (`connectionProof`) is the same signer over `htm: CONNECT` and `htu: nats:connect`, signed synchronously because nats.js asks for it inside its own synchronous handshake. Each private half is a `node:crypto` `KeyObject` rather than a WebCrypto `CryptoKey`, since WebCrypto signs only asynchronously: the one a machine's client makes (`newDpopKey`), a pod role's agent-secrets key and a box key imported from its sign-in record's PKCS#8 PEM (`importDpopKey`) alike, each held in the closure that signs and handed to no caller, so only its public half can ever reach the wire. A box key that does not parse is refused in the package's own words with no cause, since the runtime's parse error can quote the bytes it read. `token_type` is the one member read from the answer's own body rather than from the library's result, because the library lowercases it (RFC 6749 Section 7.1) while the corpus names the spelling the broker wrote.

The metadata reader uses `node:http` with an agent of its own and never `fetch`: the metadata server's address is link-local, Bun's `fetch` honours `$HTTP_PROXY`, a Node host can install a proxying global dispatcher, and Node 24 proxies `node:http` through its global agent when `NODE_USE_ENV_PROXY` is set — any of which would hand whatever a proxy variable names this machine's identity token, fetched afresh before every renewal. The Go reader's bare transport exists for the same reason.

The grant issues no refresh token, so a renewal is a fresh subject token traded again: `token()` answers the token in hand until its renewal (`renewalAt`), five minutes before it lapses and never before half the life it had when it landed, worked out once as it lands, and after that the answer of the client's one retry loop (`#run`), with nothing of the caller's restarted.
The Go client's `renewalAt` is the same rule, and `testdata/renewal.json` beside `wire.json` holds both clients to it, as `wire.json` holds them to the wire. The Go client also trades again 15 minutes before the expiry of the launcher credential a token names (`credential_expires_at`), by the same rule, where that comes first: a Go caller enrols sessions under that credential, which the broker renews only while it is live, and no TypeScript caller holds a session under it, so the TypeScript rule reads the access token alone.
No caller starts a second loop or cuts its wait short, so however many callers ask, the broker sees one trade per slot of the loop's schedule: gRPC's connection backoff, capped exponential backoff with equal jitter around a per-trade timeout of 30 s (`TRADE_ATTEMPT_MS`, the Go client's `callTimeout`). A caller is one of gRPC's two kinds (`TokenCallOptions`): fail-fast, the default, told at once with `TradeRetryingError` where the loop's last trade failed in a way it trades again on and no live token is in hand; or wait-for-ready, which waits through the retries until a token lands, a refusal ends the loop or its signal ends: the startup paths in envoy-client's NATS credential (a channel server's start for its life, an Oh My Pi start for at most 20 s, and a switch's follow within its bound). Either kind waits out a pod session not registered yet within its signal. A pod session the broker holds no registration for yet (`podSessionUnregistered`, `invalid_grant` whose description begins `pod_session_not_registered:`) is traded again 2 s later, doubling to 30 s (`PENDING_*`), so the trade after a registration lands is at most 30 s away (that trade has its own 30 s); no answer, no connection, a 5xx, the broker's 429 or a DPoP refusal, an answer that is not the grant's, or an identity source that could not be read, 15 s later, doubling to 5 minutes (`RETRY_*`, the Go client's schedule). A final refusal (`isFinalRefusal`) ends the loop and drops the token in hand at once: a `BrokerRefusedError` no retry cures, or a `SignInEndedError`, the issuer's 400 or 401 `invalid_grant` for a sign-in the person or Google ended, the rule Go's `oauthrefusal.EndsGrant` states for ending a grant (an issuer's 403 or 429 naming `invalid_grant` ends nothing, and the library reads no error body from a 5xx, so an outage stays one); a call before the next slot is told the same refusal with no trade. Once a renewal has failed, a call takes the token in hand at once while it is live, and a caller whose signal ends while a live token is in hand takes it. A caller whose signal ends with none gets `RegistrationPendingError`, naming the session, or `TradeRetryingError`, saying what the last trade came to; `TradeUnansweredError` where a trade is out and none has ended yet; or its signal's reason where no trade is out at all. One with no signal waits until a token lands, a refusal ends the loop or, failing fast, a trade fails. The loop's waits hold no process open, and `close()` ends it, a caller with nothing live in hand told `TokenClientClosedError`. It logs as the Go client does (where the caller passes no `log`, `console.warn` of each line through the held-secret scrub): a pending registration once, naming the session, again every 30 minutes while it lasts and once when it ends; every other failure at each wait, saying when it trades again. `drop()` forgets the token in hand, for a caller a server has told that the token is no longer live. The subject, actor and access tokens of each trade are held for the scrub until an hour past their lapse.

`packages/envoy-client`'s `src/broker-credential.ts` is its one caller: it makes one client for each session a process acts as (`CLIENTS`, dropped by `forgetBrokerSession` when the host leaves that session), which both that session's Dispatch client and its listener client present as `Authorization: DPoP <token>` with a proof of their own for each request. A Dispatch credential narrowed to reading (`DISPATCH_TOKEN_BROKER_READ`) gets a client of its own beside that one, keyed by its read trade and its cut too. It keeps a final refusal of a person's client against that sign-in (the person and the box key's thumbprint, the `signIn` the factory answers beside the client), as Go's `SignInAuthority` does, and refuses that sign-in again with no network call until the store holds another one. It keeps no factory that failed, so a store the person corrected is read again at the next call, and its `stale()` calls `drop()` when Dispatch answers `401 BROKER_TOKEN_NOT_ACTIVE`.
