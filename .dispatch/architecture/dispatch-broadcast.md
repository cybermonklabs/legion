One person's message to several live sessions at once, sent from the Agents page (`POST /api/v1/broadcasts`, which needs the `person` scope). A broadcast is a grouping over Dispatch's targeted messages, not a second delivery mechanism: one `broadcasts` row and one issue-less message per recipient carrying its `broadcast_id`, written in one transaction and then delivered behind the request through the ordinary targeted-message path, so each recipient's attempts, retries and replies are a single message's. A selected session that is not live, or does not advertise the chosen mode, is excluded and named in the response rather than switched to another mode; `GET /api/v1/broadcasts/{id}` reads every recipient's attempts and replies back in the order the send named them. A send may carry an `Idempotency-Key` header, and the dashboard sends one per composed send; the keyed-write layer every write goes through (`api/request_keys.go`, table `request_keys`) records it per person with a digest of the request, so a repeat of the same send is answered the broadcast it already made rather than reaching every agent twice (LEGION-446, INFRA-258). The broadcast's own key table from before that layer, `broadcast_idempotency_keys` (`0055`), is dropped by `0141_drop_broadcast_idempotency_keys`.

The dashboard's broadcast writes state their method to the write store: the broadcast itself (`broadcast-queue.ts`, `enqueueBroadcast`) and each recipient's delivery again in another mode (`BroadcastPage.tsx`, and the Agents page's two retries in `AgentsPage.tsx`) are `POST`s, so the store records each as a write under its key, and a stopped one's Retry is said and sent as the `POST` it is, asked again under that key (`retryNote`, `keyed-write.ts`); the Agents page's Clear is a `PUT`, which sends no key and is the same change however often it is sent.
