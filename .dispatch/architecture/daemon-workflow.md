Planned: the issue-cap admission line, durable Dispatch and GitHub event intake, classification, the transition table, status and notice effects, and the Go Dispatch client
— `internal/admit`, `internal/intake`, `internal/workflow`, `internal/classify`, `internal/dispatch`, `internal/notify`, `internal/phase`.
LEGION-219 (Stage 3) carries them; none exists on `main` yet, so this component has no paths.
The planned workflow advances phases from facts the coordinator observes; agents do not choose the next phase.

Admission and the workflow read the deployment's repository equivalence (`repository_renames`, `config.Config.RepositoryRenames`, a `ghrepo.Renames`) wherever they compare a repository's name, so a transfer that renames a repository leaves the trees already recorded under the old name running:
in intake, `ConsumerSpec.Renames` carries the pair into the consumer's `recordedPullRequest` read;
in `workflow`, one `Engine.sameRepository` stands where `strings.EqualFold` stood, at `issueForBranch`, `ownPullRequest`, the opened handler's redelivery test, `check.go`'s comparison of a recorded check, and `Engine.ApplyRepositoryChange`, which therefore corrects nothing when Dispatch re-points an issue at the repository the one it is recorded on moved to, or still names the old name after the rename pass wrote the new one.
`ApplyRepositoryChange` makes a recorded issue's repository follow the one Dispatch resolves the issue to, in each pass that reads that resolution
— a live Dispatch event (`Engine.dispatchIssue`), the boot listing (admission's reconcile), admission's hand-over of a recorded child as a root of its own, and `internal/daemon`'s `followRecorded`, which runs over every recorded issue once a boot is over, for the changes that boot's listing found and read GitHub for none of, over each recorded issue whose event's or hand-over's reads GitHub did not answer, at once unless a follow already owed covers it and otherwise on the refresher's backoff, until GitHub answers, over each record the refresher's backfill filled, once the fill has committed (`backfillLater`), and over each issue whose correction the engine skipped because its record moved after the fact was prepared.
Each correction is written from what the fact's own preparation read of GitHub for the repository it moves onto (`intake.DispatchIssue.RepositoryRead`: both role Apps' installations, GitHub's spelling and the default branch), never from a read the daemon kept, and a fact no preparation read GitHub for, or whose reads GitHub did not answer, writes nothing.
It applies the correction with one statement of the caller's transaction (`record.(*Postgres).CorrectIssueRepository`), which writes the new repository, its default branch and GitHub's spelling of it, keeps the repository the record held and the moment of the correction, and clears whatever change was waiting.
A fact also carries the repository its record held at its preparation (`intake.DispatchIssue.PreparedAgainst`, `intake.Handover.PreparedAgainst`), and `ApplyRepositoryChange` writes nothing from one whose record holds another repository now: two reads of Dispatch at one sequence cannot be ordered and a correction moves no sequence, so such a fact would put the record back on an older resolution.
The engine asks for a follow of that issue on its transaction's commit instead (`workflow.Config.FollowIssue`, the daemon's `requestFollowOf`), and the next boot's listing covers a process that stopped between the commit and the ask.
A repository a role App is not installed on is not written onto the record:
the record keeps what it has, the issue is told once, and the change waits on the record (`record.Store.NoteIssueRepositoryChange`) for the issue's next event or the next boot, whose preparation reads GitHub again.
Since dispatch://INFRA-4401 (#4493) the daemon reads no repository mapping, so nothing else reads such a repository again, and every waiting change waits for one of those two.
No deploy run is matched any more: the production check a merge opens is woken only by the `wake_at` its own agent
— the role the project's `production_check` names
— gave on a `pending` report, by the retry of a look nobody reported, or by the check's own bound, so `projects.<KEY>.deploys` is read for nothing and only warned about.
The reads keyed on the `pull_requests` table's `repo` column
— the engine's `pullRequest` and `pullRequestByBranch`, `internal/daemon`'s `reviewedRepository` and intake's `recordedPullRequest` — ask under each name `Renames.Lookups` gives, the fact's own first and the pair's other name only when the first finds nothing, which is what lets a pull request already open at the transfer go on taking its CI, its review and its merge.
The equivalence writes no record but for one pass of this release, `internal/daemon`'s rename pass (`record.RenameIssueRepository`), which writes each pair's `to` over its `from` on the stored rows of each issue with no live pod, at boot and when the issue's pod ends;
until it writes a record, the record keeps the repository it was written under, so the pair must stay configured until no row names the old repository.
The pass writes beside `CorrectIssueRepository` and is no correction: the pair names one repository, so it records no repository the issue left, and its statement matches the old name rather than a copy read earlier.
It serves no repository of its own either
— a name is served when GitHub answers that both role Apps are installed on it, and until GitHub has answered for a pair's names its `to` counts as served and its `from` does not
— so a pair may be configured before the transfer and simply answers nothing until the events arrive under the new name.
What moves a record onto another repository is Dispatch's own resolution of the issue, which `ApplyRepositoryChange` applies, and nothing else moves it.

A new version of an approved document of a gated step closes the tree's standing gate (`classify.StandingGate`), and the deployment's `gates.hold` (`Config.Hold`) says what the closed gate holds. Under `merge`, the default, the merger's start and the first phase of each issue that has not started wait, and `tellGateMoved` tells each phase worker of the tree and the root's architect of the move. Under both holds, the close message to a merger whose idle pod the daemon released is marked to wake it (`record.RoleMessage.Wake`), so the merger can take its pull request out of GitHub's merge queue. Under `merge`, the close also gives that mark to the message to a merger whose claim is live, or whose start a lane runs now (`mergersToWake`): the outbox reads the gate once before a start acts, so such a merger can launch with its task after the close, and the message waits for the merger's session. A message to a merger with no claim yet, or with a claim that runs nothing and is not released (suspended by the daemon or an operator, failed or retired), waits only while a lane runs a start of the merger or the record holds a claim of it that is not gone, and while its issue can be woken, and otherwise finishes with no stop (`internal/daemon`'s `closeWaitsForAMerger`). Under `merge`, a merger whose start is only queued gets no mark: that start waits at the fence through the hold, and a message that waited for it would keep the issue's pod from its idle release. Under both holds, every message of the close, the architect's among them, is marked as a close message (`record.RoleMessage.Close`). Such a message reads the standing gate at the head of each attempt, and a message that carries a stop reads the tree's record of its work hold in the same REPEATABLE READ transaction, so the two reads come from one snapshot. The message finishes unpublished, with no stop, when the gate no longer stands closed, or when a hold stands that names another step or another version than its stop (`record.HoldStop.Step`, `HoldVersion`): a newer close of the gate stands (`internal/daemon`'s `closeOutrun`). A hold that ended while the gate stays closed, as the boot ends it after a move to `merge`, ends no message: the merger still hears the close, and no stop is made under `merge`. Under `work`, the move is the work hold's close or its opening (`internal/workflow/work_hold.go`). The close writes the tree's `work_holds` row (`record.WorkHold`) and tells every live architect and phase worker of the tree, and each phase worker's message carries its stop (`record.RoleMessage.Stop`, a `record.HoldStop`, from which the outbox builds the suspend once the message ends). Every merger that the close reaches gets that message marked to wait for its session (`Wake`): a live merger, a released one, and one whose start is under way (`StartUnderWay`). The merger takes its pull request out of the merge queue only on this message. So the message waits while the merger's claim is not gone and its session does not hold the role's topic yet, and while the listener reports its holder unresponsive, and the outbox posts the stop only once the message ended. The close records the hold at once on a released worker that is not a merger. It also records the hold at once on a phase worker that is not a merger and is neither live nor released while a start of it is under way. That start read the gate open before the close, and the stop, which the outbox runs after the start, stops the launching claim at its ready, before the claim takes a task. A wake that passed the fence can launch a released worker after the close in the same way. Both stops that the close records at once store a deadline 2 minutes after the close, so where a daemon restart or a failed attempt of the stop lets the ready come first, the stop cuts the claim's turn at that deadline. A stop that meets a claim with no launch yet, queued or with a launch that a restart left uncertain, waits on its row's backoff, at most 64 seconds, for the launch (`internal/daemon`'s `holdStop`). The boot's relaunch of an uncertain launch spawns the claim with no fence, so the stop holds that launch until its ready, or cuts its turn at the stored deadline and at most 64 seconds after its ready. The opening decides the opening of each holder that the hold did not stop in `openingDelivery`, live or not, as `tellGateMoved` does under `merge`: a holder owed news is sent no role message, and the task that carries its news leads with the opened sentence. Every other live architect and phase worker is told the open message. The opening deletes the row and starts each claim the hold stopped, and no other, with one task that begins with the opening's sentences (`openHeldClaims`). Where the opening read the tree's row, the holder row of such a claim records the opening as told. That start ends the hold of its claim, so it carries the news the claim is owed behind those sentences (`startNewsOf`), and a news-only start does not reach a claim the hold stopped. Where the claim kept a task that no turn took and the start carries no newer work (`supervise.OpeningKeeps`), the start renders that news over the kept work, and the claim's one task is that work with that news. Only a start that finds its claim stopped by the hold, or the retry of the opening's start whose earlier attempt ended the hold, settles the holder row as told (`settleHeldOpening`). The opening writes no start where a queued start of the opening stands (`OpeningStartStands`). In the same transaction, it keeps the hold and the open message as the record of the tree's last opening (`work_hold_openings`, `record.Store.OpenWorkHold`). A claim that the hold stopped after the opening read the tree's claims is started later with the same task, built from that record (`heldClaimOpening`). A start that the outbox runs against a claim that the hold holds builds its opening's sentences from that record when it runs (`HeldClaimOpening`), so a start queued before a later close and opening gives the later words. Where the claim kept an earlier opening's task, the new task carries the newest sentences once, in front of that task's work (`supervise.Delivery.Work`). Each send of a task that carries news renders the news again with the opening's sentences in front (`renderNews`, `supervise.Delivery.Opening`). The boot reconciles each running tree with its row (`workHoldBooted`). The standing gate (`record.TreeGate.Standing`, over the steps the tree is gated on), read under `work` alone (`holdIsWork`), is the one predicate that the close, the opening and the boot read, and `internal/daemon`'s start fence (`startWaitsForTheHold`) reads the same standing gate. A merger's fence is `mergerWaitsForTheDesignGate` under both holds: once the gate is open, it also waits until what changed in the approved design is recorded, so under `work` the opening's start of a merger the hold stopped waits for its news to be recorded. The state's `why: held` reads the tree's `work_holds` row.

The 2 minutes of the stop that a close message carries count from the delivery of the message that the daemon confirmed (`internal/daemon`'s `postHoldStop`). A daemon restart or a late confirmation can make the cut later, by the length of the restart or of the backoff, but never earlier. A project pause can release a worker before its close message runs. The pause's resume relaunches that worker, the worker gets the close message, and the daemon stops it 2 minutes later at most. The opening never retires an operator's task that the claim kept and no turn took (`supervise.KeptOperatorTask`, a task of no run): an operator's act overrides the hold. `supervise.Machine.EndHold` starts the claim with that task first, and `supervise.OpeningKeeps` does not put that task's work behind the opening's sentences. The start's own task waits behind the operator's task by `supervise.Machine.queue`'s rule for a task that no rule replaces (`ErrDeliveryPending`), so the start's row waits on its backoff. A retry of the row that ended the hold goes on (`openingStartFindsNoHold`, `retriesItsStart`), settles the holder row as told again, since the role may hold its member's phase only now (`startNewsOf`), and builds the opening's sentences again (`startOfAHeldClaim`). A start with no opening's sentences waits while the claim's own start of the opening is queued: while the hold stops the claim (`openingGoesFirst`), and after that start ended the hold (`waitForOpeningInFlight`). So the worker gets the operator's task, then the opening's task, then that start's task. The second wait reads the role's queued rows only under `work` (`openingMayBeInFlight`). Where no start of the opening is queued, a start with no opening's sentences ends the hold itself and settles no opening as told (`startNewsOf`), so its news carries an opening its issue's holder row still owes. The transaction of `postHoldStop` opens the commit scope itself (`committing`), so the supervise lane wakes once the stop's row has committed.

Under `work`, no architect is told to start its own acceptance while the tree's standing gate is closed.
In this release `accepting` is always the owner's place: the step `acceptance:owner` of a plan, and the `accepting` of the default steps, which an issue with no plan rows walks (`workflow.TellsOwnersAcceptance`).
`internal/daemon`'s `readNoticeTree` reads the standing gate, under `work` alone, in the same REPEATABLE READ snapshot as the notice's issue (`treeSnapshot.holdsWork`).
`deliverNotice` then holds, as a routine wait before any wake of a released architect (`heldForTheOwner`), a notice of an issue that stands in `accepting` that tells its acceptance: a `phase-finished` notice, or the `awaiting-children` notice of a return out of `awaiting_children` into `accepting` (`workflow.ReturnFromChildren`), the one notice of that kind whose `phase` is `awaiting_children`. The `awaiting-children` notice of a move into the wait names the phase the issue left, and goes.
`earlierNoticeFor` lets every later notice of that architect pass the held row.
Each attempt reads the notice against the issue again, so a notice whose issue left `accepting` meanwhile, by the architect's own sign-off or move back, goes.
A catch-up names the issues that wait in `accepting` for its architect's acceptance only while no work hold of the tree stands (`workflow.TreeCatchUp`, `workHoldStands`), both where `QueueCatchUp` queues it and where `readNoticeTree` composes it again at delivery.
`deliverNotice` then takes that clause out of the reason it publishes, after that recomposition, while the gate that each attempt reads stands closed under `work` (`workflow.CatchUpWithoutAcceptance`).
When the work hold ends (`tellAndEndWorkHold`), `tellOwnersAcceptance` queues again, for each in-workflow member that stands in `accepting`, the `phase-finished` notice that moved it there (`ownersAcceptanceNotice`).
A member with a notice of its acceptance still in the outbox, a held return's `awaiting-children` notice among them, gets no second one: that notice goes once the gate is open.
The architect's own report gets no fence: the daemon records its sign-off or move back, and the start that the transition makes waits at `startWaitsForTheHold`, as every held start does.
The architect's close message under `work` says so: `Your own work goes on, and a step that you report starts nothing until every gated step stands open again.`

Each path that tells a root architect of an approval (the `design-approved` and `carried-gate-opened` notices, the `basis-ended` notice of a person's approval of the root's own spec that ended a step's wait on an ancestor's request, the role message that the gate opened, a resume or start task, the catch-up, and a decision kept for a root out of the workflow) reaches the architect after the transaction that writes the gate row commits, so pi-legion's next read of `POST /legion/v1/claims/approval` sees the approval (`internal/workflow/approval_route_paths_test.go`). The route reads a root's own approval with `record.DesignGate.ApprovedByPerson`, so a step that an ancestor's approval opened counts as no approval of the root's own spec, and every other act that writes a `design-approved` or `basis-ended` notice, and every `resting-root` notice, tells none (the same test's `silentPaths`). A root's re-admission records the approved `spec` row that it deletes (`record.ClearedSpecApproval`), and the carry of a gate records the root whose document the carried `spec` row holds (`record.HandedOverRoot.FromRoot`), the carried root itself where the carry brought no `spec` row.

News of an approved new version reaches the holders of a tree's work from the record, never from a message composed when the gate moved.
Migration `20261119203047_design_news` adds the told record, `design_news_told`, one row per issue and audience: the `holder` row is what the session holding that issue's phase took, the `architect` row of a tree root what that tree's root architect took, `versions` maps each gated step to the approved version taken, and `opening_owed` says the gate's opening is owed to that audience.
A confirmed delivery's copy of the news its prompt carried (`pending_task_deliveries.carried_news`) is a credit, not a write to the row: every reader reads the told rows through `design_news_told_in`, which adds each standing credit, and a credit counts only in the run it was rendered in (`design_news_current`).
The write that records `carried_ran`, once the turn's result says the turn ran, folds the credit into the row (`store.settleDesignNews`).
A take-back or a retirement writes nothing to the told rows: the delivery written without its copy, or deleted, ends its credit.
`Engine.enter` writes a member's baseline at its first working entry (`record.Store.BaselineTold`), so a delivery retired before its turn ran leaves its news owed.
`record.OwedNews` is the one rule over it: news is owed while the standing gate is open and a step's approved version is above the told one, `spec` and `decisions` concerning every member and `criteria` the tree root alone, and never to a member whose pull request merged, which `Engine.backward` also refuses to move back (`BACKWARD_REFUSED`).
The change set is Dispatch's, read from `GET /api/v1/artifacts/{id}/changes` and kept in `design_changes` once per document and version pair, `read` or `unavailable` with its reason, since two stored versions never change.
The outbox kind `design_changes` (`record.DesignNewsReconcile`, one unrun row per tree) runs on a lane of its own, `record.LaneDocuments`, so its Dispatch read holds back no start, stop or suspend of the lifecycle lane and waits behind no architect notice of the board lane;
its executor, the daemon's `designChanges`, records each pair, raises the told versions of a change that changed nothing of the work (decision blocks alone, or a version Dispatch answers `unchanged`: `record.DesignChanges.WorkUnchanged`), and queues a news-only start (`record.SuperviseRequest.News`) for each holder owed news.
`putGateTold` queues that row when an approved version rises or the standing gate opens, `Engine.queueMovedNews` when a move leaves its holder owed news, and the entry sweep's tick (`queueOwedDesignNews`) is the backstop.
Every phase start and every news-only start carries the news, which `workflow.RenderNews` renders at send from the record as it stands then, and a merger's start waits while its change set is not recorded (`mergerWaitsForTheDesignGate`).
The opening is decided for each holder in one function, `openingDelivery`, which `tellGateMoved` calls: a holder owed news is sent no role message, its `opening_owed` is set, and the news task leads with the opened sentence;
every other holder is sent the opened role message, with the clause that nothing its issue holds changed where its told row shows it.
The closed message goes to every holder as before.
