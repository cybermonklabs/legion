Planned: the issue-cap admission line, durable Dispatch and GitHub event intake, classification, the transition table, status and notice effects, and the Go Dispatch client — `internal/admit`, `internal/intake`, `internal/workflow`, `internal/classify`, `internal/dispatch`, `internal/notify`, `internal/phase`. LEGION-219 (Stage 3) carries them; none exists on `main` yet, so this component has no paths. The planned workflow advances phases from facts the coordinator observes; agents do not choose the next phase.

Admission and the workflow read the deployment's repository equivalence (`repository_renames`, `config.Config.RepositoryRenames`, a `ghrepo.Renames`) wherever they compare a repository's name, so a transfer that renames a repository leaves the trees already recorded under the old name running: in intake, `ConsumerSpec.Renames` carries the pair into the consumer's `recordedPullRequest` read; in `workflow`, one `Engine.sameRepository` stands where `strings.EqualFold` stood, at `issueForBranch`, `ownPullRequest`, the opened handler's redelivery test, `check.go`'s comparison of a recorded check, and `NoteRepositoryKept`, which therefore says nothing when Dispatch re-points an issue at the repository the one it is recorded on moved to. No deploy run is matched any more: the production check a merge opens is woken only by the `wake_at` its own agent — the role the project's `production_check` names — gave on a `pending` report, by the retry of a look nobody reported, or by the check's own bound, so `projects.<KEY>.deploys` is read for nothing and only warned about. The reads keyed on the `pull_requests` table's `repo` column — the engine's `pullRequest` and `pullRequestByBranch`, `internal/daemon`'s `reviewedRepository` and intake's `recordedPullRequest` — ask under each name `Renames.Lookups` gives, the fact's own first and the pair's other name only when the first finds nothing, which is what lets a pull request already open at the transfer go on taking its CI, its review and its merge. The equivalence writes no record but for one pass of this release, `internal/daemon`'s rename pass (`record.RenameIssueRepository`), which writes each pair's `to` over its `from` on the stored rows of each issue with no live pod, at boot and when the issue's pod ends; until it writes a record, the record keeps the repository it was written under, so the pair must stay configured until no row names the old repository. It serves no repository of its own either — a name is served when GitHub answers that both role Apps are installed on it, and until GitHub has answered for a pair's names its `to` counts as served and its `from` does not — so a pair may be configured before the transfer and simply answers nothing until the events arrive under the new name.

News of an approved new version reaches the holders of a tree's work from the record, never from a message composed when the gate moved. Migration `20261119203047_design_news` adds the told record, `design_news_told`, one row per issue and audience: the `holder` row is what the session holding that issue's phase took, the `architect` row of a tree root what that tree's root architect took, `versions` maps each gated step to the approved version taken, and `opening_owed` says the gate's opening is owed to that audience. A confirmed delivery's copy of the news its prompt carried (`pending_task_deliveries.carried_news`) is a credit, not a write to the row: every reader reads the told rows through `design_news_told_in`, which adds each standing credit, and a credit counts only in the run it was rendered in (`design_news_current`). The write that records `carried_ran`, once the turn's result says the turn ran, folds the credit into the row (`store.settleDesignNews`). A take-back or a retirement writes nothing to the told rows: the delivery written without its copy, or deleted, ends its credit. `Engine.enter` writes a member's baseline at its first working entry (`record.Store.BaselineTold`), so a delivery retired before its turn ran leaves its news owed. `record.OwedNews` is the one rule over it: news is owed while the standing gate is open and a step's approved version is above the told one, `spec` and `decisions` concerning every member and `criteria` the tree root alone, and never to a member whose pull request merged, which `Engine.backward` also refuses to move back (`BACKWARD_REFUSED`). The change set is Dispatch's, read from `GET /api/v1/artifacts/{id}/changes` and kept in `design_changes` once per document and version pair, `read` or `unavailable` with its reason, since two stored versions never change. The outbox kind `design_changes` (`record.DesignNewsReconcile`, one unrun row per tree) runs on a lane of its own, `record.LaneDocuments`, so its Dispatch read holds back no start, stop or suspend of the lifecycle lane and waits behind no architect notice of the board lane; its executor, the daemon's `designChanges`, records each pair, raises the told versions of a change that changed nothing of the work (decision blocks alone, or a version Dispatch answers `unchanged`: `record.DesignChanges.WorkUnchanged`), and queues a news-only start (`record.SuperviseRequest.News`) for each holder owed news. `putGateTold` queues that row when an approved version rises or the standing gate opens, `Engine.queueMovedNews` when a move leaves its holder owed news, and the entry sweep's tick (`queueOwedDesignNews`) is the backstop. Every phase start and every news-only start carries the news, which `workflow.RenderNews` renders at send from the record as it stands then, and a merger's start waits while its change set is not recorded (`mergerWaitsForTheDesignGate`). The opening is decided for each holder in one function, `openingDelivery`, which `tellGateMoved` calls: a holder owed news is sent no role message, its `opening_owed` is set, and the news task leads with the opened sentence; every other holder is sent the opened role message, with the clause that nothing its issue holds changed where its told row shows it. The closed message goes to every holder as before.

A message of the daemon's own reaches a role whose pod an idle release took only at a moment that role can take it (dispatch://INFRA-4480). A work-back hook's prompt (`record.HookPrompt`) waits in the outbox, waking nothing and publishing nothing, while the start its move back queued in the same transaction is still queued (`record.Store.MoveStartQueued`: a start of the role of the prompt's `To` phase that names it, carries `workflow.StartOrOwe`'s slot mark for it and was written after the prompt). That start can also leave unprompted, taken out by a later start of the issue or finished by the phase fence, so with none queued the prompt reads the issue (`outbox.moveRound`): it ends unpublished where the issue no longer stands in `To`, and waits where the issue is held there or holds no slot of a phase that keeps one. A role message (`record.RoleMessage`) to a released claim still ends with no wake, but for two cases that wait and wake nothing: a wake of the role already under way (an open `pod_resumes` row, an issue that can be woken, and a queued start of the role or a claim that has left released since, the claim read again after the queued starts), and a design gate's move to a phase holder that is no merger, which `tellGateMoved` marks (`record.RoleMessage.Gate`, with the opening number the holder's `design_news_told` row took at the move) and which waits while the claim reads released. Both publish with keep (`publishKeptToRole`) once the claim has left released, so the listener holds the message for the woken session. A gate row is decided at publish time, against the record as it stands then (`outbox.gateMoveStale`): it is published only while the holder's row still holds its opening number, which every move of the gate and nothing else moves, and the gate still stands open or closed as the move left it; every other gate row ends unpublished. The merger's gate moves and the root architect's are left to their own rules. A rollback strips the `gate` key first (`record.RoleMessageGateWayBack`, docs/kubernetes.md).
