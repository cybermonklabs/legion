Stages 1 and 2 on `main` provide the `legion` command (including `worker-shim` and `claims`), configuration, boot and shutdown assembly, the state and health routes, and the claim-registration and operator routes. Stages 3 and 4 complete the agent API and CLI commands. Its API compatibility with the language-neutral contracts is not a Go source dependency.

`legion.yaml`'s top-level `repository_renames` (a list of `from`/`to` pairs) settles onto `config.Config.RepositoryRenames`, the `ghrepo.Renames` every consumer takes; `legion config check` prints one line per pair after its `Config OK:` line, and `api.SettingsOf` carries them as `settings.repository_renames`, so `legion state --json` reads back what the daemon treats as one repository.

`legion.yaml`'s `projects.<KEY>.memory` (`mode`, `config_files`, `instructions`) settles onto `config.Project.Memory`, which `readProject` reads and nothing else maps: the declared list is built at each call from the project's own keys, the `memory` block's experiment first, unless `experiments.memory` declares it instead, and the `experiments` key's own after it (`Project.ExperimentsDeclared`), and a launch takes the arms that list and the unit's recorded rows agree on through `runtime.SpawnSpec.Variants`; `api.SettingsOf` carries the block as `settings.projects.<KEY>.memory` and the `experiments` key as `settings.projects.<KEY>.experiments`, and `GET /legion/v1/state` carries on every issue the answers that apply to it as `assignments` (`api.Issue.Assignments`, daemon API contract 141; a caller in a pod whose claims record a contract below 141 is served the state without them, the band of `shapeState` in `packages/daemon/internal/api/shaping.go` that applies `withoutAssignments`) and, beside them, its tree's `memoryGroup`, `memoryDrawMode` and `memoryDrawnAt`, read off the `memory` answer alone and only where it records a draw, the three absent together while no draw has reached that tree (contract 49; `withoutMemory` below it). So `legion state --json` reads back each issue's answers, under which mode and when, and `legion state` prints one line per declared experiment counting the issues that hold each arm, naming no issue. It counts issues because each issue's `assignments` holds its tree's tree-unit rows and its own issue-unit rows (`internal/projection`'s `assignmentViews`), so one count serves an experiment of either unit; a count of trees, read off `api.Issue.Tree`, would fit a tree-unit experiment alone and would not count draws even there, since a child handed over as a tree of its own becomes its own tree's root (`internal/admit`'s `readmit`) and carries its old tree's tree-unit rows verbatim, arm, mode and instant (`record.Postgres.CarryAssignments`), so two trees hold one draw.

`legion controller start` hands the controller's session the secrets broker's route to a Dispatch credential where the controller's own file asks for it (`controller_dispatch_token.go`): `dispatch_token_broker: true`, the alternative to `dispatch_token_file` and never set beside it, has the session's own Envoy client trade this machine's identity for a DPoP-bound access token and renew it, so nobody copies a person's Dispatch token onto a machine. The start writes no token and hands the session no `DISPATCH_TOKEN_FILE` or `DISPATCH_TOKEN` — Dispatch refuses such a token presented as a bearer (RFC 9449 Section 7.2) — and drops an inherited one; it hands it `DISPATCH_TOKEN_BROKER=1` instead, under which the Envoy client reads no bearer from any source and turns Dispatch off with an error rather than falling back, because the controller keeps the operator's HOME and the envoy.json there is that person's own, `dispatch.token` and all, which would otherwise resolve first and write Dispatch as the operator. It trades once itself through `github.com/sjawhar/envoy/brokerclient`, before the daemon mints a capability, so a machine that proves no identity (`AGENT_SECRETS_MACHINE_IDENTITY`), a deployment that names no broker (`AGENT_SECRETS_URL`), or a broker that refuses this machine refuses the start, in the broker's own words where they are the broker's. With `dispatch_token_file` instead, the controller reads that bearer, as it always has; the loader reads no environment, so it takes a `dispatch_url` naming neither credential and the start is what refuses it. That import is this component's one Go source dependency on Envoy.

Under either credential, the start also sets `PERSON_SIGNIN_TRADE=off` in the controller's environment (`controllerEnvironment`, `controllerPersonTradeVar`). The TypeScript client (`packages/broker-client`, which pi-envoy, pi-legion, claude-envoy and the `dispatch` command use) then trades this machine's identity for the controller's own Dispatch credential under `dispatch_token_broker`, and for its Envoy credential where no bearer names one, even where the operator ran `agent-secrets login` on the machine and the controller finds that sign-in under the operator's HOME, which it keeps, so no credential the controller trades at the broker acts in its operator's name. A bearer the controller is given is presented as it is at main: the token `dispatch_token_file` names, and an Envoy bearer from the operator's environment or from the `envoy.json` under that HOME, each of which resolves before the broker route. That client alone reads the setting, and its name lies outside `AGENT_SECRETS_*` because `agent-secrets NAME -- <cmd>` strips that prefix's variables from its child but for a few (`sessionIdentityVars`), so a `dispatch` command the controller runs under `agent-secrets NAME --` keeps it. The setting does not change the controller's own `agent-secrets` secret reads: they are signed exactly as they would be without it.
