Stages 1 and 2 on `main` provide the `legion` command (including `worker-shim` and `claims`), configuration, boot and shutdown assembly, the state and health routes, and the claim-registration and operator routes. Stages 3 and 4 complete the agent API and CLI commands. Its API compatibility with the language-neutral contracts is not a Go source dependency.

`legion.yaml`'s top-level `repository_renames` (a list of `from`/`to` pairs) settles onto `config.Config.RepositoryRenames`, the `ghrepo.Renames` every consumer takes; `legion config check` prints one line per pair after its `Config OK:` line, and `api.SettingsOf` carries them as `settings.repository_renames`, so `legion state --json` reads back what the daemon treats as one repository.

`legion.yaml`'s `projects.<KEY>.memory` (`mode`, `config_files`, `instructions`) settles onto `config.Project.Memory`, which `readProject` reads and nothing else maps: the declared list is built at each call from the project's own keys, the `memory` block's experiment first, unless `experiments.memory` declares it instead, and the `experiments` key's own after it (`Project.ExperimentsDeclared`), and a launch takes the arms that list and the unit's recorded rows agree on through `runtime.SpawnSpec.Variants`; `api.SettingsOf` carries the block as `settings.projects.<KEY>.memory` and the `experiments` key as `settings.projects.<KEY>.experiments`, and `GET /legion/v1/state` carries on every issue the answers that apply to it as `assignments` (`api.Issue.Assignments`, daemon API contract 141; a caller in a pod whose claims record a contract below 141 is served the state without them, `stateFor`'s `withoutAssignments`) and, beside them, its tree's `memoryGroup`, `memoryDrawMode` and `memoryDrawnAt`, read off the `memory` answer alone and only where it records a draw, the three absent together while no draw has reached that tree (contract 49; `withoutMemory` below it). So `legion state --json` reads back each issue's answers, under which mode and when, and `legion state` prints one line per declared experiment counting the issues that hold each arm, naming no issue. It counts issues because each issue's `assignments` holds its tree's tree-unit rows and its own issue-unit rows (`internal/projection`'s `assignmentViews`), so one count serves an experiment of either unit; a count of trees, read off `api.Issue.Tree`, would fit a tree-unit experiment alone and would not count draws even there, since a child handed over as a tree of its own becomes its own tree's root (`internal/admit`'s `readmit`) and carries its old tree's tree-unit rows verbatim, arm, mode and instant (`record.Postgres.CarryAssignments`), so two trees hold one draw.

`legion controller start` hands the controller's session the secrets broker's route to a Dispatch credential where the controller's own file asks for it (`controller_dispatch_token.go`): `dispatch_token_broker: true`, the alternative to `dispatch_token_file` and never set beside it, has the session's own Envoy client trade this machine's identity for a DPoP-bound access token and renew it, so nobody copies a person's Dispatch token onto a machine. The start writes no token and hands the session no `DISPATCH_TOKEN_FILE` or `DISPATCH_TOKEN` — Dispatch refuses such a token presented as a bearer (RFC 9449 Section 7.2) — and drops an inherited one; it hands it `DISPATCH_TOKEN_BROKER=1` instead, under which the Envoy client reads no bearer from any source and turns Dispatch off with an error rather than falling back, because the controller keeps the operator's HOME and the envoy.json there is that person's own, `dispatch.token` and all, which would otherwise resolve first and write Dispatch as the operator. It trades once itself through `github.com/sjawhar/envoy/cipherclient`, before the daemon mints a capability, so a machine that proves no identity (`AGENT_SECRETS_MACHINE_IDENTITY`), a deployment that names no broker (`AGENT_SECRETS_URL`), or a broker that refuses this machine refuses the start, in the broker's own words where they are the broker's. With `dispatch_token_file` instead, the controller reads that bearer; the loader reads no environment, so it takes a `dispatch_url` naming neither credential and the start is what refuses it. That import is this component's one Go source dependency on Envoy.

Under either credential, the start also sets `PERSON_SIGNIN_TRADE=off` in the controller's environment (`controllerEnvironment`, `controllerPersonTradeVar`). The TypeScript client (`packages/cipher-client`, which pi-envoy, pi-legion, claude-envoy and the `dispatch` command use) then trades this machine's identity for the controller's own Dispatch credential under `dispatch_token_broker`, and for its Envoy credential where no bearer names one, even where the operator ran `agent-secrets login` on the machine and the controller finds that sign-in under the operator's HOME, which it keeps, so no credential the controller trades at the broker acts in its operator's name. A bearer the controller is given is presented as that bearer: the token `dispatch_token_file` names, and an Envoy bearer from the operator's environment or from the `envoy.json` under that HOME, each of which resolves before the broker route. That client alone reads the setting, and its name lies outside `AGENT_SECRETS_*` because `agent-secrets NAME -- <cmd>` strips that prefix's variables from its child but for a few (`sessionIdentityVars`), so a `dispatch` command the controller runs under `agent-secrets NAME --` keeps it. The setting does not change the controller's own `agent-secrets` secret reads: they are signed exactly as they would be without it.

The outbox runs a waiting row at the event it waits for, and between events on a backoff capped at 5 minutes (dispatch://INFRA-4131). Nine kinds publish to one role: `notice`, `controller_notice`, `merge_queue_removal`, `merge_holds_changed`, `merge_forward`, `hook_prompt`, `phase_ended`, `role_message` and `update_ask` (`record.OutboxKind.WaitsForRole`). Before each publish, a row of these kinds asks one gate, `roleWaitGate` (`role_wait.go`), which reads the role's claim in the daemon's own record. A role with no machine, whose start is still owed, and a launch that has not registered its session get no publish. A registered launch that has not said it is ready, and a claim suspended by any source but the idle release, get at most one publish for each launch (`Claim.Generation`). A failed or retired claim ends the row as its kind ends. A released claim keeps what each kind did before: a row that wakes its role asks for the wake, and a `role_message` that a pause holds publishes on the capped waits, since that publish is its role's only wake. A claim that said it is ready (`supervise.SaidReady`) gets the publish. A `notice`, a `role_message` that no pause holds and an `update_ask` whose role has no machine end with no publish. Each ready of a claim of any role, the controller's included, is a change of the claim that the end of the ready's decision tells `supervise.Deps.ClaimChanged` (`workflowRuntime.claimChanged`), and `outbox.releaseChanged` then makes every row that waits for that claim due at once, once for each ready: the ready route's own hook (`claimReadyHook`) hands only the controller's ready to its keeper, for the start message, and releases no row. A restart is no ready: a machine that the boot restores (`supervisor.restore`) tells the hook nothing, so a row's wait reads back across the restart. A catch-up that the wake pacing holds to a later moment keeps that moment. A launched session takes its role's Envoy name only at its first turn, or 30 seconds after its ready. So a publish that the listener refuses because no session holds the role, while the claim said it is ready and has started no turn since, runs again at the claim's next turn start or at `roleNameBound` after the ready, whichever comes first. A row that waits for another event that the daemon records itself returns an `eventWaiting` that names the event's key (`record.WaitForClaim`, `WaitForTreeClaims`, `WaitForGate`, `WaitForNews`, `WaitForRow` and the other builders in `record`). Examples are a start behind its claim's pending delivery, a merger's start or a held message behind a closed design gate, a start that waits for another claim to stop, a tree close that waits for its claims to retire, a child architect's first start that waits for its tree to run, an update ask behind its claim's machine lock, and a notice behind an earlier notice to the same architect. The write that records the event makes the row due in the same transaction (`record.Store.ExpediteWaits`). Each change of a claim reaches the outbox through `supervise.Deps.ClaimChanged` (`workflowRuntime.claimChanged`, then `releaseChanged`). Between events, such a row, and each failed publish that keeps a row of the nine kinds (`publishFailed`: a refusal of the listener's, a 5xx, or a publish that did not reach the listener), waits `record.RoleWaitBackoff`: one second, doubled at each step, up to `record.RoleWaitBackoffMost`, 5 minutes, the bound of `parkedWakeBound`. So at the cap a row runs at most 12 times an hour. A ready or the event starts the steps again from one second. No count of attempts ends such a row while its claim stands, and a notice answered `receipt_timeout` keeps its row. The one failed publish that keeps no row is the listener's refusal of the message itself, a 400 or a 413 with its own error (`notify.ErrMessageRefused`), which no retry of the same message changes: a row of any of the nine kinds ends undelivered at that run (`messageRefused`, `permanentRefusal`, `finishRefused`), takes no wait and writes no wait line, and writes one line at Error, `outbox row's message refused by the listener and dropped; no retry of the same message is taken, since the listener refuses it however often it is sent`, naming the row, its kind and issue, its attempts, the role (or the topic held to no claim of the daemon) and the listener's refusal. None of the kind's own follow-ups runs: a hook prompt posts no message on the issue, and a merge-forward ask is not sent again at the row's end. Every publish carries the row's own key (`record.OutboxKey`). `settle` logs such a row by its wait, not by its attempts. It writes `outbox row waits` at Info when the wait starts. At 30 minutes it writes one line: at Error, `outbox row's role is ready and took nothing for 30 minutes`, for a ready role that took nothing, and at WARN, `outbox row has waited 30 minutes`, for every other wait. Each line names the listener's last answer, the failure of the row's publish, where there is one. When the row ends, by its run or by a delete, it writes `outbox row's wait ended` at Info. Every other run logs at Debug. A failure that is no publish, a store read or a Dispatch read the row makes before or after it, keeps `record.RetryBackoff` and `outbox row failed`. A wait whose end the daemon does not record keeps `record.RetryBackoff`, at most 64 seconds, and its earlier lines: a Dispatch that does not serve a route yet, a Dispatch claim of another session, the listener's freeing of a role, and a named moment.
