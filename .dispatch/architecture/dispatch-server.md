The composition root of the native Dispatch API: `cmd/dispatch` reads its boot configuration from the environment and assembles the server, and `internal/dispatch/routes` is the route table and the router wiring every handler package together. Each subsystem it composes is a child component below. Its wire types match the language-neutral contracts, which is a compatibility rule rather than a Go source dependency, so no edge is drawn for it. It hands the background loops the background pool and the leased loops the lease pool, so no loop waits for a request's connection nor a request for a loop's, and it makes the one admission limiter the API admits through. Logging never blocks a caller: `internal/dispatch/logging` formats each line in its caller and hands it to one writer goroutine through a bounded buffer, dropping and counting what does not fit, and every exit writes what is still buffered. With `DISPATCH_METRICS_ADDR` set it serves Prometheus `/metrics` (per-pool connections and acquire waits, admission, the writer gates, settlements, the outbox's lag and publishes, events committed, the Go runtime, dropped log lines) on the repository's own `internal/metrics`; with `DISPATCH_PPROF_PORT` set the profiler records mutex and block profiles too. Shutdown runs every stage inside one deadline, `stopGrace` less three seconds, made at the signal.

It also starts the background loops, in three shapes (`cmd/dispatch/README.md`, "Background loops"): woken loops (the embedding queue, the reference excerpts, the edit notices, the suggestion outcomes, the intakes' delivery settings, and the copy of the GitHub reads' record, `githubreads.Copy`, which `/healthz` answers `github` from), boot passes (embedding coverage, task progress), and timers that stay because nothing announces what they would miss (the delivery reconcile, the architecture import and the webhook redelivery sweep, each jittered every period, the keyed writes' maintenance sweep, `api.RunMaintenanceSweep`, once a minute under lease `suggestion-outcomes`, and the Legion sampler, `legion.RunSampler`, once a minute under lease `legion-state`, which reads each configured project's daemon in turn). Every woken loop waits on one shared listener per process, a `pglisten.Hub` named `dispatch-listener <process id>` in `pg_stat_activity`, which the document rooms' room sync is registered on too, on one held connection of the store's listener pool: it LISTENs on `dispatch_embeddings`, `dispatch_excerpts_owed`, `dispatch_edit_notices`, `dispatch_events`, `dispatch_duty_holds`, `dispatch_delivery_settings` and `dispatch_github_read_attempts` (each only when its loop runs) beside the room-sync channels, and signals every loop after each successful LISTEN, since Postgres does not replay a notification sent while it was reconnecting. No loop waits for it: each runs its boot pass whether or not it has connected.

It starts one loop only after the server listens and the registry of live server processes admits the process: the keyword fill (`textversions.Run`, `dispatch-textversions`).
So the fill never runs inside a migration, and it never runs in a process that the registry refuses or has not admitted yet.
The pause of the fill reads the answers reads that its process serves, and a process that the registry has not admitted serves none.
The fill is a held duty, and it has none of the three shapes above.
One process at a time holds its `duty.Hold`, `search-text-versions-fill`, and writes `search_text_versions` from the event log, its hold and its batches on its two connections of the lease pool, and the other processes stand by.
Its two wakes are on the shared listener: `dispatch_events` wakes the holder's next pass, and `dispatch_duty_holds` wakes a standby's next try for the hold.
It continues from its cursor row in `search_text_versions_fill`, and before each batch it pauses while an answers read that its process serves takes longer than 800 ms.
`store.TextVersionsAt` answers the table at a past time for a search, and refuses a time past the reach of the fill (`dispatch-store`).
The shutdown's background stage waits for the fill inside the shutdown's one deadline, so the fill releases its hold before the pools close.

Beside the suggestion-outcome sweep, `cmd/dispatch` starts the term-statistics refresh the related-item check picks its keywords from, at boot and every ten minutes, on the background pool. `cmd/dispatch/README.md` describes under "Search" what each check answers. That `advice.suggestions` shape holds no `decision` field: a check offers the items of the project it searched, and a check whose write asks a person a question also offers the answered questions of other projects. The check of such a write holds three connections of the request pool for a moment rather than two, since its cross-project read runs beside its one-project read, which is the weight the routes that run such a check are admitted for.

`cmd/dispatch`'s `brokerTokenVerifier` builds the broker-token verifier with `ciphertoken.Options.ServesReadOnly` set.
So Dispatch accepts a read-only broker token, and its route table's read list (`readScopeRoutes`) and gate decide which routes that token reaches.
