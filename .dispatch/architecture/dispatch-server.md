The composition root of the native Dispatch API: `cmd/dispatch` reads its boot configuration from the environment and assembles the server, and `internal/dispatch/routes` is the route table and the router wiring every handler package together. Each subsystem it composes is a child component below. Its wire types match the language-neutral contracts, which is a compatibility rule rather than a Go source dependency, so no edge is drawn for it.

It also starts the background loops, in three shapes (`cmd/dispatch/README.md`, "Background loops"): woken loops (the embedding queue, the reference excerpts, the edit notices, the suggestion outcomes, the intakes' delivery settings), boot passes (embedding coverage, task progress), and timers that stay because nothing announces what they would miss (the delivery reconcile, the architecture import and the webhook redelivery sweep, each jittered every period, and the keyed writes' maintenance sweep, `api.RunMaintenanceSweep`, once a minute under lease `suggestion-outcomes`). Every woken loop waits on one shared listener per process, a `pglisten.Hub` named `dispatch-listener <process id>` in `pg_stat_activity`, which the document rooms' room sync is registered on too, on one held connection of the store's listener pool: it LISTENs on `dispatch_embeddings`, `dispatch_excerpts_owed`, `dispatch_edit_notices`, `dispatch_events` and `dispatch_delivery_settings` (each only when its loop runs) beside the room-sync channels, and signals every loop after each successful LISTEN, since Postgres does not replay a notification sent while it was reconnecting. No loop waits for it: each runs its boot pass whether or not it has connected.

Beside the suggestion-outcome sweep, `cmd/dispatch` starts the term-statistics refresh the related-item check picks its keywords from, at boot and every ten minutes. `cmd/dispatch/README.md` describes under "Search" what each check answers. That `advice.suggestions` shape holds no `decision` field: a check offers the items of the project it searched, and a check whose write asks a person a question also offers the answered questions of other projects. The check of such a write holds three connections of the store's shared pool for a moment rather than two, since its cross-project read runs beside its one-project read.

`cmd/dispatch` also builds the command bar's two models and hands both to the API through the router (`AppContextOptions.Answerer`, `AnswerModel` and `Decider`). `DISPATCH_ANSWERER` names the answering model, on Azure or at an endpoint. `resolveAnswerer` builds it as one `agentloop.Model` of the Chat Completions shape, with the `api-version` as a query parameter and the token read on every attempt, and gives it to `going.NewAnswerer`. `DISPATCH_DECISION_MODEL`, `DISPATCH_DECISION_MODEL_ENDPOINT` and `DISPATCH_DECISION_MODEL_TOKEN_FILE` name the decision model (`decision.go`). Boot refuses an endpoint without its token file, a token file without its endpoint, and an endpoint that is not an absolute https URL with a host and no query or fragment. `newDecider` builds an `api.Decider` only for a model that `packages/envoy/going/decision_models.json` holds. With no model, no endpoint, or a model that record does not hold, it logs one line, and the server boots and decides nothing. The token file is read on every decision call and never at boot, so a file written after the start refuses no boot. The router wraps the whole server in `api.EnforceCookieOrigin`, the one cross-site check of a cookie's write, which the API also puts in front of the route table that the command bar's writes call in process. The keyed writes' maintenance sweep also deletes the command bar's run records past their thirty days (`cmd/dispatch/README.md`, "Answering a question").
