The composition root of the native Dispatch API: `cmd/dispatch` reads its boot configuration from the environment and assembles the server, and `internal/dispatch/routes` is the route table and the router wiring every handler package together. Each subsystem it composes is a child component below. Its wire types match the language-neutral contracts, which is a compatibility rule rather than a Go source dependency, so no edge is drawn for it.

It also starts the background loops, in three shapes (`cmd/dispatch/README.md`, "Background loops"): woken loops (the embedding queue, the reference excerpts, the edit notices, the suggestion outcomes, the intakes' delivery settings, and the copy of the GitHub reads' record, `githubreads.Copy`, which `/healthz` answers `github` from), boot passes (embedding coverage, task progress), and timers that stay because nothing announces what they would miss (the delivery reconcile, the architecture import and the webhook redelivery sweep, each jittered every period, the keyed writes' maintenance sweep, `api.RunMaintenanceSweep`, once a minute under lease `suggestion-outcomes`, the Legion sampler, `legion.RunSampler`, once a minute under lease `legion-state`, which reads each configured project's daemon in turn, and the GitHub rate reading, `runRateReading`, in every process with no lease, which logs one `github_rate_reading` JSON line for each installation of the App, with its listed permissions, every ten minutes and in the last minute before each counter reset of any installation: a pass is due 45 s before each known reset it has not yet tried in that minute, or at once when one is already inside it, and a reset counts as tried once a line of its installation is written in that minute, failed or not; it keeps the resets a failed reading could not read, and counts the process's own calls by caller kind on the one `githubrate.Counter` that the process's two clients calling with installation tokens count on). Every woken loop waits on one shared listener per process, a `pglisten.Hub` named `dispatch-listener <process id>` in `pg_stat_activity`, which the document rooms' room sync is registered on too, on one held connection of the store's listener pool: it LISTENs on `dispatch_embeddings`, `dispatch_excerpts_owed`, `dispatch_edit_notices`, `dispatch_events`, `dispatch_duty_holds`, `dispatch_delivery_settings` and `dispatch_github_read_attempts` (each only when its loop runs) beside the room-sync channels, and signals every loop after each successful LISTEN, since Postgres does not replay a notification sent while it was reconnecting. No loop waits for it: each runs its boot pass whether or not it has connected.

It starts one loop only after the server listens and the registry of live server processes admits the process: the keyword fill (`textversions.Run`, `dispatch-textversions`).
So the fill never runs inside a migration, and it never runs in a process that the registry refuses or has not admitted yet.
The pause of the fill reads the answers reads that its process serves, and a process that the registry has not admitted serves none.
The fill is a held duty, and it has none of the three shapes above.
One process at a time holds its `duty.Hold`, `search-text-versions-fill`, and writes `search_text_versions` from the event log, and the other processes stand by.
Its two wakes are on the shared listener: `dispatch_events` wakes the holder's next pass, and `dispatch_duty_holds` wakes a standby's next try for the hold.
It continues from its cursor row in `search_text_versions_fill`, and before each batch it pauses while an answers read that its process serves takes longer than 800 ms.
`store.TextVersionsAt` answers the table at a past time for a search, and refuses a time past the reach of the fill (`dispatch-store`).
The shutdown waits for the fill, so the fill releases its hold before the pool closes.

Beside the suggestion-outcome sweep, `cmd/dispatch` starts the term-statistics refresh the related-item check picks its keywords from, at boot and every ten minutes. `cmd/dispatch/README.md` describes under "Search" what each check answers. That `advice.suggestions` shape holds no `decision` field: a check offers the items of the project it searched, and a check whose write asks a person a question also offers the answered questions of other projects. The check of such a write holds three connections of the store's shared pool for a moment rather than two, since its cross-project read runs beside its one-project read.

`cmd/dispatch`'s `brokerTokenVerifier` builds the broker-token verifier with `ciphertoken.Options.ServesReadOnly` set. So Dispatch accepts a read-only broker token, a read entry's or one narrowed to reading with or without a cut, and its route table's read class (`readClasses`) and gate decide which routes that token reaches.

The server serves two versions of the API from the one route table the handlers declare (`dispatch-api`): `/api/v2`, from the first `legion-envoy` release that carries pull request #4274, and the deprecated `/api/v1`. `cmd/dispatch` reads `DISPATCH_API_V1_END` at boot, an RFC 3339 instant it refuses to start on when it does not parse, and hands it to the router, whose check in front of every route sets `Sunset` on each `/api/v1` answer while the instant is ahead and answers every path under `/api/v1`, an unknown one and a test hook's included, `410 API_V1_ENDED` once it has passed, reading the clock on each request; every `/api/v1` answer carries `Deprecation` and a `Link` to its `/api/v2` route whatever the setting says. `routes/router.go` answers an unknown `/api/v2` path `404 NO_ROUTE` and any other unknown API path `404 NOT_FOUND`, and every refusal it writes in front of a route, the cookie-origin guard's and the `/auth` routes' among them, is `{code, error}`, under `/api/v2`'s name of the code on a `/api/v2` path and `/api/v1`'s on any other (`writeAPIRefusal`). `envoy-dispatch routes --version 2` prints the body `GET /api/v2` answers, as `envoy-dispatch routes` prints `GET /api/v1`'s, and `envoy-dispatch openapi` writes and checks the OpenAPI document of each version.
