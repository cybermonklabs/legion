The composition root of the native Dispatch API: `cmd/dispatch` reads its boot configuration from the environment and assembles the server, and `internal/dispatch/routes` is the route table and the router wiring every handler package together. Each subsystem it composes is a child component below. Its wire types match the language-neutral contracts, which is a compatibility rule rather than a Go source dependency, so no edge is drawn for it.

It also starts the background loops, in three shapes (`cmd/dispatch/README.md`, "Background loops"): woken loops (the embedding queue, the reference excerpts, the edit notices, the suggestion outcomes, the intakes' delivery settings, and the copy of the GitHub reads' record, `githubreads.Copy`, which `/healthz` answers `github` from), boot passes (embedding coverage, task progress), and timers that stay because nothing announces what they would miss (the delivery reconcile, the architecture import and the webhook redelivery sweep, each jittered every period, the keyed writes' maintenance sweep, `api.RunMaintenanceSweep`, once a minute under lease `suggestion-outcomes`, and the Legion sampler, `legion.RunSampler`, once a minute under lease `legion-state`, which reads each configured project's daemon in turn). Every woken loop waits on one shared listener per process, a `pglisten.Hub` named `dispatch-listener <process id>` in `pg_stat_activity`, which the document rooms' room sync is registered on too, on one held connection of the store's listener pool: it LISTENs on `dispatch_embeddings`, `dispatch_excerpts_owed`, `dispatch_edit_notices`, `dispatch_events`, `dispatch_duty_holds`, `dispatch_delivery_settings` and `dispatch_github_read_attempts` (each only when its loop runs) beside the room-sync channels, and signals every loop after each successful LISTEN, since Postgres does not replay a notification sent while it was reconnecting. No loop waits for it: each runs its boot pass whether or not it has connected.

It starts one loop only after the server listens and the registry of live server processes admits the process: the keyword fill (`textversions.Run`, `dispatch-textversions`).
So the fill never runs inside a migration, and it never runs in a process that the registry refuses or has not admitted yet.
The pause of the fill reads the answers reads that its process serves, and a process that the registry has not admitted serves none.
The fill is a held duty, and it has none of the three shapes above.
One process at a time holds its `duty.Hold`, `search-text-versions-fill`, and writes `search_text_versions` from the event log, and the other processes stand by.
Its two wakes are on the shared listener: `dispatch_events` wakes the holder's next pass, and `dispatch_duty_holds` wakes a standby's next try for the hold.
It continues from its cursor row in `search_text_versions_fill`, and before each batch it pauses while an answers read that its process serves takes longer than 800 ms.
`store.TextVersionsAt` answers the table at a past time for a search, and refuses a time past the reach of the fill (`dispatch-store`).
The shutdown waits for the fill, so the fill releases its hold before the pool closes.

Beside the suggestion-outcome sweep, `cmd/dispatch` starts the term-statistics refresh the related-item check picks its keywords from, at boot and every ten minutes. `cmd/dispatch/README.md` describes under "Search" what each check answers. That `advice.suggestions` shape holds no `decision` field: a check offers the items of the project it searched, and a check whose write asks a person a question also offers the answered questions of other projects. The check of such a write holds three connections of the store's shared pool for a moment rather than two, since its cross-project read runs beside its one-project read.

`cmd/dispatch` also builds the command bar's two models and hands both to the API through the router (`AppContextOptions.Answerer`, `AnswerModel` and `Decider`). `DISPATCH_ANSWERER` names the answering model, on Azure or at an endpoint. `resolveAnswerer` builds it as one `agentloop.Model` of the Chat Completions shape, with the `api-version` as a query parameter and the token read on every attempt, and gives it to `going.NewAnswerer`. `DISPATCH_DECISION_MODEL`, `DISPATCH_DECISION_MODEL_ENDPOINT` and `DISPATCH_DECISION_MODEL_TOKEN_FILE` name the decision model (`decision.go`). Boot refuses an endpoint without its token file, a token file without its endpoint, and an endpoint that is not an absolute https URL with a host and no query or fragment. `newDecider` builds an `api.Decider` only for a model that `packages/envoy/going/decision_models.json` holds. With no model, no endpoint, or a model that record does not hold, it logs one line, and the server boots and decides nothing. The token file is read on every decision call and never at boot, so a file written after the start refuses no boot. The router wraps the whole server in `api.EnforceCookieOrigin`, the one cross-site check of a browser credential's write, which the API also puts in front of the route table a command-bar run's calls go through in process. The keyed writes' maintenance sweep also deletes each command-bar conversation whose newest run is seven days old, and stops a run that works under no live lease past its working budget (`cmd/dispatch/README.md`, "Answering a question").

`cmd/dispatch` also runs the command bar's agent process (`agent_supervisor.go`): its own binary as `envoy-dispatch agent` (the `agent` row of `subcommands.go`), with an environment of the agent's socket and slots, `GOMAXPROCS`, `GOMEMLIMIT`, the chat model's settings and the server's own `SSL_CERT_FILE`, and nothing else, and the secret on its standard input, which stays open, so the agent exits when the server does. It starts the agent again after each exit, waiting longer after each exit soon after a start; it reads the agent's `VmRSS` every 50 ms and kills it above its ceiling, and kills an agent that has renewed nothing for 30 s. `memlimits.go` reads the container's memory limit and sets from it the agent's ceiling and `GOMEMLIMIT` and the server's own Go memory limit, where `GOMEMLIMIT` sets none. At shutdown, after the HTTP drain, the server answers no claim, closes the agent's standard input, waits for the calls in flight and kills an agent still running. `/metrics` shows both processes' memory and goroutines, the runs by state, and the agent's slots, stuck goroutines and kills for memory.

`cmd/dispatch`'s `brokerTokenVerifier` builds the broker-token verifier with `ciphertoken.Options.ServesReadOnly` set. So Dispatch accepts a read-only broker token, and its route table's read list (`readScopeRoutes`) and gate decide which routes that token reaches.
