The composition root of the native Dispatch API: `cmd/dispatch` reads its boot configuration from the environment and assembles the server, and `internal/dispatch/routes` is the route table and the router wiring every handler package together. Each subsystem it composes is a child component below. Its wire types match the language-neutral contracts, which is a compatibility rule rather than a Go source dependency, so no edge is drawn for it.

It also starts the background loops, in three shapes (`cmd/dispatch/README.md`, "Background loops"): woken loops (the embedding queue, the reference excerpts, the edit notices, the suggestion outcomes, the intakes' delivery settings, and the copy of the GitHub reads' record, `githubreads.Copy`, which `/healthz` answers `github` from), boot passes (embedding coverage, task progress), and timers that stay because nothing announces what they would miss (the delivery reconcile, the architecture import and the webhook redelivery sweep, each jittered every period, the keyed writes' maintenance sweep, `api.RunMaintenanceSweep`, once a minute under lease `suggestion-outcomes`, the Legion sampler, `legion.RunSampler`, once a minute under lease `legion-state`, which reads each configured project's daemon in turn, and the GitHub rate reading, `runRateReading`, in every process with no lease, which logs one `github_rate_reading` JSON line for each installation of the App, with its listed permissions, every ten minutes and in the last minute before each counter reset of any installation: a pass is due 45 s before each known reset it has not yet tried in that minute, or at once when one is already inside it, and a reset counts as tried once a line of its installation is written in that minute, failed or not; it keeps the resets a failed reading could not read, and counts the process's own calls by caller kind on the one `githubrate.Counter` that the process's two clients calling with installation tokens count on). Every woken loop waits on one shared listener per process, a `pglisten.Hub` named `dispatch-listener <process id>` in `pg_stat_activity`, which the document rooms' room sync is registered on too, on one held connection of the store's listener pool: it LISTENs on `dispatch_embeddings`, `dispatch_excerpts_owed`, `dispatch_edit_notices`, `dispatch_events`, `dispatch_delivery_settings` and `dispatch_github_read_attempts` (each only when its loop runs) beside the room-sync channels, and signals every loop after each successful LISTEN, since Postgres does not replay a notification sent while it was reconnecting. No loop waits for it: each runs its boot pass whether or not it has connected.

Beside the suggestion-outcome sweep, `cmd/dispatch` starts the term-statistics refresh the related-item check picks its keywords from, at boot and every ten minutes. `cmd/dispatch/README.md` describes under "Search" what each check answers. That `advice.suggestions` shape holds no `decision` field: a check offers the items of the project it searched, and a check whose write asks a person a question also offers the answered questions of other projects. The check of such a write holds three connections of the store's shared pool for a moment rather than two, since its cross-project read runs beside its one-project read.

`cmd/dispatch`'s `brokerTokenVerifier` builds the broker-token verifier with `ciphertoken.Options.ServesReadOnly` set. So Dispatch accepts a read-only broker token, and its route table's read list (`readScopeRoutes`) and gate decide which routes that token reaches.
