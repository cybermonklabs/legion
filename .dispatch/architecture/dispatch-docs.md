The live document surface: the collaborative websocket room, where ygo returns a read-write peer's awareness update to its sender, and a read-only peer an empty awareness response, so the Hocuspocus provider stays connected without Dispatch writing frames; two-phase settlement that mints block ids before it persists and compares what it rendered; the agent edit operations (`replace`, `delete`, `insert`, `retype`, `move`, `delete_row`, `delete_column`) and the ask blocks an edit adds, which the API checks for related items, block tokens and preconditions, and ask and comment anchor refresh. Every durable writer of a room stores the room's unstored updates through the point it read the room at, in the room's commit order, before its own (`flushThrough`), so the stored updates replay to every version; `envoy-dispatch stored-order` checks that.

A whole-document upload is a conditional write too. `ReplaceText` takes the token of the version the caller believes it is replacing and checks it inside the write's own locks, before the replacement is parsed, so no other writer lands between the check and the write, as `ApplyOps` checks a conditional edit's (`mutation.go`). A document whose live tree is outside the Proof schema is the one exception: it renders no markdown and so has no token at all, and the upload is the only way to repair it, so a repair names no token and one that names a token is refused `ErrPreconditionUnavailable`, since a token this document has never had is a guard nothing could check and dropping it would tell the caller its write was conditional. `ValidateUploadPrecondition` (`edits.go`) holds an upload's precondition to the document token alone: a `blocks` guard names part of a tree the upload rewrites whole, and a precondition naming nothing guards nothing at all, each refused in words true of an upload rather than in the doc-edit rule about selecting document or blocks, which offers a choice an upload does not have. `ErrPreconditionFailed` carries the token the live tree holds now and nothing else: how far behind the client is and what it should do next are its caller's, since the write reads no version rows and knows no command its reader runs, so the upload route holds both (`api.writeUploadDocumentError`) and an edit's refusal reads as it always has. The refusal that tells a caller to upload the document again rather than write a question beside a paragraph no edit reaches (`ask_block_text.go`) names the token in the command it prints.

A transaction a handler joins (`Docs.Join`) or a settlement opens has a read phase and a write phase. The read phase takes the document owner's advisory lock (`lockArtifactOwner`), the in-memory writer slot, the copy lock where one is needed and the document's advisory lock, in that order - none of them a row lock, so none gives the transaction a transaction id while no earlier build is in the fleet (beside one, the owner lock takes the owner's row too: `dispatch-store`) - reads, and does every operation's work: forks and renders, `refreshAnchors`' walk, version capture, reference extraction, the approval carry. Every write an operation makes goes through `write`, which queues it on the transaction's ledger (`WriteStep`; a handler queues its own writes in the same queue with `Ledger.Queue`), and a read that would have seen the transaction's own write is answered from the ledger: pending appends count toward the document head (`withOwnAppends`), pending anchors toward a refresh's walk (`RegisterPendingAnchor`), a pending version's number, time and markdown (`NextVersion`, `Now`, `PendingVersionMarkdown`, `PendingVersionNumber`). The room flush is part of the read phase too: `flushThrough` takes the room's unstored updates through the read point and measures their classes there, against the same state the operation read, and queues their inserts in the room's commit order before the operation's own append, so a flush renders nothing and sends nothing between two of the transaction's statements. The write phase is one pipelined batch: `Ledger.Commit` has each queued step put its statements on one `store.WriteBatch`, in the order the transaction made them, so statements and events keep that order, appends the settlement credit's statements and the one announcement of the documents it appended to (`commitWrites`), and sends the batch in one round trip; Postgres runs the statements back to back and the client reads their results once, so no Go code - and no wait for this process to be scheduled, which cost 10-140 ms a statement under CPU load while each statement went on its own - runs between two of them while the transaction holds its id. A step reads no result: a value a later statement needs is derived in SQL (an event's sequence from its owner row, a stamp's or a review's event from the events id sequence's `currval`, `store.LatestEventID`) or read in the read phase (a row's time, its id), and a value needed after `Commit` - an appended event, a guarded update's row - is filled by the statement's callback. A flushed update is marked stored by the commit, not by a callback: once `tx.Commit` has returned, `commitConsuming` marks each class the flush stored and lands its credit (`RoomFlush.markStored`), so the room learns what was stored only once the transaction has committed, and a transaction that rolls back marks nothing. The first statement that fails or callback that refuses its result (a guarded answer of an approval request, a route's guarded update) stops the batch, the transaction rolls back, no room sees its changes, and `Commit` returns that error unchanged; otherwise `Commit` commits and publishes to the rooms. `Discard` drops the queue. Settlement, the block-index backfill (`indexOwedDocument`) and decided-wording restoration (`RestoreDecidedWordings`) queue their writes on a ledger of their own - a settlement on a `Ledger` it opens, the other two through `queueWrites` - and send them as one batch (`runQueue`) right before they commit, outside `Commit`: the restoration's update refuses there when it restored other asks than it read (`errDecidedWordingsMoved`), and its transaction rolls back. A write in a transaction no ledger queues sends its statements as a batch of its own (`store.RunWrite`): the block-id backfill's, and the edit-notice sweep's claim of a notice with its `artifact.human_edited` append (`sendEditNotice`), whose claim refuses a notice that no longer matches what it read (`errEditNoticeUnclaimed`), so that transaction rolls back and sends nothing. The anchor-refresh writes ride in the batch: one update per table, of the asks and of the comments, setting every changed anchor's quote and orphaned flag from arrays (`unnest`), then one `*.anchor_refreshed` append per changed anchor (`refreshAnchors`), so they cost server time but no round trip.

A room load or a cold read reads the document's compacted row and the rows written since in one transaction on the rooms pool, buffers them in memory up to 32 MiB, and folds them after that transaction ends (a larger log it folds as it streams it). Compaction folds only rows older than 2 minutes on the database clock and leaves younger rows as written: a per-process queue fed by every append and every load compacts a document once 16 rows after its first are older than 2 minutes or one is older than 15 minutes, and an hourly sweep under the `document-compaction` lease, whose first tick comes at start and then one an hour, whether or not NATS is configured, compacts what the queues missed. The sweep reads only the documents `doc_compaction_owed` names, never a scan of `doc_updates`: each append names its document there in its own statement once the document has a row after its first, and a compaction that leaves no row above its fold point clears it. Compaction runs on its own two-connection pool and holds no document lock while it folds; only its short write takes the lock, and that write drops the fold if the rows changed.

It also owns three background loops over what version writes record. The task progress reconciliation runs once at start, counting every issue whose stored task count is not its latest version's, and retries only the issues whose owner lock another writer held, briefly: it tries those locks without waiting (`store.TryLockOwners`) and locks no issue row while no earlier build is in the fleet. Every version write records its own count, so no timer follows. The reference excerpt reconciliation is a woken loop (`duty.RunWoken`, lease `reference-excerpts`) on the `refs` trigger's `dispatch_excerpts_owed`: batches of 20 documents at least 2 s apart, and a document it cannot read or record deferred in `reference_excerpt_backoff`, one minute after its first failure and doubling to six hours, so failing documents neither hold the loop's pace nor keep the documents after them waiting. The edit notice sweep is a woken loop too (lease `edit-notices`) on the `document_edit_notices` trigger's `dispatch_edit_notices`, which a notice given a due time announces: each sweep sends the due notices as `artifact.human_edited` events and waits for the earliest due time left, sweeps at least 5 s apart.

A room's browser updates go to the store in batches. ygo hands each update to the room's persistence once (`StoreUpdateContext`); the call waits until 50 ms after the room committed the update for the room's queue to fill, cut short when a settlement, Shutdown's drain or any other durability waiter waits on the room, and then stores its own update and the run of the room's queued updates after it, at most 256 updates and 1 MiB, in one transaction with one row per update: the rows the same updates leave stored one at a time. The transaction runs on a connection of the `RoomAppends` pool (8 connections, `application_name=dispatch-room-appends`; the rooms pool that loads documents is `dispatch-rooms`) in about three round trips per batch: the document's session lock, the transaction and the gate in one pipeline, the insert with both notifications and the document's compaction entry, the owed settlement, the pending authors and the ask blocks' authors and the commit in a second, and the unlock in a third. A batch whose gate read finds a prune's checkpoint spends one more round trip reading the gate again under that checkpoint's ceiling. It finishes that prune at the head of its second pipeline, before its own writes, so the transaction holds a transaction id in that pipeline alone. The transaction takes no advisory lock of its own: the session already holds the document's lock on that connection. A batch takes no second connection while it holds the document's lock, and no holder of a document lock waits for a `RoomAppends` connection (settlements, live writes and the other `withRoomLock` writers keep theirs), so the pool cannot deadlock.

Every write that changes a document's stored content (an append batch, a rebuild, a prune's checkpoint, a deletion) sends two notifications in one statement inside its transaction: `dispatch_doc_changed` with the bare artifact id, and `dispatch_doc_head` with `{r,v,p}`, the document, its head once the transaction commits and the writing process's id (`announceDocumentHead`). A compaction sends neither: it changes neither the document's state nor its head. An append folds its announcement into its own insert (`appendUpdatesStatement`) rather than spending a round trip on it, so nothing announces a change the store does not hold and a process that hears one and reads the stored rows reads a head at or past the version that transaction wrote. Each process hears both on its shared LISTEN connection, the `pglisten.Hub` that `cmd/dispatch` names `dispatch-listener <process id>` and room sync registers its lanes on. A process drops its own head announcement; for another process's it catches the room it holds of that document up from `doc_updates` and leaves the room open (`roomCatchUps`), and closes and reloads the room only when the stored history was replaced under it. A bare `dispatch_doc_changed` that is not the twin of this process's own announcement wakes the same catch-up, so a write of an earlier build during a roll is followed too.

Settlement waits are signalled: a room's record closes an idle signal once it counts no update its persistence has not taken and no append that has not landed, and the waits for a room's updates and appends, Shutdown's drain and a settlement run at once for a caller (`settleOwedNow`) among them, wake on it rather than polling. A settlement during shutdown waits for the document's lock at most 100 ms, in one statement under `lock_timeout`. A version's changed ask and comment anchors are written with one update per table and one batch of events.

A document settles whether or not its issue is closed: nothing that arms a settlement, or decides whether one goes on, reads the issue's state, and the settlement reads that state only to decide what it writes, from the issue's row, which it reads plainly in the statement after it takes the issue's owner lock (`lockArtifactOwner`, `store.LockOwnerAndRead`). Every durable update marks the document owed in `doc_settlements_pending`, and a settlement that commits deletes that row. A room's load and the leased resumption (`RunSettlementResumption`, lease `settlement-resumption`, once a minute) arm what is owed. One resumption pass arms at most 50 documents: first those no pass has tried, oldest mark first, then those a pass tried, oldest `tried_at` first. So documents whose settlement fails every time never hold the bound. On a closed issue the settlement saves the text the store holds but changes no ask and wakes nobody. When an ask block has no ask row, the settlement saves the block with `state="resolved"`, opens no ask for it and records the block's author. The reopen marks owed each document whose ask blocks wait for it. The settlement records no edit notice and deletes the document's notice row. It carries no approval and moves no approval request, gives its repair events the settlement's own actor, and sweeps no marks. Its commit keeps the editor it credited (`doc_closed_edit_sources`), so the settlement after the reopen names that editor, as it did when the pending row stood through the closed period, and the reopen moves an approval request to a version such a settlement wrote in that editor's name. A settlement that saved nothing (`savedNothing`: no version, no stored update, no author), such as one armed while another commits, deletes only the pending row and keeps the editor the settlement before it kept. A settlement whose room took an update the append gate refused after the close margin saves nothing of that room and counts no failure, and the resumption settles the document from the store once the room has closed. The block index treats a closed issue's document as any other: one whose live text is ahead of its version is left owed for the settlement that writes its next version.

A document socket's admission reads the issue and the caller once per open and hands both to ygo's authorization of the same request. The room and connection caps are counters (`DISPATCH_MAX_LIVE_ROOMS` and `DISPATCH_MAX_DOC_CONNECTIONS`, 1,000 each by default), a warm room's schema verdict is the one its replica observer recorded, and a cold open renders its document once. The cold reads' cache holds one sixteenth of the Go memory limit, at least 64 MiB and at most 1 GiB, and 256 MiB when no limit is set. The room figures (resident rooms, room records, connections, pending updates and their bytes, durable appends, append batches, appended updates and round trips, the batch-size histogram, the room-appends and rooms pools, the read cache, the preloads, the resident bytes and the settlement wake-ups) are the expvar variable `dispatch_rooms` on the profiler port's `/debug/vars`.
