The live document surface: the collaborative websocket room, where ygo returns a read-write peer's awareness update to its sender, and a read-only peer an empty awareness response, so the Hocuspocus provider stays connected without Dispatch writing frames; two-phase settlement that mints block ids before it persists and compares what it rendered; the agent edit operations (`replace`, `delete`, `insert`, `retype`, `move`, `delete_row`, `delete_column`) and the ask blocks an edit adds, which the API checks for related items, block tokens and preconditions, and ask and comment anchor refresh. Every durable writer of a room stores the room's unstored updates through the point it read the room at, in the room's commit order, before its own (`flushThrough`), so the stored updates replay to every version; `envoy-dispatch stored-order` checks that.

A transaction a handler joins (`Docs.Join`) or a settlement opens has a read phase and a write phase. The read phase takes the document owner's advisory lock (`lockArtifactOwner`), the in-memory writer slot, the copy lock where one is needed and the document's advisory lock, in that order - none of them a row lock, so none gives the transaction a transaction id - reads, and does every operation's work: forks and renders, `refreshAnchors`' walk, version capture, reference extraction, the approval carry. Every write an operation makes goes through `write`, which queues it on the transaction's ledger (`WriteStep`; a handler queues its own writes in the same queue with `Ledger.Queue`), and a read that would have seen the transaction's own write is answered from the ledger: pending appends count toward the document head (`withOwnAppends`), pending anchors toward a refresh's walk (`RegisterPendingAnchor`), a pending version's number, time and markdown (`NextVersion`, `Now`, `PendingVersionMarkdown`). The room flush is part of the read phase too: `flushThrough` takes the room's unstored updates through the read point and measures their classes there, against the same state the operation read, and queues their inserts in the room's commit order before the operation's own append, so a flush renders nothing and sends nothing between two of the transaction's statements. The write phase is one pipelined batch: `Ledger.Commit` has each queued step put its statements on one `store.WriteBatch`, in the order the transaction made them, so statements and events keep that order, appends the settlement credit's statements, and sends the batch in one round trip; Postgres runs the statements back to back and the client reads their results once, so no Go code - and no wait for this process to be scheduled - runs between two of them while the transaction holds its id. A step reads no result: a value a later statement needs is derived in SQL (an event's sequence from its owner row, a stamp's or a review's event from the events id sequence's `currval`, `store.LatestEventID`) or read in the read phase (a row's time, its id), and a value needed after `Commit` is filled by the statement's callback - a flushed update is marked stored by its own callback, so the room learns what was stored only once the batch has run. The first statement that fails or callback that refuses its result (a guarded answer of an approval request, an edit-notice claim that no longer matches, a decided-wording restoration that restored other asks) stops it, the transaction rolls back, no room sees its changes, and `Commit` returns that error unchanged; then `Commit` commits and publishes to the rooms. `Discard` drops the queue. Settlement, the block-index backfill and decided-wording restoration queue their writes on a ledger of their own (`queueWrites`) and send them as one batch right before they commit; a write outside any ledger sends its statements as a batch of its own (`store.RunWrite`). The anchor-refresh writes, an update and a `*.anchor_refreshed` append per changed anchor, ride in the batch, so they cost server time but no round trip; folding them into one statement is INFRA-605's.

A room load or a cold read reads the document's compacted row and the rows written since in one transaction on the rooms pool, buffers them in memory up to 32 MiB, and folds them after that transaction ends (a larger log it folds as it streams it). Compaction folds only rows older than 2 minutes on the database clock and leaves younger rows as written: a per-process queue fed by every append and every load compacts a document once 16 rows after its first are older than 2 minutes or one is older than 15 minutes, and an hourly sweep under the `document-compaction` lease, whose first tick comes at start and then one an hour, whether or not NATS is configured, compacts what the queues missed. The sweep reads only the documents `doc_compaction_owed` names, never a scan of `doc_updates`: each append names its document there in its own statement once the document has a row after its first, and a compaction that leaves no row above its fold point clears it. Compaction runs on its own two-connection pool and holds no document lock while it folds; only its short write takes the lock, and that write drops the fold if the rows changed.

It also owns three background loops over what version writes record. The task progress reconciliation runs once at start, counting every issue whose stored task count is not its latest version's, and retries only the rows another writer held, briefly; every version write records its own count, so no timer follows. The reference excerpt reconciliation is a woken loop (`duty.RunWoken`, lease `reference-excerpts`) on the `refs` trigger's `dispatch_excerpts_owed`: batches of 20 documents at least 2 s apart, and a document it cannot read or record deferred in `reference_excerpt_backoff`, one minute after its first failure and doubling to six hours, so failing documents neither hold the loop's pace nor keep the documents after them waiting. The edit notice sweep is a woken loop too (lease `edit-notices`) on the `document_edit_notices` trigger's `dispatch_edit_notices`, which a notice given a due time announces: each sweep sends the due notices as `artifact.human_edited` events and waits for the earliest due time left, sweeps at least 5 s apart.

A room's browser updates go to the store in batches. ygo hands each update to the room's persistence once (`StoreUpdateContext`); the call waits until 50 ms after the room committed the update for the room's queue to fill, cut short when a settlement, Shutdown's drain or any other durability waiter waits on the room, and then stores its own update and the run of the room's queued updates after it, at most 256 updates and 1 MiB, in one transaction with one row per update: the rows the same updates leave stored one at a time. The transaction runs on a connection of the `RoomAppends` pool (8 connections, `application_name=dispatch-room-appends`; the rooms pool that loads documents is `dispatch-rooms`) in about three round trips per batch: the document's session lock, the transaction and the gate in one pipeline, the insert with both notifications and the document's compaction entry, the owed settlement, the pending authors and the ask blocks' authors and the commit in a second, and the unlock in a third. A batch whose gate read finds a prune's checkpoint spends one more round trip finishing that prune and reading the gate again. The transaction takes no advisory lock of its own: the session already holds the document's lock on that connection. A batch takes no second connection while it holds the document's lock, and no holder of a document lock waits for a `RoomAppends` connection (settlements, live writes and the other `withRoomLock` writers keep theirs), so the pool cannot deadlock.

Every write that changes a document's stored content (an append batch, a rebuild, a prune's checkpoint, a deletion) sends two notifications in one statement inside its transaction: `dispatch_doc_changed` with the bare artifact id, and `dispatch_doc_head` with `{r,v,p}`, the document, its head once the transaction commits and the writing process's id (`announceDocumentHead`). A compaction sends neither: it changes neither the document's state nor its head. An append folds its announcement into its own insert (`appendUpdatesStatement`) rather than spending a round trip on it, so nothing announces a change the store does not hold and a process that hears one and reads the stored rows reads a head at or past the version that transaction wrote. Each process hears both on its shared LISTEN connection, the `pglisten.Hub` that `cmd/dispatch` names `dispatch-listener <process id>` and room sync registers its lanes on. A process drops its own head announcement; for another process's it catches the room it holds of that document up from `doc_updates` and leaves the room open (`roomCatchUps`), and closes and reloads the room only when the stored history was replaced under it. A bare `dispatch_doc_changed` that is not the twin of this process's own announcement wakes the same catch-up, so a write of an earlier build during a roll is followed too.

Settlement waits are signalled: a room's record closes an idle signal once it counts no update its persistence has not taken and no append that has not landed, and the waits for a room's updates and appends, Shutdown's drain and a settlement run at once for a caller (`settleOwedNow`) among them, wake on it rather than polling. A settlement during shutdown waits for the document's lock at most 100 ms, in one statement under `lock_timeout`. A version's changed ask and comment anchors are written with one update per table and one batch of events.

A document socket's admission reads the issue and the caller once per open and hands both to ygo's authorization of the same request. The room and connection caps are counters (`DISPATCH_MAX_LIVE_ROOMS` and `DISPATCH_MAX_DOC_CONNECTIONS`, 1,000 each by default), a warm room's schema verdict is the one its replica observer recorded, and a cold open renders its document once. The cold reads' cache holds one sixteenth of the Go memory limit, at least 64 MiB and at most 1 GiB, and 256 MiB when no limit is set. The room figures (resident rooms, room records, connections, pending updates and their bytes, durable appends, append batches, appended updates and round trips, the batch-size histogram, the room-appends and rooms pools, the read cache, the preloads, the resident bytes and the settlement wake-ups) are the expvar variable `dispatch_rooms` on the profiler port's `/debug/vars`.
