The Oh My Pi plugin a Legion pane loads beside the Envoy plugin (`@sjawhar/pi-legion`): the Legion lifecycle tool, the daemon handshake and credential grants for root architects, phase workers and the controller, the task agents Legion's prompts dispatch, and the six Legion skills. It needs the Envoy plugin's interface from `pi-shared` at the version it speaks, and refuses to run a Legion session without it. The skill-scenario rig's (`scripts/skill-scenarios/rig.sh`) Dispatch database is the pgvector-on-PostgreSQL-18 image Envoy's `internal/testpg` pins, by the same digest.

Its Dispatch client, its listener publisher and the production-Dispatch reader of `scripts/skill-scenarios/` present the `credential` that `ActiveDispatchConfig` and `EnabledEnvoySettings` carry rather than a bearer string, so they work under a deployment whose Dispatch token is the secrets broker's DPoP-bound access token.

In a root architect's own session (never a `task` subagent's) it places the approval message while a person's approval of the root's spec stands: it reads the daemon's `POST /legion/v1/claims/approval` at `session_start` and before the next model request after an entry that is not the model's or a tool's (800 ms, the last answer kept when a read fails), and its `context` handler puts the daemon's text last in a request of the conversation's own loop, as a custom message of pi-shared's `legion-approval` type that is never a session message (`src/approval-message.ts`). Each copy placed is recorded once the model's answer to its request is saved, as the session entry `legion-approval-sent`, which a reader of the session store finds on the branch as `{"type": "custom", "customType": "legion-approval-sent", "data": {...}, "timestamp": "<when it was recorded: at the answer's save, or at the next request at the latest>", ...}`. Its `data` is `{"version": <the approved version the text names>, "text": "<the message, byte for byte>", "timestamp": <epoch milliseconds when the copy was first placed>, "answer": "assistant@<the timestamp of the assistant message that answered>"}`. Every later request that holds that answer carries the copy right before it, rebuilt from the entry with the same bytes, so the entries say which versions the architect was told of and when.

A side turn, the handoff prompt and a compaction's own request get no new placement, and each of them rebuilds the copies whose answers it holds. Oh My Pi adds its date reminder after the `context` handlers, so on the one request whose new placement the reminder follows, the plugin's `before_provider_request` handler moves the reminder right after the last message that is not per-call, before every per-call message, as a user message. The placement then stays last and goes as `system`, and the request's messages are the next request's messages before the answer.

It reads whether the model takes a system message inside the conversation from `ctx.model.compat.supportsMidConversationSystem`, in the `context` handler and in `before_provider_request`, whose `ctx.model` is the model of that provider request. On a model that does not take one (`gemini-4-neon`, `gpt-6.2-sol` and `kimi-k3.1-pro` of INFRA's chain, and any model whose catalogue flag is off), the `context` handler places no message and rebuilds no copy. The `before_provider_request` handler takes out any message whose text equals a text the plugin placed or stands for (a request built before a fallback switch still holds a copy), then puts the standing version's text at the end of the top-level system prompt of the request: a new last text block of an Anthropic request's `system`; `\n\n` and the text at the end of the last of the leading `system` or `developer` messages of a chat completion; `\n\n` and the text at the end of a Responses request's `instructions`, or of its last leading `developer` item where Oh My Pi sends the system prompt as `developer` items. Every request of the architect's own conversation to such a model gets it, a side turn's and a compaction's summary request that reach `before_provider_request` among them; a `task` subagent's does not. A server-side compaction request (Anthropic native, OpenAI remote compaction) passes no payload hook and holds none: the next request of the conversation does. The plugin makes and records a placement only on a model that takes a system message inside the conversation, and a return to such a model rebuilds each earlier copy at its place from its record.

When the answer of a model that takes none to the first request that carried a version's text is saved, the plugin appends one mark entry, once for each version and model, which a reader of the session store finds on the branch as `{"type": "custom", "customType": "legion-approval-top-level", "data": {...}, ...}`. Its `data` is `{"version": <the approved version the text names>, "model": "<provider>/<id>", "answer": "assistant@<the timestamp of the assistant message that answered>"}`. The mark rebuilds nothing, and no log line takes its place.
