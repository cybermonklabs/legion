The Oh My Pi plugin a Legion pane loads beside the Envoy plugin (`@sjawhar/pi-legion`): the Legion lifecycle tool, the daemon handshake and credential grants for root architects, phase workers and the controller, the task agents Legion's prompts dispatch, and the six Legion skills. It needs the Envoy plugin's interface from `pi-shared` at the version it speaks, and refuses to run a Legion session without it. The skill-scenario rig's (`scripts/skill-scenarios/rig.sh`) Dispatch database is the pgvector-on-PostgreSQL-18 image Envoy's `internal/testpg` pins, by the same digest.

Its Dispatch client, its listener publisher and the production-Dispatch reader of `scripts/skill-scenarios/` present the `credential` that `ActiveDispatchConfig` and `EnabledEnvoySettings` carry rather than a bearer string, so they work under a deployment whose Dispatch token is the secrets broker's DPoP-bound access token.

In a root architect's own session (never a `task` subagent's) it places the approval message while a person's approval of the root's spec stands: it reads the daemon's `POST /legion/v1/claims/approval` at `session_start` and before the next model request after an entry that is not the model's or a tool's (800 ms, the last answer kept when a read fails), and its `context` handler puts the daemon's text last in a request of the conversation's own loop, as a custom message of pi-shared's `legion-approval` type that is never a session message (`src/approval-message.ts`). Each copy placed is recorded once the model's answer to its request is saved, as the session entry `legion-approval-sent`, which a reader of the session store finds on the branch as `{"type": "custom", "customType": "legion-approval-sent", "data": {...}, "timestamp": "<when it was recorded: at the answer's save, or at the next request at the latest>", ...}`. Its `data` is `{"version": <the approved version the text names>, "text": "<the message, byte for byte>", "timestamp": <epoch milliseconds when the copy was first placed>, "answer": "assistant@<the timestamp of the assistant message that answered>"}`. Every later request that holds that answer carries the copy right before it, rebuilt from the entry with the same bytes, so the entries say which versions the architect was told of and when.

A side turn, the handoff prompt and a compaction's own request get no new placement, and each of them rebuilds the copies whose answers it holds. Oh My Pi adds its date reminder after the `context` handlers, so on the one request whose new placement the reminder follows, the plugin's `before_provider_request` handler moves the reminder right after the last message that is not per-call, before every per-call message, as a user message. The placement then stays last and goes as `system` where the model takes one, and the request's messages are the next request's messages before the answer. Where the model takes no mid-conversation system message (its `compat.supportsMidConversationSystem` is not set, after a fallback for example), Oh My Pi sends the approval message as a user message at the same place, and the plugin logs one warning for each session and model, which names the model.
