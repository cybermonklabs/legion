The eval registry: every number a project's pages show is an eval, with its definition, its series and its readings (`evals.go`, migration `20261117100005_eval_registry`).
A definition is append-only: each change, a target's among them, writes the next version, and a reader reads the newest, so every version a reader once saw stays readable (`Register`, `Current`).
A reading is append-only too: a correction is a new reading naming the one it replaces (`WriteReadings`).
A logged eval's day rows are kept by its readings write; a computed eval's are the refresher's, the delivery and CI evals' built from one day's delivery population (`delivery_days.go`), the Legion evals' from one day's stored Legion facts and filings (`legion_days.go`) and `unowned-p0`'s from the count of open P0 issues with no owner (`WriteUnownedP0Day`), and a reading logged under a computed eval's slug is stored and answered by its items alone (`evals.go`).
A read folds each listed series of a computed eval through the one fold its source names (`computed:<function>`), the fold the delivery and Legion routes answer through too, and each series of a logged eval through its own `agg` (`statistics.go`, `computedSources`).
The seeded catalogue is every computed eval: the delivery and CI evals, the six Legion evals and `unowned-p0` (`catalogue.go`), each with its method in `methods/<slug>.md`.
A project's `evals-md` document holds one section per eval, a `##` heading of its slug and the method block its version's `doc_block` names (`document.go`).
The package serves no request and makes none: the routes are `api`'s, and its own files import no HTTP client (`imports_test.go`).

Its tables are created by these migrations, whose headers say what each column holds (`dispatch-store`).
`20261117100005_eval_registry`: `eval_versions`, one row per version of one definition, never updated, whose newest per eval the view `evals_current` reads; `eval_series`, one row per version of one series of one eval, the newest in `eval_series_current`; and `eval_readings`, one row per value logged under an eval, where a correction names the reading it corrects in `replaces` and its write sets `superseded_at` on that reading.
`20261117100006_eval_days`: `eval_days`, the stored per-day aggregates every window read folds, one row per owner, eval, writer, deploy repository, series, repository and day; `eval_day_members`, where each item a family of day rows counted was last counted; `eval_days_owed`, each day whose rows count an item a write of another day took from them, which the refresher writes again; `eval_day_owners`, one row per owner key (`owners.go`, `OwnerKey`); and `eval_days_defaults`, the default repository each project's reads stand under, published (`defaults.go`), by which the views `eval_project_repos` and `eval_project_owners` and the function `eval_owner_readers` choose the owner keys a read of a project folds.
`20261117100012_eval_readings_changes`, `20261117100013_eval_versions_changes` and `20261117100014_eval_days_changes`: the triggers that log each write of an eval's readings, versions and day rows in the change log's outbox (`delivery_changes_pending`, `20261117100001_delivery_changes_pending`) as the kinds `eval_readings`, `eval_versions` and `eval_days`, so every view built on the eval wakes.
`20261117100021_eval_days_refresher`: the refresher's own state, `eval_days_cursor` (where it stands in each feed it reads), `eval_days_walks` (how far each walk has come), `eval_days_serving` (which build's rules built each served family of day rows, and the first day they are not whole through) and `eval_days_settings` (the one rule the release before records for every repository, which this release reads and writes nowhere); and the rebuilds, `eval_rebuilds`, `eval_rebuild_walks`, `eval_rebuild_firsts` and `eval_rebuild_reverify`, with what a rebuild stages in `eval_rebuild_days`, `eval_rebuild_members`, `eval_rebuild_range_figures` and `eval_rebuild_day_figures`.
`20261120072042_eval_figures`: the stored figures, `eval_range_figures` (the fold of each stored range of each eval in each cut) and `eval_day_figures` (each day's figures of each eval in each cut), `eval_figures_built` (each project whose figures are built, and the last end day they are built through) and `eval_figure_cuts_stale` (each cut whose stored figures a move of its project's default repository or of a deploy source, the boot's rename pass or a new version that moved an eval's fold key left behind, until the refresher has folded it again).
`20261123020640_eval_days_rules`: `eval_days_rules`, the rule each source repository's delivery and CI rows stand built under, with the project whose source reads it and the first day its rows are kept from, from which a read takes the repositories each project reads and their rules (`deploy_repos.go`'s `DeployReposIn`, `settings_rewrite.go`'s `BuiltSettingsIn`).

Its writers are the two write routes, the seed, the day-row refresher and the boot.
The readings route (`POST /api/v1/projects/{key}/evals/{slug}/readings`, `api/evals.go`'s `logEvalReadings`) stores one batch of readings in one transaction through `Store.WriteReadings` (`readings.go`), which registers a slug no eval holds as a logged eval and keeps a logged eval's day rows in the same transaction, the zero rows its readings leave owed among them, and deletes a row a correction leaves with no value (`days.go`: `writeDays`, `writeLoggedZeros`, `dropEmptiedRows`), and `PUT` and `DELETE` of a reading answer `405 READING_APPEND_ONLY` (`refuseReadingChange`).
The register route (`POST /api/v1/projects/{key}/evals`, `registerEval`) writes the next version of a definition and of the series it names through `Store.Register` (`register.go`), copying forward every field it leaves out, and refuses a field of a computed eval's computation (`computationField`).
The seed writes the catalogue into a project (`seed.go`): in the transaction that creates the project (`api/projects.go`'s `createProject`, through `Store.EnsureTx`), and on the refresher's passes, the first pass of each process seeding every project (`Store.Ensure`, `UnseededProjects`).
The day-row refresher (`refresher.go`, `Store.RunRefresher`, which `cmd/dispatch` starts) is one woken loop under the lease `eval-days` (`RefresherLease`) that keeps every project's computed day rows true to their inputs, and the zero rows of every series from its first input day on, the logged evals' included.
Its pages read the delivery change log, woken by `delivery.ChangesChannel`, and the event log up to its safe horizon, woken by `api.EventsChannel`, from their cursors, and write the days each change names (`refresher_work.go` lists what each change touches) and every other day those changes move (`span.go`).
Its walks (`eval_days_walks`) are the work no change asks for: the delivery and CI rows of every project, each project's Legion rows, each project's logged evals' zero rows (`fillLoggedZeros`), each project's `unowned-p0` rows of today, one for each repository that holds a counted issue (`WriteUnownedP0Day`), and each project's stored figures; the computed day rows are written through `day_rows.go` (`writeProjectDay`, `writeProjectDays`), and a walk commits one day of every owner key in one transaction (`refresher_work.go`'s `deliveryWalkDay`).
What counts for a project only through a default repository is written under an owner key of its repository, which a read selects by the defaults the refresher publishes (`owners.go`, `defaults.go`), and the evals that read a deploy repository are kept for every source repository that holds a delivery run, each under its own source's rule (`deploy_repos.go`, `eval_days_rules`), so a move of either rewrites no day row.
A change of a source repository's rule stages the rows of the delivery and CI evals it moves for that repository, without starting a walk (`settings_rewrite.go`: `settingsMoves` says what each setting moves, `rewriteSettings` builds it; `rebuild.go`'s `ruleStaging` stages it).
Reads use the old rule until one transaction records the new rule, publishes its rows, and folds the affected figures.
A repository's first rule follows the same process: the page stages its rows, then publishes them in the transaction that records the rule (`span.go`'s `stageKept`).
Rules that move no row are recorded with the page's cursors, with one change that tells the delivery views to recompute (`recordRules`, `logRulesRecorded`).
A release, a lost change cursor and delivery settings the served rows stand built under that are not recorded rebuild the served families aside, stage only what differs, verify the days written meanwhile a batch a transaction, and make it visible in one short commit, the flip (`rebuild.go`, `flipRebuild`); a family no rows are served of yet is walked in the open.
A process of an older build that starts after a flip rebuilds the rows back, and the newer build takes them back once no live server process serves the older one (`liveBuilds`, read from `server_processes`).
The stored figures are folds of the day rows kept ahead of the read (`figures.go`): each write of day rows folds again the figures of the days it moved, in its own transaction, but for a readings write past what one transaction folds (`inlineFoldDaySeries`), which folds the first paint of each cut it reaches and marks the cuts stale for the refold (`foldWrittenPaints`), and a walk those of its batch at the batch's end; the refresher's part (`figures_refresher.go`) reads the change log from the figures' own cursor (`figureChanges`), marks stale each cut whose stored figures hold an eval's old fold key (`markMovedKeys`), walks each project's figures (`walkFigures`) and folds again each stale cut, its first paint first and then in batches of about 250 ms (`refoldStaleCuts`).
The boot folds the first paint of each stale cut that owes one before the server serves (`FoldFirstPaintsAtBoot`, which `cmd/dispatch`'s `foldFirstPaints` calls).
The boot's rename pass rewrites a renamed repository in the owner keys and the published defaults, and marks the cuts of its old and its new name stale (`store/repo_rename_pass.go`, `dispatch-store`).

Its readers are the eval routes (`api/evals.go`, `api/evals_items.go`): `GET /api/v1/projects/{key}/evals` and `GET /api/v1/evals` read the list, each eval's current definition with each listed series' statistics over a window and a compare range; `GET /api/v1/projects/{key}/evals/{slug}` reads one eval's versions and the method its section holds; and `GET /api/v1/projects/{key}/evals/{slug}/items` reads the rows behind its numbers.
A list read resolves each repository it names to the spellings the stored rows hold (`StoredRepos`), states each eval from its stored figures where they answer it (`FiguresOffered`, `ReadStoredFiguresIn`) and from one read of the day rows otherwise (`DayWindowIn`), never from the population, and reads "no data" for a window that holds a day the walks have not built (`BuiltIn`, `Withhold`), in one read-only snapshot (`Store.BeginSnapshot`), with the refresher's age (`RefresherAgeIn`; `api/evals.go`'s `readEvalList` and `readEvalValues`).
The live hub's `evals` view of `/ws/live` (`api/live_frames.go`) reads the list through the function the route answers with (`api/delivery_live_hub_worker.go`'s `readEvalsView`, `readProjectEvalList`), and a change of the kinds `eval_readings`, `eval_versions` or `eval_days` that names its project marks it (`api/delivery_live_hub_intake.go`'s `touchedBy`).
The delivery routes' measures, timeline and Pipeline judge their figures by the targets of the delivery evals of the project whose deploy sources read every source repository, where one project owns them all, and by the catalogue's otherwise (`api/delivery.go`'s `deliveryEvals`; `delivery_targets.go`: `Store.DeployRepoEvals`, `VerdictOf`), and read each repository's runs under the rule recorded with its rows (`BuiltSettingsIn`, `api/delivery.go`'s `readDeliveryRules`).

Every writer takes its locks in the eval tables' lock order, which `defaults.go` states once: the eval locks first (`lockEval`, `lockEvals`, in the order of their keys, before any row lock), then `eval_days`, `eval_day_owners`, the members and owed days, the stored figures, `eval_days_defaults` and `eval_figure_cuts_stale`; a write of a section takes the owner lock of the project's `evals-md` after its eval locks (`lockDocument`).
A computed eval's day rows are written by the refresher, whose lease runs one pass at a time, and by the boot's rename pass and a project's delete beside it; a logged eval's are written under its eval's lock, which a fold of stored figures takes for each logged eval it folds (`figures_refresher.go`'s `lockLogged`).
No eval write takes the change log's lock: its change rows wait in the outbox, and a batch of the outbox is moved into the log after it commits (`store.go`'s `inWrite` and `drainChanges`).
`lock_order_test.go` runs two writers at once in the orders that once deadlocked, and the rename pass's own tests hold its place in the order (`store/repo_rename_pass_test.go`: it locks the day rows before the owner rows, and the published defaults in the order of their keys).

Beside the package, `evalbench` loads the fixture the registry's measurement Job reads (`Load`, which with `Spec.Base` writes the same history but the readings into a database the base migrated, for the base's negative controls, and `AddFailureDay`, which adds a day of deploy failures), `evalbench/cmd` is its command, `evalbench/measure` is the instrument that waits for the server's consumers and measures the first paint, and `run.sh` and `job.sh` run them, on the build farm through `job.yaml`, which `render-job.py` fills from its inputs: one pod whose server and Postgres each run in a container of their own under `supervise.sh`, and whose `SHAPE` line says whether the run is on the timing class at production's size and so gates.
`evalfixture` loads the histories the registry's checks read into a database that already holds Dispatch's schema, one mode a flag of `evalfixture/cmd` (`-legion`, `-base`, `-attribution`, `-delivery`, `-merge-pr`).
`independent` is a second reading of the six Legion measures, written from the requirement's words rather than from the code that serves them, and imports neither `legion/metrics`, `legionfacts` nor `evals` (`independent/imports_test.go`), so the check that compares it with the eval routes can fail; `independent/cmd` prints it as JSON.

The edges are the store's pool, its owner lock and the tables above (`dispatch-store`); the leased woken loop (`dispatch-duty`); the delivery reads, measures and attribution the delivery and CI rows are built with, and the change log the refresher reads and every eval write's changes are drained into (`dispatch-delivery`); the Legion day builders (`legion/metrics`), the daemon's observation fields and the session-title rule (`legion`), and the stored per-issue facts and filings the Legion rows read (`legionfacts`, `dispatch-legion`); the document service the `evals-md` sections are written through and the block tree their methods are parsed into (`dispatch-docs`, `dispatch-pmdoc`); the event broker and the event log's safe horizon (`dispatch-events`); the actors, events and edit operations it records (`dispatch-model`); and the stamp of a document event's references and the depth an issue's parent links are walked to (`refs.QueueStamp`, `refs.IssueDepthCap`, `dispatch-refs`).
