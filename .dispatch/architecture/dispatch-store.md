The schema every other package reads and writes through: ordered migrations applied in one transaction each at boot, the pool, and the session and people rows — which is why it imports `auth`. The boot's migration lock goes back through `duty.FreeSessionLockThenReset`, which returns the connection to the pool only once Postgres has freed the lock — which is why it imports `duty`. `internal/pgmigrate` holds the runner's rules, which the secrets broker's runner shares: the whole migration set is refused before anything applies when two files share a version or a file is misnamed or unreadable, and every migration's lock waits are bounded at five seconds. `internal/pgmigrate` reads migration and census SQL as Postgres 18's lexer does.

`store/ownerlock.go` holds Dispatch's per-owner serialization, the owner lock: `pg_advisory_xact_lock(0x4F574E52, hashtext('<kind>:<key>'))` for an issue, a project document (keyed by its artifact) or a project, in a two-key namespace ("OWNR") no other lock family takes. `LockOwner`, `LockOwners` (one statement, sorted and deduplicated by lock key, so two writers never take two owners in opposite orders), `LockOwnersShared` (the same sorted statement in shared mode, which the Inbox's Mark all read and its dismissal take for the owners of the threads they mark, through `api/inbox_read.go`'s `lockInboxReadOwners`) and `TryLockOwners` (the advisory form of `skip locked`, for background passes) are how every writer of an owner's rows orders itself against the others; the owner row itself is locked only in a transaction's write phase, by the event broker's append (`events.lockEventOwner`) or by a write of the row itself, unless an earlier build is in the fleet (the next paragraph). `TestNoForUpdateOnOwnerTables` (`api/lock_level_test.go`) holds that over the module's SQL: it refuses a row lock of any level on `issues`, `artifacts` or `projects` outside `events.lockEventOwner` and the row locks the owner lock takes beside an earlier build (`ownerLockExclusive`, `ownerLockShared`, `ownerLockTry`), and `for update` on those tables and on `asks`. An advisory lock assigns no transaction id, so a write transaction whose read phase takes only advisory locks holds none through it and holds one only from its first write or row lock to its commit. The lock and the read it guards are always separate statements (`LockOwnerAndRead` and `LockOwnersAndRead` send them in one batch): under READ COMMITTED a statement's snapshot is taken before it waits, so a read made in the lock's own statement would miss a close committed while it waited. The lock order is the owner lock first (several at once in one statement, sorted by key, or one after another where the later one is the project whose event the write appends, as `putThreadRead` takes its thread's owner and then the project's), then the document service's writer slot, the copy lock and the document's advisory lock, and only in the write phase the owner row and every row lock and row write. Most writers keep that order; these do not. The Inbox's Mark all read and its dismissal (`markInboxReadThreads`, `dismissInboxThreads`) read the threads they mark before any lock, take those threads' owners in shared mode in two statements, the documents' and then the issues' (`lockInboxReadOwners`), lock and write the caller's rows (a dismissal first the Agent threads' roots, `for update`), and take the owner locks of the projects those writes moved only after them, right before their appends (`commitInboxMarks`); the order they keep instead is written down at `markInboxReadThreads`. A project document's upload (`storeArtifact`) and its rename or removal (`beginArtifactWrite`) take the project's upload lock (`lockProjectArtifacts`, an advisory lock of its own) before the document's owner lock, which comes after it in every taker, so it joins no cycle. A project's default-repository write (`PUT /api/v1/projects/{key}/default-repository`, `api/project_default_repository.go`) keeps the order: it takes the project's owner lock before it updates the project row, as every projects writer does. The issue create and the issue patch take the dependency locks (`lockIssueDependencyWrite`: the dependency lock of the issue's own project and of each project a `blocked_by` target belongs to, `lockProjectIssueDependencies`, in `docs.ProjectsInLockOrder`'s order, then the deployment's own, `lockDeploymentIssueDependencies`), when they write a parent or blockers, before their owner locks, and the patch the project's rank-allocation lock (`lockProjectRankAllocation`) too when it moves the rank, the patch reading the issue's project before them and the create its parent issue before its owner lock; the targets' projects are read by a plain read and every dependency lock is advisory, so that step assigns no transaction id. The create takes the rank-allocation lock after its first write. A patch or create that names a repository locks no project row for it (its reads of the issue join the project's default repository, `refs.IssueRepoJoin` over `projects.default_repo`, a plain read): an issue's own repository is any `owner/name` GitHub could hold (`api/issue_repo.go`'s `githubCouldHoldRepo`, INFRA-2543 R3, migration `20261112004945`), so the repository is written with the issue's row. The delivery-attempt routes (`recordPendingMessageDelivery`, `claimCommentDeliveryAttempt`, and the message and comment reply routes) take their owner lock and then lock their message, mention or attempt row (`for no key update` or `for update`) before their first write, and `acceptDelivery` locks its message's row with no owner lock, since the direct message it accepts appends an event with no owner; so each holds a transaction id from that row lock through the reads that decide its write; nothing else runs between, and none takes an owner lock after it, so they join no cycle. A read of which owner to lock comes before that lock where the row it reads names an owner that never changes: `putThreadRead`'s read of its `user_threads` row and `lockArtifactOwner`'s read of the document's `artifacts` row. The writers `dispatch-events` lists under dispatch://INFRA-3397 write or lock a row before the owner lock of the event they append.

A build before the owner lock serialises an owner's writers on the owner's row instead: each takes the row `for no key update` (its Inbox `for share`) first and holds it to its commit, and never takes the advisory lock, so the two builds' writers would not exclude each other's read phase during a rolling release. Each server process registers the protocol it serialises by in `server_processes.owner_lock_protocol` (migration `20261115100924_server_processes_owner_lock_protocol`), and names it in the `dashboard_builds` row its boot publishes (migration `20261115200014_owner_lock_legacy_gate`): this build 1 (`store.OwnerLockProtocol`), and an earlier build's rows read the columns' default, 0. An earlier build is in the fleet while a row of it at 0 in `server_processes` has heartbeated within `store.OwnerLockLegacyWindow` (10 minutes, the registry's prune age), so until it is deregistered or pruned, or for `store.OwnerLockMarkWindow` (an hour) after its last arrival: its dashboard publish, its registration or its lapsed row's return. An earlier build that serves a dashboard (the image always does) publishes before any write an owner lock guards, and its boot ends when that publish fails; every earlier build's registration is an arrival too, and for one that serves none (its web dist holds no `index.html`) it is the first, made after its boot's repairs and background passes have begun writing. The migration stamps the mark itself at the newest earlier publish already in `dashboard_builds` when that is within the hour, since a publish that came before its trigger made no arrival. An earlier boot that takes more than the hour from its publish to its registration is not seen from the hour's end until it registers, a process of it silent past the prune age is not seen until a heartbeat's admission of it commits, and each such admission waits for the gate at most 2 seconds, its heartbeat's bound, so a write of this build holding the gate longer defers it while that process serves writes in its row-first order, as the registry counts a silent process gone for every other fleet decision, and a subcommand of it an operator runs is never seen, since it neither publishes nor registers. Each arrival's insert, a row at 0, fires a trigger that takes the owner lock gate (`pg_advisory_xact_lock(0x4F574E47, 0)`, `store.OwnerLockGateNamespace` and `OwnerLockGateKey`, a two-key namespace of its own, "OWNG") exclusively and stamps `owner_lock_legacy_mark`: the trigger `dashboard_builds_owner_lock_legacy_arrival` runs the function `owner_lock_legacy_arrival` on a publish, which waits as long as the earlier build's publish runs (every earlier build gives it up at 60 seconds and exits), and the trigger `server_processes_owner_lock_legacy_arrival` runs the function `owner_lock_legacy_registration` on a registration, which holds the registry's lock that every heartbeat takes, so its wait is bounded at 5 seconds (`lock_timeout`) and its insert then fails with `55P03`, which ends an earlier build's fresh registration; a lapsed row's return is ended sooner, at its heartbeat's own 2-second bound, and is tried again at its next heartbeat. Every read-phase owner lock statement is one call of `public.owner_lock`, one statement and no round trip of its own: it reads the fleet (`public.owner_lock_fleet`), and when it finds no earlier build it tries the gate shared, without waiting, and reads again behind it, under a snapshot of its own; then it takes the advisory locks, exclusive, shared or tried. A try that fails - an arrival holds the gate or waits for it, and Postgres grants no conditional request that conflicts with a waiting one - answers as an earlier build in the fleet, so no owner lock ever queues behind an arrival, and an arrival waits only for the transactions that held the gate when it asked. A plpgsql function is what fixes the fleet read and the try before every owner lock of the transaction, since Postgres orders no expressions of one statement. So an earlier build's arrival waits for every transaction of this build that holds the gate, and every owner lock from the moment it asks takes the owner's row and, after it commits, reads it in the fleet. While an earlier build is in the fleet the lock takes no gate, and takes each owner's row too, in a statement for each owner kind, sent in the same round trip, right after the advisory lock and before any read the lock guards (`lockOwnerRows`): `for no key update` for `LockOwner` and `LockOwners`, `for share` for `LockOwnersShared`, and `for no key update skip locked` for `TryLockOwners`, which leaves out an owner whose row it did not take. The rows go documents, then issues, then projects, each kind's keys in byte order, which is the order the earlier build takes several owners' rows in (its broker sorts owners by `<kind>:<key>`), and always after the advisory lock, never before it: this build's advisory-mode writers hold the lock and take the row in their write phase, so the row first would wait on them while they wait on the lock. `LockOwnersAndRead` sends its read in the lock's batch before the answer is known, so in that mode it drops that read's answer and sends the row locks and the read again, one round trip more; the write phase's re-lock (`QueueLockOwner`) carries no fleet read and no gate. An arrival's transaction holds the gate exclusively from its grant until it commits, and a write that starts meanwhile takes the owner's rows: an earlier build's first publish of its build holds it across the upload of its assets. A process logs once each time its mode changes (`noteOwnerLockMode`).

The schema also announces the changes the background loops wake on: `embeddings_enqueue` notifies `dispatch_embeddings` when it writes a row (0151), a row trigger on `refs` notifies `dispatch_excerpts_owed` for each document mention left owed an excerpt (0153), `project_delivery_settings_changed`, the row trigger of `project_delivery_settings` and of `project_deploy_sources`, notifies `dispatch_delivery_settings` with the project's key for a change of anything but a source's bookkeeping and who saved the settings when (`last_event_at`, `last_reconcile_at`, `last_error`, `updated_by`, `updated_at`; `20261123010254_project_delivery_settings`), as `delivery_settings_changed` does for the singleton `delivery_settings` row kept for the release before this one (0156, `20261120111107_delivery_settings_bookkeeping`), a row trigger on `delivery_reverts` notifies `dispatch_delivery_reverts` with the repository at each write (`20261123041500_delivery_reverts`), a row trigger on `document_edit_notices` notifies `dispatch_edit_notices` for each notice given a due time (0157), every event commit notifies `dispatch_events` (0107), and a row trigger on `github_read_attempts` notifies `dispatch_github_read_attempts` with the read's name at each write (`20261118020802`). That table holds the newest attempt of each GitHub read Dispatch makes under a lease, one row per read, which the loop holding that read's lease writes over when its pass ends; `GET /healthz` names those attempts as `github` from each process's copy of the table, which that notification refreshes. The loops' own state is three additions: `reference_excerpt_backoff` (0152), each failing document's version, failures in a row and next attempt; `suggestion_outcome_cursor` (0154), the one row holding the highest event id the outcome sweep has judged by; and `write_suggestions.swept` (0155), whether a pass has judged a suggestion against all its events, with the partial indexes `write_suggestions_unswept` and `write_suggestions_pending_artifact`. The pool's listener pool dials the held LISTEN connections: the delivery hub's and the event stream relay's, the process's one shared listener, which carries the background loops' wakes and the document rooms' room sync, and the document rooms' NOTIFY sender.

The store also holds what the related-item check reads and writes: each project's term statistics (`search_term_stats`, `search_term_totals`, kept up to date under the `search-term-stats` lease), one `related_checks` row per check, and the trigger that embeds an issue as its title and spec (migrations 0139 and 0140). A pass of that refresh applies what changed rather than counting every item again: triggers on `asks`, `comments`, `issues`, `messages` and `document_search` queue each item whose search text a write changed, with the vector it held before (`search_term_queue`, migrations `20261101182508_search_term_queue` and `20261101182522_search_term_queue_triggers`), and a pass drops exactly the queued rows its own snapshot sees, which it writes beside the counts (`search_term_totals.snapshot`, migration `20261101182515_search_term_totals_snapshot`) so that a later pass can tell its own work from another writer's. It holds the items each check offered too, one `write_suggestions` row per item, and `write_suggestions.role` admits three values since migration `20261111212235_write_suggestions_other_project`: `related`, `decision`, and `other_project`, the role of an answered question of another project. That migration drops the narrower check constraint and adds the wider one in one statement, so no moment passes with the column unchecked, and it rewrites no row. No release after it writes a `decision` row, and the rows written under that role before it stay, because each is the record of what its own check offered. The lease pool has one connection per leased loop, one for the boot's one-time parent status fix (lease `parent-status-fix`), one for the code survival run (lease `code-survival`), one per caller of a delivery intake's hold and one per caller of the keyword fill's hold, thirty-one, and the count is not kept by hand: each of those callers reserves its connection by name before the server starts any of its loops, whether or not this configuration runs its loop, and a server whose reservations are not exactly the pool's size refuses to serve, naming them (`store.LeaseCallers`). The check sees only callers that reserve a name: a goroutine added inside a caller that has reserved already, or one reservation passed to a second consumer, takes a connection nothing counted, and the count still matches.

It holds the near-copy gate's record too: one `near_copy_checks` row for each answer the gate gives an issue create (`20261115182525_near_copy_checks`), with the outcome, the reason a check was not made, the candidates it read with their scores, the two bars and the build's commit, how long the gate's read took and the step it was in when it answered or ended (`20261125005337_near_copy_checks_read_time`; both null on older rows), and the spec of a refused create alone, which no issue holds. A refusal's row is written before its `409`, a create's row after its commit or, for a refusal whose row could not be confirmed, in the create's own transaction, where it replaces a refused row under the same id; table checks keep a refused row free of an issue and every other row free of a spec.

It holds the record of each run of each step of an issue's workflow as a node and its tuples, in `workflow_nodes` and `workflow_tuples` (`20261116235202_workflow_nodes`), the priority's columns, keys and indexes under another name, so the rows copy into the node and tuple store the day it lands. `internal/dispatch/workflowstore` is their one writer: a run is one node of kind `step`, `part_of` its issue, each field an attribute written once, so the start and the end the Legion daemon writes under one id merge in either order and a write that runs again changes nothing; its read answers an issue's runs with each one's attempt, which no write stores. Each node and tuple it writes records its writer as a `model.Actor` (`made_by`), which is why it imports `model`.
A write of a run that appends a tuple (`PutStep`) sends `pg_notify` on `dispatch_workflow_runs` (`workflowstore.RunsChannel`) with the run's issue key, inside the write's own transaction.
So Postgres delivers the signal at the commit, to every Dispatch process that listens, and never for a write rolled back.
A write sent again appends nothing and sends nothing, and a plan's write (`PutPlan`) sends nothing, because a plan is no run.
A run's write appends no event, so this signal is how the live hub learns of a run (`dispatch-api`).
`IssueRunsRevision` counts the tuples of an issue's runs, `0` for an issue with no run, through `workflow_tuples_inbound` and the two partial indexes that key a node's tuples by the node, so it reads the issue's own runs' tuples and nothing else.
No write updates or deletes a tuple, so the count rises with each commit of a write that appends one, stays where it is for a write sent again, and never falls.
It is a count and not the newest `seq`, because two writes of one issue's runs do not wait for each other, and the write that drew the earlier `seq` can commit after the other.

It holds each session's newest stamped title in `session_titles`, one row a session keyed by `session_id` (`20261117100008_session_titles`).
`delivery.ResolveSessionTitles` reads that table by its primary key, one `session_id = any($1)` read for every id it is given, and reads no row of `events`.
The constraint trigger `events_session_title` on `events` (`20261117100015_events_session_titles`), deferred to the commit, writes the row in the transaction that inserts an event of a session actor whose origin stamps a non-empty `session_title`.
It replaces a stored title only with the title of a later `created_at`, so an event that stamps no title takes no title away.
Every event of one transaction has the transaction's start as its `created_at`, and of two titled events of one session in one transaction the one inserted first keeps the title.
Two transactions of one session that start in the same microsecond also give their events one `created_at`: the one that commits first keeps the title, and a later titled event of the session replaces either.
The boot's fill, `store.FillSessionTitles`, writes the titles of the events stored before the trigger, after the migrations and before the server listens (`cmd/dispatch/main.go`), and the boot stops when the fill fails.
It takes `store.SessionTitlesFillBatch` (1,000) sessions in each transaction, under the trigger's own guard, and keeps its keyset cursor in the one row of `session_titles_backfill` (`20261117100016_session_titles_backfill`), which the batch that finds no further session deletes.
The partial index `issues_open_p0` on `issues (project_key) where priority = 0 and status <> 'done'` (`20261117100010_issues_unowned_p0`, built `concurrently`) holds the open P0 issues alone.
`delivery.ListUnownedP0`, `delivery.CountUnownedP0` and `delivery.OpenP0Keys` repeat its predicate, so each reads `issues` through that index and no other row of `issues`.

It holds the keyword table of each past version of the searchable text, in two tables with no foreign key (`20261120021308_search_text_versions`).
`search_text_versions` holds one row for each version of the text that keyword search reads of an issue, a comment, an issue message or an ask; a new version is a new row.
`search_text_versions_fill` holds the one cursor row of the keyword fill: every event at or below its `event_id` has its rows.
The keyword fill (`dispatch-textversions`) is the one writer of both tables, and no migration writes them.
Rows are updated in one case: the fill's re-read, after a fill of a lower rules version wrote, writes again the rows that version decided otherwise.
The cursor row's `rules` is the lowest rules version that wrote the rows up to the cursor, which only that re-read raises.
The relation's `deleted_at` is the post's own delete mark on every version of a deleted comment or message.
`store.TextVersionsAt` gives `store.TextVersions`, the relation of the version of each item that held at a cut, only for a cut at or before the reach.
It refuses a later cut with `store.TextVersionsNotReachedError`, which names the reach.
The reach is the latest time at or before which every event has its rows, an event that a transaction still open will commit included.
`store.ComputeTextVersionsReach` takes the earliest of the oldest open transaction that can write an event, the oldest event above the cursor, and the time less 1 s.

It holds the eval registry's tables, which `internal/dispatch/evals` writes and reads (`dispatch-evals`).
`eval_versions` holds one row per version of an eval's definition and `eval_series` one per version of one of its series, neither ever updated, with the views `evals_current` and `eval_series_current` of the newest, and `eval_readings` one row per value logged under an eval, a correction being a new row that names the one it replaces (`20261117100005_eval_registry`).
`eval_days` holds the stored per-day aggregates every window read of an eval folds, `eval_day_members` where each item a family of day rows counted was last counted, `eval_days_owed` each day whose rows count an item a write of another day took from them, `eval_day_owners` each owner key, under which what counts for a project only through a default repository is stored, and `eval_days_defaults` each project's published default repository (`20261117100006_eval_days`).
`eval_days_cursor`, `eval_days_walks`, `eval_days_serving` and `eval_days_settings` hold the day-row refresher's state, and `eval_rebuilds`, `eval_rebuild_walks`, `eval_rebuild_firsts`, `eval_rebuild_days`, `eval_rebuild_members`, `eval_rebuild_range_figures`, `eval_rebuild_day_figures` and `eval_rebuild_reverify` its rebuilds (`20261117100021_eval_days_refresher`).
`eval_range_figures`, `eval_day_figures`, `eval_figures_built` and `eval_figure_cuts_stale` hold the stored figures, folds of the day rows kept ahead of the eval list's read (`20261120072042_eval_figures`).
The triggers on `eval_readings`, `eval_versions`, `eval_series` and `eval_days` log each write as the change kinds `eval_readings`, `eval_versions` and `eval_days` in the change log's outbox, `delivery_changes_pending`, through `delivery_change_log_pending`, which takes no lock (`20261117100001_delivery_changes_pending`, and `20261117100012_eval_readings_changes` to `20261117100014_eval_days_changes`).
The boot's rename pass rewrites a renamed repository in the owner keys and the published defaults, and marks the stored figures of its old and its new name stale (`store/repo_rename_pass.go`, `markRenamedCuts`).

It holds the results of the code survival run (`dispatch-delivery`) in five tables (`20261126103753_code_survival`), which `internal/dispatch/codesurvival` writes and reads: counts and keys, and never a patch, a file's text or a list of a branch's commits.
`code_repos` holds one row per repository the run reads, each project's default repository: the branch it read, its start day, before which no day is measured, whether the App can read it and, where it cannot, why, the day of its last finished daily pass, the day it last stored a result, and when a pass that GitHub's budget or a rate limit stopped may start again.
`code_changes` holds one row per measured change, the commit a merged pull request landed as: its day, its committer time, its pull request, head branch, author login and issue, the lines it added, those still there at its 30-day mark and those that commits which merged no pull request removed before the mark.
`code_pairs` holds one row per pair of a measured change and a later change that removed some of its lines by the mark: the remover's SHA, pull request, head branch, author login and issue, the lines it removed and the days between the two; its key references the change's row on delete and on update cascade, so a pair goes with its change.
`code_days` holds one row per day a run replayed: the count of the day's first-parent commits and the sha256 of their SHAs in chain order, which each pass compares with the chain to find a force-push, and the day's state, `replayed` (that fingerprint alone), `measured`, `marked` or `blocked`, with the commit that blocks it kept only while it does.
`code_projects` holds one row per project whose day rows of the two code evals a builder has locked: the sha256 of the default repository and the code groups those rows stand built under and when they were built, both null until the first build; the run and the regroup lock the row (`select … for update`) before either builds the project's rows.
A SHA is stored only for a change, for the remover of a stored pair and for a blocked day's blocking commit, and the two `bytea` columns hold 32-byte digests, which their checks hold them to.
The run writes the two evals' day rows itself, in its results transaction, and so do its marks' transaction and the regroup (`evals.WriteCodeDaysTx`, `dispatch-evals`); no refresher family builds them, and no change kind is added for them or for the five tables, which carry no trigger.
Those writes log `eval_days` changes through `eval_days`' own trigger (`20261117100014_eval_days_changes`), and the group series' writes `eval_versions` changes through `eval_series`' trigger, which wake the evals views once the writer drains the outbox.
The boot's rename pass rewrites a renamed repository in `code_repos`, `code_changes` and `code_days`, and the cascade carries each change's pairs with it.
