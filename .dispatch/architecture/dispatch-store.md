The schema every other package reads and writes through: ordered migrations applied in one transaction each at boot, the pool, and the session and people rows — which is why it imports `auth`. `internal/pgmigrate` holds the runner's rules, which the secrets broker's runner shares: the whole migration set is refused before anything applies when two files share a version or a file is misnamed or unreadable, and every migration's lock waits are bounded at five seconds. `internal/pgmigrate` reads migration and census SQL as Postgres 18's lexer does.

`store/ownerlock.go` holds Dispatch's per-owner serialization, the owner lock: `pg_advisory_xact_lock(0x4F574E52, hashtext('<kind>:<key>'))` for an issue, a project document (keyed by its artifact) or a project, in a two-key namespace ("OWNR") no other lock family takes. `LockOwner`, `LockOwners` (one statement, sorted and deduplicated by lock key, so two writers never take two owners in opposite orders), `LockOwnersShared` (the same sorted statement in shared mode, which the Inbox's Mark all read and its dismissal take for the owners of the threads they mark, through `api/inbox_read.go`'s `lockInboxReadOwners`) and `TryLockOwners` (the advisory form of `skip locked`, for background passes) are how every writer of an owner's rows orders itself against the others; the owner row itself is locked only in a transaction's write phase, by the event broker's append, unless a server process of an earlier build is live (the next paragraph). An advisory lock assigns no transaction id, so a write transaction whose read phase takes only advisory locks holds none through it and holds one only from its first write or row lock to its commit. The lock and the read it guards are always separate statements (`LockOwnerAndRead` and `LockOwnersAndRead` send them in one batch): under READ COMMITTED a statement's snapshot is taken before it waits, so a read made in the lock's own statement would miss a close committed while it waited. The lock order is the owner lock first (several at once in one statement, sorted by key, or one after another where the later one is the project whose event the write appends, as `putThreadRead` takes its thread's owner and then the project's), then the document service's writer slot, the copy lock and the document's advisory lock, and only in the write phase the owner row and every row lock and row write. Most writers keep that order; these do not. The Inbox's Mark all read and its dismissal (`markInboxReadThreads`, `dismissInboxThreads`) read the threads they mark before any lock, take those threads' owners in shared mode in two statements, the documents' and then the issues' (`lockInboxReadOwners`), lock and write the caller's rows (a dismissal first the Agent threads' roots, `for update`), and take the owner locks of the projects those writes moved only after them, right before their appends (`commitInboxMarks`); the order they keep instead is written down at `markInboxReadThreads`. A repository-mapping write (`api/repo_projects.go`'s `lockRepoProjectWrite`, which the PUT, the DELETE and the boot seed share) takes the repository's own advisory lock and reads the mapping before the projects' owner locks, and after them locks the mapping's row `for update` in its read phase, which gives it a transaction id before its first write. The issue create and the issue patch take the dependency locks (`lockIssueDependencyWrite`: the dependency lock of the issue's own project and of each project a `blocked_by` target belongs to, `lockProjectIssueDependencies`, in `docs.ProjectsInLockOrder`'s order, then the deployment's own, `lockDeploymentIssueDependencies`), when they write a parent or blockers, before their owner locks, and the patch the project's rank-allocation lock (`lockProjectRankAllocation`) too when it moves the rank, the patch reading the issue's project before them and the create its parent issue before its owner lock; the targets' projects are read by a plain read and every dependency lock is advisory, so that step assigns no transaction id. A patch or create that names a repository keeps the mapping it names from being moved or deleted under it by taking the mapping's row `for key share` (`checkIssueRepoMapped`) only in its write phase: the patch checks the mapping by a plain read in its read phase (`readIssueRepoMapped`), refuses `REPO_NOT_MAPPED` there, and takes the key share as the first statement of its write phase, and the create takes the rank-allocation lock and that key share after its first write. The writers `dispatch-events` lists under dispatch://INFRA-3397 write or lock a row before the owner lock of the event they append.

A build before the owner lock serialises an owner's writers on the owner's row instead: each takes the row `for no key update` (its Inbox `for share`) first and holds it to its commit, and never takes the advisory lock, so the two builds' writers would not exclude each other's read phase during a rolling release. Each server process registers the protocol it serialises by in `server_processes.owner_lock_protocol` (migration `20261115100924_server_processes_owner_lock_protocol`): this build registers 1 (`store.OwnerLockProtocol`), and an earlier build's row reads the column's default, 0. Every read-phase owner lock statement also answers, in the same statement and so with no round trip of its own, whether a live process (heartbeat within `store.ProcessLiveWindow` of the database's now(), as `processes.Live` measures it) registers 0 (`legacyFleet`). While one does, the lock takes each owner's row too, in a statement of its own right after the advisory lock and before any read the lock guards (`lockOwnerRows`): `for no key update` for `LockOwner` and `LockOwners`, `for share` for `LockOwnersShared`, and `for no key update skip locked` for `TryLockOwners`, which leaves out an owner whose row it did not take. The rows go documents, then issues, then projects, each kind's keys in byte order, which is the order the earlier build takes several owners' rows in (its broker sorts owners by `<kind>:<key>`), and always after the advisory lock, never before it: this build's advisory-mode writers hold the lock and take the row in their write phase, so the row first would wait on them while they wait on the lock. `LockOwnersAndRead` sends its read in the lock's batch before the answer is known, so in that mode it drops that read's answer and sends the row locks and the read again, one round trip more; with no such process live the lock is exactly the advisory lock above, and the write phase's re-lock (`QueueLockOwner`) carries no fleet read. A process logs once each time its mode changes (`store.LastOwnerLockMode`). The fleet read sees the statement's snapshot, so a process of an earlier build that registers after a transaction's lock statement started - a rollback to it - is not seen by that transaction, whose read phase that build's writers can then interleave until it commits.

The schema also announces the changes the background loops wake on: `embeddings_enqueue` notifies `dispatch_embeddings` when it writes a row (0151), a row trigger on `refs` notifies `dispatch_excerpts_owed` for each document mention left owed an excerpt (0153), `delivery_settings_changed` notifies `dispatch_delivery_settings` for a settings change other than freshness (0156), a row trigger on `document_edit_notices` notifies `dispatch_edit_notices` for each notice given a due time (0157), and every event commit notifies `dispatch_events` (0107). The loops' own state is three additions: `reference_excerpt_backoff` (0152), each failing document's version, failures in a row and next attempt; `suggestion_outcome_cursor` (0154), the one row holding the highest event id the outcome sweep has judged by; and `write_suggestions.swept` (0155), whether a pass has judged a suggestion against all its events, with the partial indexes `write_suggestions_unswept` and `write_suggestions_pending_artifact`. The pool's listener pool dials the held LISTEN connections: the delivery hub's and the event stream relay's, the process's one shared listener, which carries the background loops' wakes and the document rooms' room sync, and the document rooms' NOTIFY sender.

The store also holds what the related-item check reads and writes: each project's term statistics (`search_term_stats`, `search_term_totals`, kept up to date under the `search-term-stats` lease), one `related_checks` row per check, and the trigger that embeds an issue as its title and spec (migrations 0139 and 0140). A pass of that refresh applies what changed rather than counting every item again: triggers on `asks`, `comments`, `issues`, `messages` and `document_search` queue each item whose search text a write changed, with the vector it held before (`search_term_queue`, migrations `20261101182508_search_term_queue` and `20261101182522_search_term_queue_triggers`), and a pass drops exactly the queued rows its own snapshot sees, which it writes beside the counts (`search_term_totals.snapshot`, migration `20261101182515_search_term_totals_snapshot`) so that a later pass can tell its own work from another writer's. It holds the items each check offered too, one `write_suggestions` row per item, and `write_suggestions.role` admits three values since migration `20261111212235_write_suggestions_other_project`: `related`, `decision`, and `other_project`, the role of an answered question of another project. That migration drops the narrower check constraint and adds the wider one in one statement, so no moment passes with the column unchecked, and it rewrites no row. No release after it writes a `decision` row, and the rows written under that role before it stay, because each is the record of what its own check offered. The lease pool has one connection per leased loop and per caller of a delivery intake's hold, twenty-one, and the count is not kept by hand: each of those callers reserves its connection by name before the server starts any of its loops, whether or not this configuration runs its loop, and a server whose reservations are not exactly the pool's size refuses to serve, naming them (`store.LeaseCallers`). The check sees only callers that reserve a name: a goroutine added inside a caller that has reserved already, or one reservation passed to a second consumer, takes a connection nothing counted, and the count still matches.
