The Go coordinator is Legion's deterministic half: admission, workflow, the issue record, process supervision across tmux and Agent Sandbox, and credentials. It is developed separately from the current TypeScript daemon until the Stage 7 cutover. `scripts/e2e` holds each stage's live proof — the daemon booting on a real Postgres, and real Oh My Pi panes under its private tmux server. The `scripts/e2e` proofs that run Dispatch start the pgvector-on-PostgreSQL-18 image Envoy's `internal/testpg` pins, by the same digest.

Under `runtime: kubernetes` the daemon runs a second pod-release rule beside the idle release, `internal/workflow`'s `UnownedPodRelease` over the same minute pass (`internal/daemon`'s `releaseUnownedPods`): where `IdleRelease` saves the unpushed work of a quiet pod as a bundle and suspends each live claim, this rule takes an issue that has had no live claim for `runtime.kubernetes.idle_release.idle_minutes`, deletes the pod, the disk that pod owns and the issue's Sandbox, saves no bundle and changes no claim, records a hold of a pod it leaves standing only where that pod has been quiet for the whole period under one of the three reasons a deployment reads (`unowned_claim_process`, `unowned_operator_suspended`, `unowned_delivery_waiting`), the rest of its nine holds recording nothing (`internal/daemon`'s `recordableHold`), runs whether or not the Envoy listener has reported itself ready, and leaves the next start of any claim of the issue — an operator's `legion claims retry`, or a start the daemon queues — to build the Sandbox, the pod and the workspace again.

A repository that moved is configured as the top-level `legion.yaml` key `repository_renames` (`- from: … / to: …`), which settles onto `config.Config.RepositoryRenames`, the one equivalence `internal/ghrepo/renames.go` holds (`Same`, `Partner`, `Under`, `Pairs`; the zero value a deployment configuring none carries answers exactly as `strings.EqualFold` does). A configured pair's two names are one repository wherever the daemon compares a name: intake's `recordedPullRequest` read, the repository mapping's `lookup` and `kept`, `heardRepositories`, which puts both subjects on the consumer's filters so neither side goes deaf over a transfer, the boot's backfill, the pull-request listing reads and `githubrest.PullRequest.HeadIn`, `reviewedRepository`, and the whole of the workflow engine's comparisons; `appauth.GitHubCredential` still gives a role's gh bundle one directory per owner, named for the owner the record keeps, which no transfer moves, with a `<owner>/<repo>` directory under the directory named for the recorded owner and under the one named for the owner whose installation serves that repository, for each other repository each of them serves, every such directory holding the lease of the repository its own name resolves to, and what a resolving pair changes is the token in them: the directory named for the recorded owner and the directory of the owner that serves that repository now hold one lease, minted for that serving owner, so the directory a role writes through authorises nothing by its name and everything by the token in it, while `legion gh`, `legion git-credential` and both runtimes are unchanged. The equivalence is read-side only — nothing it answers rewrites a record, and a tree keeps the repository name it was recorded under for its whole life — so the pair must stay configured for as long as any record names the old repository. It adds no repository to the served set, which is Dispatch's mapping alone, and reads nothing from GitHub, so a pair may be configured before the transfer, the boot logging once that the project serves nothing under the name the repository moved to; `legion start --check-config` prints one line per pair and `legion state --json` carries them (`settings.repository_renames`).

Which repository the daemon's own GitHub calls name is the same file's second rule: `Serving` is the repository GitHub holds a recorded one under now — the pair's other name exactly when the recorded name is that pair's `from`, the project serves the pair's `to` and the project does not serve the pair's `from`, every other recorded name, the pair's `to` among them, answered unchanged — and `OwnerAliases` is each owner a pair moved a repository away from, by the owner it moved to, for the pairs that resolve by that same rule (a pair inside one owner is no alias, since a rename inside one owner moves nothing between installations). Both read the repositories the project serves, one repository at a time (`repositories.servesRepository` over the mapping's own map, `ghrepo.Serves` over a served slice), and never the set of owners those repositories have: a project that serves one more repository of the old owner serves no more of the moved one, while the owner predicate this replaces read that as the old owner being the project's own and stopped resolving the pair, which is how adding one repository to a project's mapping turned a live pair off and left 47 trees unable to push for 42 minutes. No set of owners the project serves stops a pair from resolving. `internal/daemon`'s `repositories.serving` reads the rule over the mapping and is the deployment's one copy of it: the boot hands it to `internal/api` as `Options.Serving` and to the Sandbox runtime's token source as `implementTokens`' own map, so neither reads the mapping a second time, while `appauth`'s `bundleDirs` reads both halves over the served repositories themselves, once per bundle, for `GitHubCredential`, `ControllerCredential` and `GitHubDirs` alike — the write lease for the role's own repository stands in two directories and no others, the one named for the owner its record keeps and the one named for the owner that serves it, which are one directory wherever no pair resolves, each other repository that serving owner holds gets a `<owner>/<repo>` directory with a read lease that names it alone, every other owner the project serves a repository of under its own name keeps one read lease over its own repositories, and an owner only a resolving rename puts in the bundle holds the lease of the owner that serves the moved repository. `NewRenames` still refuses one owner's repositories moved to two owners, and its reason is now that `OwnerAliases` is keyed by the owner a pair moved a repository away from, so two such pairs write that key twice and the last wins, silently. The mapping load reads the pair's other name only when GitHub answers that no App of the deployment is installed on the mapped one (`checkMapping`, over `Partner`) — a mapped name that holds one of the two Apps and not the other is the operator's own gap rather than a transfer, so the entry is left out naming the App that is missing and the pair is not read — and serves and records the entry under the name both Apps answered for, two mapping entries that name one repository being served as one and keeping the default (`set`). Where the call is a REST read or write or a GraphQL query — the issue branch's create, `readyMerge` and `autoMergeDisable`, the required-checks pass's reads, the API's read of a completing implementer's pull request, the merger's READY checks and the commit identity every launch and adoption mints — both the App token's owner and the address are the serving repository's. The daemon makes no GitHub call of its own for a production check: it reads no deployment's production workflows, and a check's next look is the one the role the project's `production_check` names asked for with `wake_at` on a `pending` report. The default-branch read is mapped inside `defaultBranches.fetch`, the one place that mints for it, so the boot's backfill of a record written under the old name, the mapping's own naming and an unrecorded issue's default repository all read the repository GitHub holds it under now, while what is kept stays keyed by the name the caller asked for. The token is the half that has to move: after a transfer the installation covering the repository is the new owner's, and the old owner's token reaches nothing. The address need not, since GitHub answers an API call at the old name too (measured: `GET /repos/twitter/bootstrap` answers 301 to `/repositories/2126244`, and GraphQL's `repository(owner:"twitter",name:"bootstrap")` answers `twbs/bootstrap`), but naming the served repository keeps a write off a redirect and names the right repository in a log line. Where the address is a git remote, the token alone follows the pair and the address stays the name the record keeps: the outbox's workspace provisioning and `implementTokens`, the one source the Sandbox runtime's three mint sites share, whose addresses also key a pod's feed, its clone and the repository cache's volume and Service, which a rename must not move.

A project's experiments are `legion.yaml`'s `projects.<KEY>.experiments`, read by `internal/config/experiments.go` onto `config.Project.Experiments`: a mapping of an experiment's name to its block, kept in the file's order, since a launch loads a drawn unit's files in that order and a mapping's iteration order is no contract. A name, and a variant's name, is 1 to 32 characters of `a-z`, `0-9` and `-` (`experimentNamePattern`) and is named once, because every draw records both. `mode` is `off` (the default a block naming none leaves), `on` or `random`; `unit` is `tree` (the default) or `issue`, what one draw covers and is recorded against; `variants` are the arms, each a `name`, a `weight` (a whole number above zero, 1 where the arm names none), optional `config_files` read as `role_config_files`' lists are (`readOverlayFiles`) and an optional `instructions` path, both clean absolute paths taken as written; `on_variant` is the arm `mode: on` gives every unit, which that mode requires and which must be an arm of the experiment. Neither file key is required: the arm naming no file is the control a randomisation is measured against. A mode other than off over one variant is refused, since a draw among one arm measures nothing. The per-tree `memory` block is still `legion.yaml`'s `projects.<KEY>.memory`, read by `internal/config/memory.go` onto `config.Project.Memory` with its own reader and its own `checkMemory`, and it is the experiment named `memory`: `config.Project.ExperimentsDeclared` maps it to one of unit `tree`, mode `Memory.Word`, `on_variant: memory`, and the two arms `memory` (weight 1, the block's `config_files` and `instructions`) and `none` (weight 1, neither), first in the list and the `experiments` key's own after it in the file's order. Every reader below the loader asks that one method, so the block and the key behave alike and no reader needs a second path for the block. Every project declares that experiment, whatever it writes: a project writing `experiments.memory` declares it at that key's own mode, and a project writing neither the block nor `experiments.memory` declares it at mode off, whose draw records each new tree at no arm, which is what the daemon has recorded for every tree of such a project since the memory draw existed, and is what keeps the three memory fields such a tree answers — `memoryGroup` `none`, `memoryDrawMode` `off` and the instant of the draw — exactly where they are. The one project it is not added to is the one declaring `experiments.memory` itself, the other spelling of that one experiment, whose own block is then the whole declaration. `checkExperimentMemory` refuses three shapes of `experiments.memory` that the name `memory` forbids and every other name of the key allows: a project writing the block and `experiments.memory` both, since that is one experiment spelled twice; an `experiments.memory` whose arms are not exactly `memory` and `none`, whose draw rides to every pod as the issue state's `memoryGroup`, a `z.enum(["memory","none"])` that any other word makes fail to parse; and an `experiments.memory` whose unit is not `tree`, since that draw rides as `memoryGroup`, `memoryDrawMode` and `memoryDrawnAt`, which are the draw of the issue's tree, one answer for every issue of it. `checkExperiments` refuses, once the rest of the file is settled, an arm that names `config_files` while `worker_backends` puts an issue role on a harness other than Oh My Pi (which reads no `PI_CONFIG_FILES`) and, under `runtime: kubernetes`, an arm's overlay outside every `runtime.kubernetes.pod` mount (`checkRoleConfigMount`, the role overlays' own check); `internal/daemon`'s `checkRoleConfigFiles` refuses under tmux an overlay of any declared arm no pane could read, and `readBoot` an arm's `instructions` file it cannot read or that holds nothing. None of those reads the mode: the launch follows the record, so a unit already drawn into an arm names that arm's files under any mode, and only taking the arm out of the file takes them away. `checkMemory`'s own third rule, that a mode other than off must name `config_files`, stays the block's alone and is asked of no arm, because an experiment's control arm names no overlay by design. `internal/config/keytable.go` holds the line of every key of both, which `legion config-reference --json` prints and the documentation site's configuration reference is generated from.

The arm a unit runs under is drawn once, by `internal/experiment`'s `Draw` (`off` gives the empty variant, so the unit is recorded as drawn for at no arm; `on` gives `on_variant`; `random` takes one value below the arms' total weight from `experiment.CryptoSource`, `crypto/rand` over the operating system's own source and never a seeded sequence, and walks the arms' cumulative weights in the file's order; a mode the switch does not know is refused, which only a programming error reaches, since the loader takes three words). The package implements none of GrowthBook's hashing and depends on nothing of it: that hashing earns its keep where no durable record of a draw is kept, and this daemon writes the answer in the transaction that opens the unit and reads it back at every launch. A tree experiment is drawn at the one moment a tree's lifecycle row is first created (`treelifecycle.Lifecycle.Created`), inside that row's own transaction, on both paths that open a tree: admission's `promoteHolds` and the operator's spawn, whose draw `internal/api`'s `drawExperiments` runs inside `store.Store.OpenOperatorTreeLifecycle`. An issue experiment is drawn where the daemon first records the issue — admission's `putNewRoot` for a root or an orphan, the workflow engine's own `drawExperiments` for a child — so every issue the daemon records is drawn for as it records it. `record.Store.PutAssignments` writes one `experiment_assignments` row per answer — the issue key, the experiment, the unit, the arm, the mode in force and the instant — under `on conflict (issue_key, experiment) do nothing`, and nothing ever updates a row, so a re-admission, a new generation, `ClearTreeGeneration` and the next epoch after a cleanup all keep the draw, and an experiment a unit has been running under keeps its arm whatever the project's file says by now. Both writers guard on the issue's own record, which their inserts select from, so a key the daemon holds no record of writes no row and raises nothing. `readmit` settles a handed-over child's assignments at the hand-over (`CarryAssignments`): first every assignment row of unit `tree` of the old tree's root, copied onto the child with its arm, its mode and its instant verbatim and the `carried` mark set, so the work goes on under the arms it has been running under, while a row of unit `issue` of the old root is that issue's own answer and is not copied; then each experiment declared at the hand-over written at no arm, no mode and no instant under the same write-once insert, which lands only where the copy left that experiment unwritten and is never drawn for later. The carry's driver row is the old tree's `tree_lifecycles` row, matched on the tree and the normalized runtime token, since `tree_lifecycles.project` is that token while `issues.project` is the Dispatch key; the only issue record either insert joins is the child's own, never the old tree's root, since the copy reads the old root's assignment rows themselves, so an operator's tree the daemon recorded no root for, which holds no such row, hands over the settled rows alone. A tree with no such row was never opened, so the carry writes nothing and the child's own first open draws it like any other new tree, and a unit opened before an experiment was declared holds no row for it and runs in no arm of it. `20261111045636_experiment_assignments` created the table and back-filled it from the four `issues.memory_*` columns — every root holding a draw or the carried mark takes one `memory` row of unit `tree` with its mode, instant and mark verbatim and its group as the variant, but for one normalisation: a group drawn under mode `off`, which the column holds as the word `none`, becomes the empty variant — so no tree drawn before the deploy loses its exposure; those four columns stay in the schema, are written by nothing from this release on, and a later release drops them.

At launch the arms are the unit's: `internal/daemon`'s `launchVariants` reads the unit's rows in a transaction and hands them to `internal/experiment`'s `Launch`, which answers, for each experiment the project declares in the file's order, the arm recorded for the unit that experiment covers — the issue's tree root for a tree experiment, the issue itself for an issue experiment (`record.Store.AssignmentsFor`, over the daemon's own store in a transaction of its own, so a tree the operator's spawn drew with no workflow configured is launched with the arm it drew) — and `specs` sets `runtime.SpawnSpec.Variants` and `PromptParts.VariantInstructionsPaths` on a worker spawn alone. It reads nothing at all where no declared arm names a `config_files` or an `instructions` path: such an experiment contributes nothing to a launch whichever arm its unit drew, so the deployment that declares only the memory experiment at mode off — the one a project writing no `memory` block and no `experiments` key declares — pays no transaction per worker spawn, and the issue's own key is read beside its tree's only where some declared experiment's unit is the issue. A unit with no row for an experiment, and one whose recorded arm the file no longer names, contributes nothing and runs as a unit in no experiment does; its row stays, so naming the arm again gives the unit the arm it drew. Both runtimes then name each arm's overlays after the operator's own overlays and the role's own in `PI_CONFIG_FILES`, in that same declared order, so an arm's file outranks both (`runtime.VariantOverlays`, `tmux`'s `panePairs`, `sandbox`'s `launch.overlays` through `roleOperatorEnv`), and end the one `--append-system-prompt` value with the daemon's own copies of those arms' instructions (`config.ReadVariantInstructions` at boot and `config.WriteVariantInstructions`, `<state_dir>/experiments/<experiment>/<variant>.md`), after the deployment's own; a pane reads each copy with `$(cat …)` and a pod is given its text inlined, since a pod reads no file of the daemon's. `controllerSpawnSpec` sets neither and `validateControllerShape` refuses either, because a unit is a tree or an issue and the controller runs in neither, and an arm with no `instructions` appends nothing. A launch that keeps a live pod is told only the arm overlays that pod holds (`heldRoleOverlays`, read from the pod's own stored template), because Oh My Pi refuses to start on an entry that is not there and a role that never starts never answers the round that is to replace the pod: a pod built before an arm's mount existed starts its role in neither arm — not the control, which names no file, and not the drawn arm, whose file it cannot read — and `launch.overlays` logs that once, naming the issue, the role, the experiment, the arm and the files it dropped. The drift itself is `movedRoleOverlays`, which reads every declared arm's overlays against every issue pod of the deployment, since any unit may be drawn into any arm, and names the move by what the arm itself carries onto `runtime.Variant` from `config.Project.ExperimentsDeclared`: the `memory` block's own arm (`runtime.Variant.MemoryBlock`) as `memory.config_files <file>`, the spelling that drift had before any experiment was declared, and an arm of the `experiments` key, `experiments.memory`'s included, by the whole key the operator wrote for its `config_files` (`runtime.Variant.ConfigFilesField`), `projects.<KEY>.experiments.<experiment>.variants.<variant>.config_files <file>`; the controller's pod is moved by none of them. Every issue of the state carries the answers that apply to it (`internal/projection`, `api.Issue.Assignments`, daemon API contract 99), the declared ones in their declared order and then any the file no longer names, by name, with the three contract-49 memory fields read off the `memory` answer alone and only where it records a draw, and `legion state` prints one line per declared experiment counting the issues drawn each arm, on the same rule: a row that records no draw, which is a hand-over settling a unit at no arm, is counted in no line, for every experiment. Every project declares at least the memory experiment, so there is always a line, and a deployment that has drawn nothing yet reads `memory: none`. The state names no tree, and a tree handed over as one of its own carries its old tree's draw verbatim, so no draw is a tree's name.
