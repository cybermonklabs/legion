The Go coordinator is Legion's deterministic half: admission, workflow, the issue record, process supervision across tmux and Agent Sandbox, and credentials. It is developed separately from the current TypeScript daemon until the Stage 7 cutover. `scripts/e2e` holds each stage's live proof — the daemon booting on a real Postgres, and real Oh My Pi panes under its private tmux server. The `scripts/e2e` proofs that run Dispatch start the pgvector-on-PostgreSQL-18 image Envoy's `internal/testpg` pins, by the same digest.

Under `runtime: kubernetes` the daemon runs a second pod-release rule beside the idle release, `internal/workflow`'s `UnownedPodRelease` over the same minute pass (`internal/daemon`'s `releaseUnownedPods`): where `IdleRelease` reads the workspace of a quiet pod through a live role's shim, takes the pod only when no working copy or bookmark holds a commit origin does not hold and the working copy holds no change, and suspends each live claim, this rule takes an issue that has had no live claim for `runtime.kubernetes.idle_release.idle_minutes` and changes no claim. No role process runs in such a pod, so before it deletes the pod, the disk that pod owns and the issue's Sandbox it has the pod's launcher make the same read (`runtime.PodWorkspaceReader`, R6 of #5285); a read that finds such work, or that cannot be made, keeps the pod, records a decline, and tells the issue's architect once for the pod (a `workspace-kept` notice, which goes to the controller where that architect will not hold its role again). A Sandbox that keeps a volume the issue's next pod mounts is released with no read, since that volume stays. The close of a left pod with no live claim (`LeftPodClose`) reads the same way. The rule records a hold of a pod it leaves standing only where that pod has been quiet for the whole period under a reason a deployment reads (`unowned_claim_process`, `unowned_operator_suspended`, `unowned_delivery_waiting`, `unowned_unpushed_work`, `unowned_workspace_unread`), the rest of its holds recording nothing (`internal/daemon`'s `recordableHold`), runs whether or not the Envoy listener has reported itself ready, and leaves the next start of any claim of the issue — an operator's `legion claims retry`, or a start the daemon queues — to build the Sandbox, the pod and the workspace again.

A repository that moved is configured as the top-level `legion.yaml` key `repository_renames` (`- from: … / to: …`), which settles onto `config.Config.RepositoryRenames`, the one equivalence `internal/ghrepo/renames.go` holds (`Same`, `Partner`, `Under`, `Pairs`; the zero value a deployment configuring none carries answers exactly as `strings.EqualFold` does). A configured pair's two names are one repository wherever the daemon compares a name: intake's `recordedPullRequest` read, the repository state's `lookup` (a preparation's read, kept under both names), `heardRepositories`, which puts both subjects on the consumer's filters so neither side goes deaf over a transfer, the boot's backfill, the pull-request listing reads and `githubrest.PullRequest.HeadIn`, `reviewedRepository`, and the whole of the workflow engine's comparisons; `appauth.GitHubCredential` still gives a role's gh bundle one directory per owner, named for the owner the record keeps, which no transfer moves, and the bundle holds no repository directory at all, a lease reaching every repository its own installation holds (INFRA-2543), so what a resolving pair changes is the token in those directories: the directory named for the recorded owner and the directory of the owner that serves that repository now hold one lease, minted for that serving owner, so the directory a role writes through authorises nothing by its name and everything by the token in it, while `legion gh`, `legion git-credential` and both runtimes are unchanged. The equivalence is read-side but for one pass of this release (INFRA-4401 A10, `internal/daemon/rename_pass.go` over `record.RenameIssueRepository`): at boot, and when an issue's pod ends, it writes each pair's `to` over its `from` on every stored column of the project's issues that holds a repository name, for each issue with no live pod (under tmux, no workspace under the old name), and logs each table's rows written, failed and `left`; dispatch://INFRA-3532's own change removes it. Until the pass writes a record, the record keeps the repository name it was recorded under, so the pair must stay configured until no row is `left` on its `from`. A pair adds no repository to the ones the project serves: a name is served when GitHub answers that both role Apps are installed on it, which the refresher reads for both names of each pair once the API serves (`readPairs`), and until GitHub has answered for a name the pair's `to` counts as served and its `from` does not (`servesLocked`), so a pair may be configured before the transfer; `legion config check` prints one line per pair and `legion state --json` carries them (`settings.repository_renames`).

Which repository the daemon's own GitHub calls name is the same file's second rule: `Serving` is the repository GitHub holds a recorded one under now — the pair's other name exactly when the recorded name is that pair's `from`, the project serves the pair's `to` and the project does not serve the pair's `from`, every other recorded name, the pair's `to` among them, answered unchanged — and `OwnerAliases` is each owner a pair moved a repository away from, by the owner it moved to, for the pairs that resolve by that same rule (a pair inside one owner is no alias, since a rename inside one owner moves nothing between installations). Both ask whether the project serves each of the pair's two repositories, one repository at a time (`repositories.servesRepository`: GitHub's answer that both role Apps are installed on that name, kept in the name's own entry), and never the set of owners the project's repositories have: one more served repository of the old owner makes no more of the moved one served, while the owner predicate this replaces read that as the old owner being the project's own and stopped resolving the pair, which is how serving one more repository turned a live pair off and left 47 trees unable to push for 42 minutes. No set of owners stops a pair from resolving. `internal/daemon`'s `repositories.serving` reads the rule over those answers and is the deployment's one copy of it: the boot hands it to `internal/api` as `Options.Serving` (and `servesRepository` as `Options.Served`) and to the Sandbox runtime's token source as `implementTokens`' own `serving`, so neither keeps answers of its own, while `appauth`'s `bundleDirs` asks the same `served` predicate of both halves, once per bundle, for `GitHubCredential`, `ControllerCredential` and `GitHubDirs` alike — the write lease for the role's own repository stands in two directories and no others, the one named for the owner its record keeps and the one named for the owner that serves it, which are one directory wherever no pair resolves, every other owner the role's App is installed on keeps one read lease on its own installation, and an owner only a resolving rename puts in the bundle holds the lease of the owner that serves the moved repository. `NewRenames` still refuses one owner's repositories moved to two owners, and its reason is now that `OwnerAliases` is keyed by the owner a pair moved a repository away from, so two such pairs write that key twice and the last wins, silently. The preparation of an unrecorded issue's repository reads the pair's other name only when GitHub answers that neither role App is installed on the name the issue resolves to (`readRecordable`, over `Partner`) — a name that holds one of the two Apps and not the other is the operator's own gap rather than a transfer, so the issue is refused naming the App that is missing and the pair is not read — and records the issue under the name both Apps answered for, the read kept under both names (`recordRepository`). Where the call is a REST read or write or a GraphQL query — the issue branch's create, `readyMerge` and `autoMergeDisable`, the required-checks pass's reads, the API's read of a completing implementer's pull request, the merger's READY checks and the commit identity every launch and adoption mints — both the App token's owner and the address are the serving repository's. The daemon makes no GitHub call of its own for a production check: it reads no deployment's production workflows, and a check's next look is the one the role the project's `production_check` names asked for with `wake_at` on a `pending` report. The default-branch read is turned onto the serving repository inside `defaultBranches.fetch`, the one place that mints for it, so the boot's backfill of a record written under the old name, a repository's preparation and an unrecorded issue's launch all read the repository GitHub holds it under now, while what is kept stays keyed by the name the caller asked for. The token is the half that has to move: after a transfer the installation covering the repository is the new owner's, and the old owner's token reaches nothing. The address need not, since GitHub answers an API call at the old name too (measured: `GET /repos/twitter/bootstrap` answers 301 to `/repositories/2126244`, and GraphQL's `repository(owner:"twitter",name:"bootstrap")` answers `twbs/bootstrap`), but naming the served repository keeps a write off a redirect and names the right repository in a log line. Where the address is a git remote, the token alone follows the pair and the address stays the name the record keeps: the outbox's workspace provisioning and `implementTokens`, the one source the Sandbox runtime's three mint sites share, whose addresses also key a pod's clone and the repository cache's volume and Service, which a rename must not move.

A project's experiments are `legion.yaml`'s `projects.<KEY>.experiments`, read by `internal/config/experiments.go` onto `config.Project.Experiments`: a mapping of an experiment's name to its block, kept in the file's order, since a launch loads a drawn unit's files in that order and a mapping's iteration order is no contract. A name, and a variant's name, is 1 to 32 characters of `a-z`, `0-9` and `-` (`experimentNamePattern`) and is named once, because every draw records both. `mode` is `off` (the default a block naming none leaves), `on` or `random`; `unit` is `tree` (the default) or `issue`, what one draw covers and is recorded against; `variants` are the arms, each a `name`, a `weight` (a whole number above zero, 1 where the arm names none), optional `config_files` read as `role_config_files`' lists are (`readOverlayFiles`), an optional `instructions` path, both clean absolute paths taken as written, and an optional `plan`, how the issues drawn into the arm are done: `owner` (the owner gives each its plan) or `default` (each runs the project's default steps and Legion takes no plan from its owner); `on_variant` is the arm `mode: on` gives every unit, which that mode requires and which must be an arm of the experiment. Neither file key is required: the arm naming no file is the control a randomisation is measured against. A mode other than off over one variant is refused, since a draw among one arm measures nothing. An experiment that names `plan` on one arm names it on every arm and is `unit: issue`, since the first step reads the group from the issue's own row (`checkExperimentPlans`, which the project's reader runs after `checkExperimentMemory`), and one project has at most one such experiment (`checkExperiments`); a `plan` that is neither word is refused, `owner-alone`, which this release does not carry out, among them. The per-tree `memory` block is still `legion.yaml`'s `projects.<KEY>.memory`, read by `internal/config/memory.go` onto `config.Project.Memory` with its own reader and its own `checkMemory`, and it is the experiment named `memory`: `config.Project.ExperimentsDeclared` maps it to one of unit `tree`, mode `Memory.Word`, `on_variant: memory`, and the two arms `memory` (weight 1, the block's `config_files` and `instructions`) and `none` (weight 1, neither), first in the list and the `experiments` key's own after it in the file's order. Every reader below the loader asks that one method, so the block and the key behave alike and no reader needs a second path for the block. Every project declares that experiment, whatever it writes: a project writing `experiments.memory` declares it at that key's own mode, and a project writing neither the block nor `experiments.memory` declares it at mode off, whose draw records each new tree at no arm, which is what the daemon has recorded for every tree of such a project since the memory draw existed, and is what keeps the three memory fields such a tree answers — `memoryGroup` `none`, `memoryDrawMode` `off` and the instant of the draw — exactly where they are. The one project it is not added to is the one declaring `experiments.memory` itself, the other spelling of that one experiment, whose own block is then the whole declaration. `checkExperimentMemory` refuses four shapes of `experiments.memory` that the name `memory` forbids and every other name of the key allows: a project writing the block and `experiments.memory` both, since that is one experiment spelled twice; an `experiments.memory` whose arms name `plan`, since its draw is the tree's memory group and never says how an issue is done, which it refuses before the other rules of `plan` (`checkExperimentPlans`, `checkExperiments`) are checked, so the file is told this and not to write `unit: issue` (the rules of the word itself, a word that is neither `owner` nor `default` and `owner-alone`, are checked earlier, as each arm is read, by `readVariants`); an `experiments.memory` whose arms are not exactly `memory` and `none`, whose draw rides to every pod as the issue state's `memoryGroup`, a `z.enum(["memory","none"])` that any other word makes fail to parse; and an `experiments.memory` whose unit is not `tree`, since that draw rides as `memoryGroup`, `memoryDrawMode` and `memoryDrawnAt`, which are the draw of the issue's tree, one answer for every issue of it. `checkExperiments` refuses, once the rest of the file is settled, an arm that names `config_files` while `worker_backends` puts an issue role on a harness other than Oh My Pi (which reads no `PI_CONFIG_FILES`) and, under `runtime: kubernetes`, an arm's overlay outside every `runtime.kubernetes.pod` mount (`checkRoleConfigMount`, the role overlays' own check); `internal/daemon`'s `checkRoleConfigFiles` refuses under tmux an overlay of any declared arm no pane could read, and `readBoot` an arm's `instructions` file it cannot read or that holds nothing. None of those reads the mode: the launch follows the record, so a unit already drawn into an arm names that arm's files under any mode, and only taking the arm out of the file takes them away. `checkMemory`'s own third rule, that a mode other than off must name `config_files`, stays the block's alone and is asked of no arm, because an experiment's control arm names no overlay by design. `internal/config/keytable.go` holds the line of every key of both, which `legion config reference --json` prints and the documentation site's configuration reference is generated from.

The arm a unit runs under is drawn once, by `internal/experiment`'s `Draw` (`off` gives the empty variant, so the unit is recorded as drawn for at no arm; `on` gives `on_variant`; `random` takes one value below the arms' total weight from `experiment.CryptoSource`, `crypto/rand` over the operating system's own source and never a seeded sequence, and walks the arms' cumulative weights in the file's order; a mode the switch does not know is refused, which only a programming error reaches, since the loader takes three words). The package implements none of GrowthBook's hashing and depends on nothing of it: that hashing earns its keep where no durable record of a draw is kept, and this daemon writes the answer in the transaction that opens the unit and reads it back at every launch. A tree experiment is drawn at the one moment a tree's lifecycle row is first created (`treelifecycle.Lifecycle.Created`), inside that row's own transaction, on both paths that open a tree: admission's `promoteHolds` and the operator's spawn, whose draw `internal/api`'s `drawExperiments` runs inside `store.Store.OpenOperatorTreeLifecycle`. An issue experiment is drawn where the daemon first records the issue — admission's `putNewRoot` for a root or an orphan, the workflow engine's own `drawExperiments` for a child — so every issue the daemon records is drawn for as it records it. `record.Store.PutAssignments` writes one `experiment_assignments` row per answer — the issue key, the experiment, the unit, the arm, the arm's `plan` where the arm drawn names one (no `plan` under mode `off`, which draws no arm), the mode in force and the instant — under `on conflict (issue_key, experiment) do nothing`, and nothing ever updates a row, so a re-admission, a new generation, `ClearTreeGeneration` and the next epoch after a cleanup all keep the draw, and an experiment a unit has been running under keeps its arm and its `plan` whatever the project's file says by now; the workflow's first step and its refusals of `register_plan` and `stop_task` read the group from that row (`groupOf`), never from the file. Both writers guard on the issue's own record, which their inserts select from, so a key the daemon holds no record of writes no row and raises nothing. `readmit` settles a handed-over child's assignments at the hand-over (`CarryAssignments`): first every assignment row of unit `tree` of the old tree's root, copied onto the child with its arm, its mode and its instant verbatim and the `carried` mark set, so the work goes on under the arms it has been running under, while a row of unit `issue` of the old root is that issue's own answer and is not copied; then each experiment declared at the hand-over written at no arm, no mode and no instant under the same write-once insert, which lands only where the copy left that experiment unwritten and is never drawn for later. The carry's driver row is the old tree's `tree_lifecycles` row, matched on the tree and the normalized runtime token, since `tree_lifecycles.project` is that token while `issues.project` is the Dispatch key; the only issue record either insert joins is the child's own, never the old tree's root, since the copy reads the old root's assignment rows themselves, so an operator's tree the daemon recorded no root for, which holds no such row, hands over the settled rows alone. A tree with no such row was never opened, so the carry writes nothing and the child's own first open draws it like any other new tree, and a unit opened before an experiment was declared holds no row for it and runs in no arm of it. `20261111045636_experiment_assignments` created the table and back-filled it from the four `issues.memory_*` columns — every root holding a draw or the carried mark takes one `memory` row of unit `tree` with its mode, instant and mark verbatim and its group as the variant, but for one normalisation: a group drawn under mode `off`, which the column holds as the word `none`, becomes the empty variant — so no tree drawn before the deploy loses its exposure; those four columns stay in the schema, are written by nothing from this release on, and a later release drops them.

At launch the arms are the unit's: `internal/daemon`'s `launchVariants` reads the unit's rows in a transaction and hands them to `internal/experiment`'s `Launch`, which answers, for each experiment the project declares in the file's order, the arm recorded for the unit that experiment covers — the issue's tree root for a tree experiment, the issue itself for an issue experiment (`record.Store.AssignmentsFor`, over the daemon's own store in a transaction of its own, so a tree the operator's spawn drew with no workflow configured is launched with the arm it drew) — and `specs` sets `runtime.SpawnSpec.Variants` and `PromptParts.VariantInstructionsPaths` on a worker spawn alone. It reads nothing at all where no declared arm names a `config_files` or an `instructions` path: such an experiment contributes nothing to a launch whichever arm its unit drew, so the deployment that declares only the memory experiment at mode off — the one a project writing no `memory` block and no `experiments` key declares — pays no transaction per worker spawn, and the issue's own key is read beside its tree's only where some declared experiment's unit is the issue. A unit with no row for an experiment, and one whose recorded arm the file no longer names, contributes nothing and runs as a unit in no experiment does; its row stays, so naming the arm again gives the unit the arm it drew. Both runtimes then name each arm's overlays after the operator's own overlays and the role's own in `PI_CONFIG_FILES`, in that same declared order, so an arm's file outranks both (`runtime.VariantOverlays`, `tmux`'s `panePairs`, `sandbox`'s `launch.overlays` through `roleOperatorEnv`), and end the system prompt, the file the one `--append-system-prompt` names, with the daemon's own copies of those arms' instructions, after the deployment's own. Boot reads each arm's file and writes its copy at `config.VariantInstructionsFile` with `config.WriteVariantInstructions`: the `memory` block's own arm (`config.Variant.MemoryBlock`) is read by `config.ReadMemoryInstructions` and copied to `<state_dir>/memory-instructions.md`, the name and the `# Memory instructions` header that copy had before any experiment was declared, and every arm of the `experiments` key, `experiments.memory`'s included, is read by `config.ReadVariantInstructions` and copied to `<state_dir>/experiments/<experiment>/<variant>.md`. Each launch reads every arm's file, and the deployment's own `instructions`, again first (`internal/daemon`'s `instructionsCopies`, which `specs.SpawnSpec` refreshes) and replaces a copy whose file changed, so an edit reaches the next launch with no restart; a file that no longer reads keeps the copy last read, and the daemon logs that once for each refusal. The daemon reads each copy into the prompt it composes (`runtime.ComposePrompt`), so neither a pane nor a pod reads the copy itself. `controllerSpawnSpec` sets neither and `validateControllerShape` refuses either, because a unit is a tree or an issue and the controller runs in neither, and an arm with no `instructions` appends nothing. A launch that keeps a live pod is told only the arm overlays that pod holds (`heldRoleOverlays`, read from the pod's own stored template), because Oh My Pi refuses to start on an entry that is not there and a role that never starts never answers the round that is to replace the pod: a pod built before an arm's mount existed starts its role in neither arm — not the control, which names no file, and not the drawn arm, whose file it cannot read — and `launch.overlays` logs that once, naming the issue, the role, the experiment, the arm and the files it dropped. The drift itself is `movedRoleOverlays`, which reads every declared arm's overlays against every issue pod of the deployment, since any unit may be drawn into any arm, and names the move by what the arm itself carries onto `runtime.Variant` from `config.Project.ExperimentsDeclared`: the `memory` block's own arm (`runtime.Variant.MemoryBlock`) as `memory.config_files <file>`, the spelling that drift had before any experiment was declared, and an arm of the `experiments` key, `experiments.memory`'s included, by the whole key the operator wrote for its `config_files` (`runtime.Variant.ConfigFilesField`), `projects.<KEY>.experiments.<experiment>.variants.<variant>.config_files <file>`; the controller's pod is moved by none of them. Every issue of the state carries the answers that apply to it (`internal/projection`, `api.Issue.Assignments`, daemon API contract 141), the declared ones in their declared order and then any the file no longer names, by name, with the three contract-49 memory fields read off the `memory` answer alone and only where it records a draw, and `legion state` prints one line per declared experiment counting the issues drawn each arm, on the same rule: a row that records no draw, which is a hand-over settling a unit at no arm, is counted in no line, for every experiment. Every project declares at least the memory experiment, so there is always a line, and a deployment that has drawn nothing yet reads `memory: none`. It counts issues and not trees because each issue's answers are its tree's tree-unit rows and its own issue-unit rows (`internal/projection`'s `assignmentViews`), so one count serves an experiment of either unit; a count of trees would fit a tree experiment alone and would not count draws even there, since a child handed over as a tree of its own becomes its own tree's root (`internal/admit`'s `readmit`) and carries its old tree's tree-unit rows verbatim, arm, mode and instant (`record.Postgres.CarryAssignments`), so two trees hold one draw.

An experiment's `roles` (`readExperimentRoles`, onto `config.Experiment.Roles`) names the Legion issue roles (`claim.Roles`) whose launches load its arms, each once; the controller, a role named twice and an empty list are refused, and a block naming none reaches every issue role (`config.Experiment.Reaches`). `Launch.Arms` takes the launch's role and passes over each experiment that does not reach it, so a launch of a role an experiment leaves out runs in no arm of that experiment while its unit keeps its row and its arm; the operator's and the role's own overlays, and the arms of other experiments that reach the role, still apply. An experiment can so leave the roles that judge the work, such as the reviewer, the tester and the architect who accepts it, out of its arms, and read their verdicts as its outcome. `experiment.arm` carries the list onto `runtime.Variant.Roles`, and `runtime.RoleOverlayValues` passes over an arm for a role it does not reach (`runtime.Variant.Reaches`), so the boot gate and the image probe read only the tails a launch can start on; `checkDeclaredOverlays` asks for Oh My Pi only on the roles an experiment reaches. The draw, the record, the mount check and the pod drift read every declared arm whatever `roles` says, as they read every arm whatever the mode is: every issue pod mounts every arm's files, since any of its roles may be reached. `settings.projects.<KEY>.experiments[].roles` carries the list as the file writes it, absent where the block names none.

The role prompts the daemon hands every worker are embedded under `internal/prompts/roles` and snapshotted below the state directory at boot (`prompts.New`), so a role's own prompt is this repository's text, which no deployment replaces; a deployment's text follows it in that same `--append-system-prompt` value, its `instructions` and each drawn arm's own (above). The planner's names the one write that replaces a plan whole: an upload of `plan.md` over a plan the issue already holds replaces every word of it, so the prompt has the planner read the plan with `dispatch doc-read`, upload with `--force --precondition-json` naming the document token that read prints, `--force` being what the prompt writes for a name the issue already holds, and read and decide again when a token behind the live plan is refused `409 PRECONDITION_FAILED`; changing part of a plan the issue already holds is a `dispatch doc-edit` and not an upload.
