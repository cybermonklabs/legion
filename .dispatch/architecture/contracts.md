The language-neutral source of truth for event envelopes, subjects, the Dispatch API types (among them `SearchAsk`, the answer state a search hit for an ask carries), and the Dispatch specs the `dispatch` command is built from. `packages/envoy/internal/contracts` is the Go package `bun run gen:go` writes from it; `cmd/listener`, `internal/bus`, `internal/cistore`, `internal/session`, `internal/store`, `internal/mcpbridge` and `internal/dispatch/outbox` import that package directly, so it belongs to this component even though it sits inside `packages/envoy`.

It holds the related-item check's result types (`Suggestions` with its outcome and search mode, `SearchAsk`, `DecisionBlockCheck`, `RelatedChecksReport`) and the `dispatch_related` spec, which runs the check on a text without writing anything. `Suggestions` has no `decision` field, and `WriteSuggestion` no `answered_by` and no `answered_at`. It holds the items of the project the check searched (`related`) and, for a write that asks a person a question, `other_projects`. That field holds at most two answered question asks of other projects, and each item names in its owner the project it belongs to. `RelatedChecksReport` carries `other_project_offers` too, the writes of a window that offered such a question. The `dispatch_related` spec's description tells an agent what the tool lists, and it claims no past decision.

It also holds the refusal codes the server and every client must spell alike, among them `DISPATCH_SIGN_IN_REQUIRED` (`SIGN_IN_REQUIRED`), the `403` for a write by an access token the secrets broker issued that names a session and a service but no person and whose project scope is neither `named` nor `public`, which today is a machine's `person` token: a job's token, under `named` or `public`, and an exchange account entry's token naming no person, under `named`, write. `bun run gen:go` writes it into the Go package as `contracts.DispatchSignInRequired`, as it does `DISPATCH_LOGIN_CHANGED`, so the server's refusal and a client's reading of it cannot drift apart. `DISPATCH_READ_ONLY_TOKEN` (`READ_ONLY_TOKEN`) is another: the `403` for a request by a read-only token, any token that holds `read`, a broker's or a personal one, to a route outside Dispatch's read class. `DISPATCH_AS_OF_TOKEN_NOT_SERVED` (`AS_OF_TOKEN_NOT_SERVED`) is the `403` for a read-only token that carries a cut, on every read but `GET /api/v1/whoami`. `bun run gen:go` writes them into Go as `contracts.DispatchReadOnlyToken` and `contracts.DispatchAsOfTokenNotServed`. `DISPATCH_TOKEN_SCOPES` (`src/dispatch-api-core.ts`) is the words a token's scopes can hold where they are listed, the agent token list and `GET /api/v1/whoami`'s `scopes`: `person`, `approve`, `p0` and `read`. `DISPATCH_SCOPES` and `ActorActSchema` keep `person`, `approve` and `p0` alone, since `read` marks a token and is no scope an act records. `p0` is the scope that a priority of 0 on `POST /api/v1/issues` and `PATCH /api/v1/issues/{key}` needs when the write makes the issue's own priority 0: a browser sign-in holds it, a personal token holds it only where its maker gave it, no mint gives it by default, and no broker-issued token, shared token or service-account token holds it. A credential without it is refused `403 OAUTH_SCOPE_REQUIRED` naming `p0`. The descriptions of the `priority` field of `dispatch_issue` and `dispatch_issue_update` say so, and the `dispatch` command prints them in its help. `WhoamiAgent` carries `cut`, the past time a read-only credential reads at, null for none. The OpenAPI document `schemas/dispatch-openapi.json` describes `GET /api/v1/whoami` from Dispatch's route table: for a job's token `owner` is null, `service` is the identity its job entry lists, and `project` is the entry's one project for a `named` token and null for a `public` one.

`src/dispatch-api-events.ts` holds each event type of the `EventType` union once, in a record over the union (`EVENT_TYPE_MEMBERS`), so the compiler refuses a type left out of it and a key that is no type.
From it come `DISPATCH_EVENT_TYPES`, the types sorted, and `isEventType`, whether a string names one of them, which Dispatch's web client reads to narrow a frame's `type` (`packages/dispatch/web/src/api/event-feed.ts`).
`bun run gen:go` writes the list into the Go package as `contracts.DispatchEventTypes`, which the keyword fill's rules are held to: each type has a rule or a reason it changes no searchable text (`textversions`, `TestEveryEventTypeIsSortedForTheKeywordFill`).

`LegionIssueResponse`, generated from the OpenAPI document into `src/dispatch-api.generated.ts`, is the body of `GET /api/v1/issues/{key}/legion`: `{issue, project, configured, state, read, runs_revision}`, with `configured` a required boolean.
`src/dispatch-api-live.ts` names the live view of that body: the kind `legion_issue` of `DeliveryLiveView`, which names one issue and nothing else, and `LegionIssueResponse` in `DeliveryLiveBody`, the union of the bodies a delivery view's snapshot and deltas carry.
Dispatch never refuses such a view for a project that names no daemon: its body says `configured` `false`.
Its `state.waiting_on` is `LegionIssueWaitingOn`, `{kind, ask, artifact_id, gate_version, since, answered_at, answered_by}`, generated from the Go type that names those members, and not the daemon's camelCase object.

`HandoffBodies` and `HandoffBody` are the body of `GET /api/v1/issues/{key}/handoffs/bodies`.
Its two limits are constants of `src/dispatch-api-limits.ts`, `HANDOFF_BODIES_MAX_IDS` (20) and `HANDOFF_BODIES_MAX_BYTES` (1,048,576), which `bun run gen:go` writes into the Go package as `contracts.HandoffBodiesMaxIDs` and `contracts.HandoffBodiesMaxBytes`, so the route's refusal and the page's batches are one number.
`build:dispatch` builds `src/legion-api.ts` too, because the dashboard imports it: `features/issue-page/legion-block.ts` its `LegionPhase` and `LegionClaimState` types, and `legion-words.test.ts` its lists `LEGION_PHASES` and `LEGION_CLAIM_STATES`.

Its `fixtures/daemon-api/` goldens are the daemon's own state answer, written by `packages/daemon/internal/api`'s golden test: `settings.repository_renames` is among them, the `{from, to}` pairs a deployment tells the daemon to treat as one repository, `[]` when it configures none. `src/legion-api.ts`'s `legionSettings` stays loose, so a new settings key needs no schema change.

The Legion daemon's state lane is a contract here too (dispatch://INFRA-3931). `src/subject.ts`'s `legionStateSubject(token)` is its subject, `notifications.legion.<token>.state` (`LEGION_STATE_SUFFIX`, in the `Subject` union as `LegionStateSubject`), and `bun run gen:go` writes it into Go as `contracts.LegionStateSuffix` and `contracts.LegionStateSubject`. The daemon's `notify.StateTopic` and the Go builders are held to it through the `legionStateSubject` row of `fixtures/subject-project.json`'s `builders`. `src/legion-api.ts`'s `legionStateMessage` is one message of the lane: the state events of one committed daemon transaction, with `project`, `run`, `firstSeq`, `seq` and `at`, each event a `change`, an `admission` or a `boot` with its own `seq`, and the events running from `firstSeq` to `seq` with no gap. The daemon block of the state answer carries `stateSeq` (daemon API entry `20261125174131` state-seq), the sequence of the last state event that answer's snapshot holds. It is optional, because a daemon before that entry serves none and the route takes it out of the answer for a caller below the entry's number. `fixtures/daemon-api/state-events.json` is the daemon's golden of the lane, each step's messages beside the state it served: `packages/daemon/internal/daemon`'s `TestStateEventsGolden` writes it, `src/legion-api.test.ts` parses each message with `legionStateMessage`, and Dispatch's `TestEventsWriteTheRowsAWholeReadOfTheSameStatesWrites` applies it.

`src/legion-api.ts`'s `legionIssue` is a `z.object`, which strips a key it does not name rather than refusing the body, so a field the mirror lacks costs a reader that field and nothing else; the state's memory fields are mirrored there all the same: `memoryGroup` (`memory` or `none`), `memoryDrawMode` (`off`, `on` or `random`) and `memoryDrawnAt`, each optional and absent together while nothing has drawn for the issue's tree (daemon API contract 49). The `memory` block a project's settings carry needs no schema change, since `legionSettings` stays loose, and the `fixtures/daemon-api/` goldens carry both.

`dispatch_artifact` takes a `precondition` of its own, the document token alone, built by `uploadPreconditionArgument` in `src/dispatch-tools.ts`, apart from `dispatch_doc_edit`'s `preconditionArgument`, which also takes `blocks`: an upload rewrites the whole tree, so only the document token says which version it replaces, and the server refuses a `blocks` guard on one `400 INVALID_PRECONDITION`. `CreateArtifactOptions.precondition` carries it to the upload route as `UploadPrecondition`. `EditPreconditionCurrent.version` is the live version number a `409 PRECONDITION_FAILED` carries where its caller read that number beside the write it refused, which an upload's does and an edit's does not. `WriteAdvice.standing_review` is the review a question's issue already carries on its specification, set only on a question opened on an issue: who reviewed, when, whether they approved or asked for changes, the version the review is pinned to, the first 500 characters of their reason, and whether Dispatch carried the review forward and from which version.
