The language-neutral source of truth for event envelopes, subjects, the Dispatch API types (among them `SearchAsk`, the answer state a search hit for an ask carries), and the Dispatch specs the `dispatch` command is built from. `packages/envoy/internal/contracts` is the Go package `bun run gen:go` writes from it; `cmd/listener`, `internal/bus`, `internal/cistore`, `internal/session`, `internal/store`, `internal/mcpbridge` and `internal/dispatch/outbox` import that package directly, so it belongs to this component even though it sits inside `packages/envoy`.

It holds the related-item check's result types (`Suggestions` with its outcome and search mode, `SearchAsk`, `DecisionBlockCheck`, `RelatedChecksReport`) and the `dispatch_related` spec, which runs the check on a text without writing anything. `Suggestions` has no `decision` field, and `WriteSuggestion` no `answered_by` and no `answered_at`. It holds the items of the project the check searched (`related`) and, for a write that asks a person a question, `other_projects`. That field holds at most two answered question asks of other projects, and each item names in its owner the project it belongs to. `RelatedChecksReport` carries `other_project_offers` too, the writes of a window that offered such a question. The `dispatch_related` spec's description tells an agent what the tool lists, and it claims no past decision.

It also holds the refusal codes the server and every client must spell alike, among them `DISPATCH_SIGN_IN_REQUIRED` (`SIGN_IN_REQUIRED`), the `403` for a write by an access token the secrets broker issued that names a session and a service but no person and whose project scope is neither `named` nor `public`, which today is a machine's `person` token: a job's token, under `named` or `public`, and an exchange account entry's token naming no person, under `named`, write. `bun run gen:go` writes it into the Go package as `contracts.DispatchSignInRequired`, as it does `DISPATCH_LOGIN_CHANGED`, so the server's refusal and a client's reading of it cannot drift apart. `DISPATCH_READ_ONLY_TOKEN` (`READ_ONLY_TOKEN`) is another: the `403` for a request by a read-only token, any token that holds `read`, a broker's or a personal one, to a route outside Dispatch's read class. `DISPATCH_AS_OF_TOKEN_NOT_SERVED` (`AS_OF_TOKEN_NOT_SERVED`) is the `403` for a read-only token that carries a cut, on every read but `GET /api/v1/whoami`. `bun run gen:go` writes them into Go as `contracts.DispatchReadOnlyToken` and `contracts.DispatchAsOfTokenNotServed`. `DISPATCH_TOKEN_SCOPES` (`src/dispatch-api-core.ts`) is the words a token's scopes can hold where they are listed, the agent token list and `GET /api/v1/whoami`'s `scopes`: `person`, `approve` and `read`. `DISPATCH_SCOPES` and `ActorActSchema` keep `person` and `approve` alone, since `read` marks a token and is no scope an act records. `WhoamiAgent` carries `cut`, the past time a read-only credential reads at, null for none. The OpenAPI document `schemas/dispatch-openapi.json` describes `GET /api/v1/whoami` from Dispatch's route table: for a job's token `owner` is null, `service` is the identity its job entry lists, and `project` is the entry's one project for a `named` token and null for a `public` one.

`src/dispatch-api-events.ts` holds each event type of the `EventType` union once, in a record over the union (`EVENT_TYPE_MEMBERS`), so the compiler refuses a type left out of it and a key that is no type.
From it come `DISPATCH_EVENT_TYPES`, the types sorted, and `isEventType`, whether a string names one of them, which Dispatch's web client reads to narrow a frame's `type` (`packages/dispatch/web/src/api/event-feed.ts`).
`bun run gen:go` writes the list into the Go package as `contracts.DispatchEventTypes`, which the keyword fill's rules are held to: each type has a rule or a reason it changes no searchable text (`textversions`, `TestEveryEventTypeIsSortedForTheKeywordFill`).

`LegionIssueResponse`, generated from the OpenAPI document into `src/dispatch-api.generated.ts`, is the body of `GET /api/v1/issues/{key}/legion`: `{issue, project, configured, state, read, runs_revision}`, with `configured` a required boolean.
`src/dispatch-api-live.ts` names the live view of that body: the kind `legion_issue` of `DeliveryLiveView`, which names one issue and nothing else, and `LegionIssueResponse` in `DeliveryLiveBody`, the union of the bodies a delivery view's snapshot and deltas carry.
Dispatch never refuses such a view for a project that names no daemon: its body says `configured` `false`.

Its `fixtures/daemon-api/` goldens are the daemon's own state answer, written by `packages/daemon/internal/api`'s golden test: `settings.repository_renames` is among them, the `{from, to}` pairs a deployment tells the daemon to treat as one repository, `[]` when it configures none. `src/legion-api.ts`'s `legionSettings` stays loose, so a new settings key needs no schema change.

`src/legion-api.ts`'s `legionIssue` is a `z.object`, which strips a key it does not name rather than refusing the body, so a field the mirror lacks costs a reader that field and nothing else; the state's memory fields are mirrored there all the same: `memoryGroup` (`memory` or `none`), `memoryDrawMode` (`off`, `on` or `random`) and `memoryDrawnAt`, each optional and absent together while nothing has drawn for the issue's tree (daemon API contract 49). The `memory` block a project's settings carry needs no schema change, since `legionSettings` stays loose, and the `fixtures/daemon-api/` goldens carry both.

`src/going.ts` holds the command bar's stream vocabulary, which `bun run gen:go` writes into the Go package (`contracts.GoingEvent*`, the error codes and the bounds) for `packages/envoy/going` and the API to import. Beside the answer's frames (`text`, `item`, `cut`, `changed`, `none`, `end` and `error`) it holds three more. `decision` (`GoingDecisionEvent`) is the stream's first frame where a measured decision model answered: the action it chose, the line on top of the bar that action gives (`GoingLine`: `ask`, `do` or `file`), and the context (`GoingDecidedContext`: `page`, `named` or `none`). `block` (`GoingBlockEvent`) is one of seven kinds (`GoingBlockKind`), with a spec that names the read filling it (`GoingBlockSource`: `source`, `params` and `table`) and the fields it draws but never a number, and the rows the server's own read answered. `roster` (`GoingRosterEvent`) is `{age_ms, source}`, where `source` is `live` or `stored`. The request and response shapes of the going routes - the capability read, a run of the bar's agent (`POST /api/v1/going/runs`, its read and its stop), its plan and the person's answer to it (approve, revise, reject), the undo of a run, History (`GET /api/v1/me/going-runs`), the plans that wait in the Inbox (`GET /api/v1/me/going-plans`) and the person's `mode` - and of `GET /api/v1/projects/{key}/activity` are reflected from the Go route table into `schemas/dispatch-openapi.json` and rendered into `src/dispatch-api.generated.ts`, as every route's shapes are.

`src/dispatch-route-tools.ts` holds a tool spec for each route a person can call that no hand-written spec of `src/dispatch-tools.ts` calls, and for four routes a hand-written spec also reads, each carrying its route binding (`DispatchToolSpec.routes`: the method, the path pattern, and which arguments fill the path, go in the query and go in the JSON body), and `personToolSpecs`, the tools the command bar alone calls, which no `dispatch` command offers. `scripts/gen-go-tools.ts` writes each binding into Go as `contracts.DispatchTool.Routes` (`contracts.ToolRoute`), so the server runs every tool that carries one through one generic translation (`goingTranslateBound`) and `@legion/envoy-client` serves each with one generic command; the server's command-bar tools are built from these specs. Of `personToolSpecs`, `dispatch_hand_ask` carries its binding and `dispatch_set_issue_state` carries none: its route replaces the person's whole list of an issue's pinned and dismissed items, so the server's own translation (`goingTranslateIssueState`) reads that state first, and its row is `goingWriteTools`' own. `ActorAct` carries `agent` and `run` (`ActorActSchema` in `src/dispatch-api-core.ts`), the command bar and the run a change of a person's was made in, which `actorActText` (`src/actor-label.ts`) reads as "<person>, through the command bar". `going_plan.updated` (`GoingPlanUpdatedEventPayload`, `{login}`) says that what one person's command-bar plans wait on changed; it names no owner and never notifies.

`scripts/gen-go-tools.ts` also writes each argument of every tool spec into Go as a `contracts.ToolField`, with the bounds its schema states in `Min` and `Max` (a text's length in UTF-16 units, a list's count of items, a number's value), and the whole words of the cross-field rule a spec states beside its arguments (`DispatchToolSpec.validation`) as `contracts.DispatchTool.Validation`. The server's command bar holds a call to both wherever it holds it to its tool's schema, when a plan is proposed, approved and run: each bound (`checkGoingValue`), and each write tool's rule by a Go port of it (`goingToolRules`, `internal/dispatch/api/going_tool_rules.go`), worded as the spec words its refusal. `TestEveryWriteToolsRuleIsPortedOnce` holds the ports to the marks: one for each write tool whose spec states a rule, and none for any other tool, so a rule a spec gains or loses fails that test until the Go follows. A read tool's rule has no port, since no read of the bar is held to its tool's schema.

Every tool spec also carries a required `label` (`DispatchToolLabel`, `src/dispatch-tools.ts`), the words the command bar shows for one call of the tool: its `kind`, one of `DISPATCH_TOOL_LABEL_KINDS` (`read`, `search`, `look`, `chart`, `plan`, `review` or `write`), by which the bar counts and folds a run's steps; its base `verb`, which the words of a call that failed use ("Could not read DSP-12"); a `present` form shown while the call runs and a `past` form shown once it ended, such as "Reading {issue}" and "Read {issue}", each naming an argument as `{name}` and an argument a call may leave out as `{name|the words shown in its place}`; and, for a tool that answers a list, the noun its results are counted by (`count`). `dispatchToolLabelProblems` says what is wrong with a spec's label, and `scripts/gen-go-tools.ts` writes each label into Go as `contracts.DispatchTool.Label` (`contracts.ToolLabel`), which the agent process fills from each call's arguments into the words of that step (`going/agent/labels.go`), so the bar names no tool and shows no JSON.

`dispatch_artifact` takes a `precondition` of its own, the document token alone, built by `uploadPreconditionArgument` in `src/dispatch-tools.ts`, apart from `dispatch_doc_edit`'s `preconditionArgument`, which also takes `blocks`: an upload rewrites the whole tree, so only the document token says which version it replaces, and the server refuses a `blocks` guard on one `400 INVALID_PRECONDITION`. `CreateArtifactOptions.precondition` carries it to the upload route as `UploadPrecondition`. `EditPreconditionCurrent.version` is the live version number a `409 PRECONDITION_FAILED` carries where its caller read that number beside the write it refused, which an upload's does and an edit's does not. `WriteAdvice.standing_review` is the review a question's issue already carries on its specification, set only on a question opened on an issue: who reviewed, when, whether they approved or asked for changes, the version the review is pinned to, the first 500 characters of their reason, and whether Dispatch carried the review forward and from which version.
