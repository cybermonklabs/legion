The row and read shapes the API and the document service share (`model`, a search hit and the answer state of an ask hit among them), plus three small packages that travel with them: ask-follower bookkeeping (`asks`, whose `QueueFollowAuthor` puts the follow on a writer's write-phase batch, `store.WriteBatch`), fractional rank allocation (`rank`), and actor identity resolution with the sign-in pool's membership check, which names every person by lowercase email (`identity`, which imports `auth` and the listener's `oidc`). None is large enough to be its own component, and the bugs they produce — a rank collision, a missed follower, an ask read through the wrong columns — surface across every caller at once.

`model` carries the related-item check's result (`Suggestions`: its outcome, how it searched, the search words, the related items with each ask's answer state as `SearchAsk`, the near copies a `--force` create went past, and the likely duplicate an unforced one is told) and the records route's report (`RelatedChecksReport`). `Suggestions` also carries `OtherProjects`, which rides beside `Related`: for a write that asks a person a question, the answered questions of other projects that stand nearest to it in meaning. Each such item names its project in `Owner.Project`, which the one-project items fill for a document owner alone. `Suggestions` has no `Decision` field, and `WriteSuggestion` no `AnsweredBy` and no `AnsweredAt`. `RelatedChecksReport` carries `OtherProjectOffers`, the writes of the window that offered such a question, which the records route reads from `write_suggestions` and not from `related_checks`.

`model.Credential` carries `ReadOnly`, which is true for a broker token that holds only the OAuth scope `read`. That scope is not among `Credential.Scopes`, which are the scopes a route can require. Dispatch's read-only gate reads the mark, and serves such a credential on the routes of its read list alone. It also carries a broker token's `ProjectScope` as the broker answered it, which is how the sign-in check tells an account entry's token naming no person (`named`, whose writes are recorded under its account) from a machine's nobody signed in on (`person`, which writes nothing).
