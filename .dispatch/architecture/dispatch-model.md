The row and read shapes the API and the document service share (`model`, a search hit and the answer state of an ask hit among them), plus three small packages that travel with them: ask-follower bookkeeping (`asks`, whose `QueueFollowAuthor` puts the follow on a writer's write-phase batch, `store.WriteBatch`), fractional rank allocation (`rank`), and actor identity resolution with the sign-in pool's membership check, which names every person by lowercase email (`identity`, which imports `auth` and the listener's `oidc`). None is large enough to be its own component, and the bugs they produce — a rank collision, a missed follower, an ask read through the wrong columns — surface across every caller at once.

`model` carries the related-item check's result (`Suggestions`: its outcome, how it searched, the search words, the related items with each ask's answer state as `SearchAsk`, the near copies a `--force` create went past, and the likely duplicate an unforced one is told) and the records route's report (`RelatedChecksReport`). `Suggestions` also carries `OtherProjects`, which rides beside `Related`: for a write that asks a person a question, the answered questions of other projects that stand nearest to it in meaning. Each such item names its project in `Owner.Project`, which the one-project items fill too: a document owner's from its row, and an issue owner's from its key. `Suggestions` has no `Decision` field, and `WriteSuggestion` no `AnsweredBy` and no `AnsweredAt`. `RelatedChecksReport` carries `OtherProjectOffers`, the writes of the window that offered such a question, which the records route reads from `write_suggestions` and not from `related_checks`.

`model.Credential` carries `ReadOnly`, which is true for every credential that holds the OAuth scope `read`: a broker token from a read entry or from a trade that asked for `read`, and a personal token minted with `read`. It also carries `Cut`, the past time a read-only credential reads at, the zero time for none. `read` is not among `Credential.Scopes`, which are the scopes a route can require. `model.ScopeRead` is the word that marks a read-only credential: `GET /api/v1/whoami` lists it after the scopes, and a read-only personal token's set holds it, which the token mint takes, `agent_read_tokens.scopes` keeps, the token list names and the token's scope change refuses. Dispatch's read-only gate reads the mark and the cut, and serves such a credential on the reads of its read class alone. It also carries a broker token's `ProjectScope` as the broker answered it, read as its base word, which is how the sign-in check tells an account entry's token naming no person (`named`, whose writes are recorded under its account) from a machine's nobody signed in on (`person`, which writes nothing); a read-only credential is neither, since it writes nothing.

`model.ActorAct`, which names the agent that made an act for its person, names Dispatch's own agent where the command bar made the act: `Agent` is `ActAgentCommandBar` and `Run` the command-bar run whose call it was, beside the scopes of the credential the run acts with (a sign-in's every scope, a personal token's own) and that token's id and name (`api/going_grant.go`). Both are empty on every other act, only the server sets them, and `@legion/contracts`' `actorActText` reads such an act as the person, through the command bar. `GoingPlanEventPayload` is the payload of `going_plan.updated`, a change of what one person's command-bar plans wait on: it names the person's login and nothing of the plan, and since a run belongs to no issue, document or project, the event names no owner (`dispatch-events`).
