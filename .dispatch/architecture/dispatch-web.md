The React single-page application: Inbox, project Architecture tree, List and Board, issue pages with Spec/Conversation/Children/Artifacts, the document editor, the search palette, which marks each ask hit with its answer state, the new-issue dialog, which lists the related items the no-write check finds for the title being typed, Settings, and the Architecture sources section in Settings.

Settings also lists **Sign-ins**, the machines the viewer has signed in on with `agent-secrets login` and has not revoked, each revocable from there and nobody else's; it sits on Settings rather than on the credential page because `/credentials/machine` is itself conditional. That page is served only while the broker still serves RFC 8628's device grant, which is the only thing that makes a machine print a code: the browser reaches no broker, so it reads the one fact Dispatch relays from the broker's own metadata (`GET /api/v1/credentials/capabilities`), and a false answer renders the not-found page and leaves the Inbox's machine-login row unlinked. No Dispatch setting says any of this.

An upload from the browser names the token of the version it replaces, read when the person chooses the file. `captureUploadBase` (`features/artifacts/ArtifactUpload.tsx`) reads the token of the document the owner already holds under the name being uploaded, through the route that resolves a slug or a filename (`api/client.ts`'s `ownerArtifactText`), and the press sends it as the upload's `precondition`. So the window this guards runs from the choice of the file to the post: a write landing in it is refused `409 PRECONDITION_FAILED` rather than written over, and a change made before the file was chosen is replaced with no refusal, since the upload names what the document said at the choice. Reading the token from the open document instead, and holding it while the person reads, would guard nothing more: the document view is a live room, so the text in front of that person is the current one by construction. The token is read once for the press and every attempt of that press sends it, because Dispatch's idempotency key digests the whole body, the `precondition` field included (`bodyDigest` in the server's `api/request_keys.go`): an attempt that read the token afresh would send other bytes and be answered `422 KEY_REUSED` instead of what the first attempt did. A press after Dispatch has decided one reads the token again, so pressing Upload after a refusal names what the document says now, under a key of its own.

It names no token only where there is none to name: a conversation, which holds files and images and no document; a file whose media type is not `text/markdown`, parsed as the server parses it (`mime.ParseMediaType` in `artifactKind`, so `text/markdown; charset=utf-8` is a document here too); and the two answers that mean the owner holds no document to replace - `404 ARTIFACT_NOT_FOUND`, the first upload under that name, and `409 DOC_SCHEMA`, a tree outside the Proof schema, which renders no markdown and so has no token and which an upload is the only way to repair. Every other failure of that read - the request never reached Dispatch, the session lapsed, a 5xx, `400 ARTIFACT_REFERENCE_AMBIGUOUS` - ends the upload with its own message and posts nothing: the page does not know what it would be replacing, and an upload naming no version replaces it silently. The Plan and Verification tabs' empty states print the `dispatch artifact` line that makes the document and, under it, that a later upload under that name replaces the document and takes `--precondition-json` with the token `dispatch doc-read` prints.

What a refused upload says is the page's own words, not the server's. The server writes its refusals of that token for a caller holding the `dispatch` command, naming the command that reads the token and the argument that sends it; a person uploading here runs no command and pastes no token, so `uploadErrorMessage` answers each in words of its own and passes every other refusal through as the server wrote it. They are three different things to be told: `PRECONDITION_FAILED` is `UPLOAD_BASE_REFUSAL`, the document changed while they were uploading it, so open it and upload again; `PRECONDITION_REQUIRED` is `UPLOAD_BASE_REQUIRED_REFUSAL`, the upload named no version where Dispatch requires one, which from this page means the read found no document and one was created before the post; and a token the page could not read at all is `UPLOAD_BASE_UNREADABLE_REFUSAL`, nothing was uploaded, followed by what Dispatch said of the read. `e2e/artifacts.e2e.ts` proves the guard in a real browser against a real server: it reads the `precondition` field out of the page's own multipart request and compares it with the live token, then holds that request in a route while an agent edits the document, so the token the server reads is one version behind and the row shows the refusal. That reading of the request is the only evidence of its kind here, since every unit test of this path mocks the client the page uploads through and asserts its argument, which is how `ApiClient.uploadArtifact` came to drop the `precondition` from the body it posts without a test noticing.
