The React single-page application: Inbox, project Architecture tree, List and Board, issue pages with Spec/Conversation/Children/Artifacts, the document editor, the search palette, which marks each ask hit with its answer state, the new-issue dialog, which lists the related items the no-write check finds for the title being typed, Settings, and the Architecture sources section in Settings.

Settings also lists **Sign-ins**, the machines the viewer has signed in on with `agent-secrets login` and has not revoked, each revocable from there and nobody else's; it sits on Settings rather than on the credential page because `/credentials/machine` is itself conditional. That page is served only while the broker still serves RFC 8628's device grant, which is the only thing that makes a machine print a code: the browser reaches no broker, so it reads the one fact Dispatch relays from the broker's own metadata (`GET /api/v1/credentials/capabilities`), and a false answer renders the not-found page and leaves the Inbox's machine-login row unlinked. No Dispatch setting says any of this.

An upload from the browser names the base it replaces. `uploadFile` (`features/artifacts/ArtifactUpload.tsx`) reads the token of the document the owner already holds under the name being uploaded, through the route that resolves a slug or a filename (`api/client.ts`'s `ownerArtifactText`), and sends it as the upload's `precondition`, so an upload over a document somebody changed first is refused `409 PRECONDITION_FAILED` rather than writing over their text. It names no base where there is none to name: the first upload under a name, which that read answers `404`; a conversation, which holds files and images and no document; a file that is not markdown; and a document whose tree is outside the Proof schema, which renders no markdown and so has no token, and which an upload is the only way to repair. The Plan and Verification tabs' empty states print the `dispatch artifact` line that makes the document and, under it, that a later upload under that name replaces the document and takes `--precondition-json` with the token `dispatch doc-read` prints.

What a refused upload says is the page's own words, not the server's. The server writes both refusals of the base for a caller holding the `dispatch` command, naming the command that reads the token and the argument that sends it; a person uploading here runs no command and pastes no token, so `uploadErrorMessage` answers `PRECONDITION_FAILED` and `PRECONDITION_REQUIRED` with `UPLOAD_BASE_REFUSAL`, which says the document changed while they were uploading it and to open it and upload again, and passes every other refusal through as the server wrote it. The page reads the token again on each attempt, so pressing Upload once more sends the base the document has now. `e2e/artifacts.e2e.ts` proves both halves in a real browser against a real server: it reads the `precondition` field out of the page's own multipart request and compares it with the live token, then holds that request in a route while an agent edits the document, so the base the server reads is one version behind and the row shows the refusal. That reading of the request is the only evidence of its kind here, since every unit test of this path mocks the client the page uploads through and asserts its argument, which is how `ApiClient.uploadArtifact` came to drop the `precondition` from the body it posts without a test noticing.
