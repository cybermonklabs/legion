The React single-page application: Inbox, project Architecture tree, List and Board, issue pages with Spec/Conversation/Children/Artifacts, the document editor, the search palette, which marks each ask hit with its answer state, the new-issue dialog, which lists the related items the no-write check finds for the title being typed, Settings, and the Architecture sources section in Settings. That dialog's list (`features/issue/RelatedItems.tsx`) draws one of the check's three forms and nothing after it. It asks the GET form of the related route, which offers no answered question of another project, so the list holds the items of the chosen project alone and names no past decision.

Settings also lists **Sign-ins**, the machines the viewer has signed in on with `agent-secrets login` and has not revoked, each revocable from there and nobody else's; it sits on Settings rather than on the credential page because `/credentials/machine` is itself conditional. That page is served only while the broker still serves RFC 8628's device grant, which is the only thing that makes a machine print a code: the browser reaches no broker, so it reads the one fact Dispatch relays from the broker's own metadata (`GET /api/v1/credentials/capabilities`), and a false answer renders the not-found page and leaves the Inbox's machine-login row unlinked. No Dispatch setting says any of this.

A write that puts a value into a query the page reads - a server's answer, or the value a press shows before Dispatch answers - where nothing compares a read's answer for its age, puts it over every read of that query still out (`replaceQueryData`, `api/query-client.ts`): such a read was asked before the write, and its later answer would put back the state the write replaced, as a read asked before a read mark would put back the unread count the mark cleared, so the compact header's and the navigation's badge would read "New reply 1" again (`storeAgentState`, `features/agents/unread.ts`, writes through it). `replaceQueryData` cancels the query's reads and writes in the same synchronous step, as `askSignInAgain` and the board's moves do. A read it cancels was asked for news of its own - another session's new reply, or the page's first load of every session - so where it cancelled one, it asks the query again once the write is in (exact, and only where a read was out and something still shows the query), and whatever the cancelled read was asked for still arrives, in an answer given after the write. A write that shows its value before Dispatch answers may also hold back each read of the queries it writes, each by its exact key, that starts while it is out, that one included (`holds` on `useKeyedWrite`, or `holdBackReads`), as the board's list waits for its moves (`projectIssuesQuery`); Dispatch's query client (`DispatchQueryClient`) is what makes such a read wait. A held read keeps back whatever anybody else changed in those queries meanwhile, so a hold lets its reads go soon: at the write's answer or refusal, at the write's own live event, which Dispatch publishes once it has committed the write (`ReadHold.endsOn`, the predicates in `api/write-events.ts`, heard by `hearLiveEvent` from `useEventFeed`), or `SEND_DEADLINE_MS` (30 s) after the press, by when the write is late, whichever comes first. An Ask card that seeds its thread from the Inbox over a read of the thread already out puts the seed over that read the same way (`useAskAnswerForm`). The writes, each with its verdict, are counted at dispatch://INFRA-1503/artifact/cache-write-class-md.

Which writes hold, by the exact keys they hold, and until when. A write holds only where a moment's stable optimistic value is worth keeping back other people's changes to its queries that long, so it chooses by who else writes them:

- `["user-state"]`: an issue's pin (`writePin`, the issue page's header, the issue header), until its answer: it is the viewer's own state, which nobody else writes, and no event ends it.
- `["user-agent-state"]`: an agent's pin (`features/agents/pins.ts`), until the viewer's `user_agent_state.updated` for that session: every session's unread count is in it, which agents' replies move.
- `["inbox"]`: an answer or a decline that takes the row out, until `ask.answered` or `ask.resolved` for the ask by the viewer; a hand-on, until `ask.asked_of` for the ask by the viewer; a snooze, until the viewer's `user_state.updated` naming `snoozed`, and a bulk snooze until one of those for each ask. The Inbox lists the asks other people open.
- The Inbox's threads (`["me", "replies", "inbox", "inbox"]`), the Dismissed pages (`["me", "replies", "inbox", "dismissed"]`, a dismiss only) and the unread count (`["me", "replies", "count"]`): Mark all read and a dismiss, until the viewer's `user_thread_state.updated` naming no thread. The threads gain other people's replies.
- The owner's comments (`["comments", KEY]`, or `["artifact", id, "comments"]` on a document): a resolve, a reopen, an accept or a reject, until its `comment.resolved`, `comment.reopened`, `suggestion.accepted` or `suggestion.rejected` for the comment by the viewer.
- `["issue", KEY]` and `["architecture", project]`: a components save, until the viewer's `issue.updated` of the issue naming `components`. The issue's coverage, results and steps under `["issue", KEY, …]` are not held.
- Nothing: a project's Legion daemon (`["legion-daemon", project]`), which no event names, and a project's default repository (`["projects"]`), whose Settings page shows a default another browser sets while its own pick is out (`e2e/settings.e2e.ts`). These cancel the reads out at the press in the same synchronous step as their value, and read their query again once they settle.

An event says that one write is in, and no event names a tab: the snooze's names no ask, since every signed-in feed carries it, and a Mark all read's or a dismiss's names no thread, since one event stands for every thread it marked in a project. So one event of the viewer's can match the holds of several writes still out, and it ends one hold at most (`hearLiveEvent`): the oldest whose write's answer is in, since that write's event is due, or else the oldest whose write is still out. A write's event can reach the page seconds after its answer, with the live socket up all along: Dispatch commits the write and answers it, but the page's feed is the event stream relay, which publishes an event only once its safe horizon has passed it, and that horizon trails the longest event write open in Dispatch's database (`events/horizon.go`), whichever client of the database holds it. So a hold whose reads went before its event came - at its write's answer, or at its deadline with the write still out, since Dispatch can take a write after its deadline - still waits for that event, holding no read, until `SEND_DEADLINE_MS` (30 s) after its answer, or for a write never answered until a day after the press (`IDEMPOTENCY_KEY_TTL_MS`, the longest Dispatch keeps a write's key), and the event, when it comes, ends no later write's hold. A write Dispatch refused with no earlier attempt of the write that may have landed unseen (a 4xx, `refusedByDispatch`) committed nothing and publishes no event, so its hold waits for none, and a bulk snooze waits for none of an ask Dispatch so refused. An attempt may have landed unseen where the page had no answer to it, and wherever an earlier try of the write sent anything under its key: a lapse stops a try, and the page takes the write up in a try of its own once the person signs in again. A write refused after such an attempt may have landed - a snooze is a `PUT`, which sends no key, so its retry runs Dispatch's handler again, which refuses a moment that has passed meanwhile - and so may a stopped write, and their holds still wait. Two components saves of one issue go out in press order, so the first components event is the older save's. A hold that holds reads ends early in three cases, each showing the state from before that write's press until its answer: two snoozes taken in the other order than their presses can end the older one's hold on the newer one's event, which no event can tell apart; a write's event that comes after its hold stopped waiting for it (more than 30 s after its answer, held back by the horizon or a socket down that long, or a day after the press) ends a later write's hold; and a Mark all read or dismiss over threads of several projects publishes one event for each, so its later ones count toward the next such press still out. Every other misreading ends a hold later rather than sooner: a write Dispatch took that publishes no event (it moved nothing) can take a later write's, and so can a write still out past its deadline (a snooze Dispatch has not answered takes the next snooze event) and a write refused after an attempt that may have landed unseen, in the same try or an earlier one, none of whose attempts landed; the hold whose event it was then ends at its own answer.

An upload from the browser names the token of the version it replaces, read when the person chooses the file. `captureUploadBase` (`features/artifacts/ArtifactUpload.tsx`) reads the token of the document the owner already holds under the name being uploaded, through the route that resolves a slug or a filename (`api/client.ts`'s `ownerArtifactText`), and the press sends it as the upload's `precondition`. So the window this guards runs from the choice of the file to the post: a write landing in it is refused `409 PRECONDITION_FAILED` rather than written over, and a change made before the file was chosen is replaced with no refusal, since the upload names what the document said at the choice. Reading the token from the open document instead, and holding it while the person reads, would guard nothing more: the document view is a live room, so the text in front of that person is the current one by construction. The token is read once for the press and every attempt of that press sends it, because Dispatch's idempotency key digests the whole body, the `precondition` field included (`bodyDigest` in the server's `api/request_keys.go`): an attempt that read the token afresh would send other bytes and be answered `422 KEY_REUSED` instead of what the first attempt did. A press after Dispatch has decided one reads the token again, so pressing Upload after a refusal names what the document says now, under a key of its own.

It names no token where it reads none: a conversation, which holds files and images and no document; a file whose media type is not `text/markdown`, parsed as the server parses it (`mime.ParseMediaType` in `artifactKind`, so `text/markdown; charset=utf-8` is a document here too), whose version token (`versions[].token`) the page does not read, so its replacement is taken unchecked; and the two answers that mean the owner holds no document to replace - `404 ARTIFACT_NOT_FOUND`, the first upload under that name, and `409 DOC_SCHEMA`, a tree outside the Proof schema, which renders no markdown and so has no token and which an upload is the only way to repair. Every other failure of that read - the request never reached Dispatch, the session lapsed, a 5xx, `400 ARTIFACT_REFERENCE_AMBIGUOUS` - ends the upload with its own message and posts nothing: the page does not know what it would be replacing, and an upload naming no version replaces it silently. The Plan and Verification tabs' empty states print the `dispatch artifact` line that makes the document and, under it, that a later upload under that name replaces the document and takes `--precondition-json` with the token `dispatch doc-read` prints.

What a refused upload says is the page's own words, not the server's. The server writes its refusals of that token for a caller holding the `dispatch` command, naming the command that reads the token and the argument that sends it; a person uploading here runs no command and pastes no token, so `uploadErrorMessage` answers each in words of its own and passes every other refusal through as the server wrote it. They are three different things to be told: `PRECONDITION_FAILED` is `UPLOAD_BASE_REFUSAL`, the document changed while they were uploading it, so open it and upload again; `PRECONDITION_REQUIRED` is `UPLOAD_BASE_REQUIRED_REFUSAL`, the upload named no version where Dispatch requires one, which from this page means the read found no document and one was created before the post; and a token the page could not read at all is `UPLOAD_BASE_UNREADABLE_REFUSAL`, nothing was uploaded, followed by what Dispatch said of the read. `e2e/artifacts.e2e.ts` proves the guard in a real browser against a real server: it reads the `precondition` field out of the page's own multipart request and compares it with the live token, then holds that request in a route while an agent edits the document, so the token the server reads is one version behind and the row shows the refusal. That reading of the request is the only evidence of its kind here, since every unit test of this path mocks the client the page uploads through and asserts its argument, which is how `ApiClient.uploadArtifact` came to drop the `precondition` from the body it posts without a test noticing.

A composer's draft - typed, refused or stopped - goes where the person takes it, and stays where the host moved away from; neither lets what the person wrote go with no word. A move the reader makes with the composer's own controls - Cancel reply, Escape, and a control the host draws for it and counts in the same press (`ownMoves`, the Agents row's issue picker) - carries the draft's refusal to the new address (`HeldSends.carry`, `features/conversation/held-sends.ts`), where Send and Retry go under a key of their own, and re-points the files pasted into it (`draftHomes` in `useDraftHomes`), so a file that lands afterwards adds its reference at once, naming the owner it went to. A move of the host's - another row, another thread, a Reply on a message, a phone thread's Back - carries nothing: `HeldSends.send` refuses a press whose address is not the refusal's (`sameAddress`), and the composer says where the draft was written for. A typed draft stays as well: a composer its host moves from reply to reply, or takes off the page - the docked composer, a phone thread's, an Agents row's, the margin's compose - keeps what the field holds for the reply it answers, or for none (`AwayDraft` in `features/conversation/unsent-drafts.ts`, under the send name), puts it back in place of a new reply's prefill when it is at that address again, and while it shows another address says the text is kept, whose message it answers and the way back (`keptAwayLine` in `KeptReply`). The reader's own move onto an address that keeps a draft of its own carries nothing, so neither draft is written over. Text typed while the host holds a composer away from a refusal's address is that address's and is kept for it, and the refusal keeps its own draft. Leaving a document leaves the margin's unsent compose open for it (`useMarginSheet`), and the margin holds one open compose per document (`composeForMark` replaces only the compose on its own document, and takes its provisional mark out through that document's bridge), so a compose opened on another document leaves it open too, and the compose and its text are there on return. The margin's compose keeps its draft for the words it was written about (`AwayDraft.anchor`, which `readAway` compares) and the kind it was written as (`AwayDraft.kind`): a newer compose on the same document draws a composer of its own (`MarginSheet` keys it by its compose), and the earlier draft - typed, or handed back by a refusal, whose refusal goes - is never put in its field, while a send the person stopped, which may have been delivered, waits aside whole (`marginComposeKeptKey`). Either waits beside the newer compose, the field and an ask's fields read only and Send refused, naming the quote it was written for, the kind it was written as where the compose is another, and, for a stopped send, that it may have been delivered there and that sending it from here is a new message (`SendMovedError`), until the person presses Use my draft, which puts it in the field with an ask's options and settings (`AwayDraft.ask`) and carries a stopped send into that compose as the reader's own move carries one (`HeldSends.carryInto`), so the same words stay with Retry and Discard draft until it is sent or discarded, or Discard my draft (`offered` in `useKeptDrafts`); neither retypes the compose or its mark. A standing box's draft is its thread's, which a newer message the box moves onto leaves in the field. A stopped send may have been delivered, so its key is never used away from its own address: carried by the reader, it goes on as a new write, and its refusal says the first may already have been delivered (`SendMovedError`). On a phone the thread view's own composer does as the docked one does: its Cancel reply ends that composer and puts its draft, the refusal with it, in the docked composer at the issue's address (`HeldSends.carryInto`, `usePhoneThread`'s `cancelReply`), and while the docked composer holds a draft of its own, which is never written over, the thread composer is put away as it stands, the docked composer says the reply is kept, and that comment's Reply brings it back. A thread card's inline reply has no other composer to go to, so its Cancel reply ends the reply and keeps the draft under its own send name - typed (`unsent-drafts.ts`), refused or stopped (the held send) - and the closed card says the reply is kept and how to go on with it (`keptReply` on `ThreadCard`); its Reply brings the draft back with its refusal, and nothing is sent until the person presses. The phone thread views' Back - the margin sheet's (`closeThread` in `useMarginSheet`) and the Conversation's (`usePhoneThread`'s `leave`) - drops nothing: the card's reply and the thread composer's stay held for their thread, and opening it again brings them back.

A comment's editor keeps what the person wrote the same way when its host takes it off the page - Collapse thread, another thread opened in the margin, a phone thread view's Back - with the comment's body it was written over (`AwayDraft.base`; a refused edit's request carries its own, `SentRequest.edit.base`), and the editor drawn for that comment next puts the edit back only while the comment still holds that body, or reads as the edit would save it (`changedUnder` in `useKeptDrafts`). Over a body another writer has changed since, the field shows the newer body, read only, and the edit waits beside it with words saying the comment changed since the edit was written (`changed`); Save refuses until the person presses Use my edit, which puts the edit back in the field for their own Save, or Discard my edit, so nothing is saved over a version of the comment the person has not seen. A change under an open editor does the same: the field takes the newer body, and what the person wrote waits beside it, kept at once in its refusal or for the comment with the body it was written over, so a host's move meanwhile loses nothing; while a save of the editor's own is out, the field only takes the body. The Conversation keeps each thread's open editor by its root (`editingIn` in `ConversationTab`), as the margin keeps its own (`useMarginSheet`), so a phone thread view drawn afresh opens with it.

Every draft store keeps the person's unsent drafts in the tab's `sessionStorage` (`draft-store.ts`), beside the unconfirmed writes (`write-storage.ts`), so a browser that restores or duplicates a tab restores or copies both with it. A duplicated tab takes the copied writes up again, as the first tab does, which is safe: a `PUT` or a `DELETE` makes the same change again, and Dispatch answers a `POST` or a `PATCH` under its kept key with what the first one did. A draft sent from one of the two tabs stays in the other, where sending it is a second message.

Settings → **Agent tokens** (`features/settings/AgentTokensSection.tsx`) mints a personal token with four choices: "Act as you" (`person`), "Approve and control credentials" (`approve`), "Set P0" (`p0`) and "Read only" (`read`). Set P0 is drawn, on the mint form and on the row of each token that writes, only once `GET /api/v1/whoami` names `p0` for the person at the browser (`AgentTokensSection` reads it through the query `["whoami-scopes"]`, since `/auth/whoami` names no scopes): while that read has not answered, has failed, or was answered by a Dispatch of the build before `p0`, no Set P0 box is drawn and the form still mints, and a row's change still sends each scope its token holds that the row does not draw, so a change never drops `p0` in silence. A new token starts with Act as you and Approve ticked and Set P0 clear. Ticking Read only clears Approve and Set P0, and ticking Approve or Set P0 clears Read only; Approve ticks Act as you, and clearing Act as you clears Approve and leaves Set P0. A token's row shows its scopes. A read-only token's row has no box to change, and a writing token's row offers no `read` box, since Dispatch changes no token to or from `read`.

Its path `packages/dispatch` also holds `e2e/read-token-live.ts`, the live proof that drives read-only tokens from `packages/envoy/scripts/dev-broker.sh` against a `bun run dispatch:local` Dispatch: the read entry's token, the example entry's token traded with `scope=read`, and a machine login's token traded with `scope=read`, with and without a cut. It expects `200` on an issue read, `403 READ_ONLY_TOKEN` on a comment and on `GET /ws/live`, and each token's introspection as `ciphertoken/testdata/narrowed-answers.json` gives it. For the cut token it expects the cut in `GET /api/v1/whoami`, `404` on the issue read, since the script makes the issue after the cut, and `403 AS_OF_TOKEN_NOT_SERVED` on the issue's references and on `GET /ws/live`. Beside it is `e2e/job-token-live.ts`, the live proof that drives that rig's two job entries through this checkout's `dispatch api` against the same kind of Dispatch: the job pod (`AGENT_SECRETS_MACHINE_IDENTITY=kubernetes`) creates an issue in its one project, recorded under its session with its account as the service and no owner, and its issue in another project gets the answer that the rig's entry naming a person and the same project, the control, gets there (both create it, since that project is public); the job workflow's run (`github-actions`, against `dev-oidc-issuer`'s stand-in for GitHub's token request) comments on that issue; and whoami answers each with no owner, while the control answers that person.
