The React single-page application: Inbox, project Architecture tree, List and Board, issue pages with Spec/Conversation/Children/Artifacts, the document editor, the search palette, which marks each ask hit with its answer state, the new-issue dialog, which lists the related items the no-write check finds for the title being typed, Settings, and the Architecture sources section in Settings. That dialog's list (`features/issue/RelatedItems.tsx`) draws one of the check's three forms and nothing after it. It asks the GET form of the related route, which offers no answered question of another project, so the list holds the items of the chosen project alone and names no past decision.

Settings also lists **Sign-ins**, the machines the viewer has signed in on with `agent-secrets login` and has not revoked, each revocable from there and nobody else's; it sits on Settings rather than on the credential page because `/credentials/machine` is itself conditional. That page is served only while the broker still serves RFC 8628's device grant, which is the only thing that makes a machine print a code: the browser reaches no broker, so it reads the one fact Dispatch relays from the broker's own metadata (`GET /api/v1/credentials/capabilities`), and a false answer renders the not-found page and leaves the Inbox's machine-login row unlinked. No Dispatch setting says any of this.

The search palette is also the command bar (`features/search`). Where `GET /api/v1/going/capability` says that an answering model is configured, `useGoingAnswer` asks a question on the pause the meaning search waits for (`MEANING_PAUSE_MS`), never on a keystroke. It sends the words, the filter chip's project and the context chip to `POST /api/v1/going/requests`. It reads the run's stream through `api/event-stream.ts` and not through `EventSource`, so the request carries the page's own headers and can be aborted. The bar holds one run at most, and the next keystroke and closing the bar each cancel it (`POST /api/v1/going/requests/{id}/cancel`). `AnswerPanel.tsx` draws the answer beside the hits: the `text` frames as escaped plain text, the `item` frames as the answer's only links, one line each for a cut, a change the server made, no answer, an answer that rests on no source, the roster's age or a stored roster, and a failure, and below them what this Dispatch cannot do (`capabilityGaps`). `blocks/AnswerBlock.tsx` draws the `block` frame, with one component for each of the seven kinds, from the frame's rows alone. `ChartBlock.tsx` loads `echarts` by one dynamic `import()`, as the delivery timeline does, so the chart's chunk arrives with the first chart an answer draws and the shell's entry chunk holds none of it; the chart's rows are also written as a table under the canvas. The page keeps the last answered run outside the dialog, and the bar opening again with an empty box draws that run again from its stream's first frame while Dispatch keeps it. The page stores nothing of a chart.

The bar's operations (`OperationRows.tsx`, `going-turns.ts`) come from the `decision` and `proposal` frames. Where the decision acts, the operation is one row above the hits with a Run button, and it runs on submit: `Mod+Enter` anywhere in the bar, the Run button, or Enter on that row. The highlight never moves to that row by itself, so Enter keeps its one meaning, opening the highlighted row. Below the action threshold the two best actions are rows of their own, and neither runs until the person picks it. A submit before the proposal arrives says the row is preparing and runs when the proposal lands. An invocation that misses one argument asks for it first: a text, a number, a choice, or an item of the hits. A new issue and a send to the issue's agent stay the bar's two offers, which always ask, and they write through the run when the decision chose them. Each invocation is one write of the page's write store (`Writes.run`) to `POST /api/v1/going/runs/{id}/writes`, on the run's own line, so the writes go out one after another, and each write shows its own line: the item, the field, the value before and the value now, or the refusal. A turn's Undo stops each write that still waits its turn before it is sent, waits for the writes that are out, and then sends `POST /api/v1/going/runs/{id}/undo`. `Mod+Z` (`app.tsx`, a global binding that does not run in an editable field, so an editor's own undo is untouched) undoes the person's newest turn from any page: the turn this page is still writing, or else the newest undoable run of `GET /api/v1/me/going-runs?undoable=true&limit=1`, so the key works after a reload. `GoingUndoNotice.tsx` says in the shell's corner what that undo did. Settings has a **Command bar** section (`features/settings/CommandBarSection.tsx`) that reads and writes the person's `confirm_writes` (`GET` and `PUT /api/v1/me/going/settings`). With it on, the bar shows each write it would make and sends it `confirmed` only after the person confirms.

The browser suite has a models lane (`bun run e2e:models`, `DISPATCH_E2E_MODELS=fake`). It starts a fake writing model and a fake decision model over https on loopback, with a certificate the harness makes (`e2e/harness-models.ts`, `e2e/fake-chat-model.ts`, `e2e/fake-decision-model.ts`), and configures the server with the model that `packages/envoy/going/decision_models.json` marks chosen. Its specs read every threshold from that record. The default stack configures no model, and `e2e/going-unconfigured.e2e.ts` is its row; that row skips in the models lane unless `DISPATCH_E2E_CONTROL=unconfigured-in-models-lane` runs it there as its check's negative control, which fails.
