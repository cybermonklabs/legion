The React single-page application: Inbox, project Architecture tree, List and Board, issue pages with Spec/Conversation/Children/Artifacts, the document editor, the search palette, which marks each ask hit with its answer state, the new-issue dialog, which lists the related items the no-write check finds for the title being typed, Settings, and the Architecture sources section in Settings. That dialog's list (`features/issue/RelatedItems.tsx`) draws one of the check's three forms and nothing after it. It asks the GET form of the related route, which offers no answered question of another project, so the list holds the items of the chosen project alone and names no past decision.

Settings also lists **Sign-ins**, the machines the viewer has signed in on with `agent-secrets login` and has not revoked, each revocable from there and nobody else's; it sits on Settings rather than on the credential page because `/credentials/machine` is itself conditional. That page is served only while the broker still serves RFC 8628's device grant, which is the only thing that makes a machine print a code: the browser reaches no broker, so it reads the one fact Dispatch relays from the broker's own metadata (`GET /api/v1/credentials/capabilities`), and a false answer renders the not-found page and leaves the Inbox's machine-login row unlinked. No Dispatch setting says any of this.

A write that puts a value into a query the page reads - a server's answer, or the value a press shows before Dispatch answers - where nothing compares a read's answer for its age, puts it over every read of that query still out (`replaceQueryData`, `api/query-client.ts`): such a read was asked before the write, and its later answer would put back the state the write replaced. The query is then read again, so whatever the cancelled read was asked for still arrives, in an answer given after the write. A write that shows its value before Dispatch answers may also hold back each read of the queries it writes, each by its exact key, that starts while it is out, that one included (`holds` on `useKeyedWrite`, or `holdBackReads`), as the board's list waits for its moves (`projectIssuesQuery`); Dispatch's query client (`DispatchQueryClient`) is what makes such a read wait. A held read keeps back whatever anybody else changed in those queries meanwhile, so a hold lets its reads go soon: at the write's answer or refusal, at the write's own live event, which Dispatch publishes once it has committed the write (`ReadHold.endsOn`, the predicates in `api/write-events.ts`, heard by `hearLiveEvent` from `useEventFeed`), or `SEND_DEADLINE_MS` (30 s) after the press, by when the write is late, whichever comes first. An Ask card that seeds its thread from the Inbox over a read of the thread already out puts the seed over that read the same way (`useAskAnswerForm`). The writes, each with its verdict, are counted at dispatch://INFRA-1503/artifact/cache-write-class-md.

Which writes hold, by the exact keys they hold, and until when. A write holds only where a moment's stable optimistic value is worth keeping back other people's changes to its queries that long, so it chooses by who else writes them:

- `["user-state"]`: an issue's pin (`writePin`, the issue page's header, the issue header), until its answer: it is the viewer's own state, which nobody else writes, and no event ends it.
- `["user-agent-state"]`: an agent's pin (`features/agents/pins.ts`), until the viewer's `user_agent_state.updated` for that session: every session's unread count is in it, which agents' replies move.
- `["inbox"]`: an answer or a decline that takes the row out, until `ask.answered` or `ask.resolved` for the ask by the viewer; a hand-on, until `ask.asked_of` for the ask by the viewer; a snooze, until the viewer's `user_state.updated` naming `snoozed`, and a bulk snooze until one of those for each ask. The Inbox lists the asks other people open.
- The Inbox's threads (`["me", "replies", "inbox", "inbox"]`), the Dismissed pages (`["me", "replies", "inbox", "dismissed"]`, a dismiss only) and the unread count (`["me", "replies", "count"]`): Mark all read and a dismiss, until the viewer's `user_thread_state.updated` naming no thread. The threads gain other people's replies.
- The owner's comments (`["comments", KEY]`, or `["artifact", id, "comments"]` on a document): a resolve, a reopen, an accept or a reject, until its `comment.resolved`, `comment.reopened`, `suggestion.accepted` or `suggestion.rejected` for the comment by the viewer.
- `["issue", KEY]` and `["architecture", project]`: a components save, until the viewer's `issue.updated` of the issue naming `components`. The issue's coverage, results and steps under `["issue", KEY, …]` are not held.
- Nothing: a project's Legion daemon (`["legion-daemon", project]`), which no event names, and the repository mappings (`["repo-projects"]`), whose Settings page shows a default another browser sets while its own pick is out (`e2e/settings.e2e.ts`). These cancel the reads out at the press in the same synchronous step as their value, and read their query again once they settle.

An event says that one write is in, and no event names a tab: the snooze's names no ask, since every signed-in feed carries it, and a Mark all read's or a dismiss's names no thread, since one event stands for every thread it marked in a project. So one event of the viewer's can match the holds of several writes still out, and it ends one hold at most (`hearLiveEvent`): the oldest whose write's answer is in, since that write's event is due, or else the oldest whose write is still out. A hold whose reads went before its event came - at its write's answer, or at its deadline with the write still out, since Dispatch can take a write after its deadline - still waits for that event, holding no read, until the later of its deadline and `LATE_EVENT_GRACE_MS` after its answer (2 s, `RECONNECT_SPREAD_MS`: Dispatch publishes the event before it answers, and a socket it dropped first tries to reconnect within that), or for a write never answered until a day after the press (`IDEMPOTENCY_KEY_TTL_MS`, the longest Dispatch keeps a write's key). So the event, when it comes, ends no later write's hold. Two components saves of one issue go out in press order, so the first components event is the older save's. A hold that holds reads ends early in three cases, each showing the state from before that write's press until its answer: two snoozes taken in the other order than their presses can end the older one's hold on the newer one's event, which no event can tell apart; a write's event that comes after its hold stopped waiting for it (the socket was down past its first reconnect, or a day after the press) ends a later write's hold; and a Mark all read or dismiss over threads of several projects publishes one event for each, so its later ones count toward the next such press still out. Every other misreading ends a hold later rather than sooner: a write that publishes no event (it moved nothing, or was refused) can take a later write's, and so can a write still out past its deadline (a snooze Dispatch has not answered takes the next snooze event); the hold whose event it was then ends at its own answer.

Its path `packages/dispatch` also holds `e2e/read-token-live.ts`, the live proof that drives a read-only token from `packages/envoy/scripts/dev-broker.sh` against a `bun run dispatch:local` Dispatch and expects `200` on the architecture route and `403 READ_ONLY_TOKEN` on a comment and an issue read.
