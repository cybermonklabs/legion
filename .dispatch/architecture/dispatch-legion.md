What Dispatch records of each Legion daemon's own state, so the Legion board and the Legion delivery metrics read Dispatch's tables rather than a daemon. A project's daemon is one `legion_settings` row (`store.go`), which `GET`, `PUT` and `DELETE /api/v1/projects/{key}/legion/daemon` read and write (`api/settings_legion.go`). The daemon publishes each change of what Dispatch observes as a state event on `notifications.legion.<token>.state`: one message for each transaction it committed, or consecutive messages split between events where a transaction's events pass 900 KB (`stateMessageBound` in `packages/daemon/internal/daemon/outbox.go`), its events in the daemon's own sequence (`legionStateMessage` in `packages/contracts`). Each message names the store its sequence is counted in (`stateId`, which the state route serves as `daemon.stateId`), and each message of a split transaction but the last carries `more: true`. The intake (`intake.go`, `Intake`, which `cmd/dispatch` starts whenever it has NATS) takes the messages from the held durable `legion-state-events` (`bus.DispatchLegionStateDurable`, through `delivery.NewHeldDurable`), so one process at a time applies them, and it runs each project's messages one at a time. A message whose events do not run from its `firstSeq` to its `seq`, one sequence each, does not decode: the intake logs it, acknowledges it and moves no cursor. It applies no message whose store is not the cursor's, and no message at all while no good whole read has given the cursor a store, so no message of the daemon a setting named before is applied after the setting names another. It holds each message with `more` in `legion_event_parts` and applies nothing of its transaction until the last message arrives, so no row holds a value of a transaction that did not arrive whole. For each transaction it writes, in one transaction, every value the transaction moved in `legion_observations`, one `legion_reads` row of kind `events` at the daemon's commit time, and the project's cursor in `legion_event_cursors`: the daemon's run, the schema version of the newest boot applied and the last sequence applied; only a good whole read sets the cursor's store. It reads a daemon's `GET /legion/v1/state?view=observed` whole (`Intake.readWhole`, through `client.go`, held to `RequestTimeout`, 60 s, and `ResponseLimit`, 64 MiB, and sending no credential) only for the seven reasons the `ReadReason` constants name: a project with no cursor, or a cursor that follows another daemon, at each take-over and each write of its setting (`dispatch_legion_settings`, `SettingsChannel`) or at its next message (`start`); a boot event that does not follow the cursor (`boot`), or whose `schemaVersion` is not the cursor's (`schema`); a message past a gap the stream no longer holds, or one that does not continue the held parts of a split transaction (`gap`); a read owed since one failed (`retry`); a message of another store (`store`); and a message the database refuses for good (a Postgres error of SQLSTATE class 22 or 23), which the intake logs and acknowledges and does not try again in place (`refused`). The observed view carries only the members `state.go` decodes, and a daemon of an earlier build ignores the query and serves its whole state, which the decode reads the same way. A project's whole reads start at least a minute apart (`ReadRetryAfter`), whatever their reason, so a project has at most one read in flight and at most one owed. A settings write deletes the cursor, so the first read of a new setting has no read to wait after, and a good starting read holds back no read after it. One rule decides every call for a read (`cursor.readFor`): a read that is due is made, and a message that calls for a read inside the minute makes none, the cursor recording the read owed with the message's reason (`read_reasons`, from which Postgres generates `read_owed`). The first message that owes the read goes back to the stream unacknowledged with a redelivery delay of the time left in the minute (`delivery.HeldMessage.HandBackAfter`), and the cursor names it as the read's holder (`read_holder`), so its redelivery makes the read, recorded under the first reason it was owed for and logged with every one (`reasons`); every later message that joins the read is acknowledged, and a message that goes back is logged as held and with no other line. A read that fails sends the holder back for another minute, at most 10 times in all (`stateMaxHolds`, counted on the message's own `NumDelivered`), and the holder's next delivery is then acknowledged and the cursor names no holder; a failed read that no message holds, a failed starting read or one whose message went back 10 times, waits for the project's next message, boot, settings change or take-over. The durable sets no `MaxDeliver` and an ack wait of two minutes, past the longest delay, so the server never drops the holder, each project that owes a read holds one message of the durable's window, and, where a message holds the read, a project that goes quiet is at most a minute behind. While the holder waits, the durable's ack floor stays below it, so a take-over replays every message after it, for about 11 minutes of messages at the most. While a read is owed, the intake applies a message that follows the cursor, a boot of a moved schema among them, and drops a gap, a boot that does not follow, a part that does not continue the held parts and a message of another store, since the read holds their events. A message that is still past the next sequence after a good read it called for is dropped and logged: the daemon commits each event before it publishes it, so the read holds every event the daemon published before it. The intake takes no starting point while a Dispatch process of an earlier build is in the fleet (`processes.EarlierLegionIntake`: a `server_processes` row at `legion_state_intake` 0 that heartbeated in the last 10 minutes), because that build still reads each daemon whole every minute. Meanwhile a message of a project with no starting point writes nothing and is finished. No timer reads a daemon. A whole read runs on the project's own runner, so it never interleaves with the project's messages. It records how it went in `legion_reads` (kind `read`, with its reason) and every value that moved in `legion_observations` (`state.go` says which fields are observed, and the decode is loose so a daemon that grows the route's shape is still read), with a `null` for each field a good read no longer carries, all at one moment, 1 µs after the project's newest row where that is later than the read's time. A good read sets the cursor to the state's own `daemon.stateSeq`, the sequence that snapshot reflects, and to its `daemon.stateId` and `daemon.schemaVersion`, and it deletes the project's held parts, which its snapshot holds; a failed read keeps them. Both writes keep the newest row of each field in `legion_current`, which a trigger fills in the same transaction and which the writes and `ReadCurrent` read rather than the whole history, `ReadCurrent` answering the board's cards and the set of issues the daemon reported in one statement. Both announce themselves on `dispatch_legion_state` (`StateChannel`) when they commit, which an open `/ws/live` `legion` view hears. After a batch, at most once an hour in each process, the intake prunes reads older than a week, keeping each project's newest. A read the daemon did not answer, or answered with another project's state, keeps the last good observations. So does a read whose answer is over the cap: its `legion_reads` row names the answer's size and the cap, and its `bytes` is that size, counted to the end of the body where no Content-Length declares it. A read whose settings carry no `dispatch_url` (judged first, so a daemon that runs no workflow is read with that reason), or whose state carries no `daemon.stateSeq`, a `stateSeq` of 0, or no `daemon.stateId`, records its observations and is a failed read all the same, so the read stays owed. The board's header names the failure of each failed read, and goes on naming it over the batches applied after it while the read is owed. `tree.go` is the one rule that places an issue in a tree (`TreeRoot`, and `IsLegionIssue` for which issues are Legion's) and `session_title.go` the one reading of a Legion session's title, which both the board (`api/legion_board.go`) and `legion/metrics` ask, the board reading phase work only for the issues its walk climbs onto (`PhaseWorkOf`) and the metrics every project's (`PhaseWorkKeys`). `legion/metrics` computes the four Legion delivery metrics from the same records (`Read`, then `Compute`); no route serves them. The edges are the store's pool, the six tables its migrations create and the fleet record it reads before a starting point (`dispatch-store`, `internal/dispatch/processes`); the held durable the intake runs under, and the delivery reads phase work and the metrics take session titles and merge times from (`dispatch-delivery`); the bus client the intake connects with (`envoy-listener`, `internal/bus`); the generated subject of the state lane (`contracts`); the actor a setting records (`dispatch-model`); and the GitHub App client the metrics read merge times through (`dispatch-auth`).
