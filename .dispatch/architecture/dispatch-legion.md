What Dispatch records of each Legion daemon's own state, so the Legion board and the Legion delivery metrics read Dispatch's tables rather than a daemon. A project's daemon is one `legion_settings` row (`store.go`), which `GET`, `PUT` and `DELETE /api/v1/projects/{key}/legion/daemon` read and write (`api/settings_legion.go`). The sampler (`sampler.go`, `RunSampler`, which `cmd/dispatch` starts) is a one-minute timer loop (`duty.RunLeased`, lease `legion-state`, first tick at start) rather than a woken one, since a remote daemon announces nothing Dispatch can listen for: each pass reads every configured daemon's `GET /legion/v1/state` (`client.go`, held to `RequestTimeout`, 60 s, and `ResponseLimit`, 32 MiB, and sending no credential), records how the read went in `legion_reads` and every value that moved in `legion_observations` (`state.go` says which fields are observed, and the decode is loose so a daemon that grows the route's shape is still read), with a `null` for each field a good read no longer carries, and keeps the newest row of each field in `legion_current`, which a trigger fills in the same transaction and which the write and `ReadCurrent` read rather than the whole history, `ReadCurrent` answering the board's cards and the set of issues the daemon reported in one statement, announces the read on `dispatch_legion_state` (`StateChannel`), which an open `/ws/live` `legion` view hears, and prunes reads older than a week, keeping each project's newest. A failed read keeps the last good observations, and the board's header names the failure. `tree.go` is the one rule that places an issue in a tree (`TreeRoot`, and `IsLegionIssue` for which issues are Legion's) and `session_title.go` the one reading of a Legion session's title, which both the board (`api/legion_board.go`) and `legion/metrics` ask, the board reading phase work only for the issues its walk climbs onto (`PhaseWorkOf`) and the metrics every project's (`PhaseWorkKeys`). `legion/metrics` computes the Legion measures from the same records (`ReadProject` and `ReadIssues`, then each issue's facts and the folds of `folds.go`), and the Legion evals serve them (`GET /api/v1/projects/{key}/evals?kind=legion`). The edges are the store's pool and the four tables its migrations create (`dispatch-store`), the lease loop (`dispatch-duty`), the actor a setting records (`dispatch-model`), the delivery reads phase work and the metrics take session titles and merge times from (`dispatch-delivery`), and the GitHub App client the metrics read merge times through (`dispatch-auth`).

`issue.go` holds the one per-issue rule of what the sampler recorded, which the board (`api/legion_board.go`) and one issue's read (`GET /api/v1/issues/{key}/legion`, `api/legion_issue.go`) share, so a card and the issue's answer agree on the phase, the roles in a turn and the slot.
`IssueState` takes an issue's newest observations one by one (`Observe`): its phase and when Dispatch stored it, its slot, what it waits on as the daemon's own bytes, and the claim of each role with its state.
`Working` answers the roles in a turn, which a card shows, and `Roles` every claim, the roles `legionagents.Roles` names first and then any other by name.
`AdmissionOf` decodes the stored `admission` block, which the board and `ReadIssue` both read through it, and `Admission`'s `Place`, `Blockers` and `BlockersOf` answer where the daemon's waiting line puts an issue and which issues hold it.
`ReadIssue` reads one issue's state in one statement over `legion_current`: the issue's rows and the project's `admission` row, with `ReadCurrent`'s `null` rule, and no row of any other issue.
It also answers whether Dispatch saw the issue's phase start (`PhaseStartSeen`): whether `legion_observations` holds an older `phase` row of the issue whose value is not the newest one's, read through the index `legion_observations_point`.
`GetSettings` takes a `RowQueryer`, so the issue's read takes the setting, `ReadIssue` and the rest in one transaction, and its `configured` and its state answer one moment.
The announcement on `dispatch_legion_state` moves an open `/ws/live` `legion_issue` view of each of the project's issues too, beside the project's `legion` view.
