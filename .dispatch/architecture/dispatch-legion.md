What Dispatch records of each Legion daemon's own state, so the Legion board and the Legion delivery metrics read Dispatch's tables rather than a daemon. A project's daemon is one `legion_settings` row (`store.go`), which `GET`, `PUT` and `DELETE /api/v1/projects/{key}/legion/daemon` read and write (`api/settings_legion.go`). The sampler (`sampler.go`, `RunSampler`, which `cmd/dispatch` starts) is a one-minute timer loop (`duty.RunLeased`, lease `legion-state`, first tick at start) rather than a woken one, since a remote daemon announces nothing Dispatch can listen for: each pass reads every configured daemon's `GET /legion/v1/state` (`client.go`, held to `RequestTimeout`, 20 s, and `ResponseLimit`, 8 MiB, and sending no credential), records how the read went in `legion_reads` and every value that moved in `legion_observations` (`state.go` says which fields are observed, and the decode is loose so a daemon that grows the route's shape is still read), with a `null` for each field a good read no longer carries, and keeps the newest row of each field in `legion_current`, which a trigger fills in the same transaction and which the write and `ReadCurrent` read rather than the whole history, `ReadCurrent` answering the board's cards and the set of issues the daemon reported in one statement, announces the read on `dispatch_legion_state` (`StateChannel`), which an open `/ws/live` `legion` view hears, and prunes reads older than a week, keeping each project's newest. A failed read keeps the last good observations, and the board's header names the failure. `tree.go` is the one rule that places an issue in a tree (`TreeRoot`, and `IsLegionIssue` for which issues are Legion's) and `session_title.go` the one reading of a Legion session's title, which both the board (`api/legion_board.go`) and `legion/metrics` ask, the board reading phase work only for the issues its walk climbs onto (`PhaseWorkOf`) and the metrics every project's (`PhaseWorkKeys`). `legion/metrics` computes the Legion measures from the same records (`ReadProject` and `ReadIssues`, then each issue's facts and the folds of `folds.go`), and the Legion evals serve them (`GET /api/v1/projects/{key}/evals?kind=legion`). The edges are the store's pool and the four tables its migrations create (`dispatch-store`), the lease loop (`dispatch-duty`), the actor a setting records (`dispatch-model`), the delivery reads phase work and the metrics take session titles and merge times from (`dispatch-delivery`), and the GitHub App client the metrics read merge times through (`dispatch-auth`).
