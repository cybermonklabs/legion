What Dispatch records of each Legion daemon's own state, so the Legion board and the Legion delivery metrics read Dispatch's tables rather than a daemon. A project's daemon is one `legion_settings` row (`store.go`), which `GET`, `PUT` and `DELETE /api/v1/projects/{key}/legion/daemon` read and write (`api/settings_legion.go`). The daemon publishes each change of what Dispatch observes as a state event on `notifications.legion.<token>.state`: one message for each transaction it committed, or consecutive messages split between events where a transaction's events pass 900 KB (`stateMessageBound` in `packages/daemon/internal/daemon/outbox.go`), its events in the daemon's own sequence (`legionStateMessage` in `packages/contracts`). Each message names the store its sequence is counted in (`stateId`, which the state route serves as `daemon.stateId`), and each message of a split transaction but the last carries `more: true`. The intake (`intake.go`, `Intake`, which `cmd/dispatch` starts whenever it has NATS) takes the messages from the held durable `legion-state-events` (`bus.DispatchLegionStateDurable`, through `delivery.NewHeldDurable`), so one process at a time applies them, and it runs each project's messages one at a time on the project's runner: a message that arrives during a whole read of the project waits behind it and is judged against the cursor that read leaves. A project keeps at most 16 messages waiting on its runner (`stateMaxWaiting`); a message past that runs beside the runner, makes no read and owes one, since its events may be past the snapshot of the read in flight, a message of a store the intake finishes unapplied (below) among them while a whole read of the project is in flight, since that read can find its store behind the setting's URL, and a boot of such a store that calls for a `store` read (below) whether or not a read is in flight. The first such message since the read in flight began holds the read after it, whichever message held the read in flight, and the others are acknowledged (`judgeCrowded`), the cursor keeping the highest sequence it so skipped in each store (`skipped_state_ids`, `skipped_seqs`, 8 stores at the most, which each read empties as it begins, since it holds every event published before it): a good read whose store has one above its `stateSeq` still owes the gap read, whatever it was made for, a good read that finds a store there other than its own, which the cursor it leaves does not drop, still owes the store read, and otherwise a good read clears the reasons the messages past the cap added (`recordWhole`). A project with no cursor yet is given one that follows no daemon both by a message past the cap and by a whole read's record, before either computes what it writes (`lockCursor`), so the two take turns on the row and neither writes over the other. So a project whose daemon does not answer a read holds 17 messages of the durable's window of 256. A message whose events do not run from its `firstSeq` to its `seq`, one sequence each, does not decode: the intake logs it, acknowledges it and moves no cursor. It applies no message whose store is not the cursor's, and no message at all while no good whole read has given the cursor a store, so no message of the daemon a setting named before is applied after the setting names another; a write of the setting that names another daemon, and a delete of the setting, record the store the cursor held with the URL it followed (`previous_state_id`, `previous_state_url`), a write back to that URL clears both, and the intake finishes each message of that store unapplied while the cursor holds no store or another store, as it does each message of a store marked as no daemon of the project (`foreign_state_ids`, 8 at the most), except a boot of such a store while the cursor holds another store a read verified (`cursor.drops`), which calls for a `store` read on the runner and past the cap alike, so that a daemon a redeploy started behind the setting's URL in that store is found again: a good `store` read that a message makes and that finds the cursor's store unchanged marks that message's store, and every write that resets the cursor clears the marks. Such a message calls for no read of its own, and holds one only as a message past the cap: it asks for the owed read when that read is due and no message holds it, at most once a minute, whatever store the cursor holds, since the setting's own daemon can be redeployed into that store and its messages then carry the old store's id, and the project's runner makes that read after the message is acknowledged (`callRead`); a good read that gives the same store clears both columns. A write of the setting that names another URL, or a delete of the setting, while a message holds the owed read ends that hold, whatever daemon the cursor followed, none included, and records the message as released (`released_holders`, the newest last, 8 at the most) until its next delivery while the project has a setting, or, after a delete, until 8 newer records push it out: at its next delivery the message is acknowledged unapplied, its record goes and no other, and its store is marked unless it is the store recorded or the cursor's own; past 8 the oldest record goes, and that message is judged as any message at its next delivery, so it may hold a read again from a count of 1. It holds each message with `more` in `legion_event_parts` and applies nothing of its transaction until the last message arrives, so no row holds a value of a transaction that did not arrive whole. For each transaction it writes, in one transaction, every value the transaction moved in `legion_observations`, one `legion_reads` row of kind `events` at the daemon's commit time, and the project's cursor in `legion_event_cursors`: the daemon's run, the schema version of the newest boot applied and the last sequence applied; only a good whole read sets the cursor's store. It reads a daemon's `GET /legion/v1/state?view=observed` whole (`Intake.readWhole`, through `client.go`, held to `RequestTimeout`, 60 s, and `ResponseLimit`, 64 MiB, and sending no credential) only for the seven reasons the `ReadReason` constants name: a project with no cursor, or a cursor that follows another daemon or none, at each take-over and each write of its setting (`dispatch_legion_settings`, `SettingsChannel`) or at its next message (`start`); a boot event that does not follow the cursor (`boot`), or whose `schemaVersion` is not the cursor's (`schema`); a message past a gap the stream no longer holds, or one that does not continue the held parts of a split transaction (`gap`); a read owed since one failed (`retry`); a message of another store (`store`); and a message the database refuses for good (a Postgres error of SQLSTATE class 22 or 23), which the intake logs and acknowledges and does not try again in place (`refused`). The observed view carries only the members `state.go` decodes, and a daemon of an earlier build ignores the query and serves its whole state, which the decode reads the same way. A project's whole reads start at least a minute apart (`ReadRetryAfter`), whatever their reason, the starting read included, and a good starting read holds back the read after it as every read does: the minute runs from the start of the project's newest whole read, which every read writes on the cursor before it calls the daemon (`last_read_started_at`), so a read that a stop cuts short keeps its start, and which no write or delete of the setting resets, so a project has at most one read in flight and at most one owed. A write of the setting either leaves the cursor as it is or resets it. A write of the URL the setting names already while a message holds the owed read leaves it as it is, whether the cursor follows that URL or no daemon yet, so that read is the whole read the write calls for and the count of its hand-backs goes on. Every other write resets it: the cursor follows no daemon, with no read owed, no holder, no store marked and no held parts, and keeps the start of the project's newest whole read, and the write's wake reads the setting's daemon whole once that minute is over: a wake or a take-over that finds the starting read not due, and held by no message, queues the starting point once more for the end of the minute (`startLater`), one deferred call each, and a message that arrives meanwhile holds the starting read as any owed read; a wake or a take-over that finds a message holding the starting read makes no read and queues nothing, since the holder's redelivery makes it. A delete of the setting resets the cursor as a write of another URL does and keeps its row, with the start of the project's newest whole read and the released holders, so the first read of a setting written again waits for that minute too. `resetCursor` and `cursor.reset` (`cursor.go`) hold the whole rule, and rows 6.1 to 6.5 of dispatch://INFRA-3931/artifact/read-rule-cases-md give its cases. One rule decides every call for a read (`cursor.readFor`): a read that is due is made, and a message that calls for a read inside the minute makes none, the cursor recording the read owed with the message's reason (`read_reasons`, from which Postgres generates `read_owed`). The first message that owes the read goes back to the stream unacknowledged with a redelivery delay of the time left in the minute (`delivery.HeldMessage.HandBackAfter`), and the cursor names it as the read's holder (`read_holder`), so its redelivery makes the read, whatever store it is of, recorded under the first reason it was owed for and logged with every one (`reasons`); every later message that joins the read is acknowledged, and a message that goes back is logged as held and with no other line. A read that fails sends the holder back until a minute after that read began, at most 10 times in all (`stateMaxHolds`, counted on the cursor in `read_holds`, so neither a take-over nor a write of the setting's own URL starts the count again), and the holder's next delivery is then acknowledged and the cursor names no holder; a failed read that no message holds, a failed starting read that no message made or one whose message went back 10 times, waits for the project's next message, boot, settings change or take-over, and a settings change or a take-over makes no read of a project whose owed read a message holds, the starting read included, since it joins the read that the holder's redelivery makes. The durable sets no `MaxDeliver` and an ack wait of two minutes, past the longest delay, so the server never drops the holder, each project that owes a read holds one message of the durable's window, and, where a message holds the read, a project that goes quiet is at most a minute behind. While the holder waits, the durable's ack floor stays below it, so a take-over replays every message after it, for about 11 minutes of messages at the most however many take-overs come, since a read waits 60 s at the most, the minute counts from its start and a take-over adds no read to the hold. While a read is owed, the intake applies a message that follows the cursor, a boot of a moved schema among them, and drops a gap, a boot that does not follow, a part that does not continue the held parts and a message of another store, since the read holds their events. A message that is still past the next sequence after a good read it called for is dropped and logged: the daemon commits each event before it publishes it, so the read holds every event the daemon published before it. The intake takes no starting point while a Dispatch process of an earlier build is in the fleet (`processes.EarlierLegionIntake`: a `server_processes` row at `legion_state_intake` 0 that heartbeated in the last 10 minutes), because that build still reads each daemon whole every minute. Meanwhile a message of a project with no starting point writes nothing and is finished. No recurring timer reads a daemon. A whole read runs on the project's own runner, so it never interleaves with a message the project applies. It records how it went in `legion_reads` (kind `read`, with its reason) and every value that moved in `legion_observations` (`state.go` says which fields are observed, and the decode is loose so a daemon that grows the route's shape is still read), with a `null` for each field a good read no longer carries, all at one moment, 1 µs after the project's newest row where that is later than the read's time. A good read sets the cursor to the state's own `daemon.stateSeq`, the sequence that snapshot reflects, and to its `daemon.stateId` and `daemon.schemaVersion`, and it deletes the project's held parts, which its snapshot holds; a failed read keeps them. Both writes keep the newest row of each field in `legion_current`, which a trigger fills in the same transaction and which the writes and `ReadCurrent` read rather than the whole history, `ReadCurrent` answering the board's cards and the set of issues the daemon reported in one statement. Both announce themselves on `dispatch_legion_state` (`StateChannel`) when they commit, which an open `/ws/live` `legion` view hears. After a batch, at most once an hour in each process, the intake prunes reads older than a week, keeping each project's newest. A read the daemon did not answer, or answered with another project's state, keeps the last good observations. So does a read whose answer is over the cap, which stops one byte past the cap: its `legion_reads` row names the cap and what the read knows of the answer's size, its Content-Length, or the cap and one byte where no Content-Length declares it, and its `bytes` is that size. A read whose settings carry no `dispatch_url` (judged first, so a daemon that runs no workflow is read with that reason), or whose state carries no `daemon.stateSeq`, a `stateSeq` of 0, or no `daemon.stateId`, records its observations and is a failed read all the same, so the read stays owed. The board's header names the failure of each failed read, and goes on naming it over the batches applied after it while the read is owed. `tree.go` is the one rule that places an issue in a tree (`TreeRoot`, and `IsLegionIssue` for which issues are Legion's) and `session_title.go` the one reading of a Legion session's title, which both the board (`api/legion_board.go`) and `legion/metrics` ask, the board reading phase work only for the issues its walk climbs onto (`PhaseWorkOf`) and the metrics every project's (`PhaseWorkKeys`). `legion/metrics` computes the four Legion delivery metrics from the same records (`Read`, then `Compute`); no route serves them. The edges are the store's pool, the six tables its migrations create and the fleet record it reads before a starting point (`dispatch-store`, `internal/dispatch/processes`); the held durable the intake runs under, and the delivery reads phase work and the metrics take session titles and merge times from (`dispatch-delivery`); the bus client the intake connects with (`envoy-listener`, `internal/bus`); the generated subject of the state lane (`contracts`); the actor a setting records (`dispatch-model`); and the GitHub App client the metrics read merge times through (`dispatch-auth`).

`issue.go` holds the one per-issue rule of what the Legion intake recorded, which the board (`api/legion_board.go`) and one issue's read (`GET /api/v1/issues/{key}/legion`, `api/legion_issue.go`) share, so a card and the issue's answer agree on the phase, the roles in a turn and the slot.
`IssueState` takes an issue's newest observations one by one (`Observe`): its phase and when Dispatch stored it, its slot, what it waits on as the daemon's own bytes, and the claim of each role with its state.
`Working` answers the roles in a turn, which a card shows, and `Roles` every claim, the roles `legionagents.Roles` names first and then any other by name.
`AdmissionOf` decodes the stored `admission` block, which the board and `ReadIssue` both read through it, and `Admission`'s `Place`, `Blockers` and `BlockersOf` answer where the daemon's waiting line puts an issue and which issues hold it.
`ReadIssue` reads one issue's state in one statement over `legion_current`: the issue's rows and the project's `admission` row, with `ReadCurrent`'s `null` rule, and no row of any other issue.
It also answers whether Dispatch saw the issue's phase start (`PhaseStartSeen`): whether `legion_observations` holds an older `phase` row of the issue whose value is not the newest one's, read through the index `legion_observations_point`.
`GetSettings` takes a `RowQueryer`, so the issue's read takes the setting, `ReadIssue` and the rest in one transaction, and its `configured` and its state answer one moment.
The announcement on `dispatch_legion_state` moves an open `/ws/live` `legion_issue` view of each of the project's issues too, beside the project's `legion` view.
