What Dispatch records of each Legion daemon's own state, so the Legion board and the Legion delivery metrics read Dispatch's tables rather than a daemon. A project's daemon is one `legion_settings` row (`store.go`), which `GET`, `PUT` and `DELETE /api/v1/projects/{key}/legion/daemon` read and write (`api/settings_legion.go`). The daemon publishes each change of what Dispatch observes as a state event on `notifications.legion.<token>.state`: one message for each transaction it committed, or consecutive messages split between events where a transaction's events pass 900 KB (`stateMessageBound` in `packages/daemon/internal/daemon/outbox.go`), its events in the daemon's own sequence (`legionStateMessage` in `packages/contracts`). Each message names the store its sequence is counted in (`stateId`, which the state route serves as `daemon.stateId`), and each message of a split transaction but the last carries `more: true`; `state_message.go` decodes a message. The intake (`intake.go`, `Intake`, which `cmd/dispatch` starts whenever it has NATS) takes the messages from the held durable `legion-state-events` (`bus.DispatchLegionStateDurable`, through `delivery.NewHeldDurable`), so one process at a time applies them, and it runs each project's messages one at a time on the project's runner: a message that arrives during a whole read of the project waits behind it and is judged against the cursor that read leaves. A project keeps at most 16 messages waiting on its runner (`stateMaxWaiting`), and a message past that runs beside the runner and makes no read (`crowded.go`, `judgeCrowded`). `apply.go` applies a message: it holds each message with `more` in `legion_event_parts` and applies nothing of its transaction until the last message arrives, so no row holds a value of a transaction that did not arrive whole, and for each transaction it writes, in one transaction, every value the transaction moved in `legion_observations`, one `legion_reads` row of kind `events` at the daemon's commit time, and the project's cursor in `legion_event_cursors`: the daemon's run, the schema version of the newest boot applied and the last sequence applied. The intake applies no message whose store is not the cursor's, and no message at all while no good whole read has given the cursor a store, since only a good whole read sets the cursor's store. It reads a daemon's `GET /legion/v1/state?view=observed` whole (`Intake.readWhole` in `whole_read.go`, through `client.go`, held to `RequestTimeout`, 60 s, and `ResponseLimit`, 64 MiB, and sending no credential) only for the reasons the `ReadReason` constants name, and no recurring timer reads a daemon. The observed view carries only the members `state.go` decodes, and a daemon of an earlier build ignores the query and serves its whole state, which the decode reads the same way. One rule decides every call for a whole read (`cursor.readFor`), and `cursor.go` holds the cursor it decides on, the cursor a read leaves (`cursor.afterRead`) and the cursor a write of the setting resets it to (`resetCursor`, `cursor.reset`). The Dispatch README describes that rule for an operator, with the stores the intake drops, the message that holds an owed read, the bounds of its hold and the intake's log lines (`cmd/dispatch/README.md`, "The Legion state intake"). The intake takes no starting point while a Dispatch process of an earlier build is in the fleet (`processes.EarlierLegionIntake`: a `server_processes` row at `legion_state_intake` 0 that heartbeated in the last 10 minutes), because that build still reads each daemon whole every minute. A whole read runs on the project's own runner, so it never interleaves with a message the project applies. It records how it went in `legion_reads` (kind `read`, with its reason) and every value that moved in `legion_observations` (`state.go` says which fields are observed, and the decode is loose so a daemon that grows the route's shape is still read), with a `null` for each field a good read no longer carries, all at one moment, 1 µs after the project's newest row where that is later than the read's time. Both writes keep the newest row of each field in `legion_current`, which a trigger fills in the same transaction and which the writes and `ReadCurrent` read rather than the whole history, `ReadCurrent` answering the board's cards and the set of issues the daemon reported in one statement. Both announce themselves on `dispatch_legion_state` (`StateChannel`) when they commit, which an open `/ws/live` `legion` view hears. After a batch, at most once an hour in each process, the intake prunes reads older than a week, keeping each project's newest. A read the daemon did not answer, or answered with another project's state, keeps the last good observations, and so does a read whose answer is over the cap (`readBounded` in `client.go`). A read whose settings carry no `dispatch_url` (judged first, so a daemon that runs no workflow is read with that reason), or whose state carries no `daemon.stateSeq`, a `stateSeq` of 0, or no `daemon.stateId`, records its observations and is a failed read all the same, so the read stays owed. The board's header names the failure of each failed read, and goes on naming it over the batches applied after it while the read is owed. `tree.go` is the one rule that places an issue in a tree (`TreeRoot`, and `IsLegionIssue` for which issues are Legion's) and `session_title.go` the one reading of a Legion session's title, which both the board (`api/legion_board.go`) and `legion/metrics` ask, the board reading phase work only for the issues its walk climbs onto (`PhaseWorkOf`) and the metrics every project's (`PhaseWorkKeys`). `legion/metrics` computes the four Legion delivery metrics from the same records (`Read`, then `Compute`); no route serves them. The edges are the store's pool, the six tables its migrations create and the fleet record it reads before a starting point (`dispatch-store`, `internal/dispatch/processes`); the held durable the intake runs under, and the delivery reads phase work and the metrics take session titles and merge times from (`dispatch-delivery`); the bus client the intake connects with (`envoy-listener`, `internal/bus`); the generated subject of the state lane (`contracts`); the actor a setting records (`dispatch-model`); and the GitHub App client the metrics read merge times through (`dispatch-auth`).

`issue.go` holds the one per-issue rule of what the Legion intake recorded, which the board (`api/legion_board.go`) and one issue's read (`GET /api/v1/issues/{key}/legion`, `api/legion_issue.go`) share, so a card and the issue's answer agree on the phase, the roles in a turn and the slot.
`IssueState` takes an issue's newest observations one by one (`Observe`): its phase and when Dispatch stored it, its slot, what it waits on as the daemon's own bytes, and the claim of each role with its state.
`Working` answers the roles in a turn, which a card shows, and `Roles` every claim, the roles `legionagents.Roles` names first and then any other by name.
`AdmissionOf` decodes the stored `admission` block, which the board and `ReadIssue` both read through it, and `Admission`'s `Place`, `Blockers` and `BlockersOf` answer where the daemon's waiting line puts an issue and which issues hold it.
`ReadIssue` reads one issue's state in one statement over `legion_current`: the issue's rows and the project's `admission` row, with `ReadCurrent`'s `null` rule, and no row of any other issue.
It also answers whether Dispatch saw the issue's phase start (`PhaseStartSeen`): whether `legion_observations` holds an older `phase` row of the issue whose value is not the newest one's, read through the index `legion_observations_point`.
`GetSettings` takes a `RowQueryer`, so the issue's read takes the setting, `ReadIssue` and the rest in one transaction, and its `configured` and its state answer one moment.
The announcement on `dispatch_legion_state` moves an open `/ws/live` `legion_issue` view of each of the project's issues too, beside the project's `legion` view.

The rules a Legion card carries beside the facts the daemon reports live here too, so the board route and the per-issue facts (`internal/dispatch/legionfacts`, which stores one `issue_facts` row per issue Legion worked) read one statement of each: the column table (`board_rules.go`), the slot-use rule (`SlotUse`), the waiting rule (`CardWaiting`) and the daemon's waiting line (`waiting_line.go`, `WaitingLine`). The facts consumer runs under its own lease, `legion-facts`, and its writes record their changes in the change log's outbox (`delivery_changes_pending`), which `delivery.DrainPending` moves into `delivery_changes`. It reads `legion_observations` by id, and the intake writes two projects' observations at once, so every insert into that table takes the observations' lock (`ObservationsLockKey`, `store.go`) before it draws its ids and holds it to its commit: the ids are commit order, and a reader never passes a row that commits later below it.
