How meaning search's vectors are made and kept. `embed` is the embedder client, Cohere Embed v4 on AWS Bedrock or Azure AI Foundry, whose identity every stored vector records. `embedqueue` embeds what the write triggers enqueue in `embeddings`: a woken loop (`duty.RunWoken`) that scans when `embeddings_enqueue` notifies `dispatch_embeddings` (migration 0151), when the coverage pass writes `embeddings` rows, or when the earliest pending row falls due, at most once per 5 s, claiming its rows so two processes never embed the same one, and never calling the model inside a write's transaction. The coverage pass (`Cover`) runs once at start with no lease: it adds what no trigger saw, repairs stale issue rows and then records each issue's inputs where its row holds its current text (`recordIssueSources`, into `embedding_issue_sources`), and, once the embedder has answered, drops vectors another identity made; the identity steps and the record step run again every 10 minutes (`identityRecheckInterval`) for as long as the process runs, and a pass whose closing report fails logs it at WARN (`dispatch embedqueue: coverage pass report failed`) and fails nothing. `GET /api/v1/search/coverage` reads its counts (`Coverage`) in one statement, so one snapshot, under a 10 s `statement_timeout`, past which it counts nothing and answers `503 SEARCH_COVERAGE_TIMEOUT`; the bound is the server's own so that it ends the statement while its caller still waits (the coverage probe waits 30 s), which then gets that answer rather than a cut connection and a `500`, and so that it holds where pgx's own cancel, a CancelRequest that needs a connection of its own, cannot reach a saturated server. It reads the window kinds through two partial indexes keyed on `kind` (`embeddings_window_embedded`, `embeddings_window_unembedded`), whose predicates test the kind by a regex no other index of `embeddings` can read, grouping them by the kind's position rather than by the kind so that no index's order is of use, under settings `planCoverage` sets without reading any statistics (sequential scans, sorts, parallel workers and JIT off): one bitmap heap scan over a BitmapOr of both indexes is then the only path to the window rows, and it visits each heap page holding a window once whatever the visibility map holds, the statistics record or the share of windows embedded, never testing a window's text. It builds and hashes an issue's text only where the issue's inputs changed since they were recorded.

`embed` signs in to Azure AI Foundry through Microsoft Entra with a federated assertion, so no Azure key is stored (`EntraTokenSource`). An exchange that drew no answer from Entra - a transport error such as a TLS handshake that timed out under load, the exchange's own 30 s timeout, or an answer whose body could not be read - is made again, at most 4 exchanges in all (`entraAttempts`), after a wait of 500 ms that doubles before each later one, while the caller's context and its deadline leave the time. An answer Entra gave, a refusal or a redirect the client refused among them, is not made again. A failure is never a throttle: the caller's batch is retried as any other infrastructure failure is.
