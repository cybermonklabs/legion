Every HTTP route body: issues, artifacts, asks, comments, messages, projects, search, and the assignee, rank, label and component-attachment writes, and the per-session list of what people wrote to an agent (`GET /api/v1/agents/{session_id}/answers`, `session_answers.go`), which every agent host reads on each model request. Search reads each ask hit's answer state from its row, and a resolved ask's last answer from its `ask.answered` events, before it answers. The per-session list's read model is the small package `sessionanswers` (`List`), which travels with its one route: a person's events whose `published_destinations` hold the session's own topic (`contracts.AgentSubject`), its sent message and comment deliveries, each item at its current words as a `model.SessionAnswer` with its relation to the session and its `dispatch://` and deep-link place; the outbox's tests read back through it, so the route reads what the publisher records.
The same package holds `sessionanswers.Latency`, the begin and end of each answers read this process serves, which `routeHandler` records for that route alone through `timedAnswersReads` (`Deps.AnswersLatency`, `session_answers.go`), timed from the moment the read enters the route's handler chain, as the access log times it, and which the keyword fill's pause reads (`textversions`, `dispatch-store`).
The largest package in the server (198 Go files beside their tests) and the one every Dispatch feature touches. It resolves an agent's actor through the listener's OIDC and routing packages, hence the edge to `envoy-listener`. The edge to `contracts` is a Go import as well as the wire contract. 47 of the package's non-test files import `internal/contracts`, the Go package `bun run gen:go` writes from `packages/contracts`, for the headers, bounds, codes, subjects, the going stream's frame names and the tool specs' argument fields that the server and its clients must spell alike. The response shapes go the other way: `envoy-dispatch openapi` reflects this package's route table and the Go types of its rows into `packages/contracts/schemas/dispatch-openapi.json`, which `bun run gen:api` renders into `src/dispatch-api.generated.ts` for the web app. It also runs the related-item check every issue create, ask and new decision block gets once its write commits (a search by the text's rarest words and by meaning, waited on for at most 5 s and recorded in `related_checks`), the no-write route and the records route over it, and the term-statistics refresh its keyword picker reads.

The related-item check of a write that asks a person a question offers more than one project's items. An ask create, a new decision block, and the POST form of `/api/v1/projects/{key}/related`, which `dispatch related` calls, also carry up to two answered questions of other projects (`other_projects`, read by `related_other_projects.go`). That leg searches by meaning alone, because the keyword leg weighs each word against the term statistics of one project. It starts as soon as the check holds its embedding, on a second connection mark the check takes before it opens the one-project read, and it reuses that embedding. The meaning stage then waits at most 300 ms for it, and ends the wait 25 ms before its own deadline. A leg that fails, that overruns that wait, or that got no connection leaves the one-project answer whole, records no reason and offers no item. A check that fell back to keywords offers none either. An issue create and the GET form of that route ask for none, so the dashboard's new-issue dialog draws the asking project's items alone. Each offer of an ask create is one `write_suggestions` row of role `other_project`, beside that check's `related` rows, and the outcome sweep resolves it like any other row. A new decision block's offers reach no row, because such a row is keyed by the ask the offer was made on and a block has none. `GET /api/v1/related-checks` answers `other_project_offers` beside the counts it reads from `related_checks`: the ask creates of the window that made such an offer, counted once each. The check answers no `decision` any more, and `persistSuggestions` writes no row of that role.

`GET /api/v1/issues/{key}/legion` (`legion_issue.go`) answers one issue's Legion state from what the sampler recorded: `{issue, project, configured, state, read, runs_revision}`.
`configured` is `false` when the issue's project names no daemon, and the answer then holds `state` `null` and `read` `null`, and still the runs' revision (`workflowstore.IssueRunsRevision`).
The route refuses no project, because the daemons of other projects write runs to this Dispatch too, and an issue's runs are its own whatever daemon its project names.
Its one refusal is `404 NOT_FOUND`, for a key Dispatch holds no issue of.
The board, by contrast, answers a project with no daemon `404 LEGION_NOT_CONFIGURED`.
`readLegionIssue` reads the issue's project, the project's setting (`legion.GetSettings`), the newest read of its daemon (`readDaemonRead`, the board's header read), the issue's state (`legion.ReadIssue`) and the runs' revision in one read-only, repeatable-read transaction, so `configured` and the state answer one moment.
The board and the route take an issue's observations through one rule (`legion.IssueState`), so a card and the route agree on the phase, the roles in a turn and the slot.
The `/ws/live` kind `legion_issue` (`live_frames.go`, `parseLegionIssueLiveView`) names one issue and nothing else, and its snapshot and deltas carry the route's body, which the hub reads through `readLegionIssue` too (`readLegionIssueView`).
No project without a daemon refuses the view: its body says `configured` `false`, and a write of the project's daemon setting moves it to `true`.
Its one refusal is the route's `404 NOT_FOUND`, sent once as an `error` frame (`viewReads.refusal`).

The live paths hold bounded state per reader. The event stream relay (`event_stream_relay.go`) is the live paths' one reader of the event log: its first subscriber starts a generation that listens on `dispatch_events` and reads each commit once, encoding each event's frame once for every subscriber, and the cancel of its last subscriber stops it at once, so a process nobody subscribes to holds no LISTEN connection of the relay's and the relay reads nothing. The events view of `GET /ws/live` (`live_events.go`) subscribes to it. A resume at or below the relay's head is replayed at most 256 events whose frames total at most 1 MiB, counted by rows; past either bound it is replayed nothing. Its `events_start` says `replay_complete: true` only when the replay is everything the page lacks, which includes a resume ahead of this process's relay but within the log; a page whose subscription starts without it refreshes what it shows. A subscription whose 64-slot relay subscription overflows catches up from the log within the same bounds and goes on; past them, or when the relay's generation ends (an event log reset, shutdown), it ends as `behind` and the page subscribes again.
The check of a reset that the relay and the events view share lives in `events`, beside the log it reads, where the keyword fill reads it too: `events.EventCursorCheck` reads the newest event's id and the `created_at` of the event at a reader's cursor, and `events.EventLogWasReset` says from those whether the log was reset under that cursor.
The delivery hub takes its events from the relay's feed (1,024 slots) and itself listens only on `delivery_changes`, `delivery_freshness`, `dispatch_legion_state` (`legion.StateChannel`, the announcement of the sampler's read of one project's daemon and of a write of that project's daemon setting, which marks that project's Legion views, its board's and its issues', `dirtyLegionProject`) and `dispatch_workflow_runs` (`workflowstore.RunsChannel`, the signal a write of one issue's run that stores something new sends at its commit, which marks that issue's `legion_issue` views, `dirtyLegionIssue`); it also stops with its last view, a closed feed makes it reload the open P0 issues and recompute every view, and an event that arrives during a view's read and touches the answer that read gives recomputes that view again.
At each connection of the hub's listener, the first one included, the hub catches up the change log and then marks every Legion view, the boards and the `legion_issue` views alike (`dirtyLegionViews`, `delivery_live_hub_intake.go`).
Postgres sends a notification only to a connection that listens, so one sent while the listener was down, or before its first `LISTEN`, is lost, and the catch-up of the change log marks no Legion view.
So each Legion view is read again at each connection, and a read that finds nothing moved sends nothing.
A comment's mentions are resolved in its request, up to 8 lookups at once, each bounded at 250 ms, so a listener that answers none delays a comment with up to 8 mentions by one 250 ms timeout and each further 8 mentions add one (ceil(k/8) timeouts for k mentions); the attempts commit pending with the comment, and the response returns them pending. The mention sender (`comment_mention_sender.go`) sends them after the response on one FIFO lane per recipient (the pinned session, else the target as written: `role:X` shares its holder's lane only when its lookup found the holder, and an unanswered `role:X` is keyed by its string, so two comments to one recipient can then arrive in either order), 8 lanes at once and at most 4,096 sends queued; once shutdown starts it queues nothing more (a refused send is logged at WARN), starts no queued send and gives the sends in flight 10 s. An attempt no sender finishes is the delivery sweep's (`delivery_sweep.go`, `resumeOwedDeliveries`): one process's maintenance loop, under the sweep's lease, sends once a minute every pending attempt that is the latest of its target, is claimed by nobody or by a claim that lapsed, and was created between a claim lease (one minute) and the duplicate window ago (`model.OwedMentionAttemptSQL`), whichever process left it, through the same claim; an attempt younger than the lease is left to the process that queued it, so the sweep never takes a live process's queue out of order. So the attempts a stopping process refused, left queued or could not queue for the bound are sent by a later pass once they have waited a lease (in a rolling update the successor is up before the old process stops), and a killed process's send in flight by the first pass after its claim lapses, within a minute and a sweep interval of its taking, under its own idempotency key, so a send that had landed is dropped as a repeat. The same pass settles, superseded, every pending attempt no sender holds that a later attempt of its mention has already delivered the comment in the place of (`settleSupersededMentions`), which nothing else binds to. Each pass reads the partial indexes `message_deliveries_pending` and `comment_deliveries_pending` (pending rows by `created_at`): with nothing owed it is one statement a minute that reads no row; no event can drive it, since a killed process sends no signal and a stopping one refuses its sends after its lifetime ends. Order holds within one process only: an attempt resumed after a crash or a handoff can arrive after later comments. A session a mention may reach also gets the new comment's own copy on the route, the claimant, an author or a follower route only by one rule the outbox applies when it publishes (`attempt.leftToMention` in `internal/dispatch/outbox`), keyed by the one session each attempt counts under (`model.MentionSession`: an unanswered `session:<id>` mention counts as `<id>`'s, and a route equal to an unanswered mention's target follows that target's attempts). What the attempt came to - sent, live, abandoned, or owed to the sweep, each a predicate over its row in `internal/dispatch/model`, all built from the sweep's own definition - decides the copy and which of the outbox, a sender's claim and the sweep acts on the attempt; a copy held back for a resumed mention is a `comment_fallback_copies` row, which the outbox's fallback pass publishes to its one destination only once the resend fails, never touching the event's own row. `publishFallbackCopies` in `internal/dispatch/outbox/mentions.go` is the protocol's one description. So a mentioned session loses no comment through a kill. The copy on the own topic of a session with a failed (or abandoned) attempt, and every fallback copy, carries that attempt's mention dedupe key, `agent.<session>.<comment>:<target>:<the mention's mode>` (`contracts.AgentSendDedupeKey` of `model.CommentMentionIdempotencyKey`, the lowest failed target's when there are several; the mode in it is the one the comment recorded on the mention and never an attempt's own, every attempt of one mention sending under that one key), in place of `dispatch-<event id>`, which every other destination carries and which stays its event id. So a send the killed process had handed the listener before it died, whose resend then fails for good (the listener down after the restart), is not shown twice: the host drops a frame whose named dedupe key it claimed within 72 hours, and the stream, whose MsgId is the dedupe key and the subject, also drops a second message with that key on that subject within its 72-hour duplicate window. A session no mention reached never claimed the key and is shown the copy. An unanswered `role:X` mention reached under any other string, and a `role:X` route whose own lookup went unanswered, name no session to compare, so that session can get both copies. An agent view (`live_agent.go`, `agent_stream.go`) queues at most 8 MiB of frames; past that it ends as `behind`. A page that stops reading meets the socket's own bounds first (#2449): the writer's 10 s write deadline (`liveSocketWriteWait`) ends the socket, which holds at most 16 of the hub's frames (`liveSocketQueue`) and 64 stream frames (`liveSocketStream`); the agent view's 8 MiB bounds only what it buffers while the socket writes slower than the session produces.

It also runs the suggestion outcome sweep (`RunSuggestionOutcomeSweep`), which judges whether a write's `advice.suggestions` were acted on or overridden: a woken loop (`duty.RunWoken`, with no lease: each page holds the `suggestion_outcome_cursor` row `for update`, which serialises two processes) on `dispatch_events`, passes at least a minute apart, each reading only the events after its cursor (`suggestion_outcome_cursor`) and at or below the safe horizon of the server's one `events.Horizon`, which the server hands it (`Background.EventHorizon`) and which the live event feed reads through too, and the suggestions not yet swept (`write_suggestions.swept`), so its work follows what changed rather than how many suggestions are still pending, and its cursor never passes an event that could still commit. The keyed writes' maintenance sweep (`RunMaintenanceSweep`: the Idempotency-Keys past their window, the spent DPoP proofs, the command bar's answer runs past their window and its run records past their thirty days, then the deliveries a dead process left owed) is a timer of its own, once a minute across the processes under lease `suggestion-outcomes`, because no commit announces any of them.

A write route's transaction runs in two phases. Its read phase holds no transaction id while no earlier build is in the fleet (`dispatch-store` says what such a build adds): it takes the owner's advisory lock before it reads what the write decides on (`requireOpenOwner[Status]` and `lockIssueOwners`, through `store.LockOwnerAndRead` and `LockOwnersAndRead`, or `store.LockOwner` and `LockOwners` where the lock guards no read), reads that in the statements after that lock - never in the lock's own statement, whose READ COMMITTED snapshot is taken before the wait and would miss a close committed meanwhile - and does all its document work through `Docs.Join` and its write advice (`writeAdvice`, which counts the counted event the write is about to append); the routes that read or take another lock before their owner lock, or lock a row before their first write, are named under the lock order in `dispatch-store`, the delivery-attempt routes and the reads of which owner to lock among them. A joined route's writes are queued on the ledger in the order it makes them (`docs.Ledger.Queue`, which `api/write_queue.go`'s `queueExec`, `queueEvent`, `queueStampedEvent`, `queueLoggedEvent`, `queueNewAskReferences`, `queueEditedReferences`, `queueItemReferences`, `queueEditedItemReferences` and `queueReplacement` queue on), and `ledger.Commit` sends them as one pipelined batch, the write phase (`store.WriteBatch`): Postgres runs every statement back to back and the route waits on the batch once. No statement's result is read in Go before a later statement is sent: an event's stamp names the event's id as the events id sequence's `currval` (`store.LatestEventID`), a row's time and id are read in the read phase, and what the response needs (the appended event) is filled by the statement's callback after the batch has run. The first failing statement or refusing callback (a guarded update's `ALREADY_ACTIONED`) stops the write phase and `Commit` returns that error unchanged, so the route answers what it answers for that error. The issue create and the issue patch join a ledger for their document work (the create's spec; a close's withdrawal or a reopen's restoration of the issue's asks) but make their own row writes inline, a statement at a time, because their results steer the route: the create's `update projects`, whose number it checks, its issue, blocker, component and spec-artifact inserts, the external-link insert whose conflict answers with the issue already linked, its advances (`writeIssueAdvances`), and the `near_copy_checks` row of a near copy let in because its refusal's row could not be confirmed (`writeNearCopyCheck`), which admits no create when it cannot land; the patch's issue update, claim release, components, blockers, external links and advances, whose refusals (a component or blocker refusal, a taken external link, a priority that is gone) it answers. Each reads, does its document work and advises before that first inline write (`writeAdviceBefore`), reads the row back after it for its event, and queues every event, with its documents' writes, on the ledger, which `Commit` sends as one batch after the inline writes. The create's other `near_copy_checks` rows are written in no transaction of the create's: a refusal's is a statement of its own before the create's transaction opens (`recordNearCopyRefusal`), and a create's is written after its commit (`recordNearCopyCheck`). The claim (`claimWrite`, `api/issue_claim.go`) has no document work and joins no ledger: it reads before its first write and sends its update and its event as one batch of its own (`store.RunWrite`). Message create sends the lock of a parent whose block its reply names, that parent's owed block index, its insert, its request-key recovery point, its own index and references, its event, its stamp and a targeted message's first delivery attempt as one batch of its own (`store.RunWrite`). An issue message's edit and delete (`editMessage`, `deleteMessage`, `api/message_corrections.go`) have no document work either and send theirs the same way, as one batch of their own: the edit the body it replaces (`post_body_history`), its update, its index and references and its event with its stamp; the delete the body it clears, the update that clears it, the index of its empty body and the tombstone of its blocks' excerpts and windows (`clearDeletedPostBody`, `refs.TombstoneItem`), the settle of its pending sends, their receipts, and its event with its stamp. A comment's delete (`deleteComment`, `api/comment_delete.go`) is a joined route and queues the same clear and settle on its ledger, beside its document's writes. Each delete reads its answer, the post's delivery attempts among it, in the read phase, and sets in it the attempts its settle leaves failed: the settle's callback refuses a count other than the one that read found (`queueDeletedPostSettlement`). The results write (`POST /api/v1/issues/{key}/results`, `api/results.go`) makes its two writes a statement at a time - the batch appending `result.recorded` (`appendEvent`), then the `check_results` insert - and its read phase is bounded as well as xid-free: it resolves the check and reads the block's words out of the live Verification document before its transaction opens, takes the two issues' owner locks, and under them judges those words by the version and digest `document_blocks` holds for the block rather than reading a document while it holds a lock (`recordResultWithFreshWords`, this route's `resolveThenLock` cycle, and `indexedCheckBlock`); either of that pair moving gives the locks back, reads the words again with nothing held and takes the locks once more over the pair that read was made against, and a check reworded at every attempt (`resolutionAttempts`, two) is `409 CHECK_CONTENDED` with nothing written, carrying `Retry-After: 1`, the second the version that moved it needs to land. A comment's or an issue message's write indexes its blocks and the mentions each holds beside its own references: the index is planned in the read phase against what the item's block index holds and queued with that reconciliation (`queueItemReferences`, `queueEditedItemReferences`, `refs.ReadItemIndex`, `refs.PlanItemIndex`), and a block a reply names is read there too, with the index its parent owes (`planReplyBlock`, `refs.PlanItemIfOwed`), whose statements the same write phase carries. `putThreadRead` takes the thread owner's lock exclusively (`store.LockOwnerAndRead`), so a thread mark waits for a writer in its read phase rather than race that writer's trigger; a mark that moves the caller's row then takes the lock of the project its event names before its update, so it waits for that lock holding no transaction id too. The Inbox's Mark all read and its dismissal take their owners in shared mode, and the thread mark is ordered against them by that owner alone (`markInboxReadThreads`, `api/inbox_read.go`). The read phase still holds its pooled connection, idle in transaction.

An access token the secrets broker issued is the one credential that proves a session of its own (`broker_token.go`), and it names either the person it acts for or a service: the fleet of a machine nobody has signed in on, the service of a read entry, the account of an exchange account entry that names no person, or a job's identity as its job entry lists it (a pod's service account, a workflow as `<repository>/<workflow path>@<ref>`, or a Google account). `brokerTokenActor` carries the token's project scope and list on the credential (`model.Credential.ProjectScope`, `Projects`). `writeNeedsASignedInPerson` (`project_scope.go`) lets a broker credential that names a service and no person write only under the project scope `named` or `public`: the two shapes of a job's token, and under `named` an account entry's token that names no person (`<service account>==`), whose service is the account. Dispatch records each such write under its session and its service and no person (`model.Actor.Service`), and refuses every other such write `403 SIGN_IN_REQUIRED` naming `agent-secrets login`. The rule names the scopes that write, so it fails closed: the one other scope that reaches it today is `person`, a machine's token that names no person, which reads everything its session may read and writes nothing, since nobody signed in on that machine and no job entry lists it. The check's decision is one function, `signInRequired`, which `whoami` answers as `sign_in_required`, so a client reads the decision rather than guessing it from the owner and the service. `writeNeedsASignedInPerson` is the outermost of the three checks `Register` wraps every mutating route in, before the project and session scopes, so a machine's caller is told it may write nothing at all rather than which project the write it tried belongs to. A job's token and an account entry's token naming no person hold no OAuth scope, so a route that needs `person` or `approve` refuses them at the scope gate, and `GET /api/v1/whoami` answers a job's token with no owner, its service, its project for `named` and null for `public`, and `project_scope` `named` or `public`; whoami answers a machine's token `project_scope` `person`, and leaves the field out for every credential the broker did not issue. The credential-relay rows (`credential_requests.go`) carry the person's own sign-ins beside their machine logins — `GET /api/v1/signins` and `POST /api/v1/signins/{id}/revoke`, each naming the person from Dispatch's own session, so nobody reaches another's — and `GET /api/v1/credentials/capabilities`, which answers `{"machine_code_page": <bool>}` out of the broker's RFC 8414 metadata and, alone among these rows, answers rather than 404s for a Dispatch with no broker, since a 404 would leave the page unable to tell a deployment without a broker from a route it failed to reach.

A read-only token is any credential that holds `read`, and it may only read. The broker mints it from a read entry (the OAuth scope `read` alone, the project scope `none`, a service and a fixed session, no person and no project), and narrows any trade that asks for `read`: that token keeps the identity the same trade would have had, under the narrowed project scope `read-named`, `read-person` or `read-none`, and may carry a cut (`as_of`). `brokerTokenActor` marks its credential `model.Credential.ReadOnly`, with the cut as `model.Credential.Cut`, and gives it the `person` scope alone where it acts for its person, never `approve`, and no scope otherwise. A personal token minted with `read`, alone or beside `person` and never beside `approve`, is read-only too: it is kept in `agent_read_tokens`, which a build before it never reads, `personalTokenActor` looks a bearer up in both tables and marks such a row the same way, and `PATCH /api/v1/me/agent-tokens/{id}` changes no token to or from `read` (`agent_tokens.go`). Every GET row of the table has one read class in `readClasses` (`read_classes.go`): a read, which writes nothing but the record of the token's use and caches Dispatch rebuilds from what it holds, or a GET that writes, with a `WriteNote` naming the write. `register` refuses to mount a table with a GET row that has no class, a GET that writes with no note, or an entry that names no GET row it mounts (`readClassRefusals`). The gate `refuseReadOnlyToken` is the outermost check of every row and of `GET /ws/live` (`routeHandler`, `liveSocketHandler`). It reads a broker token from `decideBrokerToken`'s decision and resolves a personal token itself, once, carrying the result for every later layer (`resolvePersonalToken`). It answers a read-only credential `403 READ_ONLY_TOKEN` on every row that is not a read and on `/ws/live`, and one that carries a cut `403 AS_OF_TOKEN_NOT_SERVED` on every read but `GET /api/v1/whoami`, which names the cut. Both come with no `WWW-Authenticate` challenge, before the scope gate, the sign-in check, the `Idempotency-Key` and the handler. `GET /api/v1/issues/{key}/results` is a read: a read-only caller's read asks GitHub exactly what a writer's read made at the same moment asks and answers what it answers on the rows stored then, stores no `pull_request_heads` or `branch_commits` row and no event, and keeps no answer after its request. It reads the writer's claims and settles (`server.commitPulls`), the unseen holds and the default-branch cache without writing them, and each of its reads of the stored heads runs the writer's own statement over the stored rows with that request's own answers laid on (`results_comparison.go`); what it changes in the process is what a writer's read changes there: the GitHub client's token caches fill, lapsed unseen holds are deleted, and a rate limit GitHub answers is recorded in `github_rate_limits`. Each read-only read at the present time makes a writer's reads, on the same installation's rate limit: a pulls read per result commit that no stored head and no writer's claim or settle covers, the commit-message pages of each pull request it names that nothing else attributes, a compare read per walk step that no fresh row and no unseen hold answers, the check-runs read of a check CI proves, and the default-branch read where the cache entry has lapsed. A poll every N seconds of a read that makes R of them costs R × 3600 / N an hour against the installation's limit, at least 5,000 an hour; while a limit GitHub answered is recorded, the client sends no request on that installation's token for any caller (`githubapp.Client.send`), so a writer's read-through is refused, and its claim then holds the commit off for five minutes (`delivery.CommitPullReadStaleAfter`), a check CI proves answers `unread`, the CI reconcile's pass ends at the limit, and each step of the delivery reconcile is refused. No cap bounds a read-only caller's reads; the undo is ending the poll, or ending the token: revoking a personal token, or the sign-in or the dev box's machine login a narrowed token came from, or, for a read entry's token and one narrowed from a pod's, a GitHub workflow's or a Google machine's identity, taking its entry out of the broker's settings and waiting for the token to expire; Dispatch stops serving a read-only broker token at most ten seconds after the broker ends it (`ciphertoken.AffirmativeCacheTTL` after an introspection of up to `introspectTimeout`; `cmd/dispatch/README.md`). The route index and the OpenAPI document do not carry the read class, and `/ws/doc/{room}`, which reads no broker token, answers a read-only broker token `401`.

The command bar's answer path is the going routes (`going_routes.go`, with the record's reads and writes in `going.go`). `POST /api/v1/going/requests` records the question, the project it is asked of and the context chip (`{path, project, issue, block}`), answers `201` with the run, and then answers it in the background (`startGoingRun`), bounded by the 30-second `ends_at` the record holds. Words that are an issue's key, or the very key, title or name of a hit the keyword search finds for them, are the fast tier (`goingNamedHit`, `going_decision.go`): the run stores that hit's `item` frame and its end and asks no model at all. A run of any other words with a measured decision model (`Decider`, `going_decider.go`) first makes one `agentloop.Decide` call to its System One endpoint, bounded at one second. That call asks three questions (`goingDecide`, `going_decision.go`): which catalogue action the words ask for, or `none`; whether the words are about the chip's item (`page`), items they name (`named`) or nothing; and chart or prose, which the run does not read. The actions it offers are only the twenty that `going/decision_models.json` measured the decision model on, the write tools `goingWriteTools` marks `Proposed`, and of those only the ones the caller's credential may run (`GoingCatalogue.runnableBy`); never every write tool, since nothing measured the model's choice among the others, and none at all to a caller whose token needs a proof on each request. The run then stores the `decision` frame: the action chosen, the line on top of the bar it gives (`ask` for `none`, `file` for `dispatch_issue`, `do` for any other action), and the context. A decision call that fails, or that names no action it was offered, gives no decision frame, and the answer runs as with no decision model. The answer itself is `going.Answerer.Run` (component `envoy`). The run gives it the read tools its caller may call; the answer only reads and changes nothing. After the text frames the run stores a `block` frame where the structured reply drew a block the words ask for, and a `roster` frame `{age_ms, source}` where the answer read the roster. An answer that came as prose writes no block. `POST /api/v1/going/requests/{id}/cancel` sets `going_requests.cancelled_at`. After that, `goingAppendEvent` stores no frame that does not end the stream, so the answer stops at its next delta on any pod; on the pod that runs the answer, the cancel function the server holds in `goingCancels` stops it at once. `GET /api/v1/going/capability` answers `{answer: {configured, model, blocks}, decision: {configured, model, reachable}, session, label}`, and names no endpoint and no credential.

The read tools of a run (`going_reads.go`) are reads this table serves, made in process through the functions those routes answer with, as the run's author: the roster of `GET /api/v1/agents` (`agentRows`), with the claims each session holds on the open issues the run's person may read and, after the listener's sessions, each session the listener lists no more that still holds such a claim, marked gone (`goingRosterClaims`), an issue's or a project's progress from `GET /api/v1/issues`, a project's architecture counts (`architectureTree`), the three delivery reads, and `GET /api/v1/projects/{key}/activity` (`project_activity.go`), which counts the events of a project's issues per ISO week and by kind over the last weeks (default 8, at most 52) and lists every week of the span, a week with no event as 0. The bar's agent reads the roster through `GET /api/v1/agents?limit=50`, whose answer it is told with the same claims and gone sessions (`goingRosterTold`), the route's own answer unchanged for every other caller. A caller is offered a tool only where its credential may call every row the tool reads (`goingReadsFor`). A credential scoped to one project is offered no roster and no delivery read, and every other read is held to the run's project. `Register` refuses a table that does not serve a row a read tool names. The roster read waits out a `503 ENVOY_REFILLING` where the run keeps 5 s for its answer after the wait, and otherwise reads the sessions Dispatch's own rows name; the `roster` frame says which. A block's spec names one read, its arguments, its table and its fields, and never a number. The run parses the spec against its kind's schema, makes that read again as the author, and fills the block from the read's rows alone (`going_blocks.go`). It drops a block of a kind the words do not name, a chart among them, a read the run may not make, and a read that cannot fill the block, a chart of fewer than two points among them; the answer then stays prose and links.

A run of the command bar's agent is worked by the agent process (`envoy-dispatch agent`, component `envoy`), which keeps each run's model loop and makes every read and write of Dispatch as a call to this server. The contract between the two is agent/v1 (`going/agentwire`): seven calls over a Unix socket in a directory only the server's user can open, each one connection carrying one frame each way, a 4-byte length and one JSON document with a size limit, under the 32-byte secret the server wrote to the agent's standard input at its start, compared in constant time (`going_agent.go`, `AgentListener`). `hello` frees the leases of the agent's earlier instances; `claim` waits for a ready run of `going_runs` and takes it under a lease, a fresh token each claim, with at most `goingWorkingPerPerson` runs working and `goingQueuedPerPerson` queued for one person; `renew` extends the instance's leases and carries its health figures; `step` saves one step of a run with the frames its person's bar shows, the text of a `reply` frame that answers written so each issue key it names bare, as text, that a tool result of the run holds is the issue's link, which the bar draws as the issue's chip, while a key no read of the run returned stays text, and so the words the model gave a link to an item stand beside the item's chip, each item read as the run's person may see it (`going_link_words.go`); `frames` appends frames to a run's events and saves no step, the frame of a tool call as the call starts, which the bar shows while the call runs; `call` is one read or write of Dispatch by a tool's name, a GitHub read, a web read, a plan, Auto-review's answer, a block the server draws from the run's saved results, or a line call, which asks which line on top the decision model reads the run's words as and records nothing (`going_agent_line.go`); and `end` ends the run's turn. The agent makes a line call as a turn of a run whose line is Ask or none starts, since an Ask there may be only what the bar read before the decision model answered. Every step, frames, call and end carries the lease token, which the server checks in the transaction that writes it, so an owner whose lease ended writes nothing, and a NOTIFY on `GoingRunsChannel` wakes the waiting claims and renews of every process.
A `words` call, which records nothing either, answers how many words the bar draws of a reply in prose that would end the run's turn, each link as its item's chip, from the text `step` would store, which also leaves out each fenced code block that holds a block the run drew or whose info string is `draw` (`going_agent_words.go`, `going_link_words.go`), and the agent gives a reply of 120 words or more one more model turn to say it in fewer.

A run acts with its grant (`going_grant.go`). The request that starts a run, or approves its plan, records whom its credential names and by what, with no secret (`recordGoingGrant`, `going_run_grants`): a sign-in by its sessions' generation and its cookie's expiry, a sign-in through IAP by its login alone, a personal token by its row, and the header identity by its login; any other credential, a broker token, the shared token or a service token, is refused `403 RUN_NEEDS_PERSON_CREDENTIAL`. Each call of the run is made as the caller the grant resolves to at that call (`goingGrantCaller`), checked against the store as it is then, so a sign-out, an expired sign-in, a revoked token or a lost membership refuses the run's next call and the run stops with that reason; an IAP grant, whose assertion nobody keeps, lasts until the run's working budget ends. That caller carries the command bar's act, `model.ActorAct` with `Agent` `command-bar` and `Run` the run's id, so each change records the person as its actor, through the command bar.

A run changes nothing but through a plan its person approves (`going_plan.go`). The agent's plan call carries the changes the model proposed with `propose_plan`: the server checks each against its tool spec, reads as the person the item it changes, its value now and the holder of its issue's claim, and keeps the plan (`going_plans`, `going_plan_rows`) while the run waits. It refuses a plan with a `dispatch_issue_update` change that reopens a closed issue beside a field the issue route refuses on a closed issue - any but the rank's neighbours and the components, and `external_links` that add a link the issue lacks - since that row would be refused `409 ISSUE_CLOSED` when it ran, and its words tell the model to propose the reopen alone and the other fields as a second change whose needs name the first, as a person on the issue page does (`goingReopenRefusal`). A `dispatch_issue_update` change that sets `include_children`, `unlink_children` or `include_parent` is never sent to `POST /api/v1/issues/{key}/status-change`, whose single-issue writes no one landing and no Undo could cover: the plan call writes it out first as one update change for each issue the option changes (`expandStatusOptions`), in that route's own order and from its own reading (`readStatusChange`), each needing the earlier rows of its parent or child, so each row keeps its own approval, landing and Undo; a plan the rows grow past `goingPlanMostRows` is refused. `GET /api/v1/going/runs/{id}/plan` reads each waiting row's item again; `POST .../plan/approve` takes each row's tick and edited values, moves the run's grant to the approving credential and makes the run ready; `POST .../plan/revise` takes the person's words for another plan; and `POST .../plan/reject` ends the run. Which rows wait is the person's mode (`going_modes.go`, `user_going_settings.mode`): in Ask every row waits; in Auto-review the agent's review call names the rows the person's words ask for, and the server lets through those of the classes `goingAutoReviewClasses` names; in both modes a row of a class `goingClassesThatWait` names, a row whose event the outbox would deliver to an agent session (`outbox.WouldDeliver`) and a row of an issue a session claims wait. Each change of what waits for a person appends `going_plan.updated` `{login}`, and `GET /api/v1/me/going-plans` lists the waiting plans the Inbox shows.

Every read and write of a run of the bar's agent goes through the server's own route table in process (`going_writes.go`, `goingInProcess`), as the run's person, with the command bar's act beside them, named on each request's context and by no header. So every check a route makes - its auth class, its scopes, the project and session checks, the claim's rules - runs on each request exactly as on a request off the network, and a route's refusal is answered as the route answered it. The agent's calls (`going_agent_call.go`) run at most `goingCallSlots` at once, each on a context of its own bounded by `goingCallTime` and under a recover, as the person the run's grant resolves to at that call, after its lease is checked. A write tool runs only as the approved row of the run's plan that its call names (`going_plan_run.go`, `rowGate`): any other write is refused `WRITE_NOT_APPROVED`. Before each write of a row - its first try, and a second try of its call key whose own write has not landed - its item is read again as the person, and a row whose item changed since its approval waits for the person again (`ROW_WAITS`), saying what of its call already landed; a read refused as the person (a 4xx) is left to the write's own refusal, and a read that fails ends the call failed with nothing written. The row keeps the key of each such earlier try (`goingRowRecord.Resumes`), and its next try, under a new key, takes over what the newest landed, matched by each request's digest (`adoptLandings`, which moves those landings to the new key), so a close's reason is posted once; it takes them over before the change's translation can refuse (a reasoned close of an issue another person closed meanwhile), so the refusal says what landed. A refusal of the translation is answered as the call landed only where the call's own request landed. A row whose needed row failed or was skipped is skipped (`ROW_SKIPPED`), and a row whose call panicked is kept failed (`GOING_ROUTE_FAILED`, status 500), saying what of the call landed before the panic, the panic answered and logged with its stack. An upload's read of the name it writes is held to its approval too (`uploadChanged`): the row's value is the document of the name with its text now, so it is sent over a document or file only where its approval showed that artifact with that text, and a document made, written, edited without a new version or removed since makes the row wait again. Such an upload expects the artifact at the latest version its read found, a condition on the request's context that the upload route decides under the owner's lock (`goingCondition.ExpectVersion`, 409 `DOCUMENT_CHANGED` with nothing written), and names the token of the read beside it where the read answered one; a file, and a document outside the Proof schema, have no token, so the version is what holds them. A row's words name each row by its action and item, as the page does, never by number; its code and status stay in the row's own fields and the log.

A request of a call has landed when its route's transaction committed, whatever status its answer carried (`going_landed.go`): each request carries its landing on its context (`goingRunLanding`), and `goingInProcess.Do` hands its route the commit step that writes the request's `going_landings` row - keyed by the run, the phase (`do` or `undo`), the step, the call and the request's number within the call - inside the route's own transaction, so the change and the record of its landing commit together or not at all, and a stale owner's write is refused and rolled back. A route that answers what its transaction found and left hands the landing, just before its commit, the function that builds that answer (`goingRecordAnswer`). The landing builds the value in the commit step, after the transaction's write phase has run its queued writes, so a value that phase fills in - the id of the event it queued, as an opened ask's `opened_event_id`, or the `last_seq` an issue update's events leave - is recorded as the route answers it; the route calls the same function for its own response, so the record and the response are one value. A second try of a call reads the rows of its key: a request that landed is answered from its row and not sent again, and the next one is sent; a second try while the first still runs waits for it (`goingCallKeys`), and across processes the key's primary key holds the same line. A route's bookkeeping that commits before the route can refuse is no landing of the request: it commits outside the request's commit step (`store.WithoutBeforeCommit`).

`POST /api/v1/going/runs/{id}/undo` (`going_undo.go`) walks the run's landed calls newest first and undoes each as the credential that pressed Undo, in process, by the undo the row's tool states (`goingWriteTool.Undo`): `write_back` writes back the value the call found, field by field, only where the value now is the one the call left, and keeps and names a later value another writer left - an edit of a comment or an issue message among them, whose `PATCH` route answers the body it replaced (`previous`) and takes the undo's write back only while the post holds the body the edit left (`goingCondition.ExpectBody`, `409 COMMENT_CHANGED` or `409 MESSAGE_CHANGED`), a post deleted since kept and named deleted with no word of its body; `reverse` calls the row's reverse route; `close_created` closes the issue the call created; and `not_undone` names a message, a broadcast or a review "sent, not undone", and a delete of a comment or an issue message "deleted, not undone". A landed call is the row's whose key ran it or whose earlier tries the row keeps (`goingRowRecord.Resumes`), so what a try landed before its row waited again stays that row's to undo whether the person unticks the row, approves it again with other values, which its next try sends anew, or has not seen it run again; a call of which only the requests it sends before its own landed - a close's reason - is named "sent, not undone". What a call found and left is read off what its route recorded beside its landing, never off a read made since. An undo sends one request at the most, which lands under the key of the call it undoes in phase `undo` (`goingUndoLanding`), so a second press answers each call whose undo landed from that landing and sends nothing twice. Whether it landed is read from that landing, never from the status its route answered, so a request answered below 300 that committed nothing (a follow of a session that follows the ask already) says the undo changed nothing, not that it reversed the change. That line, marked `unchanged`, and the line of an undo that keeps a change another writer made since the run (`409 GOING_UNDO_CHANGED`, found by the undo's read with nothing sent or by its route's refusal) are recorded as the call's undo landing in a statement of their own (`recordUndo`), so a second press answers them from there too.

A change of a run's plan that the bar can never send as written, such as an upload of a file or a comment carrying picture files (`goingUnsendable`, `going_translate.go`), is refused before anything is sent (`GoingCaller.prepare`): when the plan's rows are read, and again when its row runs. A comment, a suggestion or a document edit placed by a `dispatch://` `ref` is kept as the row of the change that names the issue, project or document the reference names (`goingRefPlace`), and one whose `ref` names no such place is refused so.

The run record is the `going_runs` row of each run of the command bar's agent (`going_runs.go`): its person's canonical login, the words, the chip, its kind (`new_issue` for the bar's File as a new issue), its level and mode, the line on top the person pressed Enter on to start it (`line`: `ask`, `do` or `file` as the bar read it at the key, null for a run not started from the line, such as a follow-up typed in the box), the conversation it belongs to and the run it continues, its state and stop reason, the issues its landed requests touched, and what it spent of its level's budget, beside its steps, events, grant, landings and plans in tables of their own. `POST /api/v1/going/runs` writes the row and the agent works it (`going_agent.go`). The short answer of a pause in typing is a going request with its going events, and writes no row here. A run as the run routes and History answer it also says whether Undo can still take back a change of it (`undoable`, false for a run that changed nothing) and when its Undo landed (`undone_at`, null for a run never undone), and counts its changes: those Undo can still take back (`undoable_count`), those an Undo took back (`undone_count`, its undo landings whose line is ok but those marked `unchanged`) and those Undo tried and could not take back (`standing_count`: refused from the record with nothing sent, and undo landings whose line is not ok, a change kept as another writer changed it). Undo's own plan sorts each call whose undo has not landed (`goingCallUndo` over `goingUndoer.plan`); a call that is sent, not undone by design, a delete of a comment or an issue message (deleted, not undone), a call that changed nothing, and one whose undo changed nothing are in no count. All of it is read off its landings in the statement that reads the run, so History offers Undo only while it can take something back, an undone run still says when after a reload, and a page says what Undo did and will do from the counts alone. `GET /api/v1/me/going-runs` is History: the caller's own conversations, each listed until its newest run is seven days old, its runs newest first, with `?issue=` and `?q=`. The maintenance sweep deletes a conversation whole, every run of it with everything below it, once its newest run is seven days old (`sweepGoingRuns`), and the run routes answer `404 GOING_RUN_NOT_FOUND` for a run of such a conversation, for a run that is another caller's, and for a run the record does not hold.

A run is withdrawn once a comment or an issue message whose words it was given is deleted, or its row is gone (`going_run_posts.go`): each answer a call of it gets records, before the agent is given it, each post whose words the answer carries (`recordGoingRunPosts`, `going_run_posts`), a follow-up's claim records the posts of each earlier run whose turns it hands on and hands on none of a withdrawn run, and every read of the run reads the verdict as it reads the run, never written by the delete. A withdrawn run's stream writes none of its frames and one `end` frame carrying `ANSWER_WITHDRAWN` under the id of its last end; its record and History read it stopped with that reason, its words kept; its plan gives no summary, arguments or value now and is approved and revised by nobody (`409 GOING_RUN_WITHDRAWN`); and one that has not ended is stopped with that reason by the first of its stream, its read, its plan's routes, its next call and its next claim. What it stored keeps its words, as an event Dispatch wrote does. The verdict names who withdrew the run (`goingRunWithdrawerOf`): a run each of whose posts that no longer stands was deleted by a landed delete call of its own is withdrawn by itself alone, with `ANSWER_WITHDRAWN_BY_RUN`; its stream writes its `plan` frames, which carry no word, before that end frame, and its plan reads as an ended run's - its rows and results, each deleted post's value the delete's mark (`maskDeletedPosts`) - with no summary. A plan row of a post shows its author and body to the person alone: the plan call's answer to the run carries no value now of it.

A broker token that names a person under the person project scope, which is what a person's `agent-secrets login` sign-in trades for, from the Go helper and from every TypeScript session client alike, gets the `person` scope and never `approve` (`brokerTokenActor`): no broker token holds `approve`, whatever its project scope, because each is made from a file on the machine that holds it and `approve` settles what only the person settles. So a review in a person's name is recorded from their browser session or under a personal token they gave `approve`, and every route the table gives `approve`, with the answer to an approval request, refuses every broker token. Narrowed to reading, the same token gets the same `person` scope and records nothing. Two routes record that review (`reviews.go`, both through `recordArtifactReview`). `POST /api/v1/artifacts/{id}/reviews` takes `{state, reason?}` and records the version the review would record whichever it is: the version the open approval request names for the document, else the latest settled version; it is the web app's call. `POST /api/v1/artifacts/{id}/versions/{number}/reviews` takes the same body, and `{number}` is the version the caller read: when the review would record another version the route answers `409 REVIEW_VERSION_MOVED`, naming the version it would record, before it answers the request or writes anything, and a `{number}` that is not an integer from 1 is `400 INVALID_REVIEW`. The guard is a route rather than a body member because a route ignores a member it does not declare, so a build without it answers no route rather than recording a version it chooses. `dispatch review` sends only the versioned route. The going catalogue (`going_catalogue.go`) holds every write tool, but the short answer's decision chooses only among the twenty actions it marks proposed, and `dispatch_review` and `dispatch_review_document` are none of them, so that decision never names a review of these two routes in a person's name; a command-bar run reaches them only through those two write tools, rows of the class `review`, which wait for the person in every mode (`goingClassesThatWait`).

A whole-document upload says which version it replaces. `artifacts.go` reads `precondition` from the JSON body and from the multipart form field of that name, holds it to the document token alone (`docs.ValidateUploadPrecondition`) before anything is written, and hands it to `docs.ReplaceText`, which checks it under the write's own locks; a token behind the live document is refused `409 PRECONDITION_FAILED` carrying the live token, `current.version` — the version this route has already counted, the next number less one — and the sentence naming `dispatch doc-read` and the field the token goes in (no flag of a command, since a caller may have sent its token straight to the route from a client whose `dispatch artifact` has no flag for one), and nothing is written. A replacement that names no token at all is taken unchecked, as every replacement was before #3000, because no deployed `dispatch` client can name one on `dispatch artifact` (INFRA-4980): `ReplaceText` checks a token only where one is named, and `artifacts.go` counts each such replacement it commits on `/metrics` (`envoy_dispatch_document_replacements_unguarded_total`, no label) and logs it at INFO with the artifact and the document, and no caller or request header, since the access log's line for the same request names the caller and its User-Agent (`noteUnguardedReplacement`). The refusal of a missing token comes back in a later change, once every deployed client sends the token. A document whose live tree is outside the Proof schema names no token by design, since it renders no markdown and has no token for anybody to name, and the upload is the only way to repair it; one that names a token is refused. A file's or an image's version has a token too, `sha256:` and the SHA-256 of its bytes (`model.FileVersionToken`), which every read of a version row states as `versions[].token` where the artifact is a file or an image (`model.StateFileTokens`, from the row's `sha256`, called where each read knows the artifact's kind, so a document's version never carries one whatever its row holds) and `dispatch doc-read` prints; a version stored with no hash carries none, and two versions holding the same bytes carry the same token, as two holding the same document do. A first upload under a name naming any token is refused `409 PRECONDITION_FAILED` by one statement in `storeArtifact` for both kinds (`uploadNoTokenRefusal`), and for a file before its object too (`refuseUploadBeforeItsObject`). An upload replacing a file or an image names its token in the same `precondition`, and `refuseFileBase` refuses any other token with the same `409 PRECONDITION_FAILED` in words naming the artifact's kind, the standing version's token and number in `current`; a token for a version stored with no hash is refused as a first upload's is. It checks it twice: from the pool before the upload's object is written to the file store (`putUploadedFile`, the version read by `newestFileVersion`), so an upload refused there leaves no object, and in the upload's transaction under the owner's lock against the versions that transaction loaded with the artifact, which decides and reads nothing more. An upload the first check passed and the second refuses, because another upload replaced the version between the two, leaves an object no row names, as `putUploadedFile`'s other refusals can. A file replaced naming no token is taken unchecked and counted on its own counter (`envoy_dispatch_file_replacements_unguarded_total`, `noteUnguardedFileReplacement`), so the refusal of a missing token can cover files too once every client, the dashboard's upload included, sends one. While a fleet rolls onto this build, or rolls back past it, a token one process stated can reach a process of the build before it, which refuses any token on a file `400 INVALID_PRECONDITION` and writes nothing; the same upload sent again is taken once it reaches a process of this build.

Both JSON fields a multipart upload carries, its `actor` and its `precondition`, are read as the JSON body is read (`api.multipartJSONField`): a member no field of the object names is ignored and logged at debug with the route (`logUndeclaredMembers`), so one build of a fleet takes an upload another build's member rides in.
What a misspelled key cannot do is pass as the key it misspells: a precondition left naming nothing is refused `400 INVALID_PRECONDITION` by its own shape check, in a form field as in a body, and that upload writes nothing.

A question opened on an issue carries the review that issue's specification already holds (`standing_review_advice.go`'s `standingReview`), read in a savepoint of its own under a 500 ms statement timeout and reported beside the related-item check the same write answers with. Each bounded document report — this one, the superseded approval and the moved approval request — opens a savepoint of its own through one helper (`adviceSavepoint`), which sets that timeout, so a failed read costs its own report and no other and is logged where it happens (`logAdviceError`). It is reported only where it is a person's own review — an actor of kind `user` with no agent named beside them — pinned to the version the document is at now, so a review of an older version, a plan review and a review an agent wrote under a person's scope each report nothing, as do a question on a project document and a read that failed: the question is written either way. A review `dispatch review` records is one of those: it needs a personal token holding `approve`, since no broker token holds that scope (`broker_token.go`'s `brokerTokenActor`), so `actingPerson` writes that token into the review's `act` and `standingSpecReview` drops it, whoever typed the command, because the line this advice prints says the person reviewed that version and Dispatch cannot tell a person's own command from an agent's under the same scope, where a false line is worse than none and the advice refuses nothing either way. A review Dispatch carried forward to that version carries `carried_from_version`, the version its carry reason gives, and no other review carries that field, so it is what tells a carried review from one the person gave; the sentence is parsed where it is written (`docs.CarriedFromVersion`). Its stored reason, which is Dispatch's own carry sentence, is left out: a reader printing it would quote Dispatch back to the sender as the reviewer's words. The review is about the document rather than the words of the question, so it holds for a question worded in any way; the suggestions beside it are the ones that depend on the words.

A broker token carries a list of projects (`ciphertoken.Caller.Projects`). Only a token under the named project scope with its one project sets `Actor.Project` (`project_scope.go`): an operator's entry that names a person and a project, or a job's entry that names one project, whose token the project check judges as it judges a person's named token for that project. A person token's list, the projects its trade named and Dispatch said its person sees, limits no write at this release, so such a token writes wherever its person may, as one naming no project does (`broker_token.go`), and so does a job's `public` token, whose list of private projects the credential carries for a later check and no write check reads yet. A `read-named` token sets the same `Actor.Project` as the token it narrows, and writes nothing.
