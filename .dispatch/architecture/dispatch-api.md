Every HTTP route body: issues, artifacts, asks, comments, messages, projects, search, and the assignee, rank, label and component-attachment writes, and the per-session list of what people wrote to an agent (`GET /api/v1/agents/{session_id}/answers`, `session_answers.go`), which every agent host reads on each model request. Search reads each ask hit's answer state from its row, and a resolved ask's last answer from its `ask.answered` events, before it answers. The per-session list's read model is the small package `sessionanswers` (`List`), which travels with its one route: a person's events whose `published_destinations` hold the session's own topic (`contracts.AgentSubject`), its sent message and comment deliveries, each item at its current words as a `model.SessionAnswer` with its relation to the session and its `dispatch://` and deep-link place; the outbox's tests read back through it, so the route reads what the publisher records. The largest package in the server (156 Go files beside their tests) and the one every Dispatch feature touches. It resolves an agent's actor through the listener's OIDC and routing packages, hence the edge to `envoy-listener`. The edge to `contracts` is a Go import as well as the wire contract. 36 of the package's files import `internal/contracts`, the Go package `bun run gen:go` writes from `packages/contracts`, for the headers, bounds, codes, subjects, the going stream's frame names and the tool specs' argument fields that the server and its clients must spell alike. The response shapes go the other way: `envoy-dispatch openapi` reflects this package's route table and the Go types of its rows into `packages/contracts/schemas/dispatch-openapi.json`, which `bun run gen:api` renders into `src/dispatch-api.generated.ts` for the web app. It also runs the related-item check every issue create, ask and new decision block gets once its write commits (a search by the text's rarest words and by meaning, waited on for at most 5 s and recorded in `related_checks`), the no-write route and the records route over it, and the term-statistics refresh its keyword picker reads.

The related-item check of a write that asks a person a question offers more than one project's items. An ask create, a new decision block, and the POST form of `/api/v1/projects/{key}/related`, which `dispatch related` calls, also carry up to two answered questions of other projects (`other_projects`, read by `related_other_projects.go`). That leg searches by meaning alone, because the keyword leg weighs each word against the term statistics of one project. It starts as soon as the check holds its embedding, on a second connection mark the check takes before it opens the one-project read, and it reuses that embedding. The meaning stage then waits at most 300 ms for it, and ends the wait 25 ms before its own deadline. A leg that fails, that overruns that wait, or that got no connection leaves the one-project answer whole, records no reason and offers no item. A check that fell back to keywords offers none either. An issue create and the GET form of that route ask for none, so the dashboard's new-issue dialog draws the asking project's items alone. Each offer of an ask create is one `write_suggestions` row of role `other_project`, beside that check's `related` rows, and the outcome sweep resolves it like any other row. A new decision block's offers reach no row, because such a row is keyed by the ask the offer was made on and a block has none. `GET /api/v1/related-checks` answers `other_project_offers` beside the counts it reads from `related_checks`: the ask creates of the window that made such an offer, counted once each. The check answers no `decision` any more, and `persistSuggestions` writes no row of that role.

The live paths hold bounded state per reader. The event stream relay (`event_stream_relay.go`) is the live paths' one reader of the event log: its first subscriber starts a generation that listens on `dispatch_events` and reads each commit once, encoding each event's frame once for every subscriber, and the cancel of its last subscriber stops it at once, so a process nobody subscribes to holds no LISTEN connection of the relay's and the relay reads nothing. The events view of `GET /ws/live` (`live_events.go`) subscribes to it. A resume at or below the relay's head is replayed at most 256 events whose frames total at most 1 MiB, counted by rows; past either bound it is replayed nothing. Its `events_start` says `replay_complete: true` only when the replay is everything the page lacks, which includes a resume ahead of this process's relay but within the log; a page whose subscription starts without it refreshes what it shows. A subscription whose 64-slot relay subscription overflows catches up from the log within the same bounds and goes on; past them, or when the relay's generation ends (an event log reset, shutdown), it ends as `behind` and the page subscribes again. The delivery hub takes its events from the relay's feed (1,024 slots) and itself listens only on `delivery_changes` and `delivery_freshness`; it also stops with its last view, a closed feed makes it reload the open P0 issues and recompute every view, and an event that arrives during a view's read and touches the answer that read gives recomputes that view again. A comment's mentions are resolved in its request, up to 8 lookups at once, each bounded at 250 ms, so a listener that answers none delays a comment with up to 8 mentions by one 250 ms timeout and each further 8 mentions add one (ceil(k/8) timeouts for k mentions); the attempts commit pending with the comment, and the response returns them pending. The mention sender (`comment_mention_sender.go`) sends them after the response on one FIFO lane per recipient (the pinned session, else the target as written: `role:X` shares its holder's lane only when its lookup found the holder, and an unanswered `role:X` is keyed by its string, so two comments to one recipient can then arrive in either order), 8 lanes at once and at most 4,096 sends queued; once shutdown starts it queues nothing more (a refused send is logged at WARN), starts no queued send and gives the sends in flight 10 s. An attempt no sender finishes is the delivery sweep's (`delivery_sweep.go`, `resumeOwedDeliveries`): one process's maintenance loop, under the sweep's lease, sends once a minute every pending attempt that is the latest of its target, is claimed by nobody or by a claim that lapsed, and was created between a claim lease (one minute) and the duplicate window ago (`model.OwedMentionAttemptSQL`), whichever process left it, through the same claim; an attempt younger than the lease is left to the process that queued it, so the sweep never takes a live process's queue out of order. So the attempts a stopping process refused, left queued or could not queue for the bound are sent by a later pass once they have waited a lease (in a rolling update the successor is up before the old process stops), and a killed process's send in flight by the first pass after its claim lapses, within a minute and a sweep interval of its taking, under its own idempotency key, so a send that had landed is dropped as a repeat. The same pass settles, superseded, every pending attempt no sender holds that a later attempt of its mention has already delivered the comment in the place of (`settleSupersededMentions`), which nothing else binds to. Each pass reads the partial indexes `message_deliveries_pending` and `comment_deliveries_pending` (pending rows by `created_at`): with nothing owed it is one statement a minute that reads no row; no event can drive it, since a killed process sends no signal and a stopping one refuses its sends after its lifetime ends. Order holds within one process only: an attempt resumed after a crash or a handoff can arrive after later comments. A session a mention may reach also gets the new comment's own copy on the route, the claimant, an author or a follower route only by one rule the outbox applies when it publishes (`attempt.leftToMention` in `internal/dispatch/outbox`), keyed by the one session each attempt counts under (`model.MentionSession`: an unanswered `session:<id>` mention counts as `<id>`'s, and a route equal to an unanswered mention's target follows that target's attempts). What the attempt came to - sent, live, abandoned, or owed to the sweep, each a predicate over its row in `internal/dispatch/model`, all built from the sweep's own definition - decides the copy and which of the outbox, a sender's claim and the sweep acts on the attempt; a copy held back for a resumed mention is a `comment_fallback_copies` row, which the outbox's fallback pass publishes to its one destination only once the resend fails, never touching the event's own row. `publishFallbackCopies` in `internal/dispatch/outbox/mentions.go` is the protocol's one description. So a mentioned session loses no comment through a kill. The copy on the own topic of a session with a failed (or abandoned) attempt, and every fallback copy, carries that attempt's mention dedupe key, `agent.<session>.<comment>:<target>:<the mention's mode>` (`contracts.AgentSendDedupeKey` of `model.CommentMentionIdempotencyKey`, the lowest failed target's when there are several; the mode in it is the one the comment recorded on the mention and never an attempt's own, every attempt of one mention sending under that one key), in place of `dispatch-<event id>`, which every other destination carries and which stays its event id. So a send the killed process had handed the listener before it died, whose resend then fails for good (the listener down after the restart), is not shown twice: the host drops a frame whose named dedupe key it claimed within 72 hours, and the stream, whose MsgId is the dedupe key and the subject, also drops a second message with that key on that subject within its 72-hour duplicate window. A session no mention reached never claimed the key and is shown the copy. An unanswered `role:X` mention reached under any other string, and a `role:X` route whose own lookup went unanswered, name no session to compare, so that session can get both copies. An agent view (`live_agent.go`, `agent_stream.go`) queues at most 8 MiB of frames; past that it ends as `behind`. A page that stops reading meets the socket's own bounds first (#2449): the writer's 10 s write deadline (`liveSocketWriteWait`) ends the socket, which holds at most 16 of the hub's frames (`liveSocketQueue`) and 64 stream frames (`liveSocketStream`); the agent view's 8 MiB bounds only what it buffers while the socket writes slower than the session produces.

It also runs the suggestion outcome sweep (`RunSuggestionOutcomeSweep`), which judges whether a write's `advice.suggestions` were acted on or overridden: a woken loop (`duty.RunWoken`, with no lease: each page holds the `suggestion_outcome_cursor` row `for update`, which serialises two processes) on `dispatch_events`, passes at least a minute apart, each reading only the events after its cursor (`suggestion_outcome_cursor`) and at or below the safe horizon of the server's one `events.Horizon`, which the server hands it (`Background.EventHorizon`) and which the live event feed reads through too, and the suggestions not yet swept (`write_suggestions.swept`), so its work follows what changed rather than how many suggestions are still pending, and its cursor never passes an event that could still commit. The keyed writes' maintenance sweep (`RunMaintenanceSweep`: the Idempotency-Keys past their window, the spent DPoP proofs, the command bar's answer runs past their window and its run records past their thirty days, then the deliveries a dead process left owed) is a timer of its own, once a minute across the processes under lease `suggestion-outcomes`, because no commit announces any of them.

An access token the secrets broker issued is the one credential that proves a session of its own (`broker_token.go`), and it names either the person it acts for or, for a machine nobody has signed in on, that machine's fleet service. Such a caller reads everything its session may read, and `writeNeedsASignedInPerson` (`project_scope.go`) refuses its every write `403 SIGN_IN_REQUIRED` naming `agent-secrets login`: Dispatch records a write under the person who made it, and this credential names none. It is the outermost of the three checks `Register` wraps every mutating route in, before the project and session scopes, so such a caller is told it may write nothing at all rather than which project the write it tried belongs to. The credential-relay rows (`credential_requests.go`) carry the person's own sign-ins beside their machine logins — `GET /api/v1/signins` and `POST /api/v1/signins/{id}/revoke`, each naming the person from Dispatch's own session, so nobody reaches another's — and `GET /api/v1/credentials/capabilities`, which answers `{"machine_code_page": <bool>}` out of the broker's RFC 8414 metadata and, alone among these rows, answers rather than 404s for a Dispatch with no broker, since a 404 would leave the page unable to tell a deployment without a broker from a route it failed to reach.

The command bar's answer path is the going routes (`going_routes.go`, with the record's reads and writes in `going.go`). `POST /api/v1/going/requests` records the question, the project it is asked of and the context chip (`{path, project, issue, block}`), answers `201` with the run, and then answers it in the background (`startGoingRun`), bounded by the 30-second `ends_at` the record holds. A run with a measured decision model (`Decider`, `going_decider.go`) first makes one `agentloop.Decide` call to its System One endpoint, bounded at one second. That call asks three questions (`goingDecide`, `going_decision.go`): which catalogue action the words ask for, chosen only among the actions the caller's credential may run, or `none`; whether the words are about the chip's item (`page`), items they name (`named`) or nothing; and chart or prose. The thresholds the run compares the confidences with are the model's entry in `going.DecisionRecord`, and this package holds no threshold of its own. The run then stores the `decision` frame: the two best actions, `act` (the first is at or above the action threshold and is not `dispatch_send_to_agent` or `dispatch_issue`, which always ask), the context, and the display, whose `chart` is true only at or above the chart-display threshold. A decision call that fails, or that names no action it was offered, gives no decision frame, and the answer runs as with no decision model. The answer itself is `going.Answerer.Run` (component `envoy`). The run gives it the offered actions with their argument schemas, the display, and the read tools its caller may call. After the text frames the run stores a `block` frame where the structured reply drew a block the words ask for, a `roster` frame `{age_ms, source}` where the answer read the roster, and, after a decision, the `proposal` frame (`goingPropose`). For each offered action the proposal holds one invocation for each item it changes, each held to the action's own schema, with a target filled from the chip only where the context is `page`, and at most one missing argument the bar asks the person for. An answer that came as prose writes no block and no arguments, and its actions are offered on what the chip fills. `POST /api/v1/going/requests/{id}/cancel` sets `going_requests.cancelled_at`. After that, `goingAppendEvent` stores no frame that does not end the stream, so the answer stops at its next delta on any pod; on the pod that runs the answer, the cancel function the server holds in `goingCancels` stops it at once. `GET /api/v1/going/capability` answers `{answer: {configured, model, blocks}, decision: {configured, model, reachable}, session, label}`, and names no endpoint and no credential.

The read tools of a run (`going_reads.go`) are reads this table serves, made in process through the functions those routes answer with, as the run's author: the roster of `GET /api/v1/agents` (`agentRows`), an issue's or a project's progress from `GET /api/v1/issues`, a project's architecture counts (`architectureTree`), the three delivery reads, and `GET /api/v1/projects/{key}/activity` (`project_activity.go`), which counts the events of a project's issues per ISO week and by kind over the last weeks (default 8, at most 52) and lists every week of the span, a week with no event as 0. A caller is offered a tool only where its credential may call every row the tool reads (`goingReadsFor`). A credential scoped to one project is offered no roster and no delivery read, and every other read is held to the run's project. `Register` refuses a table that does not serve a row a read tool names. The roster read waits out a `503 ENVOY_REFILLING` where the run keeps 5 s for its answer after the wait, and otherwise reads the sessions Dispatch's own rows name; the `roster` frame says which. A block's spec names one read, its arguments, its table and its fields, and never a number. The run parses the spec against its kind's schema, makes that read again as the author, and fills the block from the read's rows alone (`going_blocks.go`). It drops a block of a kind the words do not name, a chart the decision did not settle on, a read the run may not make, and a read that cannot fill the block, a chart of fewer than two points among them; the answer then stays prose and links.

The bar's operations are two routes. `POST /api/v1/going/runs/{id}/writes` (`going_writes.go`) runs one invocation of one offer of the run's proposal, with any arguments the person changed, the value of the missing argument, and `approved` (`auto`, `person` or `confirmed`). It performs the write in process as the caller: it calls the route table this server mounts (`server.inProcess`, behind `EnforceCookieOrigin`, the one cross-site check, which the router also wraps the whole server in) with only the caller's `Authorization`, `Cookie`, `Origin`, `Sec-Fetch-Site` and `Dispatch-Login` headers, and the trusted identity header on a deployment that names its people by one. So every check a route makes runs as on the caller's own request. Each catalogue row's translator (`going_translate.go`) does the work the `dispatch` command does before it sends, and refuses by name a call the bar cannot send. The route reads the value before just before the write and the value after just after it, in the same way, and records the write, refused or not, on the run's record, with the undo the row it went through states and how each request it sent went (`requests`: a reasoned close posts its reason as a message, then closes); an upload's value before is the document its name finds under the owner its route writes to (`goingRouteUploadOwner`), and a write whose value after could not be read is recorded `after_unread`. Each invocation of a run is written once: the write first claims its invocation on the run's record, pending, in one statement that holds no lock and no connection past itself, so of two requests for one invocation one claims it. A request for an invocation whose write went through writes nothing and answers `200` with that write's line as the run recorded it; one for an invocation another request is writing answers `429 GOING_WRITE_IN_PROGRESS` with a `Retry-After`; and one for an invocation claimed longer ago than its request can still run and record what it did (`goingClaimBound`: the keyed handler's bound and the bookkeeping after it) answers `409 GOING_WRITE_UNSETTLED`, since that write may have landed, and is never written again. A write of several requests is one write to its `Idempotency-Key`: the in-process requests carry no commit step (`goingInProcess.Do` takes the `store.WithBeforeCommit` step off), so none of them marks the key committed, and the write's record marks it once every request landed. A refusal is recorded under `store.WithoutBeforeCommit`, with what landed before it named in its answer (`goingRefusal.after`); a refusal the keyed layer keeps an answer for (a `4xx` but `401`, `408`, `429`) is the write's final answer, replayed to a retry under the key however much of the write landed, and one it keeps none for (`5xx`, `401`, `408`, `429`) leaves the key open. Every later write of the invocation that runs - a retry under the key, or a new press, the bar's own retry or another tab under a key of its own - resumes after the requests the run's latest write of the invocation records as landed (`goingLandedBefore`, `GoingCaller.send`) and sends none of them again. It refuses `auto` with `409 GOING_APPROVAL_REQUIRED` for the two writes that always ask and for any action but the one the decision chose at or above the action threshold, with `409 GOING_NOT_AUTOMATIC` for an invocation the proposal did not mark automatic (`going_named.go`: every item it names is the chip's or a reference the person's own typed words write, every route or assignee it sets the words name or the issue already holds, an upload's name is one its owner holds no document of or one the words write, and every argument is one the catalogue's classes hold), for one sent with arguments replacing its own, and for an upload whose name the owner its route writes to holds a document of when the write runs and the words do not write (`goingUploadsOver`, read once the write's row is chosen, with nothing written; the proposal's read is the offer's hint), and with `409 GOING_CONFIRMATION_REQUIRED` while the caller's `confirm_writes` is on. `GET` and `PUT /api/v1/me/going/settings` (`going_settings.go`) read and write that setting, which is the person's own, keyed by canonical login, and false until they set it. `POST /api/v1/going/runs/{id}/undo` (`going_undo.go`) undoes every write of the run that went through and that no undo settled, newest first, in process as the caller, by the undo the catalogue row it went through states (`GoingUndo`, as the write's record keeps it): `write_back` writes the value before back, `reverse` runs the write's reverse route, `close_created` posts the reason on an issue the turn created and closes it, and `trace` records the undo and erases nothing. A field another writer changed since the write is left as it is, refused `409 GOING_UNDO_CHANGED`, and the rest of the turn is undone. A release of a claim the caller did not hold before is refused `409 GOING_UNDO_NOT_CALLERS_CLAIM`. A claim, a release and an approval request are undone by what their route answered they did, not by the read before them, which another writer may overtake: the claim routes answer `claim_changed` (`claimAnswer`), recorded `unchanged` on the write, and the approval request route answers `opened` (`approvalRequestResponse`), so a claim of an issue the caller already held, a release of one nobody held and a request that renewed an ask already open are undone by nothing. A write recorded `after_unread` is refused `409 GOING_UNDO_AFTER_UNREAD` by every undo but a trace, with nothing undone. The undo claims every write it is about to undo on the run's record, pending, in one statement before it undoes any, so a second undo of the run while one is under way answers `429 GOING_UNDO_IN_PROGRESS`; an undo it made and could not record keeps its claim, as a write does, and a pending undo older than `goingClaimBound` no longer holds the run, while its write is answered `409 GOING_UNDO_UNSETTLED` and never claimed or undone again.

The run record is the `going_runs` row a run keeps under its going request's id (`going_runs.go`), and only a credential that acts as a person keeps one. The run writes the row as it starts and fills it as it goes: the words, the chip, the hits, the decision, the proposal, `structured_output` and `finished_at`. Each write and each undo is first claimed on the row, a pending element appended in one statement, and then recorded in that element's place in another, once it went through or was refused; a claim whose request made nothing is taken off instead. A run that was cancelled or abandoned keeps what it stored and reads unfinished. `GET /api/v1/me/going-runs` answers the caller's own runs of the last thirty days, newest first, with `?issue=`, `?q=` and `?undoable=true`, which is how the bar's undo key finds the newest turn from any page. The maintenance sweep deletes a row past thirty days (`sweepGoingRuns`), and the writes and undo routes answer `404 GOING_RUN_NOT_FOUND` for a run older than that, for a run that is another caller's, and for a run the record does not hold.
