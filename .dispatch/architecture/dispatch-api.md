Every HTTP route body: issues, artifacts, asks, comments, messages, projects, search, and the assignee, rank, label and component-attachment writes, and the per-session list of what people wrote to an agent (`GET /api/v1/agents/{session_id}/answers`, `session_answers.go`), which every agent host reads on each model request. Search reads each ask hit's answer state from its row, and a resolved ask's last answer from its `ask.answered` events, before it answers. The per-session list's read model is the small package `sessionanswers` (`List`), which travels with its one route: a person's events whose `published_destinations` hold the session's own topic (`contracts.AgentSubject`), its sent message and comment deliveries, each item at its current words as a `model.SessionAnswer` with its relation to the session and its `dispatch://` and deep-link place; the outbox's tests read back through it, so the route reads what the publisher records. The largest package in the server (87 files) and the one every Dispatch feature touches. It resolves an agent's actor through the listener's OIDC and routing packages, hence the edge to `envoy-listener`. The edge to `contracts` is the wire contract rather than a Go import: `contracts/src/dispatch-api.ts` declares the response shapes these handlers produce and the web app consumes, and code generation covers only the event envelope, so there is no Go type to import. It also runs the related-item check every issue create, ask and new decision block gets once its write commits (a search by the text's rarest words and by meaning, waited on for at most 5 s and recorded in `related_checks`), the no-write route and the records route over it, and the term-statistics refresh its keyword picker reads.

It also runs the suggestion outcome sweep (`RunSuggestionOutcomeSweep`), which judges whether a write's `advice.suggestions` were acted on or overridden: a woken loop (`duty.RunWoken`, with no lease: each page holds the `suggestion_outcome_cursor` row `for update`, which serialises two processes) on `dispatch_events`, passes at least a minute apart, each reading only the events after its cursor (`suggestion_outcome_cursor`) and at or below the safe horizon of the server's one `events.Horizon`, which the server hands it (`Background.EventHorizon`) and which the live event feed reads through too, and the suggestions not yet swept (`write_suggestions.swept`), so its work follows what changed rather than how many suggestions are still pending, and its cursor never passes an event that could still commit. The keyed writes' maintenance sweep (`RunMaintenanceSweep`: the Idempotency-Keys past their window, then the deliveries a dead process left owed) is a timer of its own, once a minute across the processes under lease `suggestion-outcomes`, because no commit announces either.

An access token the secrets broker issued is the one credential that proves a session of its own (`broker_token.go`), and it names either the person it acts for or, for a machine nobody has signed in on, that machine's fleet service. Such a caller reads everything its session may read, and `writeNeedsASignedInPerson` (`project_scope.go`) refuses its every write `403 SIGN_IN_REQUIRED` naming `agent-secrets login`: Dispatch records a write under the person who made it, and this credential names none. It is the outermost of the three checks `Register` wraps every mutating route in, before the project and session scopes, so such a caller is told it may write nothing at all rather than which project the write it tried belongs to. The credential-relay rows (`credential_requests.go`) carry the person's own sign-ins beside their machine logins — `GET /api/v1/signins` and `POST /api/v1/signins/{id}/revoke`, each naming the person from Dispatch's own session, so nobody reaches another's — and `GET /api/v1/credentials/capabilities`, which answers `{"machine_code_page": <bool>}` out of the broker's RFC 8414 metadata and, alone among these rows, answers rather than 404s for a Dispatch with no broker, since a 404 would leave the page unable to tell a deployment without a broker from a route it failed to reach.

A whole-document upload says which text it replaces. `artifacts.go` reads `precondition` from the JSON body and from the multipart form field of that name, holds it to the document token alone (`docs.ValidateUploadPrecondition`) before anything is written, and hands it to `docs.ReplaceText`, which checks it under the write's own locks; a base behind the live document is refused `409 PRECONDITION_FAILED` carrying the live token, `current.version` — the version this route has already counted, the next number less one — and the sentence naming `dispatch doc-read`, and nothing is written. A replacement that names no base at all is refused `400 PRECONDITION_REQUIRED` only where `Deps.UploadBaseRequired` is set, which `cmd/dispatch` sets from `DISPATCH_UPLOAD_BASE_REQUIRED` and which is off by default: a pod runs `dispatch` from its image, so a command that sends a base reaches it only when the daemon replaces the pod. That refusal reads the document first and lets a document whose live tree is outside the Proof schema through (`refuseUploadNamingNoBase`), since such a document renders no markdown and has no token for anybody to name. A first upload under a name and a file that is no document are asked for no base.

A question opened on an issue carries the review that issue's specification already holds (`write_advice.go`'s `standingReview`), read in the advice's own savepoint under a 500 ms statement timeout and reported beside the related-item check the same write answers with. It is reported only where it is a person's own review — an actor of kind `user` with no agent named beside them — pinned to the version the document is at now, so a review of an older version, a plan review and a review an agent wrote under a person's scope each report nothing, as do a question on a project document and a read that failed: the question is written either way. A review Dispatch carried forward to that version is marked carried and names the version its carry reason gives (`carriedApprovalReasonPrefix`), and its stored reason, which is Dispatch's own carry sentence, is left out: a reader printing it would quote Dispatch back to the sender as the reviewer's words. The review is about the document rather than the words of the question, so it holds for a question worded in any way; the suggestions beside it are the ones that depend on the words.
