Every HTTP route body: issues, artifacts, asks, comments, messages, projects, search, and the assignee, rank, label and component-attachment writes, and the per-session list of what people wrote to an agent (`GET /api/v1/agents/{session_id}/answers`, `session_answers.go`), which every agent host reads on each model request. Search reads each ask hit's answer state from its row, and a resolved ask's last answer from its `ask.answered` events, before it answers. The per-session list's read model is the small package `sessionanswers` (`List`), which travels with its one route: a person's events whose `published_destinations` hold the session's own topic (`contracts.AgentSubject`), its sent message and comment deliveries, each item at its current words as a `model.SessionAnswer` with its relation to the session and its `dispatch://` and deep-link place; the outbox's tests read back through it, so the route reads what the publisher records. The largest package in the server (154 non-test files) and the one every Dispatch feature touches. It resolves an agent's actor through the listener's OIDC and routing packages, hence the edge to `envoy-listener`. The edge to `contracts` is the wire contract rather than a Go import: `contracts/src/dispatch-api.ts` declares the response shapes these handlers produce and the web app consumes, and code generation covers only the event envelope, so there is no Go type to import. It also runs the related-item check every issue create, ask and new decision block gets once its write commits (a search by the text's rarest words and by meaning, waited on for at most 5 s and recorded in `related_checks`), the no-write route and the records route over it, and the term-statistics refresh its keyword picker reads.

The related-item check of a write that asks a person a question offers more than one project's items. An ask create, a new decision block, and the POST form of `/api/v1/projects/{key}/related`, which `dispatch related` calls, also carry up to two answered questions of other projects (`other_projects`, read by `related_other_projects.go`). That leg searches by meaning alone, because the keyword leg weighs each word against the term statistics of one project. It starts as soon as the check holds its embedding, on a second connection mark the check takes before it opens the one-project read, and it reuses that embedding. The meaning stage then waits at most 300 ms for it, and ends the wait 25 ms before its own deadline. A leg that fails, that overruns that wait, or that got no connection leaves the one-project answer whole, records no reason and offers no item. A check that fell back to keywords offers none either. An issue create and the GET form of that route ask for none, so the dashboard's new-issue dialog draws the asking project's items alone. Each offer of an ask create is one `write_suggestions` row of role `other_project`, beside that check's `related` rows, and the outcome sweep resolves it like any other row. A new decision block's offers reach no row, because such a row is keyed by the ask the offer was made on and a block has none. `GET /api/v1/related-checks` answers `other_project_offers` beside the counts it reads from `related_checks`: the ask creates of the window that made such an offer, counted once each. The check answers no `decision` any more, and `persistSuggestions` writes no row of that role.

The live paths hold bounded state per reader. The event stream relay (`event_stream_relay.go`) is the live paths' one reader of the event log: its first subscriber starts a generation that listens on `dispatch_events` and reads each commit once, encoding each event's frame once for every subscriber, and the cancel of its last subscriber stops it at once, so a process nobody subscribes to holds no LISTEN connection of the relay's and the relay reads nothing. The events view of `GET /ws/live` (`live_events.go`) subscribes to it. A resume at or below the relay's head is replayed at most 256 events whose frames total at most 1 MiB, counted by rows; past either bound it is replayed nothing. Its `events_start` says `replay_complete: true` only when the replay is everything the page lacks, which includes a resume ahead of this process's relay but within the log; a page whose subscription starts without it refreshes what it shows. A subscription whose 64-slot relay subscription overflows catches up from the log within the same bounds and goes on; past them, or when the relay's generation ends (an event log reset, shutdown), it ends as `behind` and the page subscribes again. The delivery hub takes its events from the relay's feed (1,024 slots) and itself listens only on `delivery_changes`, `delivery_freshness` and `dispatch_legion_state` (`legion.StateChannel`, the sampler's announcement of a read of one project's daemon, which marks that project's Legion board views, `dirtyLegionBoard`); it also stops with its last view, a closed feed makes it reload the open P0 issues and recompute every view, and an event that arrives during a view's read and touches the answer that read gives recomputes that view again. A comment's mentions are resolved in its request, up to 8 lookups at once, each bounded at 250 ms, so a listener that answers none delays a comment with up to 8 mentions by one 250 ms timeout and each further 8 mentions add one (ceil(k/8) timeouts for k mentions); the attempts commit pending with the comment, and the response returns them pending. The mention sender (`comment_mention_sender.go`) sends them after the response on one FIFO lane per recipient (the pinned session, else the target as written: `role:X` shares its holder's lane only when its lookup found the holder, and an unanswered `role:X` is keyed by its string, so two comments to one recipient can then arrive in either order), 8 lanes at once and at most 4,096 sends queued; once shutdown starts it queues nothing more (a refused send is logged at WARN), starts no queued send and gives the sends in flight 10 s. An attempt no sender finishes is the delivery sweep's (`delivery_sweep.go`, `resumeOwedDeliveries`): one process's maintenance loop, under the sweep's lease, sends once a minute every pending attempt that is the latest of its target, is claimed by nobody or by a claim that lapsed, and was created between a claim lease (one minute) and the duplicate window ago (`model.OwedMentionAttemptSQL`), whichever process left it, through the same claim; an attempt younger than the lease is left to the process that queued it, so the sweep never takes a live process's queue out of order. So the attempts a stopping process refused, left queued or could not queue for the bound are sent by a later pass once they have waited a lease (in a rolling update the successor is up before the old process stops), and a killed process's send in flight by the first pass after its claim lapses, within a minute and a sweep interval of its taking, under its own idempotency key, so a send that had landed is dropped as a repeat. The same pass settles, superseded, every pending attempt no sender holds that a later attempt of its mention has already delivered the comment in the place of (`settleSupersededMentions`), which nothing else binds to. Each pass reads the partial indexes `message_deliveries_pending` and `comment_deliveries_pending` (pending rows by `created_at`): with nothing owed it is one statement a minute that reads no row; no event can drive it, since a killed process sends no signal and a stopping one refuses its sends after its lifetime ends. Order holds within one process only: an attempt resumed after a crash or a handoff can arrive after later comments. A session a mention may reach also gets the new comment's own copy on the route, the claimant, an author or a follower route only by one rule the outbox applies when it publishes (`attempt.leftToMention` in `internal/dispatch/outbox`), keyed by the one session each attempt counts under (`model.MentionSession`: an unanswered `session:<id>` mention counts as `<id>`'s, and a route equal to an unanswered mention's target follows that target's attempts). What the attempt came to - sent, live, abandoned, or owed to the sweep, each a predicate over its row in `internal/dispatch/model`, all built from the sweep's own definition - decides the copy and which of the outbox, a sender's claim and the sweep acts on the attempt; a copy held back for a resumed mention is a `comment_fallback_copies` row, which the outbox's fallback pass publishes to its one destination only once the resend fails, never touching the event's own row. `publishFallbackCopies` in `internal/dispatch/outbox/mentions.go` is the protocol's one description. So a mentioned session loses no comment through a kill. The copy on the own topic of a session with a failed (or abandoned) attempt, and every fallback copy, carries that attempt's mention dedupe key, `agent.<session>.<comment>:<target>:<the mention's mode>` (`contracts.AgentSendDedupeKey` of `model.CommentMentionIdempotencyKey`, the lowest failed target's when there are several; the mode in it is the one the comment recorded on the mention and never an attempt's own, every attempt of one mention sending under that one key), in place of `dispatch-<event id>`, which every other destination carries and which stays its event id. So a send the killed process had handed the listener before it died, whose resend then fails for good (the listener down after the restart), is not shown twice: the host drops a frame whose named dedupe key it claimed within 72 hours, and the stream, whose MsgId is the dedupe key and the subject, also drops a second message with that key on that subject within its 72-hour duplicate window. A session no mention reached never claimed the key and is shown the copy. An unanswered `role:X` mention reached under any other string, and a `role:X` route whose own lookup went unanswered, name no session to compare, so that session can get both copies. An agent view (`live_agent.go`, `agent_stream.go`) queues at most 8 MiB of frames; past that it ends as `behind`. A page that stops reading meets the socket's own bounds first (#2449): the writer's 10 s write deadline (`liveSocketWriteWait`) ends the socket, which holds at most 16 of the hub's frames (`liveSocketQueue`) and 64 stream frames (`liveSocketStream`); the agent view's 8 MiB bounds only what it buffers while the socket writes slower than the session produces.

It also runs the suggestion outcome sweep (`RunSuggestionOutcomeSweep`), which judges whether a write's `advice.suggestions` were acted on or overridden: a woken loop (`duty.RunWoken`, with no lease: each page holds the `suggestion_outcome_cursor` row `for update`, which serialises two processes) on `dispatch_events`, passes at least a minute apart, each reading only the events after its cursor (`suggestion_outcome_cursor`) and at or below the safe horizon of the server's one `events.Horizon`, which the server hands it (`Background.EventHorizon`) and which the live event feed reads through too, and the suggestions not yet swept (`write_suggestions.swept`), so its work follows what changed rather than how many suggestions are still pending, and its cursor never passes an event that could still commit. The keyed writes' maintenance sweep (`RunMaintenanceSweep`: the Idempotency-Keys past their window, then the deliveries a dead process left owed) is a timer of its own, once a minute across the processes under lease `suggestion-outcomes`, because no commit announces either.

A write route's transaction runs in two phases. Its read phase holds no transaction id while no earlier build is in the fleet (`dispatch-store` says what such a build adds): it takes the owner's advisory lock before it reads what the write decides on (`requireOpenOwner[Status]` and `lockIssueOwners`, through `store.LockOwnerAndRead` and `LockOwnersAndRead`, or `store.LockOwner` and `LockOwners` where the lock guards no read), reads that in the statements after that lock - never in the lock's own statement, whose READ COMMITTED snapshot is taken before the wait and would miss a close committed meanwhile - and does all its document work through `Docs.Join` and its write advice (`writeAdvice`, which counts the counted event the write is about to append); the routes that read or take another lock before their owner lock, or lock a row before their first write, are named under the lock order in `dispatch-store`, the delivery-attempt routes and the reads of which owner to lock among them. A joined route's writes are queued on the ledger in the order it makes them (`docs.Ledger.Queue`, which `api/write_queue.go`'s `queueExec`, `queueEvent`, `queueStampedEvent`, `queueLoggedEvent`, `queueNewAskReferences`, `queueEditedReferences`, `queueItemReferences`, `queueEditedItemReferences` and `queueReplacement` queue on), and `ledger.Commit` sends them as one pipelined batch, the write phase (`store.WriteBatch`): Postgres runs every statement back to back and the route waits on the batch once. No statement's result is read in Go before a later statement is sent: an event's stamp names the event's id as the events id sequence's `currval` (`store.LatestEventID`), a row's time and id are read in the read phase, and what the response needs (the appended event) is filled by the statement's callback after the batch has run. The first failing statement or refusing callback (a guarded update's `ALREADY_ACTIONED`) stops the write phase and `Commit` returns that error unchanged, so the route answers what it answers for that error. The issue create and the issue patch join a ledger for their document work (the create's spec; a close's withdrawal or a reopen's restoration of the issue's asks) but make their own row writes inline, a statement at a time, because their results steer the route: the create's `update projects`, whose number it checks, its issue, blocker, component and spec-artifact inserts, the external-link insert whose conflict answers with the issue already linked, its advances (`writeIssueAdvances`), and the `near_copy_checks` row of a near copy let in because its refusal's row could not be confirmed (`writeNearCopyCheck`), which admits no create when it cannot land; the patch's issue update, claim release, components, blockers, external links and advances, whose refusals (a component or blocker refusal, a taken external link, a priority that is gone) it answers. Each reads, does its document work and advises before that first inline write (`writeAdviceBefore`), reads the row back after it for its event, and queues every event, with its documents' writes, on the ledger, which `Commit` sends as one batch after the inline writes. The create's other `near_copy_checks` rows are written in no transaction of the create's: a refusal's is a statement of its own before the create's transaction opens (`recordNearCopyRefusal`), and a create's is written after its commit (`recordNearCopyCheck`). The claim (`claimWrite`, `api/issue_claim.go`) has no document work and joins no ledger: it reads before its first write and sends its update and its event as one batch of its own (`store.RunWrite`). Message create sends the lock of a parent whose block its reply names, that parent's owed block index, its insert, its request-key recovery point, its own index and references, its event, its stamp and a targeted message's first delivery attempt as one batch of its own (`store.RunWrite`). The results write (`POST /api/v1/issues/{key}/results`, `api/results.go`) makes its two writes a statement at a time - the batch appending `result.recorded` (`appendEvent`), then the `check_results` insert - and its read phase is bounded as well as xid-free: it resolves the check and reads the block's words out of the live Verification document before its transaction opens, takes the two issues' owner locks, and under them judges those words by the version and digest `document_blocks` holds for the block rather than reading a document while it holds a lock (`recordResultWithFreshWords`, this route's `resolveThenLock` cycle, and `indexedCheckBlock`); either of that pair moving gives the locks back, reads the words again with nothing held and takes the locks once more over the pair that read was made against, and a check reworded at every attempt (`resolutionAttempts`, two) is `409 CHECK_CONTENDED` with nothing written, carrying `Retry-After: 1`, the second the version that moved it needs to land. A comment's or an issue message's write indexes its blocks and the mentions each holds beside its own references: the index is planned in the read phase against what the item's block index holds and queued with that reconciliation (`queueItemReferences`, `queueEditedItemReferences`, `refs.ReadItemIndex`, `refs.PlanItemIndex`), and a block a reply names is read there too, with the index its parent owes (`planReplyBlock`, `refs.PlanItemIfOwed`), whose statements the same write phase carries. `putThreadRead` takes the thread owner's lock exclusively (`store.LockOwnerAndRead`), so a thread mark waits for a writer in its read phase rather than race that writer's trigger; a mark that moves the caller's row then takes the lock of the project its event names before its update, so it waits for that lock holding no transaction id too. The Inbox's Mark all read and its dismissal take their owners in shared mode, and the thread mark is ordered against them by that owner alone (`markInboxReadThreads`, `api/inbox_read.go`). The read phase still holds its pooled connection, idle in transaction.

An access token the secrets broker issued is the one credential that proves a session of its own (`broker_token.go`), and it names either the person it acts for or a service: the fleet of a machine nobody has signed in on, or the service of a read entry. A machine's token that names no person reads everything its session may read, and `writeNeedsASignedInPerson` (`project_scope.go`) refuses its every write `403 SIGN_IN_REQUIRED` naming `agent-secrets login`: Dispatch records a write under the person who made it, and this credential names none. It is the outermost of the three checks `Register` wraps every mutating route in, before the project and session scopes, so such a caller is told it may write nothing at all rather than which project the write it tried belongs to. The credential-relay rows (`credential_requests.go`) carry the person's own sign-ins beside their machine logins — `GET /api/v1/signins` and `POST /api/v1/signins/{id}/revoke`, each naming the person from Dispatch's own session, so nobody reaches another's — and `GET /api/v1/credentials/capabilities`, which answers `{"machine_code_page": <bool>}` out of the broker's RFC 8414 metadata and, alone among these rows, answers rather than 404s for a Dispatch with no broker, since a 404 would leave the page unable to tell a deployment without a broker from a route it failed to reach.

A read-only broker token is the token the broker mints from a read entry: it holds the OAuth scope `read` alone and the project scope `none`, names a service and a fixed session, and names no person and no project. `brokerTokenActor` marks its credential `model.Credential.ReadOnly` and gives it no scope. It reaches only the routes `readScopeRoutes` lists beside `routeScopes` (`routes_table.go`), today `GET /api/v1/projects/{key}/architecture` alone, and `register` refuses to mount a list that names anything but a mounted GET row (`readRoutesNotMountedAsGET`). The gate `refuseReadOnlyToken` is the outermost check of every row and of `GET /ws/live` (`routeHandler`, `liveSocketHandler`). On every route the list does not name, it answers that token `403 READ_ONLY_TOKEN` with no `WWW-Authenticate` challenge, before the scope gate, the sign-in check, the `Idempotency-Key` and the handler. The route index and the OpenAPI document do not carry the list, and `/ws/doc/{room}`, which reads no broker token, answers that token `401`.

A broker token that names a person under the person project scope, which is what a person's `agent-secrets login` sign-in trades for, from the Go helper and from every TypeScript session client alike, gets the `person` and `approve` scopes (`brokerTokenActor`), so it may record a review in that person's name. Two routes record that review (`reviews.go`, both through `recordArtifactReview`). `POST /api/v1/artifacts/{id}/reviews` takes `{state, reason?}` and records the version the review would record whichever it is: the version the open approval request names for the document, else the latest settled version; it is the web app's call. `POST /api/v1/artifacts/{id}/versions/{number}/reviews` takes the same body, and `{number}` is the version the caller read: when the review would record another version the route answers `409 REVIEW_VERSION_MOVED`, naming the version it would record, before it answers the request or writes anything, and a `{number}` that is not an integer from 1 is `400 INVALID_REVIEW`. The guard is a route rather than a body member because a route ignores a member it does not declare, so a build without it answers no route rather than recording a version it chooses. `dispatch review` sends only the versioned route. The going catalogue (`going_catalogue.go`) gives `dispatch_review` no row, so the loop that proposes operations on the graph never proposes an approval in a person's name, and both review routes stay in `goingMutatingRoutesWithNoTool`.

The reviewer of INFRA-3231's R5 reads each text an agent writes to a person before or after it reaches them (`reviewer.go`, with the component in `internal/dispatch/reviewer`). Each create path of an ask, a new issue, a comment and a message, and each reply an agent posts to a delivery it got, calls `reviewWrite` (or `reviewReply`) where it used to call the writing check alone, once its input is decoded and its actor resolved: by `DISPATCH_REVIEWER_<KIND>` the write is held (`hold`), posted and reviewed after (`after`), or left to the writing check (`off`). A held text is a row of `held_texts` and nothing else (`held_texts.go`): no person's read, count, feed, notice, event, reference or search row shows it, because none of them is written until it posts. The write answers at once with today's response shape built from the held row, under the id the hold reserved (an issue's key from its project's sequence), and a `held` object. A session's later write that names it is kept beside it and runs right after it posts: a create of a kind the reviewer holds (a child issue, a comment or a reply to one, a message) always, held by `reviewWrite` under an id of its own; any other write (a claim, an edit, a result) only when its request carries `Dispatch-Accepts-Kept-Write: 1` (`contracts.AcceptsKeptWriteHeader`, which the agents' `DispatchClient` sends on every write), answered `202 {id, held}` (`awaitHeldTarget`, `held_replay.go`), and without it `409 HELD_TEXT` with the held id, with nothing kept. A session reading a held ask, comment, message or issue by its id gets `409 HELD_TEXT` with the held id (`answerHeldRead`), and `GET /api/v1/held/{id}` serves it to any agent's token and no person. The review runs in the background; its findings go to the writer session as a `message.created` frame of Dispatch's system actor whose message id is the held id, sent through the listener with no stored message and no event (`sendFindingsFrame`), which both plugins deliver as a main turn. The writer edits the text (`PATCH /api/v1/held/{id}`, reviewed again) or posts it as written with a reason (`PUT /api/v1/held/{id}/state {state: "posted", reason}`, the one state it takes; the same PUT again answers the held text as it stands); a writer that has gone, or does not act within `DISPATCH_REVIEWER_WRITER_WINDOW`, gets what `DISPATCH_REVIEWER_UNEDITED` says, and a model that fails or runs past `DISPATCH_REVIEWER_TIMEOUT` posts the text as written. The post runs the kind's own create path in one transaction with the stored request, the recorded actor and the reserved id, so it writes today's rows and emits today's event, the post time as the row's creation time. A leased sweep (`ReviewerSweepLease`, every 10 s) reviews again what a stopped process left, acts on the writers that have gone or run out of time, and posts what is decided. Every decision is one `writing_check_events` row.

Three kinds of agent text are reviewed after their save and never held (`reviewer_after.go`): a document version, by `DISPATCH_REVIEWER_DOCUMENTS=after` (the upload and edit routes of issue and project documents); and an agent's edit of an ask, a comment or an issue's title (`PATCH /api/v1/asks/{id}`, `PATCH /api/v1/comments/{id}`, `PATCH /api/v1/issues/{key}`), whenever the kind's setting is `after` or `hold`. Their findings go to the writer in the same frame, as advice: a writer that does not act leaves the text as it saved. A decision block in a document is the one held text a person can already see (`decision_blocks.go`): its ask row exists from the settlement that opens it, so with `DISPATCH_REVIEWER_DECISION_BLOCKS=hold` the document service tells the reviewer of each new block in the settlement's own transaction (`docs.AskBlockReviewer`), which sets the ask's `held_until` and keeps a `held_texts` row of kind `decision_block` under its id. Every Inbox read, every open-ask count and the issue read's own open asks (its "Waiting on you", `listIssueAsksQueryWaiting`) leave out an open ask whose `held_until` is still to come (`askNotHeld`), while the document and the issue's conversation (its ask list) show it. The post of a held block ends the hold and appends a quiet `ask.reviewed`, which an open page refetches its Inbox and counts on; where the reviewer's rewrite posts, it first goes through the one decision-block rewrite path (`rewriteDecisionBlock`): the block's new wording written into its document, which its next version holds, and into its row, with an `ask.edited` that holds the original, who asked and why. A person's Rewrite of a decision block calls the same path. With `after` a new block is reviewed once its settlement commits, and with `after` or `hold` a later rewording of an open block (a document edit, or `PATCH /api/v1/asks/{id}`) is reviewed after it with no hold; a rewording while the block's hold has not ended is its writer's edit of the held text, reviewed again.

A write a person typed in a session carries `Dispatch-Person-Typed: 1` (`contracts.PersonTypedHeader`, which the `dispatch` command sends when pi-envoy's typed shell ran its line). On every write route it posts at once with no hold and no review, whatever the settings say, is recorded `exempt_person_typed` with its session (`personTypedWrite`, `recordPersonTyped`), and every text event it appends carries `person_typed: true` (`markPersonTyped` marks the request's context with `store.WithPersonTyped`, a write batch built under it carries the mark, `store.WriteBatch.PersonTyped`, and `events.Broker.QueueAppendWithLogins` marks each text payload by its own `WithPersonTyped`). A document write it makes records every ask block it leaves in the document as typed (`doc_ask_block_authors.person_typed`, until the settlement that indexes the block), so that settlement opens a new block, or rewords an open one, with no hold and no review, records it `exempt_person_typed` and marks its `ask.opened` or `ask.edited`; a typed rewording of a block whose hold has not ended ends the hold with the block as the person left it.

The writing check (`writing_check.go`, with its rules and its reader in `internal/dispatch/writingcheck`) reads the prose of every route that carries any, once the request is decoded and its writer resolved and before the write opens a transaction. It decides the text's reader from the record (`writing_check_reader.go`, one rule per route in `writingCheckReaderRules`), reads only an agent's write that a person reads, applies the bundle's three structure rules with the phrase detector off, and records one `writing_check_events` row per decision; it refuses no write. One registry (`writing_check_fields.go`) marks every string member of every request type as prose or not, and the route guard tests fail a route that carries prose and does not reach the check. A reply a plugin marks `Dispatch-Generated-Text: 1` on the two delivery reply routes is recorded `exempt_generated` and posts at once. `GET /api/v1/writing-check` answers the check as the process runs it, and `GET /api/v1/writing-check/counts` counts per day, project and person from `writing_check_events`, `word_questions` and the event log.

A person's Rewrite of an open question (`ask_rewrite.go`, `POST /api/v1/asks/{id}/rewrites`) and Define of words they selected (`definitions.go`, `POST /api/v1/definitions`) call the reviewer component's Rewrite and Define with the model group `DISPATCH_REWRITE_DEFINE_MODEL_*`, and are on whenever that group is set. A Rewrite answers `202` at once and runs in the background, one at a time per ask (`ask_rewrites`); it may first send the asking session one side question as Dispatch's system actor, and it applies its result only where `reviewer.Preserve` finds kept what a rewrite must keep and the agent has not changed, answered or closed the question meanwhile. An applied rewrite goes through the edit route's own path (a decision block's through `rewriteDecisionBlock`) as a quiet `ask.edited` whose `rewrite` names who asked and whose `previous` holds the original, and the run's start and failure are the quiet `ask.rewriting` and `ask.rewrite_failed`. A definition is read from the record at once and kept for its person alone (`definitions`); for words of an ask it takes the asking session's answer to one side question within 60 seconds, through `POST /api/v1/messages/{id}/reply` under the definition's id, appends no event, and is recorded as that person's word question. Every read of an ask, a comment, a message and an issue carries `rewrite` where a rewrite touched it (`text_rewrites.go`), and no event payload does. The lists this work adds, `GET /api/v1/me/definitions`, `GET /api/v1/readers/{login}/words` and the rows of `GET /api/v1/writing-check/counts`, each answer one page, `{items, total, limit, offset}`, with the bounds of the caller's own answers list (`list_page.go`).

`GET /api/v1/settings/writing-rules` and `POST /api/v1/writing-rules` (`writing_rules.go`) serve the `dispatch` command's refusal that shows the written rules: the setting, and for a write not sent yet its reader, decided as the writing check decides it, and the rules text, `skills/plain-words` as the server embeds it (`internal/dispatch/writingcheck/plainwords`). `GET /api/v1/readers/{login}/words` (`reader_words.go`) serves the words one reader asked about to any agent's token and to that person alone. The records job that writes those records, `internal/dispatch/wordrecords`, is no route: `cmd/dispatch` runs it under the lease `word-records`, and it reads the event log after each write has committed.

A whole-document upload says which version it replaces. `artifacts.go` reads `precondition` from the JSON body and from the multipart form field of that name, holds it to the document token alone (`docs.ValidateUploadPrecondition`) before anything is written, and hands it to `docs.ReplaceText`, which checks it under the write's own locks; a token behind the live document is refused `409 PRECONDITION_FAILED` carrying the live token, `current.version` — the version this route has already counted, the next number less one — and the sentence naming `dispatch doc-read`, and nothing is written. A replacement that names no token at all is refused `400 PRECONDITION_REQUIRED`, always and under no setting: `ReplaceText` decides it at its `precondition == nil` check, on the tree it has already read, and `artifacts.go` words the refusal with the document's name. A document whose live tree is outside the Proof schema is the one exception, since it renders no markdown and has no token for anybody to name, and the upload is the only way to repair it. A first upload under a name and a file that is no document replace no version, so neither names a token.

Both JSON fields a multipart upload carries, its `actor` and its `precondition`, are read as the JSON body is read (`api.multipartJSONField`): a member no field of the object names is ignored and logged at debug with the route (`logUndeclaredMembers`), so one build of a fleet takes an upload another build's member rides in.
What a misspelled key cannot do is pass as the key it misspells: a precondition left naming nothing is refused `400 INVALID_PRECONDITION` by its own shape check, in a form field as in a body, and that upload writes nothing.

A question opened on an issue carries the review that issue's specification already holds (`standing_review_advice.go`'s `standingReview`), read in a savepoint of its own under a 500 ms statement timeout and reported beside the related-item check the same write answers with. Each bounded document report — this one, the superseded approval and the moved approval request — opens a savepoint of its own through one helper (`adviceSavepoint`), which sets that timeout, so a failed read costs its own report and no other and is logged where it happens (`logAdviceError`). It is reported only where it is a person's own review — an actor of kind `user` with no agent named beside them — pinned to the version the document is at now, so a review of an older version, a plan review and a review an agent wrote under a person's scope each report nothing, as do a question on a project document and a read that failed: the question is written either way. A review `dispatch review` records is one of those: a broker token always proves a session (`broker_token.go`'s `brokerTokenActor`), so `actingPerson` writes that session into the review's `act` and `standingSpecReview` drops it, whoever typed the command, because the line this advice prints says the person reviewed that version and Dispatch cannot tell a person's own command from an agent's under the same scope, where a false line is worse than none and the advice refuses nothing either way. A review Dispatch carried forward to that version carries `carried_from_version`, the version its carry reason gives, and no other review carries that field, so it is what tells a carried review from one the person gave; the sentence is parsed where it is written (`docs.CarriedFromVersion`). Its stored reason, which is Dispatch's own carry sentence, is left out: a reader printing it would quote Dispatch back to the sender as the reviewer's words. The review is about the document rather than the words of the question, so it holds for a question worded in any way; the suggestions beside it are the ones that depend on the words.

A broker token carries a list of projects (`ciphertoken.Caller.Projects`). Only a token an operator's entry mapped, under the named project scope with its one project, sets `Actor.Project`, the one project its writes are held to (`project_scope.go`); a person token's list, the projects its trade named and Dispatch said its person sees, limits no write at this release, so such a token writes wherever its person may, as one naming no project does (`broker_token.go`).
