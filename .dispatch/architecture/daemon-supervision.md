Stage 2 on `main` provides the fenced role-claim state machine and task delivery (`internal/supervise`), the worker stream and shim (`internal/stream`, `internal/shim`, `internal/shimwire`), and the pluggable runtime with its tmux implementation (`internal/runtime`). Stage 3 plans workspace provisioning and role-prompt composition in `internal/workspace` and `internal/prompts`; Stage 4 plans the Agent Sandbox runtime beside tmux, which stays a supported runtime (LEGION-206). An open phase's agent remains reachable through Envoy and resumes as the same session on demand. Under the Sandbox runtime the state machine also enrolls each pod's key with the secrets broker once the agent registers and revokes the enrollment at every path that lets the pod go — a death, the registration deadline, a suspension, a stop, or the tree's close. In an issue pod the launcher, as the container's first process, also runs a memory guard (`internal/memoryguard`) that ends the largest process that is neither Legion's own nor an agent's own when the pod nears its memory limit, and reports the kill on the role's launcher connection (`launcher_memory_kill`), from which the daemon tells that role why on its role topic.

Every launch's system prompt is composed in the daemon (`runtime.ComposePrompt`) and reaches the agent as a file whose path is its one `--append-system-prompt` (Claude Code's `--append-system-prompt-file`), so no argument grows with the prompt past Linux's 131,072-byte `MAX_ARG_STRLEN`: a tmux launch writes it to `<state_dir>/secrets/<claim>-system-prompt.md` (`runtime.SystemPromptPath`), and a pod's launcher writes it from the start command's files into the generation's directory of the role's own private volume. The daemon sets no bound on a model's context; the one bound left is the one frame a pod's launcher reads, and a prompt whose start command would pass it is `runtime.PromptTooLarge`, which the state machine charges no launch failure: it fails the claim at once with that sentence (`promptRefused`).

The work hold's stop is a suspension source of its own, `hold` (`supervise.SuspendedByHold`, `internal/supervise/workhold.go`). Like any held suspension, it waits for the agent's turn, and it cuts a turn that still runs at the deadline the outbox stores, 2 minutes after the close message reached the claim (`RequestSuspend.Deadline`, `RequestSuspend.TurnAfter`). The claim keeps its session, its phase and its pending task. No rule starts it: the fence answers every request that could start a turn of the claim (`ruleDoor`) with a wait, `ErrHeldByWorkHold`. Only the operator's own resume or retry (`ownerDoor`) or the hold's end (`Machine.EndHold`) starts it. `EndHold` drops a stop that is not made yet, and starts a claim the hold stopped with one task, the opening's sentences in front of its work. An operator's suspension and the daemon's own take a held claim over, and the hold takes over a released claim and a pause's stop (`suspensionRank`). The idle rule keeps the pod of a claim the hold stopped (`workflow.IdleHoldUnownedWorkHeld`).
