Stage 2 on `main` provides the fenced claim state machine (one claim for each agent of an issue) and task delivery (`internal/supervise`), the worker stream and shim (`internal/stream`, `internal/shim`, `internal/shimwire`), and the pluggable runtime with its tmux implementation (`internal/runtime`). Stage 3 plans workspace provisioning and role-prompt composition in `internal/workspace` and `internal/prompts`; Stage 4 plans the Agent Sandbox runtime beside tmux, which stays a supported runtime (LEGION-206). An open phase's agent remains reachable through Envoy and resumes as the same session on demand. Under the Sandbox runtime the state machine also enrolls each pod's key with the secrets broker once the agent registers and revokes the enrollment at every path that lets the pod go — a death, the registration deadline, a suspension, a stop, or the tree's close. In an issue pod and in the controller's pod the launcher, as the container's first process, also runs a memory guard (`internal/memoryguard`) that, when the pod nears its memory limit, ends, of the processes that are neither Legion's own nor an agent's own, the process that grew the most over its last few reads, else the largest one it has read at most once in its last two readings near the limit, else the one that grew the most since the guard's first kill while the reading stays near the limit, else the largest, a fork that still runs its parent's program counted by what it holds over its parent, and, from halfway between the share it acts at and the limit, every process that grew over its last few reads and, where one it may end is not new to its stay near the limit, every one new to that stay that holds memory of its own, each a kill of its own, and reports each kill on its slot's launcher connection (`launcher_memory_kill`), from which the daemon tells the claim of that slot why: an issue pod's claim on its role topic, and the controller in a controller notice of kind `memory-guard-kill`.

Every launch's system prompt is composed in the daemon (`runtime.ComposePrompt`) and reaches the agent as a file whose path is its one `--append-system-prompt` (Claude Code's `--append-system-prompt-file`), so no argument grows with the prompt past Linux's 131,072-byte `MAX_ARG_STRLEN`: a tmux launch writes it to `<state_dir>/secrets/<claim>-system-prompt.md` (`runtime.SystemPromptPath`), and a pod's launcher writes it from the start command's files into the generation's directory of its slot's own private volume, the slot of the claim's agent whatever role its step is on. The daemon sets no bound on a model's context; the one bound left is the one frame a pod's launcher reads, and a prompt whose start command would pass it is `runtime.PromptTooLarge`, which the state machine charges no launch failure: it fails the claim at once with that sentence (`promptRefused`).
