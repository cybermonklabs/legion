Stage 2 on `main` provides the fenced role-claim state machine and task delivery (`internal/supervise`), the worker stream and shim (`internal/stream`, `internal/shim`, `internal/shimwire`), and the pluggable runtime with its tmux implementation (`internal/runtime`). Stage 3 plans workspace provisioning and role-prompt composition in `internal/workspace` and `internal/prompts`; Stage 4 plans the Agent Sandbox runtime beside tmux, which stays a supported runtime (LEGION-206). An open phase's agent remains reachable through Envoy and resumes as the same session on demand. Under the Sandbox runtime the state machine also enrolls each pod's key with the secrets broker once the agent registers and revokes the enrollment at every path that lets the pod go — a death, the registration deadline, a suspension, a stop, or the tree's close. In an issue pod and in the controller's pod the launcher, as the container's first process, also runs a memory guard (`internal/memoryguard`) that, when the pod nears its memory limit, ends, of the processes that are neither Legion's own nor an agent's own, the process that grew the most over its last few reads, else the largest one it has read at most once in its last two readings near the limit, else the one that grew the most since the guard's first kill while the reading stays near the limit, else the largest, a fork that still runs its parent's program counted by what it holds over its parent, and, from halfway between the share it acts at and the limit, every process that grew over its last few reads and, where one it may end is not new to its stay near the limit, every one new to that stay that holds memory of its own, each a kill of its own, and reports each kill on the role's launcher connection (`launcher_memory_kill`), from which the daemon tells that role why: an issue pod's role on its role topic, and the controller in a controller notice of kind `memory-guard-kill`.

Every launch's system prompt is composed in the daemon (`runtime.ComposePrompt`) and reaches the agent as a file whose path is its one `--append-system-prompt` (Claude Code's `--append-system-prompt-file`), so no argument grows with the prompt past Linux's 131,072-byte `MAX_ARG_STRLEN`: a tmux launch writes it to `<state_dir>/secrets/<claim>-system-prompt.md` (`runtime.SystemPromptPath`), and a pod's launcher writes it from the start command's files into the generation's directory of the role's own private volume. The daemon sets no bound on a model's context; the one bound left is the one frame a pod's launcher reads, and a prompt whose start command would pass it is `runtime.PromptTooLarge`, which the state machine charges no launch failure: it fails the claim at once with that sentence (`promptRefused`).

The work hold's stop is a suspension source of its own, `hold` (`supervise.SuspendedByHold`, `internal/supervise/workhold.go`). Like any held suspension, it waits for the agent's turn, and it cuts a turn that still runs at the deadline its outbox row stores (`RequestSuspend.Deadline`, `RequestSuspend.TurnAfter`). That deadline is 2 minutes after the close message reached the claim, or 2 minutes after the close for a stop that the close writes at once, which no message reaches. The claim keeps its session, its phase and its pending task. No rule starts it: the fence answers every request that could start a turn of the claim (`ruleDoor`) with a wait, `ErrHeldByWorkHold`. Only the operator's own resume or retry (`ownerDoor`) or the hold's end (`Machine.EndHold`) starts it. `EndHold` drops a stop that is not made yet, and starts a claim the hold stopped with one task, the opening's sentences in front of its work. The hold's stop does not cut a start in flight short: it waits for the start's decision. An operator's suspension and the daemon's own take a held claim over, and the hold takes over a released claim and a pause's stop (`suspensionRank`). The idle rule keeps the pod of a claim the hold stopped (`workflow.IdleHoldUnownedWorkHeld`).

The stop and the opening use one row: the tree's `work_holds` row. A decision that can make the hold's stop reads whether this row stands (`Store.WorkHoldStands`, `readHoldForStop`): the store takes the row for share in a transaction of its own, and rolls that transaction back before it answers. Such a decision is a decision of a claim whose hold stop is held, or the decision of the hold's stop itself. A tool step and a model's answer read nothing, because their rows only record what the agent did. The opening takes the same row for update before it reads the tree's claims, and deletes the row in the same transaction (`workflow`'s `tellAndEndWorkHold`). In that transaction, the opening also writes the hold and what ended the hold to `work_hold_openings` (`record.Store.OpenWorkHold`). The read does not read that table. A read that starts while the opening holds the row waits for the opening's commit. If the opening commits first, the decision reads no row and makes no stop: it drops a held stop, and the hold's stop asked now answers `ErrWorkHoldEnded`, so the outbox finishes the stop's row. The wait for the read ends at the claim-write deadline. If the read fails, a held stop stays held, and the stop's outbox row asks again.

No decision holds the row after its read. The opening waits for the row under the lock that every fact takes. A decision that held the row across a call of the runtime, such as a process stop, would stop every fact of the daemon for as long as the call ran. So the opening can commit after a decision read the row and before that decision writes the stop. One case remains: a stop decided in the instant before an opening commits is made, and the claim is started at once with the opening's task, as the next paragraph says.

Because the opening can commit before a stop is written, the opening can read a claim before its stop is written, and start nothing of it. So after each write of the hold's stop, the machine reads the row again for share, in a new transaction, and ends that transaction at once (`holdReadAfterStop`). This read waits for an opening that holds the row. If the row stands, a later opening reads the stopped claim and starts it. If the row is gone, the machine tells the daemon (`Deps.WorkHoldEndedUnderStop`). The daemon then applies `intake.WorkHoldOpened` at once. This fact starts each claim that the hold stopped and that no opening start covers, so no claim starts twice.

If the read fails, the decision returns the error, and the stop's outbox row asks again. The next attempt posts the stop again, and its decision reads the row. If the row is gone, the machine tells the daemon, as above, and the row finishes. If the write of the stop fails, the machine keeps that write owed, and no read follows. Each decision first makes an owed claim write, and `EndHold` does this too. If the write fails again, the store does not hold the stop, so the machine does not tell the daemon. Then `EndHold` changes nothing and returns an error. The stop asked again returns an error, not `ErrWorkHoldEnded`. In each case, the outbox row asks again.

The stop's outbox row reads no gate of its own (`internal/daemon`'s `holdStop`): the decision's read of the row decides the stop. Under a hold other than `work`, the row makes no stop. That check reads the deployment's hold, and not the gate or the row. After a restart into `start`, the boot ends the tree's hold beside the outbox, so the row can run while the tree's row still stands.

Each start of a claim that the hold stopped gives the claim one task, and one function builds the start of that task (`workflow`'s `heldClaimOpening`). The opening, the read after the stop, the stop asked again and the boot all use it. The opening builds the task from the row that it moves into the tree's record of its last opening. Each later start reads that record (`record.Store.TreeWorkHold`). The task names the version that closed the gate, says that the work hold stopped the turn, and carries what ended the hold: today's open message, or the boot's sentence when the deployment no longer holds the tree's work. If the tree's record shows a hold that stands, the hold stands again, and the start does not occur. If the daemon keeps no record of the hold, or the record is of an older generation of the tree, the task says that the hold has ended and that the daemon keeps no record of the version that closed the gate. This occurs after a new generation of the tree. The task never says that the deployment no longer holds the work, unless the boot ended the hold for that reason.

The outbox builds those sentences again when a start reaches a claim that the hold holds, from the tree's record as it stands then (`workflow.HeldClaimOpening`, `internal/daemon`'s `startOfAHeldClaim`). It takes the sentences that an opening start carries off the front of the start's task, and puts the new sentences there. So a start that one opening queued, and that runs after a later close and a later opening, names the later version and carries the later open message. A start that carries no sentences of its own gets them in front of its work too. Where the record shows a hold that stands, the start waits.

One rule says which queued start of the opening stands (`workflow.OpeningStartStands`). The opening reads it before it writes a start, and the outbox reads it for each start that reaches a claim that the hold holds. A start of the opening stands only if it is newer than each stop that still acts. An opening start gives way only to a newer opening start. An opening start that carries no phase work does not stand over a start that carries the phase work: that start is the role's one task, with the opening's sentences in front. An opening start that meets a claim that the hold does not hold finishes without action, because another start or the operator started the claim already.
