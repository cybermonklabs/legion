Stage 2 on `main` provides the fenced role-claim state machine and task delivery (`internal/supervise`), the worker stream and shim (`internal/stream`, `internal/shim`, `internal/shimwire`), and the pluggable runtime with its tmux implementation (`internal/runtime`). Stage 3 plans workspace provisioning and role-prompt composition in `internal/workspace` and `internal/prompts`; Stage 4 plans the Agent Sandbox runtime beside tmux, which stays a supported runtime (LEGION-206). An open phase's agent remains reachable through Envoy and resumes as the same session on demand. Under the Sandbox runtime the state machine also enrolls each pod's key with the secrets broker once the agent registers and revokes the enrollment at every path that lets the pod go — a death, the registration deadline, a suspension, a stop, or the tree's close. In an issue pod and in the controller's pod the launcher, as the container's first process, also runs a memory guard (`internal/memoryguard`) that, when the pod nears its memory limit, ends, of the processes that are neither Legion's own nor an agent's own, the process that grew the most over its last few reads, else the largest one it has read at most once in its last two readings near the limit, else the one that grew the most since the guard's first kill while the reading stays near the limit, else the largest, a fork that still runs its parent's program counted by what it holds over its parent, and, from halfway between the share it acts at and the limit, every process that grew over its last few reads and, where one it may end is not new to its stay near the limit, every one new to that stay that holds memory of its own, each a kill of its own, and reports each kill on the role's launcher connection (`launcher_memory_kill`), from which the daemon tells that role why: an issue pod's role on its role topic, and the controller in a controller notice of kind `memory-guard-kill`.

Every launch's system prompt is composed in the daemon (`runtime.ComposePrompt`) and reaches the agent as a file whose path is its one `--append-system-prompt` (Claude Code's `--append-system-prompt-file`), so no argument grows with the prompt past Linux's 131,072-byte `MAX_ARG_STRLEN`: a tmux launch writes it to `<state_dir>/secrets/<claim>-system-prompt.md` (`runtime.SystemPromptPath`), and a pod's launcher writes it from the start command's files into the generation's directory of the role's own private volume. The daemon sets no bound on a model's context; the one bound left is the one frame a pod's launcher reads, and a prompt whose start command would pass it is `runtime.PromptTooLarge`, which the state machine charges no launch failure: it fails the claim at once with that sentence (`promptRefused`).

A launch of an experiment arm's folder of texts reaches a runtime as `runtime.SpawnSpec.Texts`: the folder as the arm names it, the fingerprint the daemon read it at, the daemon's own copy of what it read and checked, `<state>/texts/<claim>/<generation>/folder`, from which the role prompt's parts were already composed, and the arm.
Beside it the spec build makes the launch's fallback once (`runtime.Texts.Fallback`): Legion's prompt parts, and the launch's arms with the folder's arm dropped whole, its overlays and its instructions copy with it.
`runtime.SpawnSpec.FallBack` is the one way a launch becomes that control, whichever check failed, the daemon's own at the spec build or a runtime's at the launch, and it answers the `runtime.TextsReport` that `Options.TextsFellBack` hands the daemon, which logs it at WARN naming the claim, the generation, the experiment, the arm, the folder, the file and the cause, and applies the intake fact `TextsFellBack`, whose handler (`workflow.Engine.textsFellBack`) posts the issue one message for each claim and cause.
`ValidateSpawnSpec` refuses a controller spec that carries a folder and a folder no arm of the launch names.
Under tmux the runtime checks before it composes the prompt (`checkArmTexts`; `PrepareTexts`, which the live proofs' local runtime calls too): it reads the daemon's copy, holds each of its agents and skills to the file of the plugin the pane's profile has installed, found as the boot gate's pane lane finds it (`texts.CheckPlugins`: a stale digest, a path no plugin ships, a frontmatter name that is not its path's), and only then, under the launch lock, builds the extension root beside the copy, `<state>/texts/<claim>/<generation>/root` (`texts.BuildRoot`: every pi-legion agent and pi-envoy skill, and each pi-legion skill the folder touches, as copies with the folder's files over them), with its settings layer `texts-settings.yml`.
`innerCommand` names `--extension <root>` ahead of `--model`, so Oh My Pi loads it before the profile's installed plugins and gives its copy of each skill the plain name, and the pane is told `LEGION_TEXTS_ROOT` (runtime-owned, so no operator pane variable can set it) and the layer last in `PI_CONFIG_FILES`.
The layer sets `skills.ignoredSkills` to what Oh My Pi would read without it (`texts.BaseIgnoredSkills`: the last overlay that sets it, else the workspace's `.omp`, else the profile's) and adds `*/<skill>` and `*/<skill>~*` for each skill the folder touches, so no collision alias of a replaced skill is offered.
Under Kubernetes the role's launcher makes the same check in the pod before it writes anything (`kubernetes-runtime`), told through three optional members of `internal/shimwire`'s frames: `LauncherHello.ChecksTexts`, `LauncherStart.Texts` (the folder, the fingerprint, the root to build, `TextsRoot` under the role's state home, and the two plugin roots the agent loads) and `LauncherStartResult.Texts` (the file, the cause and what the check saw); the sandbox runtime answers a texts refusal with the control's start in the same try, uncharged, under the id `start-<generation>-texts-fallback`, sends the control's start alone to a launcher that did not say it checks and to a launch that installs the plugin pair after its start, and charges a refusal of that second start as any start's.
