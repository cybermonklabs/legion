Parse, render and search over the Proof document tree: the typed-block schema (`schema/blocks.json`), block-id minting and repair, and the fixtures generated from the fork's headless engine (`gen`). It imports three other packages of the server: `model`, `text` and the small byte-bounded cache `bytelru`.

The display trees a read shows beside stored text (`DisplayJSON`) are kept in one cache per process (`displayCache`, a `bytelru`), bounded at `DisplayCacheBytes`, 64 MiB. Each tree is charged what it holds: its array, its key and its entry (`displayCacheEntrySize`).

A whole-document upload keeps the ids of the blocks it leaves alone. `carryBlockIDs` parses the uploaded markdown over the live tree and aligns each parent's children in the upload with that parent's children in the live tree: the unchanged children at either end pair in place, each other unchanged child pairs with the live child it equals wherever that child stands, and the children left over pair as `Update`'s own alignment pairs them, between the unchanged children the upload kept in their order. A block of the upload takes the id of the live block it pairs with wherever the uploaded markdown names no id for it: every untyped block, whose id `GET /text` renders nowhere, and a typed block whose markdown names none, which is what a body an agent composed rather than read back from the document looks like. So a version that moves a block among its parent's children without changing it keeps the id of that block and of every block the move passes, and a pointer or an anchor into any of them still resolves. A typed block whose markdown does name an id keeps the one it names, that id being part of what the markdown wrote. For the typed pair naming no id the comparison masks the block id and the whole of that block's server state, the answer with it (`unchangedAttrs`, over `node.go`'s `attrsEqualOutsideServerStateBut`), because an upload resets a typed block's server state and the settlement writes it back from the ask row, and an agent composing a body cannot know the answer a person gave: an answered ask whose question text is unchanged must read as unchanged, or it takes a fresh id, orphans the row holding that answer and opens a second row on the same question. An untyped container, a list or a table among them, that the alignment keeps in its place keeps its id though its contents changed (`carryKept`). A block whose text changed, one the upload puts under another parent, a changed container moved out of its place, one whose markdown names the live block's id anywhere, and one whose live id no ask row or anchor could store each take a fresh id from `EnsureBlockIDs`.

A table row is split into cells as the browser editor splits it: a `|` after an even run of backslashes, none included, ends the cell, and one after an odd run is the cell's text, so `| a \\| b |` is the cells `a \` and `b`, and `| a \| b |` is the one cell `a | b`. Goldmark ends a cell only at a `|` with no backslash right before it, so `table.go` splits its cells where the two differ and counts every row's cells by the browser's rule.

So code in a cell cannot hold a `|` after an odd run of backslashes (`\|`): in a cell a `|` is written `\|`, in code too, `\\|` ends the cell, and a backslash escapes nothing in code. A caller's write that adds such code to a cell (a replace, a delete by quote, an accepted suggestion) is refused: `TableCodePipes` lists every such code span of the document-level blocks the write changed, before and after it, `refuseCodePipeInTableCell` (`docs/edits.go`) compares the two by the code's text, counted, and refuses with the first one the write added, whose error names the table's block id, the cell's row and column and the header above it, and says to drop the backslash or end the code before the `|`. Such code a browser edit already left is no reason to refuse a write beside it or one that rewrites it to hold no such `|`, but the same code written again beside it is refused. A browser edit holding it is versioned at settlement as its rendering, as every browser edit is: `render_table.go` (`codePipesOutOfCode`) writes each such `|` as text after the code, so `a\|b` in code is stored `` `a\`\|`b` ``, which both parsers read back as the same cell with every character, that `|` no longer code.
