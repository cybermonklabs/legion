The Go-based event transport: webhook ingress, NATS routing and delivery, the native Dispatch server, and the MCP bridge. Dispatch's database is PostgreSQL 18 with pgvector: `envoy-infra`'s `gcp:Dispatch` defaults a new instance to `POSTGRES_18`, and `internal/testpg`, `scripts/dev-postgres.sh` and `deploy/compose/dispatch.acceptance.compose.yml` pin one pgvector-on-18 image by digest. Dispatch packages no child component claims sit here directly, among them the embedding queue (`internal/dispatch/embedqueue`) that keeps meaning search's vectors current, an issue's from its title and its spec. Its NATS hub comes in two forms, both deployed by `envoy-infra` (`packages/envoy/infra`, a Go module of its own that builds a Pulumi plugin and the `envoy-infra` command, and compiles the Envoy packages it imports from this checkout): `gcp:NatsHub`, one nats-server on a Google Cloud VM that joins the tailnet, and `gcp:ClusteredNatsHub`, three nats-server pods on a GKE cluster whose optional Tailscale Service hosts forward the tailnet's connections to NATS and to a session listener the component runs as a workload of its own. Both render their NATS users through the one function in `packages/envoy/infra/gcp/natshub.go`, from the permission sets `packages/envoy/infra/core` wraps from `packages/envoy/natsgrant`, the one grant table Envoy's NATS auth service also answers connections with.

The address Pulumi downloads the `envoy-infra` plugin from is stamped in at build time, from the repository the release ran in: `release-envoy-infra.yaml` derives it with `.github/scripts/repo-paths.sh plugin_download_url` and builds the plugin with `-ldflags -X 'github.com/sjawhar/envoy/infra/provider.downloadURL=<that URL>'`, so the schema the plugin serves points at the releases of whatever repository published it, and the job's smoke test compares `pluginDownloadURL` against the same derived value rather than a literal. That is why `provider.go` holds `downloadURL` as a `var` and no longer a `const` — `-X` writes a variable and never a constant — with today's `https://github.com/cybermonklabs/legion/releases/download/envoy-infra-v${VERSION}` as its default, which a build carrying no such flag, a developer's and the package's own tests', serves unchanged; the `${VERSION}` in it is Pulumi's placeholder, filled in at install, and nothing on the way through may expand it.

The secrets broker sits here too (`cmd/cipherd`, `internal/cipher`), and with it this repository's one Go client of its RFC 8693 token exchange: `internal/cipherclient`, re-exported as `packages/envoy/cipherclient` so a module outside this one can import it past Go's internal-package rule, which is how `packages/daemon`'s `legion controller start` proves, before it starts the controller, that this machine can trade for the Dispatch credential the controller's session then holds. Every DPoP proof that client signs, and every proof the broker's airlock proxy signs for a write it carries, comes from `internal/dpopproof`, the one DPoP signer the client and the proxy share. A machine trades the Google identity token `internal/googleidentity` reads from its metadata server for a DPoP-bound access token and the launcher credential the same trade mints, under which it enrols its session; that credential is keyed by the machine and the thumbprint of the key its proof presented, so a copy of the identity token asks for a credential of its own rather than moving the machine's, and the session it enrolled renews only while that credential is live — revoked, past its hour, or its account dropped from `BROKER_VM_SERVICES`, and the session lapses within one lease. A person signs in on that machine with `agent-secrets login`, whose device grant gives their own identity token, traded with the machine's as the actor token and recorded as a `person_signins` row keyed by the person, the box key and the machine; their sessions are not held to the machine's login and end when the sign-in is revoked. The TypeScript client (`packages/cipher-client`) trades that same sign-in for every Oh My Pi and Claude Code session and every `dispatch` command on the machine, proving the same box key, so its Dispatch token names the person. The Go client and the TypeScript one are held to one wire by the corpus at `internal/cipherclient/testdata/wire.json`, which both suites replay. `scripts/dev-stack.sh` boots the stand-in issuer (`cmd/dev-oidc-issuer`), the broker, NATS, the listener and Dispatch together, so the whole path can be driven on one machine with no Google and no cluster; with `--binaries <dir>` it runs the stack's binaries built elsewhere (a Legion pod's, built in the builds farm) in place of its own `go build`.

The exchange also mints a read-only Dispatch token from a read entry (`BROKER_EXCHANGE_READ_ACCOUNTS`, `<service account>=<service>=<session>`). That token holds the OAuth scope `read` alone and the project scope `none`, and names the entry's service and fixed session and no person and no project. `oauth.Provider.decide` writes one project-scope word for each value it knows (`writeProjectScope`) and refuses any other value, and a read entry's pod registration is `409 SESSION_FIXED`.

Any trade but a job entry's may also ask for `read` (`scope=read`): the exchange client is registered for it, and its scope strategy holds it by every subject, so a machine login granted `machine` alone may ask too. `decide` refuses a job entry's trade that asks for it with `invalid_request`, since a job's token is minted whole, with no OAuth scope. The token keeps the identity the same trade would have had, under the narrowed project-scope word `read-named`, `read-person` or `read-none` (`oauthwire.BaseProjectScope` answers the base word every check reads), holds `read`, and `person` beside it for a token that acts for its person. It may carry a cut (`as_of`, kept as the claim and the introspection member `as_of`). A read trade makes, moves and extends no launcher credential: a person's read trade names the credential the sign-in already holds, so the sign-in's revoke ends the token. The broker keeps a narrowed token in `oauth_narrowed_access_tokens` (migration 0042), which no older broker reads, so such a broker answers it inactive, and decides at each introspection whether the row, the credential it names and a machine login's subject token are all still live. Its expiry is clamped to its subject's and that credential's. No key is both a live read token's and a live launcher credential's: a read trade whose proof key holds a launcher credential binds its token to a holder key it proves in a second DPoP proof (`DPoP-Holder`), which a person's read trade always sends, and the two writers of a launcher credential's key (`enroll`) refuse a key a live read token is bound to, each side under an advisory lock on the key's thumbprint (`oauthstore.KeyHoldsReadToken`). A token that holds `read` is never the subject of a trade.

The shared verifier `internal/ciphertoken` accepts a read-only token, a read entry's or a narrowed one, only where its service sets `Options.ServesReadOnly`, and then marks the caller `Caller.ReadOnly`, with its base project scope and its cut (`Caller.Cut`). Dispatch sets that switch, and the Envoy listener and the NATS auth service do not, so they answer every read-only token as not a session. Every verifier refuses the scope `read` or a cut beside the project scope `named` or `person`, the project scope `public` beside a person, without a service or beside any OAuth scope or a cut, the project scope `named` beside no person and any OAuth scope, and the project scope `none` or a narrowed word in any other shape.

A job entry names an identity, its projects and, where it fixes one, a session, and no person: `BROKER_EXCHANGE_JOB_ACCOUNTS` (`<service account>=<projects>[=<session>]`), `BROKER_EXCHANGE_JOB_WORKFLOWS` (`<repository>=<workflow path>=<ref>=<projects>[=<session>]`) and `BROKER_VM_EXCHANGE_JOB_ACCOUNTS` (`<service account email>=<projects>[=<session>]`), each read by its own parser in `internal/cipher/config` and handed to `exchange.NewSet` as an account, workflow or Google entry whose `Job` (`exchange.JobProjects`) is set. `<projects>` is one project key, or `public` followed by `,<key>` for each of at most 16 private projects (`exchange.ParseJobProjects`). `Set.Pod`, `Set.Workflow` and `Set.Google` mint for such an entry a token that names the identity as its service (the account subject, `<repository>/<workflow path>@<ref>`, or the Google account's address) and no person, with the project scope `named` and its one project or the new word `public` and its private projects, whatever the trade names; a key outside the list is `ErrProjectsFixed`, and no question goes to Dispatch (`projectAccess`). A VM job token keeps `Claims.Fleet`, so its launcher credential names the account's VM service as before. `Load` refuses an identity a job setting and the setting of its kind that names a person both list, and an account `BROKER_EXCHANGE_JOB_ACCOUNTS` and `BROKER_EXCHANGE_READ_ACCOUNTS` both list. `exchange.Set.MappedProjects` answers a job entry's list and no person, so a job pod's or a VM job machine's secret release (`requests.credentialProjects`, `collectProjectFacts`) sees no private project of that list and asks Dispatch nothing about a person. `ciphertoken` reads a service's token in two more shapes, `named` with exactly one project and `public` with 0 to 16, on every verifier; an edge listener (`EdgeAdmits`) admits a job's `named` token for its one project and refuses a `public` one. Dispatch writes a job's token under its session and its service (`writeNeedsASignedInPerson` lets a service's token write under `named` or `public` alone), and still refuses a machine's `person` token `403 SIGN_IN_REQUIRED`.

Both broker clients take `AGENT_SECRETS_MACHINE_IDENTITY=github-actions`, a GitHub Actions run's identity (`internal/cipherclient`'s `GitHubActionsIdentity`, `packages/cipher-client`'s `github-actions-identity.ts`): it reads `ACTIONS_ID_TOKEN_REQUEST_URL`, `ACTIONS_ID_TOKEN_REQUEST_TOKEN` and `AGENT_SECRETS_MACHINE_AUDIENCE`, which must equal the broker's `BROKER_EXCHANGE_GITHUB_AUDIENCE`, and asks GitHub for a new OIDC token at every trade, since the broker takes each GitHub token once. `internal/cipherclient/testdata/machine-identities.json` lists each identity kind's variables in the order the clients read them, and a Go test and a TypeScript test hold each client to it. `agent-secrets` (`cmd/cipher`, `machineSource`) refuses `github-actions` as it refuses `kubernetes`, since the broker mints no launcher credential for either; the helper, the Legion controller and `natsprobe` take it through `cipherclient.MachineIdentity`. `cmd/dev-oidc-issuer --actions-token` stands in for GitHub's token request in `scripts/dev-broker.sh`, which lists a job pod and a job workflow.

An exchange account entry may name neither a person nor a project (`BROKER_EXCHANGE_ACCOUNTS`, `<service account>==`), and its token acts as the account itself: the project scope `named`, no person and no project, and the account as its service (`exchange.Set.Pod`). Every verifier admits such a token only when its service is a Kubernetes account, the one service the broker mints there, and it holds no OAuth scope, as the broker mints it (`ciphertoken.sessionCaller`), and Dispatch records its writes under that account. An account entry that names a project names its person, so no account entry's token held to a project is personless; a `BROKER_EXCHANGE_WORKFLOWS` entry names a person, a job entry names its projects and no person, and a read entry and a Google entry keep their own rules.

`loadtest` is the Dispatch load-test harness (`loadgen`), which no child component claims: it builds a stack from this checkout, puts the measured load of the 2026-10-26 outage on it and writes tables of what happened, and it changes no server code. It writes as a client of this release must, so each of its uploads names the token of the version it replaces, as `dispatch doc-read` prints it: the spec upload of the event mix reads the document and sends the token that read answered (`events.go`'s `specText`), the reference-target seed reads a target's token before each version after its first (`refs.go`'s `refDocumentToken`), and the replay planner gives each logged upload a read stage of its own, which takes the document's turn as the write does so that the token it reads is the one the upload meets (`replay_plan.go`, `replay_run.go`'s `takesTurn`).
