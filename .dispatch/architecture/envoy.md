The Go-based event transport: webhook ingress, NATS routing and delivery, the native Dispatch server, and the MCP bridge. Dispatch's database is PostgreSQL 18 with pgvector: `envoy-infra`'s `gcp:Dispatch` defaults a new instance to `POSTGRES_18`, and `internal/testpg`, `scripts/dev-postgres.sh` and `deploy/compose/dispatch.acceptance.compose.yml` pin one pgvector-on-18 image by digest. Dispatch packages no child component claims sit here directly, among them the embedding queue (`internal/dispatch/embedqueue`) that keeps meaning search's vectors current, an issue's from its title and its spec. Its NATS hub comes in two forms, both deployed by `envoy-infra` (`packages/envoy/infra`, a Go module of its own that builds a Pulumi plugin and the `envoy-infra` command, and compiles only `natsgrant`, `internal/bus` and what `internal/bus` imports from Envoy): `gcp:NatsHub`, one nats-server on a Google Cloud VM that joins the tailnet, and `gcp:ClusteredNatsHub`, three nats-server pods on a GKE cluster whose optional Tailscale Service hosts forward the tailnet's connections to NATS and to a session listener the component runs as a workload of its own. Both render their NATS users through the one function in `packages/envoy/infra/gcp/natshub.go`, from the permission sets `packages/envoy/infra/core` wraps from `packages/envoy/natsgrant`, the one grant table Envoy's NATS auth service also answers connections with.

The address Pulumi downloads the `envoy-infra` plugin from is stamped in at build time, from the repository the release ran in: `release-envoy-infra.yaml` derives it with `.github/scripts/repo-paths.sh plugin_download_url` and builds the plugin with `-ldflags -X 'github.com/sjawhar/envoy/infra/provider.downloadURL=<that URL>'`, so the schema the plugin serves points at the releases of whatever repository published it, and the job's smoke test compares `pluginDownloadURL` against the same derived value rather than a literal. That is why `provider.go` holds `downloadURL` as a `var` and no longer a `const` — `-X` writes a variable and never a constant — with today's `https://github.com/cybermonklabs/legion/releases/download/envoy-infra-v${VERSION}` as its default, which a build carrying no such flag, a developer's and the package's own tests', serves unchanged; the `${VERSION}` in it is Pulumi's placeholder, filled in at install, and nothing on the way through may expand it.

The secrets broker sits here too (`cmd/cipherd`, `internal/cipher`), and with it this repository's one Go client of its RFC 8693 token exchange: `internal/cipherclient`, re-exported as `packages/envoy/cipherclient` so a module outside this one can import it past Go's internal-package rule, which is how `packages/daemon`'s `legion controller start` proves, before it starts the controller, that this machine can trade for the Dispatch credential the controller's session then holds. A machine trades the Google identity token `internal/googleidentity` reads from its metadata server for a DPoP-bound access token and the launcher credential the same trade mints, under which it enrols its session; that credential is keyed by the machine and the thumbprint of the key its proof presented, so a copy of the identity token asks for a credential of its own rather than moving the machine's, and the session it enrolled renews only while that credential is live — revoked, past its hour, or its account dropped from `BROKER_VM_SERVICES`, and the session lapses within one lease. A person signs in on that machine with `agent-secrets login`, whose device grant gives their own identity token, traded with the machine's as the actor token and recorded as a `person_signins` row keyed by the person, the box key and the machine; their sessions are not held to the machine's login and end when the sign-in is revoked. The TypeScript client (`packages/cipher-client`) trades that same sign-in for every Oh My Pi and Claude Code session and every `dispatch` command on the machine, proving the same box key, so its Dispatch token names the person. The Go client and the TypeScript one are held to one wire by the corpus at `internal/cipherclient/testdata/wire.json`, which both suites replay. `scripts/dev-stack.sh` boots the stand-in issuer (`cmd/dev-oidc-issuer`), the broker, NATS, the listener and Dispatch together, so the whole path can be driven on one machine with no Google and no cluster; with `--binaries <dir>` it runs the stack's binaries built elsewhere (a Legion pod's, built in the builds farm) in place of its own `go build`.

Two packages here sit outside `internal/` so that the daemon's module can import them. `agentloop` is the one shared model loop (`Run` for a bounded run of a model and its tools, `Decide` for one System One decision call). `packages/daemon/internal/sharedloop`'s test compiles it into the daemon's module, so it stays importable there. Its `Result.Status` carries the HTTP status of a provider error, so a caller can tell a refused request (a 400) from a failure to serve. `going` is the command bar's answer and holds no store and no route. `Answerer.Run` makes the answer call through `agentloop.Run`, paced by the deployment's tokens-per-minute quota before each attempt. It asks first for the strict `Final` object (`answer`, `block`, `arguments`: every property required, no union), and streams the growth of the `answer` property through the filter. The filter escapes the text, passes on a link only as the `item` frame of a thing the model was given, and cuts the answer at 120 words. A service that refuses that request with a 400, or a reply that does not fit the schema before any of its answer reached the reader, is asked the same again for prose, which has no block and no arguments. After a 400 the process asks for prose alone until it restarts (`Answerer.Blocks`). `decide.go` holds the three questions of the decision call and the state it asks them about. `reads.go` holds the read tools an answer may call (`read_roster`, `read_progress`, `read_architecture`, `read_project_activity` and `read_delivery`, eight reads a run at most). `blocks.go` holds the seven block kinds, the words that ask for each kind, and the fill of a block from a read's rows. `record.go` reads `decision_models.json`, embedded in the binary: one entry for each measured model, with its measurement and whether R7's rule chose it. `cmd/going-bakeoff` writes that record. It puts every case of `going/bakeoff/cases.json`, whose subjects are all made up, to each named model through the questions and the catalogue the server uses, as many times as `--repeats` says, scores every answer of every repeat (`fit.go`), and names the chosen model by R7's rule (`Choose` in `record.go`): every model that meets R7's three floors is a candidate, ranked by its right choices pooled over every repeat, and the candidate ranked first alone is named. Where candidates stay level on right choices, the rule names none, and the architect names one of them with `--tie-break` and `--tie-reason`, whose reason the record keeps; `--from-record` puts a recorded tie-break to the rule again, keeping it where it still holds and refusing it where it does not. `Choose` answers what the rule came to as a typed outcome (`Choice.Outcome`: `Named`, `FullTie`, which the architect may break, or `NoCandidate`) with every candidate's right choices in rank order (`Choice.Ranked`); the tie-break (`Choice.Break`), what the tool writes and exits with, and its printed choice line read that alone and rank nothing again, and none of it is a field of the record. McNemar's exact test over the same cases and repeats (`repeats.go`) is printed and recorded beside the choice as evidence of how far the lead in right choices can be trusted, and it names no model. The record keeps each repeat's right choices, their spread and that test beside the measurement, in the bytes `EncodeRecords` writes, which biome.json's formatter leaves alone. `scripts/going-smoke.sh` boots the real `envoy-dispatch` binary against a fake https model and checks the capability read and one streamed answer.

The Dispatch server's agent process is `envoy-dispatch agent` (`going/agent`), which the server starts and supervises (component `dispatch-server`). It says hello under a new instance id, keeps one renew waiting that carries its health and answers a stop at once, and claims ready runs, each worked on a goroutine of its own under a `recover`, as many at once as its slots. A run is one `agentloop.Run` of the chat model per step, each started afresh from the run's saved steps, with five tools (`search`, `read`, `find_tools`, `call_tool` and `propose_plan`) whose every read of Dispatch, GitHub or the web is a call to the server, which makes it as the run's person; in Auto-review one more model call names the plan's rows the person's words ask for (`review_plan`). Its levels (`levels.go`: Fast, Standard and Deep) bound a run's model calls, working time and output tokens, and its pacer keeps its calls to 75% of the deployment's tokens-per-minute quota (`pacer.go`). The agent holds no Dispatch data and no Dispatch secret: its configuration is the chat model's settings alone. `going/agentwire` is agent/v1, the contract both processes import: the six calls the agent makes over the server's Unix socket (`hello`, `claim`, `renew`, `step`, `call` and `end`), each request and answer a fixed JSON shape with a size limit, one frame each way (a 4-byte big-endian length and one JSON document), and the client that makes them. `going/transform.go` holds the eight steps of a block's chain (`filter`, `group`, `count`, `sum`, `mean`, `min`, `max` and `sort`), which the server runs over a run's saved tool results, so every number a block shows is the server's. `agentloop.Request`'s `StreamLimit` and `ReplyLimit` bound the bytes of one call's response and of the reply it builds: a run sets 8 MiB and 512 KiB (`runStreamLimit`, `runReplyLimit`), and the short answer 4 MiB. `going/eval` and `cmd/going-eval` are the eval of the agent: the tasks and the seeded Dispatch they run on, and the program that runs each task through the routes as a person, against a server with its agent process and an in-process fake Envoy, grades each try, and prints pass^1 and pass^3.

The exchange also mints a read-only Dispatch token from a read entry (`BROKER_EXCHANGE_READ_ACCOUNTS`, `<service account>=<service>=<session>`). That token holds the OAuth scope `read` alone and the project scope `none`, and names the entry's service and fixed session and no person and no project. `oauth.Provider.decide` writes one project-scope word for each value it knows (`writeProjectScope`) and refuses any other value, and a read entry's pod registration is `409 SESSION_FIXED`. The shared verifier `internal/ciphertoken` accepts a read-only token only where its service sets `Options.ServesReadOnly`, and then marks the caller `Caller.ReadOnly`. Dispatch sets that switch, and the Envoy listener does not, so the listener answers that token `401`. Every verifier refuses the scope `read` beside the project scope `named` or `person`, and the project scope `none` in any other shape.

`loadtest` is the Dispatch load-test harness (`loadgen`), which no child component claims: it builds a stack from this checkout, puts the measured load of the 2026-10-26 outage on it and writes tables of what happened, and it changes no server code. It writes as a client of this release must, so each of its uploads names the token of the version it replaces, as `dispatch doc-read` prints it: the spec upload of the event mix reads the document and sends the token that read answered (`events.go`'s `specText`), the reference-target seed reads a target's token before each version after its first (`refs.go`'s `refDocumentToken`), and the replay planner gives each logged upload a read stage of its own, which takes the document's turn as the write does so that the token it reads is the one the upload meets (`replay_plan.go`, `replay_run.go`'s `takesTurn`).
