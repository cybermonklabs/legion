Stages 1 and 2 on `main` provide Postgres migrations and boot history (`internal/store`), the local daemon registry, durable role claims, and pending task delivery (`internal/registry`). Stage 3 (LEGION-219) plans the per-issue record, admission slots, phase and gate facts, transactional outbox, and `internal/projection`; the coordinator never mirrors Dispatch or GitHub.

The issue record holds no experiment answer of its own: what each unit was drawn for is a row of `experiment_assignments` (migration `20261111045636_experiment_assignments`), keyed by the issue key and the experiment's name, carrying the unit the draw covers (`tree` or `issue`, the two words the loader takes), the arm, the arm's `plan` where it names one (`experiment_assignments.plan`, migration `20261123165139_experiment_assignment_plan`, empty for every other row), the mode in force at the draw, the instant, and the carried mark. The row is written once and never updated, as the draw it records is made once: the primary key is what makes that true in the schema, since both writers insert `on conflict (issue_key, experiment) do nothing`, so an experiment a unit has been running under keeps the arm, its `plan`, the mode and the instant it was drawn with whatever the project's file says by then, and a re-admission, a new generation and `ClearTreeGeneration`, which touch the issue row alone, keep what was drawn. `record.Store.PutAssignments` is the draw's write, made by every path that opens a unit in that path's own transaction, and it selects from the issue's own record: a key the daemon holds no record of — an operator's spawn, whose tree's root it never recorded — writes no row and raises nothing, where the row's cascading foreign key would otherwise fail that admission. `CarryAssignments` is the hand-over's write: every tree-unit row of the tree a child left is copied onto the child with its arm, its mode and its instant verbatim and the carried mark set, so the work goes on running under those arms; then each experiment declared at the hand-over lands at no variant, no mode and no instant under the same write-once insert, so it settles exactly the experiments the copy left unwritten, and the child is drawn for by nothing later. Only the tree rows are copied, an issue row of the old root being that one issue's own answer. The empty variant is the record's way of saying no arm, which the two columns beside it tell apart: an experiment at mode off gives every new unit no arm and records the mode `off` with the instant of the draw, while a settled hand-over records neither. A unit opened before an experiment was declared holds no row for it and runs in no arm of it. The four `issues.memory_*` columns that `20261104073148_issue_memory_group` and `20261104153554_issue_memory_carried` added stay in the schema, are written by nothing from this release on, and are read by this release's code only through the migration's back-fill and by the documented copy by hand; `20261111045636` back-filled every root holding a draw (`memory_drawn_at` not null) or the carried mark into one `memory` row of unit `tree`, so no tree drawn before the deploy lost its exposure, and a later release drops them.

Five records serve the approval route and the work hold. `handed_over_roots.from_root` (migration `20261120210115_approval_route_records`, `record.HandedOverRoot.FromRoot`) is the root whose document a carried gate holds. The carry writes it, and the approval route names that root in the carried message. `cleared_spec_approvals` (the same migration, `record.ClearedSpecApproval`) keeps, for a root that a person moved out of the workflow and back, the approved `spec` row that its re-admission deleted: the approved version, the document, the approval's place in the issue's Dispatch event log, and the newest version of the document that the row knew of (`latest_version`, migration `20261122072401_cleared_spec_approval_latest_version`). The route answers from it while the root holds no `spec` row. A new version of that document raises its latest version, and a later approval moves it. A changes request on that document deletes it, unless the row would ignore that request: the request is on a version older than the latest version, or the approval it records came after that request. The next registration of the `spec` step deletes it, and where it names the registered document, the new row keeps its approval of an older version. `work_holds` (migration `20261121000254_work_holds`, `record.WorkHold`) holds one row for each tree that the work hold holds: its project, the root's generation, the step, the document and the version that closed the gate, and the moment of the close. The close writes it, the opening deletes it, and `ClearTreeGeneration` deletes it with the generation, so a daemon restart keeps the hold. `work_hold_openings` (migration `20261122023421_work_hold_openings`, `record.WorkHold.OpenedAt` and `Opening`) holds, for each tree, the hold that its last opening ended: the same columns, the moment of the opening, and what ended the hold. The opening writes it in the transaction that deletes the tree's `work_holds` row (`record.Store.OpenWorkHold`). The next close deletes it, and `ClearTreeGeneration` deletes it with the generation. Each start of a claim that the hold stopped reads it, so a claim that the opening did not start gets the task that the opening gave. `claims.suspended_by` also takes `hold` (migration `20261120224328_claim_suspended_by_hold`): a claim that the work hold stopped, which keeps its session, its phase and its pending delivery. `pending_task_deliveries.opening` (migration `20261122085244_pending_delivery_opening`, `supervise.Delivery.Opening`) keeps the opening's sentences that a claim's pending task begins with, on the one task that the hold's opening gives a claim it stopped. A later close can stop the claim before a turn takes that task. The next opening then puts its own sentences in front of the task's work alone (`supervise.Delivery.Work`). The header of each migration gives its way back.

Every string the daemon writes to its store passes one rule, `internal/store/storetext`: each NUL (U+0000) and each run of bytes that is not UTF-8 becomes U+FFFD, and in a `jsonb` value each `\u0000` escape and each surrogate escape that is not half of a pair does too, which are the inputs PostgreSQL refuses (SQLSTATE 22021 in `text`; 22P05 for the `\u0000` escape and 22P02 for the lone surrogate in `jsonb`). The store applies it itself, so no caller can forget it: `store.Pool` gives a string argument the rule would change as a `*string` (pgx sends a plain string in text format past every codec), and `store.PoolConfig`, which `store.Open` and `testpg.ClonePool` build their pools from, wraps pgx's own codecs of `text`, `varchar`, `bpchar`, `name`, `json` and `jsonb` on every connection, so the codec of each parameter's type applies that type's rule; a pool built without `PoolConfig` (a bare `pgxpool.New` wrapped with `store.NewPool`) runs the argument half only. `PoolConfig` refuses a DSN whose `default_query_exec_mode` is `exec` or `simple_protocol`, because pgx learns no parameter type in those modes and a `jsonb` argument would take the text rule; `legion config check` makes the same refusal (`daemon.CheckStart`). A value read back is the value as stored, and `intake.ApplyFact` gives every fact through the same rule before any handler compares it with a stored copy; `supervise.Machine.Handle` gives every event through the same rule before any row reads it, so the supervisor's claim keeps each text it also stores (a delivered task, a session, an update round's id, reasons and head) as the store keeps it, and a leak-check cause, a pod end, a death's cause and a turn's refusal message as a far side's text is kept (`storetext.FarSideText`): the prompt and the operator's answers match the stored row before a restart as after one. A far side's error text is stored as `storetext.FarSideError` keeps it, with the whole text in the log in parts under a message of their own (`storetext.LogWhole`). Oh My Pi's own session table, which `internal/ompsessions` and `legion sessions import` write byte for byte on a connection of their own, is outside the rule.
