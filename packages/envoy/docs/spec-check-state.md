# `spec-check state`

`spec-check state --scenario <dir> [--json]` reads the scenario in the directory `<dir>`, derives the state of each check and each approved statement at each of its subjects, and prints them. It changes nothing. The rules of the states are those of `Derive` in `internal/dispatch/specgraph`; this page says what the command reads and what it prints.

A scenario holds `approved.json` (the approved spec), `subjects.json` (each subject: a commit with the head of a branch, or with the deploy that production runs and, for a check of the graph, the transaction of the graph), `files/<commit>/*.md` (the spec files at the commit of each subject), `history.json`, `ties.json`, `results.json`, `jobs.json` and `uncited.json` (the checks that CI refused at each commit, `{}` for none). It may hold `units.json` (work units and the statements that they wait on) and `want.txt`, which the command does not read. Each file is read strictly: a member that the format does not name, a member written in other letters or given two times, a value of another type, a `null` at any place, a byte that is not UTF-8, and a missing member whose absence would hide a fact are each refused. An empty list or map is a value, as `[]` in `jobs.json` says that no job ran.
A file that holds more than 16 MiB (16,777,216 bytes) is refused, and none of it is decoded.

A result counts only for the procedure and subject it read. A run of a check of code counts only at the commit that it read. A failing example that the check's test caught also counts at another commit, but only when the check has known ties at both commits and no tied path changed; a program check of production or of the graph counts a result of its test the same way. A result whose current check text, current statement approval, or tied code does not match is not reused.

A CI refusal at a commit makes its check unknown at that commit. Of that commit's own results, it removes those that support true, a pass and a failing example that caught its fault (a planted one whose counted commit is the refused commit among them); it keeps that commit's failures, runs that could not run and failing examples that missed their fault wherever they count, so a refusal never moves a check toward true. It does not remove evidence from other commits, and it does not remove a record that counts from no commit, whether CI refused the check at the commit its `planted_on` names or at its own commit.

In text, the command prints for each subject a line that names it, then each statement in preorder as `statement <id>: <state>`, the state `met`, `met, partly checked`, `not built (…)`, `not met (…)` or `unknown (…)` with what decided it, and under each statement each of its own checks that reads the subject as `  check <id>: <state>`: `true (passed, counted from <x>)` or `false (failed, counted from <x>)`, where `<x>` is the commit, the deploy or the transaction of the graph that the counted result read, or `unknown (<reason>)`, which for `planted_on_outside_history` also names the commit. A check whose statement the approved spec removed is printed after the statements as `check <id> (serves no current statement): <state>`, so the text names each check that `--json` reports. With `units.json`, at a subject at the head of `main`, it prints `wait of <unit> on <statement>: ends` or `holds (<own state>)` for each wait, and after the last subject the cycle of waits, or `none`.

With `--json`, it prints one line of JSON in place of the text: the list of the states at each subject, each `{"subject":…,"checks":[…],"statements":[…]}`, or with `units.json` `{"states":[…],"cycle":[…]}`, the cycle `[]` when there is none. The JSON holds no answer of a wait: whether a wait ends is in the text alone.

The command exits 0 for a scenario that it reads, and 2, with one line on standard error that names the file and the fault, for a scenario that it refuses, for arguments that it does not take, and for a standard output that does not take its text.
