# `spec-check state`

`spec-check state --scenario <dir> [--json]` derives the state of each check and approved statement in a scenario. The command reads the same scenario format as `specgraph.ReadScenario`; it does not change the scenario or its expected output.

A scenario contains `approved.json`, `files`, `history.json`, `jobs.json`, `results.json`, `subjects.json`, `ties.json`, and `uncited.json`. It can contain `units.json`; without it, no statement wait is derived. `want.txt` is test data only and is not read by the command.

The command prints one result for every subject. A statement is `met`, `met, partly checked`, `not built`, `not met`, or `unknown`. It then prints every check that reads that subject as `true`, `false`, or `unknown`, including a reason and, for a true or false result, where its counted result came from: the commit for a check of the code, the deploy for a check of production, and the graph transaction for a check of the graph. It prints no list of a check's results with their times. If `units.json` is present, it also prints whether each wait ends or holds. `--json` emits the same derived data as JSON.

Scenario input is strict. Unknown fields, duplicate fields, invalid JSON types, and `null` values are refused rather than silently read as zero values. A missing member follows its declared input mark: some missing values are valid zero values, while members whose absence would hide a fact are refused. Empty objects can be valid values; for example, an empty `uncited.json` says CI refused no check.

A result counts only for the procedure and subject it read. For checks that count at commits, a result carries to another commit only when the check has known ties at both commits and no tied path changed. A result whose current check text, current statement approval, or tied code does not match is not reused.

A program check of code needs a valid failing example before it can be true. The failing example counts from `planted_on`, never from its own `commit`, which is the commit where CI ran the fault. It needs one or more fault paths; every path must be a source file, not a test file, and where the check's tie at `planted_on` is known, that tie must cover every path. A record with no planting commit, no fault path, an all-white-space path, a blank path beside a real path, or `planted_on` equal to its own commit counts nowhere and makes the check unknown with its specific reason when it is the newest candidate. A record whose `planted_on` names no commit of the history also counts nowhere; as the newest candidate it makes the check `unknown (planted_on_outside_history <commit>)`.

A CI refusal at a commit makes its check unknown at that commit. It removes that commit's own results, including a planted failing example whose counted commit is the refused commit, but it does not remove evidence from other commits, and it does not remove a record that counts from no commit, whether CI refused the check at the commit its `planted_on` names or at its own commit.

The scenario sweeps exercise omitted members, nulls, empty names, altered paths, and CI refusals. Each sweep fails an input whose files equal its base's, so a sweep writer that writes nothing fails by name. Each sweep also fails an input whose files are those of an earlier input of the same base, byte for byte, so that it reads no case twice; a sweep writes each JSON file with the members of each object in the order of their names, so two inputs that write one tree hold the same bytes, and a test fails when the encoder writes one tree in two orders. Each sweep also reads back each write against the write it means, which the sweep builds from its own decode of the base before the writer runs: each file by its name, with every other file of the base unchanged and no file added; a JSON file as the base's tree with the one change that the input names (a string or added member, a null, a member or element left out, a renamed key, or a text inside a block), compared whole; a spec file by its bytes; a CI refusal as the scenario reader reads it, by its commit, its check and its rule; the results that such a refusal takes out, as the reader reads them; and each file as its bytes alone, with no mode, time or sys. Each object that a writer gets is its own: a decode of the file or of the scenario made for it alone, a copy of the files, and copies of the place and the value, which the sweep compares, after the writer returns, with copies taken before the call. The input that the sweep then derives is no object that a writer got: it is the bytes encoded from the writer's tree, or a copy of the writer's files taken after the read back. So a writer that writes another value, writes it at another place, under another key or under another file name, also changes another part of the file, makes a file a directory or a link, or changes the value, the place or the results that it gets, fails by name too, and a writer that keeps what it got and changes it in a later call changes no input.

Each table that a sweep reads of its own is a function that gives a new value at each call. One guard takes a copy of each variable of the package, of its code and of its tests, then builds the writer, then calls it, then compares each variable with its copy, so a writer that changes one, a table that the reader reads among them, fails by name, whether it changes it where it is built or where it is called. The copy holds each variable as a value that no writer can reach: a list or a map cloned, and a variable that holds a pointer as its address and a copy of its object. A test fails for each variable that the package declares and the copy does not name, and for each copy that holds an object of its variable that code of the package can write through.

Each sweep judges each input that it derives: it compares the input's states with those of the base, and an input that moves a state toward true fails unless the input has a right to that move. Of each base, a sweep judges at least a fixed count of inputs that the reader reads and a fixed count that it refuses, and the kinds of its inputs, read or refused, in their order, have a fixed digest. An input counts only where the sweep judged it and found it right, so a fault that drops inputs, a sweep that skips inputs that it built or stops judging an input that moves a state toward true, and a fault that moves inputs from one kind to the other, as many each way as it likes, each fails by name. The counts and digests are those that the sweeps gave when the table was written, so a change that adds, takes out or moves an input writes the table again. Many inputs of one place read the same to the reader, and this is by design: they are the sweep's forms of one meaning, such as a member left out, an empty name and a name of one space, each read as nothing. The distinct-input check compares bytes, so it does not compare such forms; a change of them is a change of the sweep's own text, which no writer can make, and the digest fails it: with the forms of a string written as two spaces and one space, where an empty name and one space are meant, the tree sweep fails by its digest at each base. A right that names its places covers only those places. Two rights name no place, and an input that has one is judged by its right alone: a repository path of a tree written as one space, which ends the carry of each result across that tree, and a parent left out of an approved block, which puts its statement at the top of the tree and can leave each statement that was above it met. The places that such an input may move are those that the derivation itself reaches from its change, so a list of them would be a second derivation.

The command tests run the built binary against the fixture scenarios and compare its output with each fixture's `want.txt`. The derivation package is the source of truth for the state rules; this document describes the scenario interface and the invariants at its boundary.
