**Question.** What share of deploy runs reach production?

**The decision it changes.** Whether to fix the flaky or failing steps of the deploy pipeline.

**How it is measured.** For each UTC day, `measures.DeployRunSuccessDay` reads the runs of the deploy workflow on main that started that day. The denominator is the runs that concluded success or failure. The numerator is those of them whose production job concluded success. A cancelled run is no deploy attempt, so the share leaves it out and counts it beside the share, in `cancelled`. `measures.FoldDeployRunSuccess` adds up the numerators and the denominators of a window's days and divides the sums. It never takes the mean of the daily shares. The Delivery page and this eval call the same fold.

A run counts for each project whose pull requests it ships, through the issues they name. A run that ships no pull request of a project counts for each project whose published default repository is its repository, and for no project where none is. The Delivery page, which follows no project, counts it either way.

**What it does not count.** Cancelled runs, runs that are still running, runs with any other conclusion, runs on other branches, and runs of other workflows.

**Failure modes.**

- A cancelled run is no deploy attempt and is left out, so many cancellations leave the share over few runs. Guard: The count of cancelled runs stands beside the share, and the count of concluded runs says how many runs it covers.
- A run that is still running counts in neither part of the share. Guard: Dispatch builds the day again when the run concludes.
