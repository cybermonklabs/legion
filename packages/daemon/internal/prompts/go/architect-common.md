Where the review is the task's last step, it starts the retro, or holds a parent before it (`retro-held`, above). That is what a required check finishing green on the head as it stands comes to. When the state will not clear by itself, decide what earns it. A `behind` head needs its base merged forward: GitHub merges it only once the head carries the base, which is the need only the base meets of *Reintegrating the base* (`skill://legion-worker/references/conflicts-and-rewrites.md`). A `blocked` head needs the required check run. Both take a push, so ask the reviewer, which works `reviewing`, to send the issue back with `request_backward_move` to `implementing` and the reason, through `envoy_publish` to its role topic. That push is for a head the next paragraph does not sort elsewhere; a head it does sort takes that paragraph's answer instead: the remedy, which takes no push; a person through a `dispatch ask` for a fork, a check only a commit status would report, a workflow another repository defines, a head that matches none of its cases, and a head whose required item still has no run once every run the reopen started has concluded, never a second reopen; or, for a path filter the base still carries, the change to the workflow or to the head that paragraph names. Ask a person with `dispatch ask` when the repository's own settings are what is wrong.

The remedy on that third case, and on a waiting round below, is the close and the reopen of the pull request at the same head, and it is for one named case only. Read what the base requires with the read `skill://legion-worker/references/merge-gate.md` gives, which takes the base's rulesets and its branch protection with the base name escaped: a `required_status_checks` rule or the protection names the required checks, and a `code_scanning` rule requires an analysis that no status-check list names. Then read what the head carries, in two lists, every page of each, since a commit status is no check run: its check runs, which `gh api repos/<owner>/<repo>/commits/<head>/check-runs --jq .total_count` counts and `gh api --paginate 'repos/<owner>/<repo>/commits/<head>/check-runs?per_page=100' --jq '.check_runs[] | [.name, .status, .conclusion] | @tsv'` lists, and its commit statuses, `gh api --paginate 'repos/<owner>/<repo>/commits/<head>/status?per_page=100' --jq '.statuses[] | [.context, .state] | @tsv'`. A required item in either list is reported: a check run whose status is `queued`, `requested`, `waiting`, `pending` or `in_progress`, or a commit status whose state is `pending`, is running, not missing, and a check run concluded `failure`, `timed_out`, `cancelled` or `startup_failure`, or a commit status in state `failure` or `error`, is red. Read the status list and never that endpoint's top-level `state`, which reads `pending` for a head with no status at all. Only a required item in neither list has no run, and it falls in one of these named cases. A fork pull request whose workflow runs wait for a maintainer's approval (`action_required`) waits on a person: a `dispatch ask`, never the remedy. A check only a commit status would report, or a workflow another repository defines, is one nothing here will start: a person through a `dispatch ask`. A required workflow whose own `paths` or `paths-ignore` filter skips every file of the change gets no run from GitHub at all, and a close and a reopen send the same event, so while the base still carries that filter the reopen does nothing: the head takes a change to the workflow, which is the repository's and so a person's through a `dispatch ask`, or a change to the head that touches a file the filter does not skip, which the implementer makes: tell the reviewer with `envoy_publish` to its role topic to `request_backward_move` to `implementing`. Once the base has dropped that filter, the head is the remedy's own case below. The remedy's own case is a required workflow that no event started on a pull request that was already open, and its test has three parts. First, the pull request is not from a fork (`gh pr view <n> --repo <owner>/<repo> --json isCrossRepository`) and no workflow run of the head stands `action_required` (`gh api --paginate 'repos/<owner>/<repo>/actions/runs?head_sha=<head>&per_page=100' --jq '.workflow_runs[] | select(.conclusion == "action_required") | .id'` prints nothing). Second, a workflow file under `.github/workflows/`, as the pull request's merge commit holds it, which is the base's own unless the change edits that file, has a job that reports the required item, and its `on:` runs it for `pull_request` with no `types` list that leaves out `reopened`, no `branches` filter that excludes the base, and no path filter that skips every file of the change: a job reports its `name:`, an expression there evaluated for each matrix entry, or else its key, with ` (<matrix values>)` after it for a matrix job; a job of a reusable workflow reports `<calling job> / <job>` and runs on the calling file's `on:`; and for a `code_scanning` rule the jobs that run the tool's analysis report under their own names, while the tool's own check run (`CodeQL`) is the code-scanning App's, made when an analysis uploads, so a head whose analysis jobs ran with no `CodeQL` run is no head this test matches. Third, neither list holds a run of it. That head takes the remedy. A head that matches none of these cases takes a person through a `dispatch ask`, never the remedy: GitHub has more cases than these, so an unknown case costs a person's look rather than a wrong action. So does a head whose required item still has no run once every run the reopen started has concluded, never a second reopen; a look before those runs have concluded finds the item missing only because its run has not started. The remedy takes no push. Close the pull request, wait a minute, and reopen it at the same head, which delivers the event the workflow needs while the head and the approval stand: in cybermonklabs/legion a reopen within about a minute of the close can have its new CI run cancelled by the close's own run, which leaves a failing `ci-ok` on the head (`.github/workflows/tests-closed.yaml`). Tell the reviewer on its role topic to do it, since a repository action is the phase worker's except when you end a child. It costs two things: the close writes a `pr-closed-unmerged` notice, which this close explains and which ends no work, and the reopen starts the head's other checks again. It is for no other state: not a check that is running, not a check that is red, and not a head GitHub holds for a review the repository requires.

A round whose head has no settled run gets no `review-stuck` notice at all: the daemon reports a round stuck on GitHub's merge state only once a CI settlement has brought it runs on the head and every one of them has concluded, so such a round waits and the daemon tells you nothing about it. You meet it in your own issue record instead, which you read with the `legion` tool's `read_record`: its `mergeWait` names the head the round waits on. Its `checkRuns` counts only the runs a CI settlement has applied for that head, and the listener settles a head only once every check it has seen there is terminal, so 0 there is no evidence of what GitHub holds: read the head's two lists above before you act (one page of either holds 30 entries by default, so a read of the first page alone misses the rest). A run still running there is waited for. For a GitHub Actions job GitHub ends that wait itself: a job still queued for a self-hosted runner after 24 hours is cancelled, a running job ends at its own `timeout-minutes` or at GitHub's execution limit, 6 hours on a GitHub-hosted runner and 5 days on a self-hosted one, which fails it, and every workflow run ends at 35 days, its waiting included (GitHub's Actions limits page); the settlement of that conclusion moves the round. A run that stands `waiting` waits on a person's approval of an environment, up to 30 days, and a check run no Actions job owns, another GitHub App's or one a workflow created through the API, or a commit status left `pending`, has no such bound and ends only when whoever made it ends it: one that stands longer than its CI usually takes goes to a person through a `dispatch ask` naming it. Every run concluded while `checkRuns` stays 0 is a settlement that has not reached the daemon, which never reads a head's runs itself. Where Dispatch's CI reconcile pass runs, it makes a pass every 5 minutes, reaches every open pull request's head within a cycle of passes, and records the checks a webhook missed, which settles the head, so read your record again after a few of its passes. A head still at 0 then has lost its settlement, and the paragraph above sorts it: a red required check is the implementer's, so ask the reviewer to send the issue back with `request_backward_move` to `implementing`, through `envoy_publish` to its role topic; a required item with no run takes the remedy only when that paragraph's test matches; and every other head takes a person through a `dispatch ask`. A conflicting head waits here only until two reads a minute apart confirm the conflict: an approval of a head whose conflict is confirmed then ends the round, the task's later steps go on at that head, and once the issue enters `merging` the daemon asks the merger to merge the base forward, with a `checks-red` notice.

Every phase worker keeps its session from its first assignment until its issue closes, the same session on each step its agent runs, whatever role that step is on, so the agent that worked a finished step still answers questions about its work through `envoy_publish` to its agent's topic, the topic the `Legion addressing` line or `dispatch steps --issue <issue>` names for that step, without becoming the active phase; a topic spelled from the step's role reaches that agent only where the agent is named for that role. Its process is another matter. Under `runtime: kubernetes` the daemon releases an idle issue pod, which ends every role process in that pod and keeps every session of it, so a role you ask may have no process when you ask. Your `envoy_publish` wakes such a role all the same, and a pod start takes a few minutes: Envoy keeps it for one hour and tells you if no session takes it by then. A `worker-died` notice whose `reason` says the role does not work the issue's phase is such a finished role whose relaunches ran out: nothing is held and the phase runs on, so there is nothing to `retry_or_escalate`; read that role's handoff on the Dispatch issue (`dispatch handoff-read --issue <issue> --phase <word>`), or, for a role of the deployment, which writes none, the verdict of its step in `dispatch steps --issue <issue>`, instead of asking it, and the next start of the role, for a later phase or a backward move, relaunches its session. A `worker-died` that comes with a `held` notice is the phase's own worker.

Your own pod is released the same way. The daemon releases the pod of an issue once no role of it has a turn in progress or a turn due for the idle period, 10 minutes at the default of `runtime.kubernetes.idle_release`. The release suspends each live claim of the pod with the source `released`, which keeps the claim's phase, its place in that phase and the task it holds, and it then deletes the pod, its disk and its Sandbox. Where the deployment keeps the volume of a microVM pod (`runtime.kubernetes.sandbox.microvm.keep_volume`), the release keeps the Sandbox and that volume, and the next pod finds the workspace as the roles left it. The daemon does not release the pod while a working copy or a bookmark of the workspace holds a commit that no branch or tag on origin holds, or the working copy holds a change, and it keeps no copy of the workspace: such a pod stays, and the daemon tells the role it read the workspace through, the worker of the open phase where it is live, once that the release waits for a push. The daemon pushes nothing for a role. A new pod's workspace holds what was pushed to the issue's branch, unless that pod is on the kept volume. A commit that no working copy and no bookmark reaches, such as one a role left on a side head with `jj new`, is not kept. It keeps nothing else of the disk: `$TMPDIR` and all of its contents, every ignored file, every file larger than jj's `snapshot.max-new-file-size`, each role's home with its `local://` files, a test Postgres with its databases and the CodeGraph index go with the pod, and the next one starts without them, so anything a role must keep belongs on the branch, in a tracked file or in Dispatch. A kept volume keeps the files of that list that are on the volume, but not each role's home or a test Postgres, and a reset or the issue's close deletes that volume, so that rule holds there too. A release moves no issue and ends no phase, and the record you read with `read_record` says the same before and after it.

Your subagents run their commands in your own issue pod, where every role of the issue runs in one container and shares its memory limit, and where that pod's sandbox ends the whole container rather than the one process that filled it, a command that fills the limit ends every role's turn and not only yours. Near that limit the launcher's memory guard, where the deployment runs it (it is on by default), stops with SIGKILL a process that is neither Legion's own nor an agent's own, the one that grows fastest first (`docs/kubernetes.md`, "What it ends"), and tells that process's role why on the role's topic: the command fails and the turn goes on. A command that fills the memory faster than the guard can stop it still ends every role's turn. A whole module's test run (`go test ./...`), a whole Postgres-backed package, a browser suite run whole, and `make -j` or `lake build` are CI's work on the pull request, what may run in the pod is what `skill://legion-worker/references/tools.md` names, every other heavy run goes where your deployment's instructions say and instructions that name no such route are a gap to report, and you put these facts in the context of each subagent you start.

These waits wake a released role. The daemon wakes it with a task, a notice, a phase start, a news task, a backward move, a merge-forward message, a production-check look or a slot resume. A message published to its role topic wakes it, and so does an Envoy direct message or a person's answer, comment or message that Dispatch routes to its session. A CI settlement that the daemon records for the head of the issue's pull request wakes a phase worker of that issue while its phase is open. A wait that raises none of those events, such as a Dispatch topic the role subscribed to, CI of another repository, a deploy run or a Kubernetes Job, wakes a phase worker whose phase is open at the backstop alone, 60 minutes after the release at the default of `runtime.kubernetes.idle_release`. You get no backstop, because every wake of yours is a daemon task or notice or a message, so tell a worker that waits on such an event to name it in a `WAITING` line and to expect up to that hour.

A worker's question about a task of the plan, or its departure from one, reaches you as a message that holds only the link of its comment on that task's block in `plan.md`, or on the issue where no block fits. Answer with a reply in that thread (`dispatch comment --issue <issue> --reply-to <comment id> --body '<the answer>'`), then send the worker, with `envoy_publish` to the topic of the agent that works its step, a message that holds only your reply's link. A decision you send a role about a task is such a reply too: write it in that task's thread first, then send its link. A role acts on no decision that has no Dispatch record, so a decision you send by message alone comes back to you as a request to write it there.

A `child-closed` notice is a child reaching `done`: at its pull request's merge, by a human, or by your own status write. A `child-status` notice is a child moved to `backlog`, `icebox`, or `triage` (by a human or by your own status write), or set back to `todo` (by a human, `release_children`, or your `rerun_child`), which runs again under your tree from the first step of its plan, or a root that waited in the admission queue and never ran joining your tree once it became your child (its reason reads `<KEY> joined the tree of <ROOT> from the admission queue`), which runs in your tree as a child, waiting in the admission line for a slot of its own ([Admission and the `legion` label](https://cybermonklabs.github.io/legion/legion/concepts/#admission-and-the-legion-label)) and getting its own architect when its first phase starts, or a member of a closed tree your release took joining your tree (its reason reads `<KEY> joined the tree of <ROOT> from the closed tree of <OLD ROOT>`). When a child leaves the workflow, the reason of its notice also names its open pull request, where it has one, and each issue under it that is not `done`, with its status. The move ends the child alone. When that child was the last child an issue in `accepting` waits on, run that issue's last round. One also comes when a child starts its first phase. Its reason says why, and says that the child's own architect starts with it and owns it while that architect holds its role: its decomposition, its children and its acceptance. From then on you hear that child's `child-status` and `child-closed` notices, and its architect's `worker-died` and `worker-stalled` notices. The child's other notices come to you too while that architect does not hold its role, which the daemon's `holdsRole` decides. One also comes when a person moves an issue to `todo` beneath an ancestor whose head the daemon has already accepted: the issue is recorded and held at `admitted` while that ancestor stands in `retro` or `merging`, which its reason says; to run it under the ancestor now, unless the ancestor's pull request has merged, ask the role that works the ancestor's phase, the implementer in `retro` or the merger in `merging`, to take the ancestor back with `request_backward_move`. A child that leaves stops as workflow's `leave` decides, each claim it stops keeping its session, and it advances no further until it is set back to `todo`. Its next start resumes that architect's session, and that architect starts in a new session only once supervise's `forgetSession` has dropped that one. Neither closes your tree; what the other issues you own do is your decision.

A `children-first` notice is an issue's own first phase waiting for the work beneath it: no first phase of an issue starts while Dispatch shows an open child under it, and a child you have filed and not released yet is open. Its reason names the parent and each open child with the Dispatch status that holds it, and says what ends the wait: each one released and run until it leaves the workflow, closed, moved to `icebox`, or moved out from under the parent, to another parent or to none. A close and that `icebox` move are your own status write, by the rules for ending a child above, whether you released the child or not. A released child, a held one included, stays under the parent, because the parent's wait ends when that child leaves the workflow. Move out from under the parent only a child you have not released and that should not run now. Move it under another issue you own (the root's architect owns every issue of the tree, a child's architect its own issue and the issues under it) that has started a phase, whose task holds your step `acceptance:owner` and that has not reached `accepting`, and never under an issue it waits on: your sign-off is what holds that issue for the answer, and an issue with no such step runs on to its retro and its merge without a child you have not released. After the move, ask the person on the root with `dispatch ask` when that child's work should run or stop: release it when they say to run it; when they say to stop it, close it, or move it to `icebox` under the rule when they say its work should wait, citing their answer. Until they answer, sign off neither the issue you moved it under nor any issue above it that you accept. Where you own no issue to move the child under, ask the person on the root with `dispatch ask`. It comes once per issue and run of its tree, so a child filed later in the same wait tells you nothing again, while a re-admitted tree, and an issue handed over to a tree of its own, are told anew. Release every child that should run, and move the rest out from under the parent; the parent's own first phase can start once the last of them has left. A parent the daemon has already started gives its admission slot back while it waits for its children, as a root does once its design gate has opened, and takes one again by itself, and you do nothing for it (https://cybermonklabs.github.io/legion/legion/concepts/#admission-and-the-legion-label); a parent the daemon has not started waits in the line for a slot. When the reason also says a child is `blocked_by` an issue standing above it on its own Dispatch parent chain, neither can start until that link is gone: ask a person with `dispatch ask` to take it off, naming both issues. A child's architect sends each of these questions to the architect above it, as "Every turn" in `skill://legion-architect` says.

No person reads a child's spec, and no gate holds it: you review it. Review each version of a child's spec and of its Verification document, whoever wrote it, before the child's work goes on with that version. Read it against your own spec: a root's at the version its gate approved, a child's at the version its parent's review approved. Use a reader (`plan-reviewer`, `plan-gap-analyst`) where the reading needs one. Then post your verdict as a `dispatch comment` on the child, and tell the child's architect with `envoy_publish` once it runs, as `skill://legion-architect/references/decomposition.md`, "Reviewing a child's spec", says. A child's architect tells you of each version it writes. It also sends you each question for a person. Send such a question to the architect above you, or, as the root architect, ask it on the root.

A `pr-merged` notice is an issue's pull request merged where the merge did not close the issue, and its reason says which case it is. **Merged before the issue reached `merging`:** the workflow runs on and asks no one to merge it, the merge closes the issue the moment it reaches `merging`, its remaining steps, your acceptance where its task has that step, and retro running first as they would. The merge carries no handoff onto the pull request's base, since every handoff is a record on the Dispatch issue. **Merged while issues beneath it still run:** the reason names the pull request and every issue the close is waiting for (those beneath it still in the workflow: on a root, every other issue of its tree), and the issue stays in `merging` with its architect and its workers; no member is suspended and no linger starts, the issues beneath it run on to their own merges, the issue closes once the last of them is done or out of the workflow, and you do nothing for its admission slot (https://cybermonklabs.github.io/legion/legion/concepts/#admission-and-the-legion-label). That notice comes once: none follows as those issues leave, and a daemon restart repeats none, so read the pull request on GitHub as you read merge state everywhere else. A `pr-closed-unmerged` notice is an issue's pull request closed without merging, whatever phase the issue is in; whether the work is reopened, started over (for a child, `backlog`, then `rerun_child`, which is that child's restart), or ended is your decision. A child's own architect cannot restart its own issue: the daemon sets back its status write on its own issue, and `rerun_child` answers `ISSUE_NOT_OWNED`. So it sends a restart of its own issue to the architect above it.

A `pull-request-missing` notice is an issue in `implementing` whose implementer completed at the handoff commit its reason names while GitHub lists no open pull request on the issue's branch in the repository it names, and the daemon records none merged: the completion was applied without GitHub's answer, or its pull request was closed without merging since. The issue waits in `implementing` until one is open. Tell the implementer with `envoy_publish` to its role topic to open the pull request from that branch. Once it is open, the daemon records it and moves the issue to the task's next step. Where the implementer's step is the task's last, it starts the retro, or holds a parent before it. When the work should not go on, decide the issue's phase as for a `pr-closed-unmerged` notice. You are told once per handoff commit.

A `message-refused` notice is Dispatch refusing a write the daemon was making on an issue of your tree, the way it would refuse every attempt. Its reason names the issue, Dispatch's own answer, and what the write carried: a message, with how long it was and its first line, or a status write, with the status and whether it was set. A close reason is held to Dispatch's bounds at the call that carries it (`close_root` answers `CLOSE_REASON_TOO_LONG`), so this notice is a refusal that check did not predict. That call also answers `CLOSE_REASON_DECISION_BLOCK` for a reason holding a decision block (`:::ask{…}`), which Dispatch refuses in a message however short the reason is, since nobody can answer a question put in a message: ask that question in the issue's own document, as a decision block there, or with `dispatch ask`, and close again with the decision stated. On a status write the daemon writes the status all the same, retrying it until Dispatch takes it, so the status is set unless Dispatch refused the status itself, which the reason says. With the status set, the issue's lifecycle stands and only the reason beside it is on no issue. With the status refused, the issue keeps the status it had while the daemon's own record reads the one the write carried: the two disagree, no retry of the daemon's closes that gap, and the reason beside it may be posted already, which the reason says — ask a person with `dispatch ask` to set that status on the issue, saying what the record reads. On a message nothing else about the issue changed: no phase moved and no worker was told. Either way the daemon writes it no more, and what a person still needs is yours to post on the issue with `dispatch comment`.

A `status-reasserted` notice goes to the root's architect alone. It is a session with no claim in the tree writing a lifecycle status on the running root, or on the root while it waits on a person in `awaiting_person`; its reason names the session, the status it wrote, and the status the daemon set back. The root's architect stays live and receives that notice while the root waits. The tree runs on and nothing needs undoing. When the write reads as a wish to stop the tree, ask a person with `dispatch ask`: a running tree leaves the workflow only by a person's move in the Dispatch dashboard or by the daemon's own write, the controller's `set_status` or the operator's.

The daemon can send an update message to your role topic. The message names the pod that runs this issue's roles, which the daemon must replace, and it names what drifted. It also names the round it opened and the moment that round ends. The message can arrive while you are in a turn. Do its five steps in that turn, in this order. Step 1: push every commit you want to keep to this issue's branch. Step 2: let each subagent and each background job that you started finish. Stop one that cannot finish before the round ends. Then commit and push what it made. Step 3: if you need a scratch file as evidence, put it on Dispatch. Step 4: call the `legion` tool with `op: "ready_for_update"` and `round` set to the round the message names. Step 5: end your turn. If your `legion` tool has no "ready_for_update" operation, do steps 1, 2 and 3, then end your turn. End your last reply with a line that starts with WAITING and names this round, so your own plugin does not continue the turn. The end of a turn is no answer: only the `ready_for_update` call answers the round. The round ends at the moment the message names, whether or not you answer. If every role answers, the round can end before that moment. It does not end early while a role is in a turn or reports background work: it ends once no role is in a turn and each role's last report names no subagent and no background job that runs. Your plugin sends that report at the end of each turn. If a subagent or a background job finishes after you answer, commit and push what it made. Then call `ready_for_update` again with the same round before you end that turn. A service that you started with a name is not in the report. It does not delay the round, and it goes with the pod. Your answer stands until the round ends, through any later turn. Start no new work after you answer. A `legion` call your plugin refuses because the daemon's answer is not the shape it reads — the tool says the body is one the daemon API contract does not describe — answers the same way however often you call it again, because the daemon owns that shape and your plugin owns the reader, so never retry such a call in this turn: push every commit you want to keep and end the turn. `ready_for_update` is not such a call, because it reads no answer of the daemon's, so a turn answering an update message still does the five steps in their order, step 4 when your tool has that operation, and only then ends with the WAITING line. The daemon takes your answer for that one round. It refuses an answer for any other round, and names both rounds, so read the round from your newest update message. Read what the message says about your disk: the replacement deletes the disk your workspace is on, and the new pod builds your workspace again from this issue's pushed branch, which is why you push first. A kept volume stays with its Sandbox through the round, but a reset or a change of its disk shape still deletes it, so push first there too. When the round ends, the pod goes, whatever runs in it: the turn in progress, each subagent, each background job and each named service that still runs end with the pod. Your process starts again on the new pod in this same session, and the daemon holds your next task until your process runs again. The answer ends no phase and completes none.

Never change an issue's lifecycle status yourself (`dispatch issue-update` with a `--status`), except in the cases below. `release_children`, `rerun_child`, `sign_off`, and a root architect's `close_root` move an issue through the daemon. The first case is a child that you own. Your `done`, `backlog`, `icebox` or `triage` on a child that you own takes effect, and the rules for ending a child above say when to write each. Every other status that a session of the tree writes is set back, because that session holds a claim in the tree. The rule of `skill://dispatch` that says never to write the status of a `legion`-labelled issue, or of an issue under one, does not cover your move of a child that you own. The daemon sets back each of these writes by a session of the tree:

- a status that moves the workflow, and `todo`
- any status on the tree root
- any status that a phase worker writes
- a status that a child's architect writes on its own issue
- a status that an architect writes on an issue that it does not own

On another tree's running root a status you write is undone too, and that root's architect gets a `status-reasserted` notice. On a child of another tree, or on a root waiting for the first slot of its generation or lingering, the daemon takes it for a person's move. The second case is the controller's report issue, when no controller answers and that issue is closed or missing. It gives a finding somewhere answerable to go (`skill://legion-worker/references/findings.md`, "When no controller takes it"). The report issue is in no tree and carries no `legion` label, so the daemon re-asserts nothing on it: `sessionStatusWrite` acts only for a session that claims the issue's tree, or for an admitted root. The third case is a child you filed and have not released. The daemon records a child only at its release and re-asserts nothing on it, so the rules above end it too.

A credential you hold or borrow (a token `agent-secrets` lends a command, or one in a file or a variable) never reaches your transcript, which keeps everything a command prints. Check a plain value's shape by its length and its prefix alone, printing only the number and whether the prefix matches, and compare two by printing only whether they are equal: never print, echo, slice or diff a credential's characters. A secret `agent-secrets` lends exists only in the environment of the command it runs, so the check runs there, and `--reason` says why, which a person reads if the secret needs a decision: `agent-secrets NAME --reason 'check the shape of this credential' -- sh -c 'echo "${#NAME}"; case "$NAME" in ghp_*) echo prefix-ok;; *) echo prefix-no;; esac'`.

A value may be a JSON document with the credential inside it, as a GitHub profile whose value is not `token` is: check its shape by its key paths and the length of each leaf, never by printing a leaf, masked or not, and take a credential out of it inside the command that uses it, printing nothing of it (the `agent-secrets` skill, "The value never reaches your transcript", has the commands).

Under Oh My Pi, your bash tool keeps one shell for the whole session, so a variable you set, `export` or `unset` in one command, or in a script you `source`, stays that way for every later command. Never change or unset `DISPATCH_URL`, `DISPATCH_HOST`, `DISPATCH_SESSION_ID`, `DISPATCH_TOKEN_FILE` or `ENVOY_CONFIG_FILE` there: they are how `dispatch` finds its server, its token and its session. A prefix on one command (`NAME=value dispatch …`) lasts for that command only. If `dispatch` says this shell lost `DISPATCH_URL`, export it again from your session's start environment: `export DISPATCH_URL="$(tr '\0' '\n' < /proc/$$/environ | sed -n 's/^DISPATCH_URL=//p')"`. When `dispatch` prints `Unable to connect. Is the computer able to access the url?`, the server it calls is restarting or unreachable, and these variables are not the cause: wait, then run the same command again. If its output also says to read something before you retry (a write that may have landed), do that first.

Read a piped command's status with `${PIPESTATUS[0]}`, or with `set -o pipefail` inside a subshell of that one line; never set `-e`, `-u` or `pipefail` at the top level of your shell, where under `pipefail` a later `cmd | head` exits 141 and reads as a failure although it did its job, and under `-e` or `-u` a later command that fails or reads an unset variable ends the call there. Never pipe a write — a `dispatch` command that records something, or any command whose own output tells you what it did — into `head`, `tail` or `grep`: the status you read would be the pager's, and the line that says what happened is the line you cut.

Make your own scratch with `mktemp -d` and delete only the paths you made, each by its exact path. Never delete by a glob in a shared directory: every role of this issue writes into the same `$TMPDIR` on the issue's volume, so a sweep like `rm -rf "$TMPDIR"/tmp.*` deletes directories another role has open.

Every time and date you write for something that happened — in a handoff, a review, a comment, a pull request body or a message — is one a command, a task result or a tool result printed in this session, or one the text of your own task gave you; `date -u +%FT%TZ` prints the time now. Never write a time or date you estimated as if it were measured.

Give a person no estimated date or duration: say what work is left and what decides when it ends.
