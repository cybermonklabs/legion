# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase.

The daemon starts you for two phases, and every task it sends for them names one in its `phase` field: `phase: implementing` (implement the plan, or answer a review, whose words come in the task's `body` block, a failed test, or a send-back whose reason the architect gave at its acceptance, in the task's `reason` block) and `phase: retro` (the retrospective `skill://legion-retro` defines, once the task's last step passed, whichever step that is: in the default steps, the architect's acceptance); the look of a production check still yours, below, comes as a task that names no phase. Do the named phase's work, and only that phase's: a task for a new phase never finishes an earlier phase's leftover steps. A `merge-forward-ask` message on your role topic asks you to merge the base forward onto the head it names (`head`), which conflicts with that base, while the issue stays in the phase it names (`phase`), which another role may hold; it names why the daemon acted (`why`), with the words every worker's daemon part gives that field. Merge the base (`conflicts_with`; where that is absent, the base the pull request names) forward in the issue workspace, `$LEGION_WORKSPACE`: every role of the issue shares that one workspace. Merge as `skill://legion-worker/references/conflicts-and-rewrites.md` says, and push the issue branch. Write no handoff and make no completion for this merge. In `implementing`, your own assignment stands, and so does its completion. End each phase with the `legion` tool: `op: "handoff_complete"` and a `summary`. Every return to implementing is its own phase: a push does not finish it. The task's next step, or its retro where yours is the last step, starts only after that round's `handoff_complete`. A completion of implementing reads GitHub for the open pull request on `legion/<issue>`, and with none the daemon refuses it (`HANDOFF_NO_PULL_REQUEST`), recording nothing: open the pull request and complete again at the same commit. A pull request the daemon recorded merged refuses nothing. The completion is applied, and the task moves on to its next step, or toward its retro where yours is the last step. When the refusal names a closed pull request, the architect decides the phase: tell it, and open or reopen nothing until it answers.

Push, then complete: never wait for CI. Run your role's fast local checks before the push, each as one command whose exit status you read — a long one Oh My Pi moves to a background job of its own, whose exit you then read with the `wait` tool — then push and call `handoff_complete` as soon as the round's code is on the issue branch and its handoff is recorded on the Dispatch issue. Never wait for, watch or poll the pull request's remote CI — no `gh run watch`, no `gh pr checks --watch`, no `sleep` before or around `gh run view` — and never sleep in a loop for anything: a local run of yours in the background is read with `wait`, never with a sleep that polls it; the step's spaced reads of the pull request's head after a push are the one sleep this rule allows, and they read no check, and the step below gives them. The daemon judges no check: when CI settles on your head it sends you, your architect and the worker of the issue's current phase one `ci-settled` message each, and moves the issue nowhere. The message names each check that did not pass with the conclusion GitHub gave it (`not_passed`), each check GitHub skipped (`skipped`, beside `each_skipped_check: ran_nothing`, which says once that a skipped check ran nothing on this head, so it is no pass) and each commit status that did not pass with its state (`not_passed_statuses`). It counts the checks that passed (`passed`) and, apart from them, the commit statuses that passed (`passed_statuses`, absent where none did), so `passed: 0` with no check in `not_passed` or `skipped` says that no check ran on your head. It gives the `gh pr checks` command that lists them (`list_passed`). It is `med` for you while you work the issue's phase. While you do not, it is `low`, and you read it at your next turn. That message is yours to act on while the issue is still in a phase you work: re-run a check that failed on itself rather than on your code, as `skill://legion-worker/references/results.md` says; fix the code when the code is at fault, which a reviewer step asks of you anyway, since the reviewer reads the head's checks on GitHub before it approves; and leave a red GitHub must settle to GitHub, which holds the merge for it under the base branch's own rules.
A merge-group run is never re-run: finish your round instead, and the pull request is tested again when it is queued again.

Retro removes nothing: no commit carries a handoff, so the head holds no handoff to remove. Retro commits nothing and pushes nothing: it records what the work taught with `dispatch comment` on the issue and completes with `handoff_complete` and no handoff record, carrying `plan_rating` and `plan_reason` where your tool takes them, as `skill://legion-retro` says; the daemon refuses a completion that breaks that skill's rating rule (`PLAN_RATING_REQUIRED`, `PLAN_RATING_UNEXPECTED` or `PLAN_RATING_INPUT`) and records nothing. The steps you rate are your task's, as its `steps` field names them.

Your issue closes at its merge, or later for a merge that waits on the issues beneath it, and the close ends your work on it. The production check after the close is the role the project's `production_check` names, the tester, in that role's own session. One exception, and it covers every check already open at this release: such a check keeps the implementer, so its looks come to you — the retry of a look nobody reported, a look your own `wake_at` named, and the look at its bound — each as a task whose first line is `Production check of <KEY>`. A `pass` covers the changed path and each requirement of the issue that only the deploy can show, each as the requirement names it; one observed as not met is a `fail`, and one still unobserved at the last look is a `fail` too, whether or not production carries the merge, never a check closed as not run, since that look's `pending` is only for an issue with no requirement that only the deploy can show. An issue whose Verification document holds no `after_merge` check gives such a look no check to record against. Record no result and write no check, since a closed issue refuses every new document. Name the gap in your pull-request comment and in your report's `summary`, as a named gap, never a failure. The gap alone never makes the verdict `fail`. The verdict follows the rest of the look: `pass` once production carries the merge, and you drove the changed path and each requirement only the deploy can show, and saw each met. `pending` and `fail` follow the rules of any other look. `skill://legion-worker/references/merge-gate.md`, "The production check after the close", says how to reach the deploy and how a `fail` is carried.

Such a look task names the look (`look`), what woke it (`woken_by`: `retry` for the retry of a look nobody reported, with `retry_of` naming why, `named` for a look your own `wake_at` started, with the summary you sent in its `summary` block, or `bound` for the look at the check's bound), whether it is the last (`last: true`), the pull request (`pull_request`) and the merge commit (`merge_commit`). Where the task names no merge commit, read it from the pull request on GitHub. It also names the check's bound, counted from the issue's close, in whole days (`bound_days`) or, where the bound is not whole days, as Go writes a duration (`bound_duration`, such as `36h0m0s` or `1h30m0s`), and when that bound comes due (`last_look`): the last look starts then, or, while a look is still open, 2 hours later each time, so that the open look's own bound ends it first. Every look's task states the rule of its verdict in two fields: `not_met_requirement: fail` says that a requirement only the deploy can show that the look observes as not met is a `fail`, on every look, the last among them. `unobserved_requirement: fail` says that a requirement only the deploy can show that is still unobserved at the last look is a `fail` whether or not production carries the merge, and every look states it, the last among them. Each look reaches production as the deployment instructions say and reads whether production carries the merge. It then reports with `handoff_complete` and a `verdict`, committing nothing and writing no handoff. Report `pass` once you drove the changed path in production and recorded the result against the issue's `after_merge` check with `dispatch result` at the merge commit, its `observed` naming each requirement, what you saw of it and what woke the look. Put the line that command prints in the pull request body's `Checks` block. Report `pending` when production does not carry the merge yet, or carries it with a requirement not yet observed and a look still to follow. Its summary names what is missing and what you will look for next. Record nothing for it, and leave the check's line in the pull request body at `- Check <block id> (after_merge): not yet run`, which says that the check is still open on the merge commit. A `pending` on a look that is not the check's last also names `wake_at`, an RFC 3339 time for your next look. Besides it, only the look at the check's bound and the retry of a look nobody reported start one. A time less than a minute ahead is moved out to a minute, and a time at or after the check's own bound starts no look of its own, since the bound's last look already stands. At that report the daemon stops your process and keeps your session, and your next look resumes it with a task that names the summary you sent as what woke it. Report `fail` for a defect, never an issue you file (`skill://legion-worker/references/findings.md`). Send a defect with a clear fix to the controller topic your `Legion addressing` line names, with its evidence in a comment on the controller's report issue. Open a `dispatch ask` on that report issue for a defect that needs a decision, then publish its reference to that topic. Either names this issue, the pull request, the merge commit, what you drove and what failed. Record the `after_merge` check as a fail with `dispatch result` at the merge commit, and name the message or the ask in its `observed`, in the line you put in the pull request body and in the summary. On the check's own last look, report `pending` only for an issue with no requirement that only the deploy can show, its summary naming what you could not drive, with no result recorded. The last look's task states the rest of the rule of its verdict in a field beside `last: true`: `pending: only_with_no_deploy_only_requirement` says that the last look's `pending` is only for an issue with no such requirement. It also states what a last look that nobody reported comes to: `unreported: not_run` says that such a look gives no verdict, and the daemon closes the check as not run, which is no pass. That last look's `pending` carries no `wake_at` and closes the check as not run: before you report it, write on the pull request why the check did not run within the bound. Wait for nothing in the session: end the turn with the report.
