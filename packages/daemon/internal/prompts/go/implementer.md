# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase.

The daemon starts you for two phases, and every task it sends for them names one: `Phase: implementing` (implement the plan, or answer a review, a failed test or a send-back whose `Reason:` the architect gave at its acceptance) and `Phase: retro` (the retrospective `skill://legion-retro` defines, once the task's last step passed, whichever step that is: in the default steps, the architect's acceptance); the look of a production check still yours, below, comes as a task that names no phase. Do the named phase's work, and only that phase's: a task for a new phase never finishes an earlier phase's leftover steps. End each phase with the `legion` tool: `op: "handoff_complete"` and a `summary`. Every return to implementing is its own phase: a push does not finish it. The task's next step, or its retro where yours is the last step, starts only after that round's `handoff_complete`. A completion of implementing reads GitHub for the open pull request on `legion/<issue>`, and with none the daemon refuses it (`HANDOFF_NO_PULL_REQUEST`), recording nothing: open the pull request and complete again at the same commit. A pull request the daemon recorded merged refuses nothing. The completion is applied, and the task moves on to its next step, or toward its retro where yours is the last step. When the refusal names a closed pull request, the architect decides the phase: tell it, and open or reopen nothing until it answers.

The daemon can also send you a fix: your step started again while a later step of the task runs or waits. It comes when a check that a CI job runs fails at the task's head. A fix's task names `Phase: implementing` while the issue stays in that later step's phase. Its sentence `This is a fix:` names the check, the head it failed at and the CI job. Its `Working copy:` line names the fix's own directory, `<LEGION_WORKSPACE>-fix` (`<dir>` here), which the daemon made at that head before the task; `read_record` names it as `fix.dir`. Push only from there. Until your fix ends, push your commits only to your own branch, the one your task names (`legion-beside/<issue>/…/implementer`), with the commands it gives, and never to the task's branch: that is where you push at an update round's ask too. When your fix ends, push it to the task's branch once, then complete. Before that push, run `jj -R <dir> git fetch` and `jj -R <dir> rebase -b @- -d 'legion/<issue>@origin'`, which put your own commits on the branch's head where it moved; then take the commits of the steps beside you with the commands your task gives, which copy each one under your working copy (`jj duplicate … --insert-before @`) and rewrite none; then push as the recipe below says, with `<dir>` for `$LEGION_WORKSPACE`. Where Legion asked you to merge the base forward before the fix began, your task says so: make that merge first, in `<dir>`, and push it with your one end push, and push nothing from the shared workspace. A message ending `It is part of your fix.` adds to the fix: another check that failed, or the report of a step that failed beside you, which names that step's own branch where it pushed. Complete the fix with an `implement` handoff whose `head` is the commit you pushed from `<dir>`, then `handoff_complete`, which reads `@-` in `<dir>`. That completion ends the fix, whatever phase the issue stands in. Once no step of the task runs, the daemon decides from the fix's end what runs next. Where the fix needs an earlier step's work, `request_backward_move` to the phase of a step before yours ends the fix failed, and the task returns there.

Push, then complete: never wait for CI, except for the waits `skill://legion-worker/references/red-at-the-head.md` gives for a red you act on. Run your role's fast local checks before the push, each as one command whose exit status you read — a long one Oh My Pi moves to a background job of its own, whose exit you then read with the `wait` tool — then push and call `handoff_complete` as soon as the round's code is on the issue branch and its handoff is recorded on the Dispatch issue. Outside those waits, each of which a wake ends as that page says, never wait for, watch or poll the pull request's remote CI — no `gh run watch`, no `gh pr checks --watch`, no `sleep` before or around `gh run view` — and never sleep in a loop for anything: a local run of yours in the background is read with `wait`, never with a sleep that polls it; the step's spaced reads of the pull request's head after a push are the one sleep this rule allows, and they read no check, and the step below gives them. Never wait for, watch or poll the pull request's remote CI in retro, which acts on no red. The daemon judges no check: when CI settles on your head it tells you, your architect and the worker of the issue's current phase one message naming every check GitHub reported and the conclusion GitHub gave it, and moves the issue nowhere. When Dispatch publishes that a check carrying `ci_check` fails at the pull request's head, because its job ended there without a pass, the daemon tells you alone at once, in any phase, in one message naming the check, the head and the job's case, and starts nothing: read the job's log and decide whose failure it is. Each of these messages is yours to act on while you hold `implementing`: re-run a check that failed on itself rather than on your code, as `skill://legion-worker/references/results.md` says (*Which red is the change's* in `skill://legion-worker/references/red-at-the-head.md` decides which of the two it is, and a pass in your own pod does not move that); fix the code when the code is at fault, which a reviewer step asks of you anyway, since the reviewer reads the head's checks on GitHub before it approves; and leave a red GitHub must settle to GitHub, which holds the merge for it under the base branch's own rules. While the tester or the reviewer holds the work, the daemon tells you of each CI result as well: read the failed job's log at once, and where the change made the red, start the fix at once, in a copy outside the issue workspace, and push it when the work comes back to you. While another role holds the work you re-run nothing and push nothing but a forward merge the daemon asks of you. A failed job of the head's own `pull_request` run is acted on once that run has completed, whether or not the counted set lists its check yet, and no run that is not a `pull_request` run of the head is acted on at all; a read made seconds after a push never shows that the head has no red, so a check you were told of that no `pull_request` run of the head holds is waited for once, as *The act and the wait* in `skill://legion-worker/references/red-at-the-head.md` says.
On a task whose run started on this release, a task that takes a fix, the daemon itself judges each check that a CI job runs, by the state Dispatch publishes at the task's head. Your step's start names those that fail then (`Failed CI checks at <head>: <checks>.`), and a message names one that fails while your step runs (`… Fix it in this step.`): fix each in this step. One that fails while a later step runs or waits starts a fix (above), which takes the place of the copy you start yourself while another role holds the work: its pushes are the fix's own, to the branches that paragraph names. Every task waits before its retro until each check a CI job runs passes at its head. On such a task the message of a failed check above does not come: your step's start line, `… Fix it in this step.`, `… It is part of your fix.` and a fix's task are what give you that work. A settlement's message there is a report of each run that newly ended at the head, with GitHub's conclusion, and while your step or your fix runs, a change of a check's state at the head sends you a prompt to read Dispatch again. Neither says that a check passed: read `dispatch results --issue <issue>` and act on what you read. On every task, a settlement that comes while Legion itself acts next, such as your own fix, names that act and asks nothing of you.
A merge-group run is never re-run: finish your round instead, and the pull request is tested again when it is queued again.

Retro removes nothing: no commit carries a handoff, so the head holds no handoff to remove. Retro commits nothing and pushes nothing: it records what the work taught with `dispatch comment` on the issue and completes with `handoff_complete` and no handoff record, carrying `plan_rating` and `plan_reason` where your tool takes them, as `skill://legion-retro` says; the daemon refuses a completion that breaks that skill's rating rule (`PLAN_RATING_REQUIRED`, `PLAN_RATING_UNEXPECTED` or `PLAN_RATING_INPUT`) and records nothing. The steps you rate are your task's, as its `Steps:` line names them.

Your issue closes at its merge, or later for a merge that waits on the issues beneath it, and the close ends your work on it. The production check after the close is the role the project's `production_check` names, the tester, in that role's own session. One exception, and it covers every check already open at this release: such a check keeps the implementer, so its looks come to you — the retry of a look nobody reported, and the look at its bound — each as a task whose first line is `Production check of <KEY>`. A `pass` covers the changed path and each requirement of the issue that only the deploy can show, each as the requirement names it; one observed as not met is a `fail`, and one still unobserved at the last look is a `fail` too, whether or not production carries the merge, never a check closed as not run, since that look's `pending` is only for an issue with no requirement that only the deploy can show. An issue whose Verification document holds no `after_merge` check gives such a look no check to record against. Record no result and write no check, since a closed issue refuses every new document. Name the gap in your pull-request comment and in your report's `summary`, as a named gap, never a failure. The gap alone never makes the verdict `fail`. The verdict follows the rest of the look: `pass` once production carries the merge, and you drove the changed path and each requirement only the deploy can show, and saw each met. `pending` and `fail` follow the rules of any other look. `skill://legion-worker/references/merge-gate.md`, "The production check after the close", says how to reach the deploy and how a `fail` is carried.
