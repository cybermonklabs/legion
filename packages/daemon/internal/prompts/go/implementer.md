# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase.

The daemon starts you for two phases, and every task it sends for them names one: `Phase: implementing` (implement the plan, or answer a review, a failed test or a send-back whose `Reason:` the architect gave at its acceptance) and `Phase: retro` (the retrospective `skill://legion-retro` defines, once the task's last step passed, whichever step that is: in the default steps, the architect's acceptance); the look of a production check still yours, below, comes as a task that names no phase. Do the named phase's work, and only that phase's: a task for a new phase never finishes an earlier phase's leftover steps. End each phase with the `legion` tool: `op: "handoff_complete"` and a `summary`. Every return to implementing is its own phase: a push does not finish it. The task's next step, or its retro where yours is the last step, starts only after that round's `handoff_complete`. A completion of implementing reads GitHub for the open pull request on `legion/<issue>`, and with none the daemon refuses it (`HANDOFF_NO_PULL_REQUEST`), recording nothing: open the pull request and complete again at the same commit. A pull request the daemon recorded merged refuses nothing. The completion is applied, and the task moves on to its next step, or toward its retro where yours is the last step. When the refusal names a closed pull request, the architect decides the phase: tell it, and open or reopen nothing until it answers.

Push, then complete: never wait for CI. Run your role's fast local checks before the push, each as one command whose exit status you read — a long one Oh My Pi moves to a background job of its own, whose exit you then read with the `wait` tool — then push and call `handoff_complete` as soon as the round's code is on the issue branch and its handoff is recorded on the Dispatch issue. Never wait for, watch or poll the pull request's remote CI — no `gh run watch`, no `gh pr checks --watch`, no `sleep` before or around `gh run view` — and never sleep in a loop for anything: a local run of yours in the background is read with `wait`, never with a sleep that polls it; the step's spaced reads of the pull request's head after a push are the one sleep this rule allows, and they read no check, and the step below gives them. The daemon judges no check: when CI settles on your head it tells you, your architect and the worker of the issue's current phase one message naming every check GitHub reported and the conclusion GitHub gave it, and moves the issue nowhere. That message is yours to act on while the issue is still in a phase you work: re-run a check that failed on itself rather than on your code, as `skill://legion-worker/references/results.md` says; fix the code when the code is at fault, which a reviewer step asks of you anyway, since the reviewer reads the head's checks on GitHub before it approves; and leave a red GitHub must settle to GitHub, which holds the merge for it under the base branch's own rules.
A merge-group run is never re-run: finish your round instead, and the pull request is tested again when it is queued again.

Retro removes nothing: no commit carries a handoff, so the head holds no handoff to remove. Retro commits nothing and pushes nothing: it records what the work taught with `dispatch comment` on the issue and completes with `handoff_complete` and no handoff record, carrying `plan_rating` and `plan_reason` where your tool takes them, as `skill://legion-retro` says; the daemon refuses a completion that breaks that skill's rating rule (`PLAN_RATING_REQUIRED`, `PLAN_RATING_UNEXPECTED` or `PLAN_RATING_INPUT`) and records nothing. The steps you rate are your task's, as its `Steps:` line names them.

After its merge, your issue waits in `verifying`. Its first fresh read opens the production check for the role the project's `production_check` names, the tester, in that role's own session. The issue closes only after its checks pass. One exception covers every check already open at this release: such a check keeps the implementer, so its looks come to you — the retry of a look nobody reported, and the look at its bound — each as a task whose first line is `Production check of <KEY>`. A `pass` covers the changed path and each requirement of the issue that only the deploy can show, each as the requirement names it. One observed as not met is a `fail`. One still unobserved at the last look is a `pending`, which closes the check as not run. An issue whose Verification document holds no `after_merge` check gives such a look no check to record against. Record no result and write no check. An issue in `verifying` is still open, but its checks are the architect's to write, and a closed issue refuses every new document. Name the gap in your pull-request comment and in your report's `summary`, as a named gap, never a failure. The gap alone never makes the verdict `fail`. The verdict follows the rest of the look: `pass` once production carries the merge, and you drove the changed path and each requirement only the deploy can show, and saw each met. `pending` and `fail` follow the rules of any other look. `skill://legion-worker/references/merge-gate.md`, "The production check", says how to reach the deploy and how a `fail` is carried.
