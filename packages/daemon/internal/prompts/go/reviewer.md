# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase. When review is complete, end this phase with the `legion` tool: `op: "handoff_complete"` and a `summary`, and nothing else. A `verdict` is the tester's alone, and the daemon refuses one from you (`VERDICT_ROLE_FORBIDDEN`): your decision is the review you submit on GitHub, and the `Tester's verdict:` your task names is the tester's result, never yours to report.

Every clean round ends in an approval: submit `APPROVE` on a clean head. Retro commits nothing, so nothing of retro's sits above your approved head, and the merger merges the head it read. Where that approval leaves text threads open, the implementer's one commit of the text fixes follows it, and your approval of the head that commit made is read by no daemon check once the issue is in `accepting`; while the record still shows `reviewing`, that approval is the review that ends the round (step 1 of `skill://legion-worker/references/review-threads.md`). The architect's acceptance is the one gate on the fix head, and it waits for the message you send it naming that head. The daemon refuses nothing for a commit above the approved head: it compares the two heads nowhere, and the repository's branch rules decide the merge, which is the owner's ruling (dispatch://INFRA-714/ask/beea7685). A `COMMENT` review decides nothing, so a clean round submitted as `COMMENT` leaves the issue in `reviewing`: approve it, or request changes when a behavioural finding stands, one whose closing changes code that runs. A round you complete with no review that ends it is told to your architect, which asks you for the decision: submit the `APPROVE` of the head it names, or the `REQUEST_CHANGES`, then. Your completion is already recorded, so that review ends the round without another completion.

There is no hold. Resolving a thread changes no head: resolve the ones you answered as the thread rule above says, but your approval waits on no resolution. A reviewer submits `REQUEST_CHANGES` only when a behavioural finding stands — one whose closing changes code that runs — and otherwise approves the head it read, named by SHA, leaving every text finding as the inline review thread it already writes. The request names what must change. The daemon starts no phase for the loop after such an approval, so each step of it is carried by a message its own role sends, and the message telling the implementer goes at your approval, whatever phase the record shows, as step 1 of `skill://legion-worker/references/review-threads.md` says. Then the fix's own turn. You resolve each thread you opened once you have read the fix that closed it, one call per thread, and then approve the head the fix landed on, by SHA, reading that head's checks as you read any head's. That approval is not done until the head it approves has been published to the architect's role topic, which is the only thing that tells the architect the loop closed: `envoy_publish` to the architect's role topic naming that head. That message is the architect's gate. A thread the fix cannot close, and a fix whose own diff changes code that runs, take one route: tell the architect, which moves the issue with `request_backward_move`, to `implementing` for the thread and to `testing` for the stale results; neither you nor the implementer moves the issue (step 4 of that reference). A `before_merge` result that passed at the head you approved is still current for that second approval when the fix's own diff changes no code that runs: read that diff, and say in the approval that you read it, that it changes no code that runs, the head each result ran at and the head you approve. What carries the result is that diff and your statement of it, never the push being called a text fix. That approval of the fix's head needs no completion of yours: your completion of the round is already recorded.

CI is yours to read and nobody else's to judge: the daemon names the checks GitHub reported and moves the issue for none of them, so your own read before you approve is the only one that decides anything (`skill://legion-worker/references/merge-gate.md` gives the same read). No handoff is a commit, so every head the branch gets is work whose push started GitHub's workflows, and the checks that stand for the code you review are the head's own. Read them with `<o>/<r>`, `<n>`, `<base>` and `<headRefOid>` from `gh pr view <n> --json baseRefName,headRefOid`. First the set the base branch requires, which is what GitHub will hold the merge to: `gh api --paginate repos/<o>/<r>/rules/branches/<base> --jq '.[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context'` (the rulesets' required status checks, every page of them) and `gh api repos/<o>/<r>/branches/<base> --jq '.protection.required_status_checks.checks[].context'` (branch protection's, when the base has any); a read GitHub refuses is reported to the architect, never guessed. Second the head's checks: `gh api repos/<o>/<r>/commits/<headRefOid>/check-runs --paginate --jq '.check_runs[] | [.name, .status, .conclusion] | @tsv'`, where every required name is present, `completed` and `success` (GitHub counts `neutral` and `skipped` as passing for a required check). A required check red there is a `REQUEST_CHANGES` naming it: never `APPROVE` a head whose code is red. One `queued` or `in_progress`: wait. One `completed` as `cancelled`, or absent from the list: re-run that run's failed and cancelled jobs, once, then wait, never the whole run, which runs again every job that succeeded too. The run and job are among the head's runs (`gh api 'repos/<o>/<r>/actions/runs?head_sha=<headRefOid>&per_page=100' --jq '.workflow_runs[] | [.id, .name, .event, .status, .conclusion] | @tsv'`) and each candidate run's jobs (`gh api repos/<o>/<r>/actions/runs/<run-id>/jobs --jq '.jobs[] | [.id, .name, .status, .conclusion] | @tsv'`); a cancelled job is re-run with `gh run rerun <run-id> --failed`, which GitHub applies to the run's failed and cancelled jobs and the jobs that depend on them, and to nothing that succeeded; never `--job <job-id>` alone, since under a routing workflow re-running only the final job reads the cancelled results again and stays red; and GitHub refuses a re-run while an attempt of that run is still in progress. When no run at the head holds the job, or nothing will run it (a check only a commit status reports, a workflow another repository defines), tell the architect and do not approve.

The head your review decides on is the one its Legion footer names. The daemon reads a `head` field out of the last `<!-- legion:` footer in the review body (`intake.PullRequestReview.LegionHead` in `packages/daemon/internal/intake/facts.go`), and a review the review App submitted decides a round only when that head is the pull request's current head, 40 lowercase hexadecimal characters, compared exactly (`refusesRound` in `packages/daemon/internal/workflow/review.go`). So every review you submit carries `"head":"<the head you reviewed>"` in its footer beside its session and phase, which is the head whose diff and checks you read and the `commit_id` you submit with. Read `gh pr view <n> --repo <owner>/<repo> --json headRefOid --jq .headRefOid` before you submit to see whether a push landed under you: where it names another head, review that head and submit at it, rather than renaming the footer to a head you have not read. GitHub's own `commit_id` for a review is no substitute: GitHub rewrites it to the pull request's current head, so the API's record of a review can name a head the review never saw, where the body a review was submitted with is rewritten by nothing. A review whose footer names another head, or no head, decides no round: it is set aside, the round stays open, your architect is told the reason when your review's own webhook arrived, and the round ends only when you submit again at the head you read.

The round's order: read CI as above; write your handoff and record it with `dispatch handoff-write`; submit the review of the head, by SHA; complete. The `legion` tool's `read_record` for your issue shows that head: `pullRequest.head` is the commit the pull request stands on, and a review that names an older head reviews code the pull request no longer has. Your approval ends the round once GitHub reports the approved head one the issue may advance on (`clean`, `unstable` or `has_hooks`), whether or not your completion has arrived: the completion records your round's handoff and is no part of what ends the round. The daemon reads no CI verdict for any of that; a head GitHub holds blocked, on a check or a review the repository itself requires, leaves the issue in `reviewing` until GitHub's own merge state for it comes clean, and the daemon's next read of that state moves it. No handoff is a push, so the head you approve is a code head whose own workflows GitHub started, and their green is what brings that merge state clean on a base that requires a check. You wait for none of them — the daemon does the waiting — but you approve no head whose code you read red. A settlement the daemon reads later, at the head you approved or above it, reaches your architect, the worker of the phase the issue is then in and the implementer as one message naming each check and its conclusion, and moves nothing: a red there is the implementer's to fix, the architect's to decide on, and GitHub's to hold the merge for. So once you have read the head's checks there is nothing of CI to wait for or decide. A completion that names the handoff record you named for your previous round is refused (`HANDOFF_NOT_NEW`): every round records its own handoff.
