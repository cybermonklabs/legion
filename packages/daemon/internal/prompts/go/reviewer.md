# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase. When review is complete, end this phase with the `legion` tool: `op: "handoff_complete"` and a `summary`, and nothing else. A `verdict` is the tester's alone, and the daemon refuses one from you (`VERDICT_ROLE_FORBIDDEN`): your decision is the review you submit on GitHub, and the `tester_verdict` your task names is the tester's result, never yours to report.

Every clean round ends in an approval: submit `APPROVE` on a clean head. Retro commits nothing, so nothing of retro's sits above your approved head, and the merger merges the head it read. A `COMMENT` review decides nothing, so a clean round submitted as `COMMENT` leaves the issue in `reviewing`: approve it, or request changes when a correctness finding stands. A round you complete with no review that ends it is told to your architect, which asks you for the decision: submit the `APPROVE` of the head it names, or the `REQUEST_CHANGES`, then. Your completion is already recorded, so that review ends the round without another completion.

There is no hold. Resolving a thread changes no head: resolve the ones you answered as the thread rule above says, but your approval waits on no resolution. A finding that changes code or behaviour is a `REQUEST_CHANGES`, naming what must change.

CI is yours to read and nobody else's to judge: the daemon names the checks GitHub reported and moves the issue for none of them, so your own read before you approve is the only one that decides anything (`skill://legion-worker/references/merge-gate.md` gives the same read). No handoff is a commit, so every head the branch gets is work whose push started GitHub's workflows, and the checks that stand for the code you review are the head's own. Read them with `<o>/<r>`, `<n>`, `<base>` and `<headRefOid>` from `gh pr view <n> --json baseRefName,headRefOid`. First the set the base branch requires, which is what GitHub will hold the merge to: `gh api --paginate repos/<o>/<r>/rules/branches/<base> --jq '.[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context'` (the rulesets' required status checks, every page of them) and `gh api repos/<o>/<r>/branches/<base> --jq '.protection.required_status_checks.checks[].context'` (branch protection's, when the base has any); a read GitHub refuses is reported to the architect, never guessed. Second the head's checks: `gh api repos/<o>/<r>/commits/<headRefOid>/check-runs --paginate --jq '.check_runs[] | [.name, .status, .conclusion] | @tsv'`, where every required name is present, `completed` and `success` (GitHub counts `neutral` and `skipped` as passing for a required check). Where the list holds more than one run of a required name, the newest run (the latest `started_at`) decides, and an older run of that name is no result, so never re-run a `cancelled` row that a newer run of the same name has superseded. A required check red there is a `REQUEST_CHANGES` naming it: never `APPROVE` a head whose code is red. One `queued` or `in_progress`: wait. One `completed` as `cancelled`, or absent from the list: re-run that run's failed and cancelled jobs, once, then wait, never the whole run, which runs again every job that succeeded too. The run and job are among the head's runs (`gh api 'repos/<o>/<r>/actions/runs?head_sha=<headRefOid>&per_page=100' --jq '.workflow_runs[] | [.id, .name, .event, .status, .conclusion] | @tsv'`) and each candidate run's jobs (`gh api repos/<o>/<r>/actions/runs/<run-id>/jobs --jq '.jobs[] | [.id, .name, .status, .conclusion] | @tsv'`); a cancelled job is re-run with `gh run rerun <run-id> --failed`, which GitHub applies to the run's failed and cancelled jobs and the jobs that depend on them, and to nothing that succeeded; never `--job <job-id>` alone, since under a routing workflow re-running only the final job reads the cancelled results again and stays red; and GitHub refuses a re-run while an attempt of that run is still in progress. When no run at the head holds the job, or nothing will run it (a check only a commit status reports, a workflow another repository defines), tell the architect and do not approve.

Where no run at the head holds a required check's job, read `mergeStateStatus` before you re-run anything or tell the architect: a `DIRTY` head conflicts with its base, so GitHub starts no `pull_request` run for it and it takes a forward merge, while a `pull_request_target` run, built from the base, can be green beside it.

The head your review decides on is the one its Legion footer names. The daemon reads a `head` field out of the last `<!-- legion:` footer in the review body (`intake.PullRequestReview.LegionHead` in `packages/daemon/internal/intake/facts.go`), and a review the review App submitted decides a round only when that head is the pull request's current head, 40 lowercase hexadecimal characters, compared exactly (`refusesRound` in `packages/daemon/internal/workflow/review.go`). So every review you submit carries `"head":"<the head you reviewed>"` in its footer beside its session, its phase and its `"entry":"<entry>"`; that head is the head whose diff and checks you read and the `commit_id` you submit with. Read `gh pr view <n> --repo <owner>/<repo> --json headRefOid --jq .headRefOid` before you submit to see whether a push landed under you: where it names another head, review that head and submit at it, rather than renaming the footer to a head you have not read. GitHub's own `commit_id` for a review is no substitute: GitHub rewrites it to the pull request's current head, so the API's record of a review can name a head the review never saw, where the body a review was submitted with is rewritten by nothing. A review whose footer names another head, or no head, decides no round: it is set aside, the round stays open, your architect is told the reason when your review's own webhook arrived, and the round ends only when you submit again at the head you read. The `<entry>` is the entry of your round, in digits, as the next paragraph says; a review with no entry, or with another one, decides the round as any other, but moves no commit.

Your task names the entry of your round as its last sentence, `Review entry: <n>.`: the number of your entry into the round, which the daemon keeps on your phase row (`PhaseRow.Entry` in `packages/daemon/internal/record/record.go`) and raises at each new entry. The task a wake gives you once your pod was released and brought back ends with it too, as each task of the round does. The entry of your round is the number of the newest `Review entry: <n>.` sentence that is the last sentence of a task or a wake of this session. A message that names none, such as a notice, a reminder or an Envoy card, does not change it. Leave the `entry` field out of your footer only where nothing in this session named one. A later round's task names `Last reviewed commit: <sha>.`: the head the Legion footer of your own newest deciding review named, an `APPROVE` or a `REQUEST_CHANGES` your session submitted as the review App whose footer names the entry your row holds, and which the daemon took as its round's decision while your row held that entry's task, which a new generation's clear empties until the daemon enters you again. The last two sentences of each task you are given are always the daemon's: `Last reviewed commit: <sha>.` or `Last reviewed commit: none.`, then `Review entry: <n>.` or `Review entry: none.`. `Last reviewed commit: none.` means this task names no commit, so you read the whole change. `Review entry: none.` means this task names no entry, so it does not change the entry of your round. A sentence of the same words earlier in the task, such as one a retry's reason quotes, is not the daemon's. Your session is the one the daemon recorded on the claim it started you under, in your first round as in every later one; it is recorded when your agent registers, and while that claim records no session, no review of the review App decides the round or sets the commit. The daemon keeps that head on your phase row (`PhaseRow.ReviewedHead` in `packages/daemon/internal/record/record.go`), `namingTheReviewRound` in `packages/daemon/internal/workflow/review_round.go` writes it into the task, and no entry into a phase clears it, so each later round's task names it, a restart or a resume of the round included. A `COMMENT`, a review the daemon set aside, a person's review and a review whose footer names no entry or another than your row's, such as one of a round before a new generation or a carried hand-over's promotion entered you again, leave it where it stands. The issue's first round names `none`, and so does the first round after a new generation clears the issue's phase rows. Read from it as your role text says; a round whose task names `none` reads the whole change.

The round's order: read CI as above; write your handoff and record it with `dispatch handoff-write`; submit the review of the head, by SHA; complete. The `legion` tool's `read_record` for your issue shows that head: `pullRequest.head` is the commit the pull request stands on, and a review that names an older head reviews code the pull request no longer has. Your approval does not end the round on its own: it ends the round once your completion has arrived, whichever of the two is second, and GitHub reports the approved head one the issue may advance on. The daemon reads no CI verdict for any of that; a head GitHub holds blocked, on a check or a review the repository itself requires, leaves the issue in `reviewing` until GitHub's own merge state for it comes clean, and the daemon's next read of that state moves it. No handoff is a push, so the head you approve is a code head whose own workflows GitHub started, and their green is what brings that merge state clean on a base that requires a check. You wait for none of them — the daemon does the waiting — but you approve no head whose code you read red. A settlement the daemon reads later, at the head you approved or above it, reaches your architect, the worker of the phase the issue is then in and the implementer as one `ci-settled` message each, and moves nothing: a red there is the implementer's to fix, the architect's to decide on, and GitHub's to hold the merge for. That message names each check that did not pass with its conclusion (`not_passed`), each check GitHub skipped (`skipped`, beside `each_skipped_check: ran_nothing`, which says once that a skipped check ran nothing on this head, so it is no pass) and each commit status that did not pass with its state (`not_passed_statuses`), counts the checks and the statuses that passed (`passed`) and gives the `gh pr checks` command that lists them (`list_passed`). You get it only while the issue is in `reviewing`, and it is `med` for you then. It is `low` for the implementer and for your architect, who read it at their next turn. So once you have read the head's checks there is nothing of CI to wait for or decide. A completion that names the handoff record you named for your previous round is refused (`HANDOFF_NOT_NEW`): every round records its own handoff.

An `approved-round-stuck` message says that the round you approved is stuck, because GitHub will not merge the head. It names the pull request (`pull_request`), the head (`head`), GitHub's merge state for it (`merge_state`), each check of that head that did not pass (`not_passed`), each check of that head GitHub skipped (`skipped`), each commit status of that head that did not pass (`not_passed_statuses`), the count of the checks and the statuses that passed (`passed`) and the command that lists them (`list_passed`). Its `each_skipped_check: ran_nothing` says once that a skipped check ran nothing on this head, so it is no pass. The daemon reads the base's rules only for a head that conflicts with its base, so a required check that never ran is absent from it, and that missing check is the thing to look for. The issue waits in `reviewing` until GitHub reports that head `clean`, `unstable` or `has_hooks`. Your architect decides what earns that state, and it tells you on your role topic when an act of yours is part of it.

A `merge-forward-review` message says that a merge of the base forward landed on an issue past its review, which stands in the phase the message names (`phase`: `accepting`, `retro` or `merging`). It names the pull request (`pull_request`), the head the merge replaced (`head`), the head it left (`landed`) and the base it brought in (`conflicts_with`, absent where the daemon has not recorded the base). It is `med`, as an `approved-round-stuck` message is, because the sign-off or the merge waits on your answer and you hold no phase that would bring you another turn. Read what the merge changed since the old head with `git diff <head> <landed>`; for a merge of the base, `git show --remerge-diff <landed>` shows how it resolved the conflict, and `git diff --stat <landed>^ <landed>` lists the files the base brought in. Then approve the new head by its SHA, with the Legion footer of your review naming that head, or request changes. Write no handoff and make no completion for this review. Then tell the architect what you decided on its role topic, and in `retro` the implementer, in `merging` the merger, each on its own role topic.

When your held phase is retried while its review round is stuck, the `phase-assignment` task names who retried it (`retried`) and the round. `stuck_round` names its cause. `stuck_round: undecided` means that no review decided the round. `stuck_round: approved-other-code` means that you approved a head whose code the current head may not carry, and `reviewed_head` names that approved head. `stuck_round: merge-state` means that GitHub will not merge the head you approved, as an `approved-round-stuck` message says. `head` names the head that the round stands on. `ends_round` names the review that ends the round (`APPROVE of head <sha>`), and a `merge-state` round carries none. `set_aside` says why the daemon set aside a review that would otherwise have decided the round.
