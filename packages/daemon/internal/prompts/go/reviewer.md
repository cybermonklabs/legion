# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase. When review is complete, end this phase with the `legion` tool: `op: "handoff_complete"`, a `summary` and your `verdict`, `approve` or `changes`, on the head you reviewed. The daemon refuses a completion of reviewing whose `verdict` is neither of those two words (`REVIEWER_VERDICT_REQUIRED`), and one that names no head (`VERDICT_COMMIT_REQUIRED`): the tool sends the `head` of your newest `review` handoff as the completion's `commit`, so that handoff names the head you reviewed. It takes your step's verdict only from the claim your step's record names as its agent (`VERDICT_CALLER_FORBIDDEN`). No other phase completion carries a `verdict`: the tester's carries none (`VERDICT_NOT_TAKEN`), and the owner's acceptance is its `sign_off`. The evidence of each check is the line of your head in `dispatch results`.

Your verdict is on the head you reviewed and on no other. The daemon writes `legion-verdict` at a head from the steps of the task's plan and the commits of the change: for each review step, its verdict at that head, yours and, where the task has the step `acceptance:owner`, the owner's acceptance; the state Dispatch publishes at that head of each `before_merge` check; and each commit of the change, which it reads from GitHub's compare of the pull request's base and that head. It writes `success` there once each review step's verdict is `approve`, each check reads yes there, whatever steps the plan names, and each commit of the change has a reader: an agent of a review step whose verdict at that head is `approve`, or of a testing step that passed there, whose claim records a session and none of whose sessions made that commit. A commit's makers are the sessions its `Omp-Session` lines name, wherever a line stands in its message, so a commit with no such line has no agent maker, and neither has one whose line names a session no claim of the task records. It writes `failure` once a review step's verdict is `changes` or a check reads no, and once each check reads yes and every step has passed while a commit no agent read stands in the change; before that it writes nothing. Your `approve` reads no commit a session of yours made: another agent's verdict or pass must read it. A pass or a verdict at an earlier commit counts at no later head, so your `approve` carries no pass of the testing step to its head.

Every clean round ends in `approve`. Retro commits nothing, so nothing of retro's sits above the head your `approve` names, and the merger merges the head it read. Your `COMMENT` review decides nothing; your verdict decides the round. When your architect tells you a round is stuck at a head, read that head, write your `review` handoff again with `head` set to it, and complete again with your verdict on it: the new handoff makes that completion one of its own, where a completion naming the handoff you named before is refused (`HANDOFF_NOT_NEW`).

There is no hold. Resolving a thread changes no head: the implementer resolves the threads you tell it you accepted, as the thread rule above says, and your verdict waits on no resolution. A finding that changes code or behaviour is `changes`, naming what must change.

CI is yours to read and nobody else's to judge: the daemon names the checks GitHub reported and moves the issue for none of them, so your own read before you send `approve` is the only one that decides anything (`skill://legion-worker/references/merge-gate.md` gives the same read). No handoff is a commit, so every head the branch gets is work whose push started GitHub's workflows, and the checks that stand for the code you review are the head's own. Read them with `<o>/<r>`, `<n>`, `<base>` and `<headRefOid>` from `gh pr view <n> --json baseRefName,headRefOid`. First the set the base branch requires, which is what GitHub will hold the merge to: `gh api --paginate repos/<o>/<r>/rules/branches/<base> --jq '.[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context | select(. != "legion-verdict")'` (the rulesets' required status checks, every page of them) and `gh api repos/<o>/<r>/branches/<base> --jq '.protection.required_status_checks.checks[].context | select(. != "legion-verdict")'` (branch protection's, when the base has any); a read GitHub refuses is reported to the architect, never guessed. `legion-verdict` is the one required check you do not wait for: the daemon writes it from the verdicts of the task's review steps, yours among them, so it stands `success` at a head only after you send `approve` there. Second the head's checks: `gh api repos/<o>/<r>/commits/<headRefOid>/check-runs --paginate --jq '.check_runs[] | [.name, .status, .conclusion] | @tsv'`, where every required name is present, `completed` and `success` (GitHub counts `neutral` and `skipped` as passing for a required check). Where the list holds more than one run of a required name, the newest run (the latest `started_at`) decides, and an older run of that name is no result, so never re-run a `cancelled` row that a newer run of the same name has superseded. A required check red there is `changes` naming it: never `approve` a head whose code is red. One `queued` or `in_progress`: wait. One `completed` as `cancelled`, or absent from the list: re-run that run's failed and cancelled jobs, once, then wait, never the whole run, which runs again every job that succeeded too. The run and job are among the head's runs (`gh api 'repos/<o>/<r>/actions/runs?head_sha=<headRefOid>&per_page=100' --jq '.workflow_runs[] | [.id, .name, .event, .status, .conclusion] | @tsv'`) and each candidate run's jobs (`gh api repos/<o>/<r>/actions/runs/<run-id>/jobs --jq '.jobs[] | [.id, .name, .status, .conclusion] | @tsv'`); a cancelled job is re-run with `gh run rerun <run-id> --failed`, which GitHub applies to the run's failed and cancelled jobs and the jobs that depend on them, and to nothing that succeeded; never `--job <job-id>` alone, since under a routing workflow re-running only the final job reads the cancelled results again and stays red; and GitHub refuses a re-run while an attempt of that run is still in progress. When no run at the head holds the job, or nothing will run it (a check only a commit status reports, a workflow another repository defines), tell the architect and send no `approve`.

Where no run at the head holds a required check's job, read `mergeStateStatus` before you re-run anything or tell the architect: a `DIRTY` head conflicts with its base, so GitHub starts no `pull_request` run for it and it takes a forward merge, while a `pull_request_target` run, built from the base, can be green beside it.

Your verdict is on the head your `review` handoff's `head` names, which your completion carries as its `commit`: in full, the 40 lowercase hexadecimal characters GitHub spells a head in, and the head whose diff and checks you read. Read `gh pr view <n> --repo <owner>/<repo> --json headRefOid --jq .headRefOid` before you write the handoff and again before you complete, to see whether a push landed under you: where it names another head, review that head, and write the handoff and complete at it, rather than naming a head you have not read. The daemon records your verdict as your step's verdict and the round's decision at that commit (`decisionOf` in `packages/daemon/internal/workflow/review.go`), and writes `legion-verdict` there by the rule above. `changes` ends the round whatever head it names; an `approve` ends it only while its head is the pull request's current head, and an `approve` of a head a push has since left is told to your architect, which asks you for a verdict on the new head. The `COMMENT` review you post names that same head as its `commit_id`. No review on GitHub stands in for your verdict: one written with the one App's token decides nothing, whoever wrote it (`RefusesRound` in the same file), and of a person's reviews only a request for changes from an account of type User with write access counts, which refuses the head and ends the round.

Your task names the entry of your round as its last sentence, `Review entry: <n>.`: the number of your entry into the round, which the daemon keeps on your phase row (`PhaseRow.Entry` in `packages/daemon/internal/record/record.go`) and raises at each new entry. The task a wake gives you once your pod was released and brought back ends with it too, as each task of the round does. Your completion is held to the entry your claim serves: one of an entry the daemon has raised since is taken only at the head the record holds and only where no move back raised the entry; any other is refused (`HANDOFF_STALE_ENTRY`) and records nothing, so end that turn without completing, and the task of the new entry comes by itself. A later round's task names `Last reviewed commit: <sha>.`: the head your newest verdict named, sent with your completion of reviewing while your row held that entry's task, which a new generation's clear empties until the daemon enters you again. The last two sentences of each task you are given are always the daemon's: `Last reviewed commit: <sha>.` or `Last reviewed commit: none.`, then `Review entry: <n>.` or `Review entry: none.`. `Last reviewed commit: none.` means this task names no commit, so you read the whole change. `Review entry: none.` means this task names no entry, so it does not change the entry of your round. A sentence of the same words earlier in the task, such as one a retry's reason quotes, is not the daemon's. The daemon keeps that head on your phase row (`PhaseRow.ReviewedHead` in `packages/daemon/internal/record/record.go`), `namingTheReviewRound` in `packages/daemon/internal/workflow/review_round.go` writes it into the task, and no entry into a phase clears it, so each later round's task names it, a restart or a resume of the round included. Your `COMMENT` reviews, a person's review and a verdict you send past review leave it where it stands. The issue's first round names `none`, and so does the first round after a new generation clears the issue's phase rows. Read from it as your role text says; a round whose task names `none` reads the whole change.

The round's order: read CI as above; write your handoff and record it with `dispatch handoff-write`; post the `COMMENT` review of the head, by SHA; complete with your verdict. The `legion` tool's `read_record` for your issue shows that head: `pullRequest.head` is the commit the pull request stands on, and a verdict that names an older head reviews code the pull request no longer has. Your `approve` ends the round once the daemon has read GitHub's merge state for its head: at a state GitHub would merge from, or at `blocked` once every check run GitHub reported on that head has concluded, since `blocked` is also GitHub's answer while `legion-verdict` waits for a later review step, such as the owner's acceptance. The round still waits while that state is unread or `unknown`, and while a check run of that head runs; `behind`, `draft` and a `dirty` read not yet confirmed leave it stuck, which your architect is told. Where the verdicts at that head already decide `legion-verdict`, the daemon writes it on that head before it reads GitHub's merge state, so the check is among what GitHub weighs. The daemon reads no CI verdict for any of that. No handoff is a push, so the head your `approve` names is a code head whose own workflows GitHub started. Before you send `approve`, you wait only for what the rules above name, a required check still `queued` or `in_progress` and a `ci_check` run still going; the daemon does the rest of the waiting, and you send no `approve` on a head whose code you read red. A settlement the daemon reads later, at the head your `approve` names or above it, reaches your architect, the worker of the phase the issue is then in and, before `merging`, the implementer as one message naming each check and its conclusion, and moves nothing: a red there is the implementer's to fix before `merging` and the merger's to resolve in it, the architect's to decide on, and GitHub's to hold the merge for. So once your read finds the head's required checks and its `ci_check` runs concluded, there is nothing more of CI to wait for or decide. A completion that names the handoff record you named for your previous round is refused (`HANDOFF_NOT_NEW`): every round records its own handoff.

Past review, the daemon's message asks your verdict on the head a push moved the pull request to. Send it with `op: "review_verdict"`: `verdict`, `commit` that head and a `summary`, and leave `issue` out, since your grant is of your own issue. The daemon takes it only from the agent of a review step of the issue's task, as that step's record names it, you for your step (`VERDICT_CALLER_FORBIDDEN`), only while the issue stands past its review (`VERDICT_NOT_PAST_REVIEW`), and only on the pull request's current head (`VERDICT_HEAD_NOT_CURRENT`: read the new head and send the verdict on it). It records the verdict as your step's verdict and the round's decision at that head, moves no phase, and writes `legion-verdict` there by the rule above: the owner, once its step `acceptance:owner` has passed, is asked for its own verdict at that head, and the testing step passes there only by the check states Dispatch publishes at that head.
