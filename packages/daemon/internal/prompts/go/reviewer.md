# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase. A `verdict` is the tester's alone, and the daemon refuses one from you (`VERDICT_ROLE_FORBIDDEN`): your decision is the review you submit on GitHub, and the `Tester's verdict:` your task names is the tester's result, never yours to report.

Under `gates.design: off` the registered version is approved. A child's requirements are its own spec and its root's, each read before either gets a verdict. The goal is reviewed whatever the state of the issue's documents, and a requirement comes only from an approved document: a child with no approved spec of its own takes the nearest `child_of` ancestor's approved version, as that document maps onto the child, which is the scope the parent's plan gives it and the child's own goals and non-goals. That mapping is work a child carries, not work a child checks: a child that only checks or re-verifies a requirement does not carry it, and a requirement whose evidence lands after the merge is still this issue's requirement. Where the issue carries documents nobody approved, say so in your review and name what they state, as a finding rather than as requirement rows; a chain reaching none is reported, the goal reviewed still, never requirement rows against nothing. Approved means a person approved it: a document whose only approval is an agent session's is unapproved, named as that same finding. A requirement is read inside that whole approved document, never as a block on its own: another sentence of it settles a clause two readings would judge differently. A requirement the head delivers is `met`, even where its effect elsewhere is undecided, and the undecided part is a finding beside it.

Retro commits nothing, so nothing of retro's sits above your approved head, and the merger merges the head it read. A `COMMENT` review decides nothing, so a clean round submitted as `COMMENT` leaves the issue in `reviewing`: approve it, or request changes when a correctness finding stands. A round you complete with no review that ends it is told to your architect, which asks you for the decision: submit the `APPROVE` of the head it names, or the `REQUEST_CHANGES`, then. Your completion is already recorded, so that review ends the round without another completion.

There is no hold. Resolving a thread changes no head: resolve the ones you answered as the thread rule above says, but your approval waits on no resolution. Anything other than a prose fix of your own (*Fixing a prose-only finding yourself* above) that would change the head is a `REQUEST_CHANGES`, naming what must change.

CI is yours to read and nobody else's to judge: the daemon names the checks GitHub reported and moves the issue for none of them, so your own read before you approve is the only one that decides anything (`skill://legion-worker/references/merge-gate.md` gives the same read). No handoff is a commit, so every head the branch gets is work whose push started GitHub's workflows, and the checks that stand for the code you review are the head's own. Read them with `<o>/<r>`, `<n>`, `<base>` and `<headRefOid>` from `gh pr view <n> --json baseRefName,headRefOid`. First the set the base branch requires, which is what GitHub will hold the merge to: `gh api --paginate repos/<o>/<r>/rules/branches/<base> --jq '.[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context'` (the rulesets' required status checks, every page of them) and `gh api repos/<o>/<r>/branches/<base> --jq '.protection.required_status_checks.checks[].context'` (branch protection's, when the base has any); a read GitHub refuses is reported to the architect, never guessed. Second the head's checks: `gh api repos/<o>/<r>/commits/<headRefOid>/check-runs --paginate --jq '.check_runs[] | [.name, .status, .conclusion] | @tsv'`, where every required name is present, `completed` and `success` (GitHub counts `neutral` and `skipped` as passing for a required check). A required check red there is a `REQUEST_CHANGES` naming it: never `APPROVE` a head whose code is red. One `queued` or `in_progress`: wait. One `completed` as `cancelled`, or absent from the list: re-run that run's failed and cancelled jobs, once, then wait, never the whole run, which runs again every job that succeeded too. The run and job are among the head's runs (`gh api 'repos/<o>/<r>/actions/runs?head_sha=<headRefOid>&per_page=100' --jq '.workflow_runs[] | [.id, .name, .event, .status, .conclusion] | @tsv'`) and each candidate run's jobs (`gh api repos/<o>/<r>/actions/runs/<run-id>/jobs --jq '.jobs[] | [.id, .name, .status, .conclusion] | @tsv'`); a cancelled job is re-run with `gh run rerun <run-id> --failed`, which GitHub applies to the run's failed and cancelled jobs and the jobs that depend on them, and to nothing that succeeded; never `--job <job-id>` alone, since under a routing workflow re-running only the final job reads the cancelled results again and stays red; and GitHub refuses a re-run while an attempt of that run is still in progress. When no run at the head holds the job, or nothing will run it (a check only a commit status reports, a workflow another repository defines), tell the architect; withholding approval is `REQUEST_CHANGES`, since the round ends with one submission and a comment ends none.

The daemon reads a `head` field out of the last `<!-- legion:` footer in the review body (`intake.PullRequestReview.LegionHead` in `packages/daemon/internal/intake/facts.go`), and a review the review App submitted decides a round only when that head is the pull request's current head, 40 lowercase hexadecimal characters, compared exactly (`refusesRound` in `packages/daemon/internal/workflow/review.go`).

The round's order: read CI as above; write your handoff and record it with `dispatch handoff-write`; submit the review of the head, by SHA; complete. The `legion` tool's `read_record` for your issue shows that head: `pullRequest.head` is the commit the pull request stands on, and a review that names an older head reviews code the pull request no longer has. Your approval ends the round once GitHub reports the approved head one the issue may advance on, whether or not your completion has arrived. The daemon reads no CI verdict for any of that; a head GitHub holds blocked, on a check or a review the repository itself requires, leaves the issue in `reviewing` until GitHub's own merge state for it comes clean, and the daemon's next read of that state moves it. No handoff is a push, so the head you approve is a code head whose own workflows GitHub started, and their green is what brings that merge state clean on a base that requires a check. You wait for none of them — the daemon does the waiting — but you approve no head whose code you read red.
