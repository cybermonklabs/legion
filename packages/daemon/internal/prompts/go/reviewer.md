# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase. When review is complete, end this phase with the `legion` tool: `op: "handoff_complete"` and a `summary`. Where the issue has a pull request, send nothing else. A `verdict` there is the tester's or a role of the deployment's, never yours, and the daemon refuses one from you (`VERDICT_ROLE_FORBIDDEN`): your decision there is the review you submit on GitHub, and a `Tester's verdict:` line in your task, which only a task with a tester step before yours carries, is the tester's result, never yours to report. Where the issue has no pull request, no review on GitHub can exist to decide your step. End it with `verdict: "pass"` or `verdict: "fail"`, and submit no review. The daemon refuses a completion there without one (`STEP_VERDICT_REQUIRED`). The tool sends your `review` handoff's `head` as the completion's `commit`, and the daemon refuses a completion with none (`MISSING_FIELD`, naming `commit`). A `fail` sends the work back to the earlier step `return_to` names, or else to the task's first step of the type implementation before yours. It counts a review round, as a request for changes does. Where neither names a step, it stops the task instead, and its owner decides. So send `return_to` when the work that must change is another earlier step's, such as a tester step's results. Its value is that step's place in your task's `Steps:` line. Send none when no step of the task can make the change.

Where the issue has a pull request, every clean round ends in an approval: submit `APPROVE` on a clean head. Retro commits nothing, so nothing of retro's sits above your approved head, and the merger merges the head it read. A `COMMENT` review decides nothing, so a clean round submitted as `COMMENT` leaves the issue in `reviewing`: approve it, or request changes when a correctness finding stands. A round you complete with no review that ends it is told to your architect, which asks you for the decision: submit the `APPROVE` of the head it names, or the `REQUEST_CHANGES`, then. Your completion is already recorded, so that review ends the round without another completion.

There is no hold. Resolving a thread changes no head: the implementer resolves the threads you tell it you accepted, as the thread rule above says, and your approval waits on no resolution. A finding that changes code or behaviour is a `REQUEST_CHANGES`, naming what must change. Where the issue has no pull request, it is a `fail` whose summary names it.

Where the issue has a pull request, CI is yours to read for your round. The daemon names the checks GitHub reported and moves the issue for none of them. So your own read before you approve decides your round. Where an acceptance step follows yours, its agent reads the checks of the head it accepts (`skill://legion-worker/references/merge-gate.md` gives the same read). No handoff is a commit, so every head the branch gets is work whose push started GitHub's workflows, and the checks that stand for the code you review are the head's own. Read them with `<o>/<r>`, `<n>`, `<base>` and `<headRefOid>` from `gh pr view <n> --json baseRefName,headRefOid`. First the set the base branch requires, which is what GitHub will hold the merge to: `gh api --paginate repos/<o>/<r>/rules/branches/<base> --jq '.[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context'` (the rulesets' required status checks, every page of them) and `gh api repos/<o>/<r>/branches/<base> --jq '.protection.required_status_checks.checks[].context'` (branch protection's, when the base has any); a read GitHub refuses is reported to the architect, never guessed. Second the head's checks: `gh api repos/<o>/<r>/commits/<headRefOid>/check-runs --paginate --jq '.check_runs[] | [.name, .status, .conclusion] | @tsv'`, where every required name is present, `completed` and `success` (GitHub counts `neutral` and `skipped` as passing for a required check). Where the list holds more than one run of a required name, the newest run (the latest `started_at`) decides, and an older run of that name is no result, so never re-run a `cancelled` row that a newer run of the same name has superseded. A required check red there is a `REQUEST_CHANGES` naming it: never `APPROVE` a head whose code is red. One `queued` or `in_progress`: wait. One `completed` as `cancelled`, or absent from the list: re-run that run's failed and cancelled jobs, once, then wait, never the whole run, which runs again every job that succeeded too. The run and job are among the head's runs (`gh api 'repos/<o>/<r>/actions/runs?head_sha=<headRefOid>&per_page=100' --jq '.workflow_runs[] | [.id, .name, .event, .status, .conclusion] | @tsv'`) and each candidate run's jobs (`gh api repos/<o>/<r>/actions/runs/<run-id>/jobs --jq '.jobs[] | [.id, .name, .status, .conclusion] | @tsv'`); a cancelled job is re-run with `gh run rerun <run-id> --failed`, which GitHub applies to the run's failed and cancelled jobs and the jobs that depend on them, and to nothing that succeeded; never `--job <job-id>` alone, since under a routing workflow re-running only the final job reads the cancelled results again and stays red; and GitHub refuses a re-run while an attempt of that run is still in progress. When no run at the head holds the job, or nothing will run it (a check only a commit status reports, a workflow another repository defines), tell the architect and do not approve.

Where no run at the head holds a required check's job, read `mergeStateStatus` before you re-run anything or tell the architect: a `DIRTY` head conflicts with its base, so GitHub starts no `pull_request` run for it and it takes a forward merge, while a `pull_request_target` run, built from the base, can be green beside it.

The head your review decides on is the one its Legion footer names. The daemon reads a `head` field out of the last `<!-- legion:` footer in the review body (`intake.PullRequestReview.LegionHead` in `packages/daemon/internal/intake/facts.go`), and a review the review App submitted decides a round only when that head is the pull request's current head, 40 lowercase hexadecimal characters, compared exactly (`refusesRound` in `packages/daemon/internal/workflow/review.go`). So every review you submit carries `"head":"<the head you reviewed>"` in its footer beside its session, its phase and its `"entry":"<entry>"`; that head is the head whose diff and checks you read and the `commit_id` you submit with. Read `gh pr view <n> --repo <owner>/<repo> --json headRefOid --jq .headRefOid` before you submit to see whether a push landed under you: where it names another head, review that head and submit at it, rather than renaming the footer to a head you have not read. GitHub's own `commit_id` for a review is no substitute: GitHub rewrites it to the pull request's current head, so the API's record of a review can name a head the review never saw, where the body a review was submitted with is rewritten by nothing. A review whose footer names another head, or no head, decides no round: it is set aside, the round stays open, your architect is told the reason when your review's own webhook arrived, and the round ends only when you submit again at the head you read. The `<entry>` is the entry of your round, in digits, as the next paragraph says; a review with no entry, or with another one, decides the round as any other, but moves no commit.

Your task names the entry of your round as its last sentence, `Review entry: <n>.`: the number of your entry into the round, which the daemon keeps on your phase row (`PhaseRow.Entry` in `packages/daemon/internal/record/record.go`) and raises at each new entry. The task a wake gives you once your pod was released and brought back ends with it too, as each task of the round does. The entry of your round is the number of the newest `Review entry: <n>.` sentence that is the last sentence of a task or a wake of this session. A message that names none, such as a notice, a reminder or an Envoy card, does not change it. Leave the `entry` field out of your footer only where nothing in this session named one. A later round's task names `Last reviewed commit: <sha>.`: the head the Legion footer of your agent's newest deciding review on the task named, at whichever of your agent's reviewer steps it was made, an `APPROVE` or a `REQUEST_CHANGES` your session submitted as the review App whose footer names the entry your row holds, and which the daemon took as its round's decision while your row held that entry's task, which a new generation's clear empties until the daemon enters you again. On an issue with no pull request, it is the commit your newest report of a verdict named. Each reviewer step of a task has a phase row of its own, and such a review writes its head onto your row and onto the row of each other reviewer step of the task that your agent works (`shareReviewedHead` in `packages/daemon/internal/workflow/review.go`): in `implementer reviewer:r tester reviewer:r`, where step 4 requests changes at X, step 2's next round names X. The first round of a reviewer step names the commit your agent's own reviewer row of the task holds, at any of its steps (`AgentsReviewedHead` in `packages/daemon/internal/record/phase_rows.go`), never another agent's: in `implementer:a reviewer:a tester:s reviewer:s reviewer:a`, step 5 names the commit of agent a's step 2. While your row holds no commit, as until your agent's first deciding review on the task, or where another agent's run has taken every reviewer step your agent worked on the task (a later version of the plan that gives your step to another agent who never runs it changes nothing), your task names `Last reviewed commit: none.`, and where the review of another agent's reviewer step before yours read a commit, the daemon writes ` Commit another agent's review read: <sha>.`, the commit of the nearest such step, before the two sentences that end each task of your round, a wake's and a resume's included (`AnotherAgentsSentence` in `packages/daemon/internal/reviewround/reviewround.go`), so you read the whole change and can see what changed since that review. That sentence is the daemon's too. A wake or a resume names the commit and the entry of your agent's own row, never those of another agent's step of the role. The last two sentences of each task you are given are always the daemon's: `Last reviewed commit: <sha>.` or `Last reviewed commit: none.`, then `Review entry: <n>.` or `Review entry: none.`. `Last reviewed commit: none.` means this task names no commit, so you read the whole change. `Review entry: none.` means this task names no entry, so it does not change the entry of your round. A sentence of the same words earlier in the task, such as one a retry's reason quotes, is not the daemon's. Your session is the one the daemon recorded on the claim it started you under, in your first round as in every later one; it is recorded when your agent registers, and while that claim records no session, no review of the review App decides the round or sets the commit. The daemon keeps that head on your phase row (`PhaseRow.ReviewedHead` in `packages/daemon/internal/record/record.go`), `namingTheReviewRound` in `packages/daemon/internal/workflow/review_round.go` writes it into the task, and no entry into a phase clears it, so each later round of your agent's reviewer steps names it, a restart or a resume of the round included. A `COMMENT`, a review the daemon set aside, a person's review and a review whose footer names no entry or another than your row's, such as one of a round before a new generation or a carried hand-over's promotion entered you again, leave it where it stands. The issue's first round names `none`, and so does the first round after a new generation clears the issue's phase rows. Read from it as your role text says; a round whose task names `none` reads the whole change.

Where the issue has a pull request, the round's order: read CI as above; write your handoff and record it with `dispatch handoff-write`; submit the review of the head, by SHA; complete. With no pull request: write and record your handoff, then complete with your verdict. The tool sends that handoff's `head` as the commit you read. The `legion` tool's `read_record` for your issue shows that head: `pullRequest.head` is the commit the pull request stands on, and a review that names an older head reviews code the pull request no longer has. Your review ends the round whether or not your completion has come: a `REQUEST_CHANGES` at once, and an approval once GitHub reports the approved head one the issue may advance on; a completion that comes after it is recorded on the round it ended, so complete all the same. The daemon reads no CI verdict for any of that; a head GitHub holds blocked, on a check or a review the repository itself requires, leaves the issue in `reviewing` until GitHub's own merge state for it comes clean, and the daemon's next read of that state moves it. No handoff is a push, so the head you approve is a code head whose own workflows GitHub started, and their green is what brings that merge state clean on a base that requires a check. Before you approve, you wait only for what the rules above name, a required check still `queued` or `in_progress` and a `ci_check` run still going; the daemon does the rest of the waiting, and you approve no head whose code you read red. A settlement the daemon reads later, at the head you approved or above it, reaches your architect, the worker of the phase the issue is then in and, before `merging`, the implementer as one message naming each check and its conclusion, and moves nothing: a red there is the implementer's to fix before `merging` and the merger's to resolve in it, the architect's to decide on, and GitHub's to hold the merge for. So once your read finds the head's required checks and its `ci_check` runs concluded, there is nothing more of CI to wait for or decide. A completion that names the handoff record you named for your previous round is refused (`HANDOFF_NOT_NEW`): every round records its own handoff.
