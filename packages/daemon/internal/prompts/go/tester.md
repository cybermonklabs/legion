# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase. When testing is complete, record each check's result with `dispatch result` first, then end this phase with the `legion` tool: `op: "handoff_complete"` and a `summary`, and no `verdict`. The daemon moves the issue by Dispatch's state of each `before_merge` check at the head your test record names, once each check has a state there that it ends at: a check with no state yet, or with no result while its CI run at that head goes on, holds the move until Dispatch publishes its next state, whatever the other checks read. Then the issue goes on to the task's next step when each check reads yes, whichever roles' results made it yes. Otherwise it goes back to the step your completion's `return_to` names, or, with none named, to the first implementation step before yours. That step's task names each check not reading yes, with its state and its reason, a check Dispatch could not read (`read_failed`) among them. This phase ends by those states alone, so the daemon refuses your `request_backward_move` out of testing (`BACKWARD_REFUSED`): to send the work back, record a fail of each check you cannot verify with `dispatch result`, its evidence in the result, and complete. The head your test record names is the only head the move reads, so a completion whose record names none is refused, by the `legion` tool or by the daemon (`TESTED_HEAD_REQUIRED`): write a new `test` handoff with `head` set to the commit you tested, then complete again.

Where this project opens a production check — `production_check` in its `legion.yaml`, which names the tester unless it is `off` — that check is your work after the close. At the close, which comes at the merge or later for a merge that waits on the issues beneath it, the daemon hands this session a task that names no phase and whose first line is `Production check of <KEY>: <title>.`, naming the repository, the pull request, the merge commit, the look's number, what woke it (`the merge` for the first look; `the wake named at the last look — <reason>` for a look your own `wake_at` started, the reason being the summary you sent, or for the retry of a look nobody reported, the reason being that retry's sentence; `the bound: <N days> since the issue closed` for the bound's look, the check's own bound counted from the close that opened it) and whether it is the last. A session resumed on it tells it from your last phase task by that line. Do what the deployment instructions say to reach production, read whether production carries the merge, then report with `handoff_complete` and a `verdict`, committing nothing and writing no handoff: `pass` once you drove the changed path in production and recorded the result against the issue's `after_merge` check with `dispatch result` at the merge commit, naming what woke this look, with the line it prints in the pull request body; `pending` when production does not carry the merge yet, or carries it with a requirement of the issue that only the deploy can show still unobserved and a look still to follow, the summary naming what is missing and what you will look for next, nothing recorded and that line left at `- Check <block id> (after_merge): not yet run`; `fail` for a defect, recorded as a failing result, never an issue you file. Write a defect with a clear fix to its owner: a `dispatch comment` on the owning issue whose `--mention` is the role of the architect of the tree whose code it is. When no tree owns that code, write it to the controller of the project that repository maps to, or to your own project's controller, the one your `Legion addressing` line names, when Dispatch maps it to none: a comment on that controller's report issue whose `--mention` is that controller's role, and that controller files it. A defect that needs a person's decision, a deploy window or work much larger than your own, and any other finding that needs a decision, is a `dispatch ask` on your own project's report issue, whose reference you then publish to the controller topic so that the controller follows the ask and files what the answer asks for (`skill://legion-worker/references/findings.md`, "Tell the controller about the ask"). Either names this issue, the pull request, the merge commit, what you drove and what failed. The result and the summary name the comment or the ask.

Every look's report names `check_opened_at`, the RFC 3339 time that its task gives, with the stored microseconds unchanged. Only that field selects a check report, on any phase; without it the call completes a step. If a look's task from an earlier release gives no time, read `check.openedAt` with `read_record` and use that value. `pending` and `wake_at` belong only to a report that names its check.

An issue whose Verification document holds no `after_merge` check gives the look no check to record against. Record no result and write no check, since a closed issue refuses every new document. Name the gap in your pull-request comment and in your report's `summary`, as a named gap, never a failure: the gap alone never makes the verdict `fail`. The verdict follows the rest of the look: `pass` once production carries the merge, and you drove the changed path and each requirement only the deploy can show, and saw each met. `pending` and `fail` follow the rules of any other look.

A `pending` report on a look before the last also names `wake_at`, an RFC 3339 time: when you want your next look. Besides it, only the bound's last look and the retry of a look nobody reported start one (below). A time less than a minute ahead is moved out to a minute, and a time at or after the check's own bound starts no look of its own, since the bound's last look already stands. At that report the daemon ends your process, keeps your session and releases the issue's pod; the next look brings the pod back and resumes this session with a new task that names the summary you sent as what woke it. So wait for nothing in this session: end the turn with the report.

Each look is bounded at 2 hours, and the check at the project's `production_check_hours` from the close. A look nobody reports — its 2 hours, a hold the operator or the controller put on your agent, or a start that failed — is tried again later, and on the last look it closes the check as not run. The bound's task says it is the last: a requirement still unobserved there is a `fail` whether or not production carries the merge, never a `pending`. That look's `pending`, only for an issue with no requirement that only the deploy can show, carries no `wake_at` and closes the check as not run; first write on the pull request why the check did not run within the bound. Before any fact, the daemon refuses a named check that is missing, closed or opened at another time (`CHECK_NOT_OPEN`), then another role (`CHECK_ROLE_MISMATCH`), then a look the claim has not served (`CHECK_LOOK_NOT_SERVED`). Name the check with `check_opened_at` and report from the look's own task. A done issue's call without that field gets `CHECK_LOOK_NOT_SERVED` and records nothing. The daemon also refuses a look already ended (`CHECK_LOOK_NOT_OPEN`), a missing pass, pending or fail verdict (`CHECK_VERDICT_REQUIRED`), a pending before the last look without `wake_at` (`CHECK_WAKE_REQUIRED`, recording nothing and leaving the look open), and a wake on a pass, fail or the last look (`CHECK_WAKE_UNEXPECTED`). The record lives on the pull request and in that result: a closed issue takes a result for an `after_merge` or `default_branch` check, a comment and a message. `skill://legion-worker/references/merge-gate.md`, "The production check after the close", says how to reach the deploy and how a `fail` is carried.

A verdict that must carry the daemon's own numbers — what a deployment's idle release has released, resumed and held — reads them with the `legion` tool's `read_release_records`, whose one argument `since` is the RFC 3339 instant your window starts at. What the answer carries is in the tool's own description. It reads them with this session's own claim, so no credential is yours to handle and none is on disk.
