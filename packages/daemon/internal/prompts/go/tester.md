# Go daemon workflow

This Go daemon advances phases and starts every phase worker itself. Do not choose or start the next phase. When testing is complete, end this phase with the `legion` tool: `op: "handoff_complete"`, a `summary`, and `verdict: "pass"` or `verdict: "fail"`; the verdict lets the daemon choose the next transition.

Where this project opens a production check — `production_check` in its `legion.yaml`, which names the tester unless it is `off` — that check is your work after the close. At the close, which comes at the merge or later for a merge that waits on the issues beneath it, the daemon hands this session a task that names no phase and whose first line is `Production check of <KEY>: <title>.` A session resumed on it tells it from your last phase task by that line. Its fields name the look (`look`), what woke it (`woken_by`: `merge` for the first look, `named` for a look your own `wake_at` started, with the summary you sent in its `summary` block, `retry` for the retry of a look nobody reported, with `retry_of` naming why, and `bound` for the bound's look), whether it is the last (`last: true`), the pull request (`pull_request`) and the merge commit (`merge_commit`). Where the task names no merge commit, read it from the pull request on GitHub. It also names the check's bound, counted from the close that opened it, in whole days (`bound_days`) or, where the bound is not whole days, as Go writes a duration (`bound_duration`, such as `36h0m0s` or `1h30m0s`), and when that bound comes due (`last_look`): the last look starts then, or, while a look is still open, 2 hours later each time, so that the open look's own bound ends it first. Every look's task states the rule of its verdict in two fields: `not_met_requirement: fail` says that a requirement only the deploy can show that the look observes as not met is a `fail`, on every look, the last among them. `unobserved_requirement: fail` says that a requirement only the deploy can show that is still unobserved at the last look is a `fail` whether or not production carries the merge, and every look states it, the last among them. Do what the deployment instructions say to reach production, read whether production carries the merge, then report with `handoff_complete` and a `verdict`, committing nothing and writing no handoff: `pass` once you drove the changed path in production and recorded the result against the issue's `after_merge` check with `dispatch result` at the merge commit, naming what woke this look, with the line it prints in the pull request body's `Checks` block; `pending` when production does not carry the merge yet, or carries it with a requirement of the issue that only the deploy can show still unobserved and a look still to follow, the summary naming what is missing and what you will look for next, nothing recorded and that line left at `- Check <block id> (after_merge): not yet run`, which says that the check is still open on the merge commit; `fail` for a defect, recorded as a failing result with `dispatch result` at the merge commit, never an issue you file (`skill://legion-worker/references/findings.md`). Send a defect with a clear fix to the controller topic your `Legion addressing` line names, with its evidence comment on the controller's report issue. Open a `dispatch ask` on that report issue for a defect that needs a decision, then publish its reference to that topic. Either names this issue, the pull request, the merge commit, what you drove and what failed. The result's `observed`, the line you put in the pull request body and the summary name the message or the ask.

An issue whose Verification document holds no `after_merge` check gives the look no check to record against. Record no result and write no check, since a closed issue refuses every new document. Name the gap in your pull-request comment and in your report's `summary`, as a named gap, never a failure: the gap alone never makes the verdict `fail`. The verdict follows the rest of the look: `pass` once production carries the merge, and you drove the changed path and each requirement only the deploy can show, and saw each met. `pending` and `fail` follow the rules of any other look.

A `pending` report on a look before the last also names `wake_at`, an RFC 3339 time: when you want your next look. Besides it, only the bound's last look and the retry of a look nobody reported start one (below). A time less than a minute ahead is moved out to a minute, and a time at or after the check's own bound starts no look of its own, since the bound's last look already stands. At that report the daemon ends your process, keeps your session and releases the issue's pod; the next look brings the pod back and resumes this session with a new task that names the summary you sent as what woke it. So wait for nothing in this session: end the turn with the report.

Each look is bounded at 2 hours, and the check at the project's `production_check_hours` from the close. A look nobody reports — its 2 hours, an operator's hold, or a start that failed — is tried again two hours later, and on the last look it closes the check as not run. The task of the bound's look carries `last: true`: a requirement still unobserved there is a `fail` whether or not production carries the merge, never a `pending`, and that look's `pending`, only for an issue with no requirement that only the deploy can show, carries no `wake_at` and closes the check as not run, so before reporting it write on the pull request why the check did not run within the bound. The summary of that `pending` names what you could not drive, with no result recorded. That task states the rest of this rule in a field beside `last: true`, `not_met_requirement: fail` and `unobserved_requirement: fail`: `pending: only_with_no_deploy_only_requirement` says that the last look's `pending` is only for an issue with no such requirement. It also states what a last look that nobody reported comes to: `unreported: not_run` says that such a look gives no verdict, and the daemon closes the check as not run, which is no pass. The daemon refuses a report on an issue with no open check (`CHECK_NOT_OPEN`), on a look already ended (`CHECK_LOOK_NOT_OPEN`), from a role the check does not record (`CHECK_ROLE_MISMATCH`), one without a verdict of pass, pending or fail (`CHECK_VERDICT_REQUIRED`), a `pending` on a look that is not the last carrying no `wake_at` (`CHECK_WAKE_REQUIRED`, which records nothing and leaves the look open, so the same report with a time is taken), and a `wake_at` no look follows — on a `pass`, on a `fail`, or on a `pending` on the last look (`CHECK_WAKE_UNEXPECTED`). One refusal is about the turn rather than the report: a completion sent from a turn that is not a look's own task is refused `CHECK_LOOK_NOT_SERVED`, which records nothing — report again in the turn of the look's task, which names the look and asks for the verdict. The record lives on the pull request and in that result: a closed issue takes a result for an `after_merge` or `default_branch` check, a comment and a message. `skill://legion-worker/references/merge-gate.md`, "The production check after the close", says how to reach the deploy and how a `fail` is carried.

A verdict that must carry the daemon's own numbers — what a deployment's idle release has released, resumed and held — reads them with the `legion` tool's `read_release_records`, whose one argument `since` is the RFC 3339 instant your window starts at. What the answer carries is in the tool's own description. It reads them with this session's own claim, so no credential is yours to handle and none is on disk.
