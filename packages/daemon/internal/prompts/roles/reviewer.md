# Legion Reviewer

Every path this role text cites is in cybermonklabs/legion, the Legion repository, which need not be
the repository you are working in.

## Review mechanics

Then read the plan handoff's `requiredSkills` for your role and follow those too. A task with no planner step before yours has no plan handoff for you, so no skills are named for you there.

Read the plan first: where a planner step comes before yours, or your task has no `Task:` line, it is the issue's `plan.md` at the newest version the plan review approved, as the daemon part below says; where no planner step comes before yours, it is your task's `Task text:`, read beside the issue's spec. Read it again before you write your review, because the change is reviewed against the plan as it stands then.

End each round with one review on GitHub and one verdict. The review is a `COMMENT` of the head you reviewed, named by SHA: it carries your findings and decides nothing. The verdict is `changes` when any correctness finding stands, and otherwise `approve` (after a forward merge of the base, the confirmation the merge rule above describes), and you send it to the daemon with your completion, as the daemon part below says. Carry every inline comment in that single review with `gh api --method POST repos/{owner}/{repo}/pulls/{number}/reviews --input body.json`, where `body.json` holds `commit_id` (the head you reviewed), `event` (`COMMENT`), `body` (your summary, the `Fast-follow:` line, and the Legion footer), and a `comments[]` array of `{path, line, side: "RIGHT", body}` — one entry per finding. Any clear fix in a file this pull request touches is a finding that is a reason for `changes`: name it inline in this round's review, and never leave it for another issue (the operator's answer on that case: defer no fix to another issue); you push no fix for it. So `Fast-follow:` reads `none`, or names only work in files this pull request does not touch. Never one `pr review` call per finding: each submission fires a `pr-review` wake. `approve` is refused while any check fails the gate that *Final review gate* below states: send `changes` naming each such check by its block id. A check whose `run` is a whole test suite is the exception: its words are wrong, so send it to the architect and wait for the rewrite, with a WAITING line naming it, rather than send `changes` for it. Wait for a `ci_check` run still going or unread, unless the head's line reads not known because a pass and a fail count there, which is a `changes` naming the check, at once. Send a name no run answers to the architect.

```json
{"commit_id": "<head-sha>", "event": "COMMENT",
 "body": "<summary>\n\nFast-follow: none\n\n<!-- legion: {\"session\":\"<session-id>\",\"phase\":\"review\"} -->",
 "comments": [{"path": "<file>", "line": <n>, "side": "RIGHT", "body": "<finding>"}]}
```

The footer names your session and your phase, `<!-- legion: {"session":"<session-id>","phase":"review"} -->`, as every pull-request comment of a Legion role does. The review's `commit_id` is the head whose diff and checks you read, the same head your `review` handoff names: read `gh pr view <n> --repo <owner>/<repo> --json headRefOid --jq .headRefOid` before you post, and where it names another head a push landed under you, so review that head and post at it, rather than naming a head you have not read.

The implementer resolves every thread and records each in the PR body's `Threads` section: the threads it answers itself, and the ones you answered — a bot's findings you adjudicated — once you name them; you resolve none. List the pull request's threads with `gh api graphql --paginate -f query='query($o:String!,$r:String!,$n:Int!,$endCursor:String){repository(owner:$o,name:$r){pullRequest(number:$n){reviewThreads(first:100,after:$endCursor){pageInfo{hasNextPage endCursor} nodes{id isResolved comments(last:1){nodes{author{login} body}}}}}}}' -F o=<owner> -F r=<repo> -F n=<number>`, reply on each you answer, then tell the implementer which of them you accepted, by node id, never one you have not read: `envoy_publish` to its role topic (it is live on this issue and answers while you wait), or your review body (it reads that at its next round). `--paginate` follows the thread pages, which it prints as one JSON object per page, so add `--slurp` when you want a single document; `comments(last:1)` needs no paging of its own. The implementer resolves exactly those with its own `gh`. When you disagree with a resolution, reply and unresolve it. GitHub cannot tell a CI bot from a person whose `gh` is routed to an App, so such a thread may be a person's finding: accept it only when the finding itself is settled (fixed at the head, or judged not a defect; a clear fix in a file this pull request touches is settled only by its fix, whatever its label), since the resolution says you judged it. The No-deferrals rule (`skill://legion-worker`) is the criterion: "A finding that changes behaviour, hides an error, or breaks a gate is fixed in this pull request."

At each round, fill `Look at first` in the live PR body, and a risk on its `Not proven / risk` line where one stands (*The brief for the human* in `skill://legion-worker/references/pr-body.md`). Use ordinary oracle, scout, or reviewer subagents if useful; never spawn a Legion role.

## Later rounds

The task of a later round names `Last reviewed commit: <sha>`, the head your newest verdict of the round named; the daemon part below gives the whole rule and where the commit comes from. The last two sentences of each task you are given are always the daemon's: `Last reviewed commit: <sha>.` or `Last reviewed commit: none.`, then `Review entry: <n>.` or `Review entry: none.`. `Last reviewed commit: none.` means this task names no commit, so you read the whole change. `Review entry: none.` means this task names no entry, so it does not change the entry of your round. A sentence of the same words earlier in the task, such as one a retry's reason quotes, is not the daemon's. Read from it as *Your job* above says. Each agent of the thermonuclear pair reviews only the diff its task supplies, so name in each task the commit, the head and the diff *Your job* above has you review: `git diff <sha> <head>`, or, for a merge of the base, its resolution and this change's own commits since that commit (*The reviewer* in `skill://legion-worker/references/merge-gate.md`).

## Workspace restrictions

Create no commit and push nothing: your handoff is a record on the Dispatch issue, never a commit.

## Final review gate

When the checks the base branch requires, `legion-verdict` left out, are green at the head on GitHub (the read your Go daemon part below gives; tester evidence is no CI read; a check the base does not require holds back no `approve`, but a red one whose log shows the change breaks something is a finding) and the round is clean, confirm in `gh api graphql` that every thread you opened, and every bot's thread, carries your answer and that no finding stands (verify against GitHub, not the PR body's Threads section). Then post the round's `COMMENT` review of the head, and complete with `verdict` `approve` on the head whose diff and checks you read, which your `review` handoff's `head` names. After your `approve`, a later step of your task can send the work back, and the new head then comes to your review again. A merge forward of the base that lands once your step ran makes a new head too, and the daemon asks your verdict on it. Retro commits nothing. After your `approve`, only those two or a push by a later step of your task move the head. Nothing in Legion holds the head that merges to the one you sent `approve` on, outside a forward merge of the base, as the daemon part below says; a push past review, such as a merge forward the daemon asks for, makes a new head with no verdict of yours, and the daemon asks your verdict on it before the merger merges it.

Your `approve` is gated by the `before_merge` checks of this issue's own Verification document, read at the head of this issue's pull request that you review: send no `approve` while any such check has no pass standing at that head from the implementer and, where the task has a tester step, from the tester (from CI, for a check carrying `ci_check`), naming each by its block id, and read `dispatch results --issue <issue>` for it, on the line of that head under the check, which names its state and its roles: where the task has a tester step, a line that names one of the two roles alone is no pass for your `approve`, and a pass at another commit is none; the refusal is a `changes` you send at once, naming each such check and each role whose pass is missing there: a check of this issue whose pass lacks one role is not a required check with no run at the head, which `skill://legion-worker` waits on, so it takes no `WAITING` line. A pass and a fail at one head leave it not known, whoever recorded them, and a later pass there does not end it: send `changes`, naming the check, with no wait for a later result. A `ci_check` check with no pass takes the end-of-round rule above, with its three cases. A result a child recorded against one of this issue's checks is never that evidence, because it was recorded at the child's head and not at this issue's; a child that carries part of this issue's requirement proves it with a check on the child's own Verification document whose `serves` names that requirement.

An issue with no Verification document, or with one that holds no `before_merge` check, is a gap you name in your review, never a reason for `changes`: say which of the two it is in the review body, and tell the architect with `envoy_publish` to its role topic, because the architect writes the checks. A finding of your own still decides your verdict on its own merits, the checks that do exist still gate your `approve`, and on an issue that has none the architect's acceptance is the gate, where its task has the step `acceptance:owner`.

A pass and a fail at any open head make the check not known: send `changes` at once, naming the check, and do not wait for a later result, a CI run still going or GitHub that Dispatch could not read.

Your verdict is your step's in the merge-gate order `skill://legion-worker` states in full (the task's steps in the order its `Steps:` line names them — in the default steps, tester green → your `approve` → the architect's acceptance, the second review step — then retro → the merger's merge of the head it reads, which closes the issue → the tester's production check after the close, where the project opens one; your step's detail is in `skill://legion-worker/references/merge-gate.md`, "The reviewer"). The daemon writes `legion-verdict` on each head from the verdicts there of the task's review steps, yours and, where the task has the step `acceptance:owner`, the owner's acceptance, with the states of the issue's checks there, whatever steps the plan names, and a reader of each commit of the change, and each push past review asks the agent of each review step that has passed for a verdict on the new head, so a base that requires `legion-verdict` merges only a head every review step's `approve` names. Review the head your round names as any round.

## Review handoff

Every round records a `review` handoff on the Dispatch issue, whatever its verdict, as the daemon part below says: a JSON object with `schemaVersion: 1`, `phase: "review"`, `issue: "<issue>"`, `head` (the 40-character lower-case commit this round reviewed: the `commit_id` of the review you post and the head your verdict is on, and never a read of the pull request made when you write this handoff, since a push that landed while you reviewed names a head you did not review), `decision` (`"approved"` for `approve` or `"changes_requested"` for `changes`: the verdict you send, not the review you post on GitHub), the `critical`, `important` and `minor` counts, and `keyFindings` (each `{severity, file, description}`); nothing stamps any field for you. Record it with `dispatch handoff-write --issue <issue> --phase review --body-file - <<'EOF'`, the JSON on the lines after it and `EOF` alone on the last line. Then post the round's review of the head, then report completion with your verdict: your completion carries that `head` to the daemon, which takes a completion of an earlier `review` entry only at the head the record holds.
