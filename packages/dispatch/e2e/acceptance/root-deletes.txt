# What this change keeps for one release, for the root's own pull request to delete
# (dispatch://INFRA-1150's pull request, which lands after this one).
#
# One line for each kept thing: its id, a tab, the thing, a tab, and what holds it - the condition
# the root's architect reads before deleting it, and the tests that hold it now. Every place in the
# repository that serves a kept thing carries one comment `kept for one release: <id>`, the id the
# last thing on its line, in Go, SQL, TypeScript and YAML alike, on the line that serves it or the
# line above it. .github/scripts/check-kept-for-one-release.sh (ci.yaml's lint job) fails on a
# comment whose id this file does not list and on a listed id no comment names.
asks-arms	The `anchored_to` and `owned_by` arms of graph_edges over `asks`, the `followed_by` arm over `ask_followers`, and the tuple arm's three joins to those rows (migrations 20261125163553 and 20261125163554)	The arms answer every row whose `node_kind` is null, so they go only once no such row exists in production, which the root's architect reads as two read-only counts that must each answer 0: `select count(*) from public.asks where node_kind is null` and `select count(*) from public.ask_followers where node_kind is null`. This build writes such rows itself: an asks row that names no node for every ask that relates to a document whose address is past the store's 1,024-byte bound (graphstore.AskFacts and AskPlaces.Fit in packages/envoy/internal/dispatch/graphstore/ask.go write the ask's node and mark no row, the decisions step's backfill skips such a row, askRowsOwed in graphcensus/backfill_asks.go, and no other write marks it), so while a document past the bound holds an ask the count over `public.asks` stays above 0 and the arms stay for its rows; and an ask_followers row that names no node for a session whose id is past that bound (queueFollow in asks/followers.go), since a follower row of an ask whose node stands, a past-bound document's ask's among them, names that node. Every other such row is one the decisions step's backfill marks (graphcensus.AsksOwed): a row a process of an earlier build wrote, or a follower row of an ask such a process made, written before the backfill wrote the ask's node. And the build a rollback would reach announces anchored_to, owned_by and followed_by in server_build_announcements.tuple_kinds (refs.TupleKinds), so it writes them as tuples too; TestTheAsksArmsAnswerEachRowOnce, TestGraphEdgesLosesEveryArmOverAMovedKind (docs/graph_edges_cutover_test.go)
catch-up	The decisions step's catch-up of the ask events a process of another build appended on a row this build marked (its phase 2), and keptFromItsNode, by which a write on a fleet of one build keeps an ask's kept state as its row holds it while the catch-up owes the ask's node that row's state	The catch-up's last pass has run clean once the fleet is one build: the first tick that finds no process of another build live (DecisionStep.anotherBuildLive) runs one more pass, and a pass on which an ask fails, or that fails itself, leaves that pass owed to the next tick (catchUpOwed in packages/envoy/internal/dispatch/docs/decision_step.go), so the code serves nothing once a pass on such a tick has run with no failure. An ask whose row names no node needs nothing of the catch-up, which catches up only a row this build marked: one on a document whose address is past the store's 1,024-byte bound is never marked, and onItsNode in packages/envoy/internal/dispatch/docs/ask_roll_window.go keeps such an ask as its row holds it, under stored-ask-state, where keptFromItsNode compares with the row only a node the row names. A clean pass writes no log line and /healthz has no field for it; a failed pass writes `dispatch: decisions step could not catch up an ask; the next tick tries again` or `dispatch: decisions step catch-up; the next tick tries again`, and a tick that fails its probe or its lock writes `dispatch: decisions step tick; the next tick tries again` and runs no pass (catchUp, Tick and Run in that file). So the root's architect reads it in Dispatch's log: every process has answered /healthz with a `fleet_commit` equal to its `commit` (healthzHandler in packages/envoy/cmd/dispatch/main.go) for longer than two of the step's 30-second ticks (BlockIndexReconcileInterval), and no process has written any of those three lines in the last two ticks; TestTheCatchUpStatesAWriteCommittedBetweenItsReadAndItsLock, TestACatchUpPassNeverReadsAgainAnEventAPassBeforeItRead, TestTheCatchUpOfARollForwardAfterARollbackStatesWhatTheReleaseBeforeWroteInBetween (docs/decision_step_test.go), TestAVersionWrittenBeforeTheCatchUpKeepsTheAnswerTheReleaseBeforeWroteIntoTheRow (docs/ask_roll_window_test.go), TestThePreviousReleasesCLIRequestsApprovalOverAnAskItAnsweredBeforeTheCatchUp (cmd/dispatch/twobuild_previous_cli_test.go)
