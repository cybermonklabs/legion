Find the message you see. `agent-secrets` prints a broker refusal as
`<message> (<CODE>) (answer <id>)` and a helper refusal as `<CODE>: <message>`; the
[error reference](/legion/broker/reference/errors/), generated from the code, lists every code. For
a refusal, an answer from 400 to 499 but a `429`, the answer id names the broker's own log line
for it, so quote it to whoever runs the broker
([Refusals and the answer id](/legion/broker/operate/#refusals-and-the-answer-id)). A `429` and a
failure of 500 and above print an id too, which names no line. For `MINT_FAILED`, tell whoever
runs the broker the secret's name and the time instead: its `broker: mint failed` line names
both. A broker from before the answer id sends none, and the message then ends at `(<CODE>)`.
Every message about a secret also names where `agent-secrets` looked - `the broker
AGENT_SECRETS_URL names (<store kind>)`, or `the broker AGENT_SECRETS_URL names` alone where the
broker did not say what its store is - so a message of this CLI's is never read as another
secrets CLI's about the same name. It names no host, account or project; a message about a broker
that was never reached names the address it tried when that address is a plain http(s) URL, and
says `(not printed: the value carries a credential or is not a plain http(s) URL)` instead when
it carries a user name, password, query, fragment or `%` escape, with the failure named by its
class alone (`connection refused`, `name resolution failed`, `timed out`, and so on). The
messages below leave that part and the answer id out.

## The session has no broker identity

| Message | Cause | Fix |
| --- | --- | --- |
| `AGENT_SECRETS_URL is required: it names the secrets broker this command reads every secret from, and this command reads no local secrets file` (exit 2) | The process does not know the broker's address, and this CLI answers from no other store. | Set `AGENT_SECRETS_URL` to the broker's public URL, or write `AGENT_SECRETS_URL=<url>` in `~/.config/agent-secrets/config`, which a process with no such variable reads (a systemd unit, a cron job). A command run by `agent-secrets NAME -- …` keeps the variable. |
| `no broker identity for this process: key-dir: …; sign-in: …; helper: …; machine: …` (exit 1) | None of the four sources a command takes its identity from has one for this process, and each names why ([where a command takes its identity](/legion/broker/concepts/#where-a-command-takes-its-identity)). `helper: this process is in no session the helper … registered` is a process that inherited `AGENT_SECRETS_HELPER_SOCK` but descends from no session `agent-secrets register` started; the helper is skipped for it rather than refusing. A Kubernetes pod that enrolled itself with `agent-secrets enroll --pod --out <dir>` reads `key-dir: no key.pem in …` when a later command does not name `<dir>`: `--out` writes the key there, and every other form finds it only through `AGENT_SECRETS_KEY_DIR`. | Set up any one source. On a Google Cloud VM, or a GKE pod whose metadata server answers for its own Google service account, nothing more is needed once the broker names its Google exchange audience: `machine: the broker at … names no exchange audience` is a broker that accepts no machine identity, and `machine: GOOGLE_APPLICATION_CREDENTIALS is unset; no Google metadata server` a machine with none (on EC2, always). A pod's projected Kubernetes token is never the machine's identity, since the broker mints no launcher credential for it. A person signs in with `agent-secrets login`; an agent runs under `agent-secrets register --wait 10 --exec -- <agent>`; a container's launcher enrolls it. In a pod that enrolled itself, run the command `enroll --pod` printed, which names the key directory (`AGENT_SECRETS_KEY_DIR=<dir> agent-secrets renew --pod-token-file <file>`), or export `AGENT_SECRETS_KEY_DIR=<dir>` for the pod. A unit or a cron job with no environment reads `AGENT_SECRETS_URL` and the sign-in settings from `~/.config/agent-secrets/config`. `agent-secrets identity --source` prints the source a command would use. |
| `agent-secrets-helper at … did not answer: the socket AGENT_SECRETS_HELPER_SOCK names is absent, so the helper is stopped …`, or `… the socket is absent and the helper is installed (…), so the helper is stopped …` (exit 1) | The process names the helper's socket, or the helper's unit is installed on this machine, and the socket is gone: the helper is stopped or restarting (a clean stop removes the socket). The command stops rather than act as the machine's own identity, since a process in one of the helper's sessions is not the machine. | Start the helper (`systemctl --user start agent-secrets-helper`) and run the command again. A process that is in none of its sessions, such as a cron job, unsets `AGENT_SECRETS_HELPER_SOCK`; on a machine with the helper installed it takes the machine's identity only while the helper runs and answers that the process is in no session. |
| `AGENT_SECRETS_KEY_DIR holds enrollment.pending and no key.pem yet: the launcher that wrote it is still enrolling this process (waited …, its bound …, while AGENT_SECRETS_KEY_DIR held enrollment.pending)` (exit 1; the key dir is named by its setting, or by its default where that is unset, never by its path; the first time is how long the command waited, the second `AGENT_SECRETS_ENROLL_WAIT`) | A box's or a pod's launcher is still enrolling it and wrote no `key.pem` within `AGENT_SECRETS_ENROLL_WAIT`. The command stops rather than act as another identity. | Wait for the launcher, or raise `AGENT_SECRETS_ENROLL_WAIT`. A marker older than 160 seconds is a launcher that died, and no longer stops anything. |
| `the broker at … names "…" as its Google exchange audience, and this machine first read "…" there (kept in google-exchange-audience in the machine cache (${XDG_STATE_HOME:-$HOME/.local/state}/agent-secrets/machine))` (exit 1) | `GET /v1/settings` named a Google audience other than the one this machine first read there. Either `AGENT_SECRETS_URL` now names another broker, or the broker's `BROKER_GOOGLE_OIDC_AUDIENCE` changed. No identity token was minted for the new audience. | Check `AGENT_SECRETS_URL` first. Only if the broker's audience really changed, remove the file the message names and run the command again. |
| `AGENT_SECRETS_URL "…" must be https, or http only when the broker's host is loopback …` (exit 2) | The broker's address is plain `http` to a host on the network, and the command was about to act on its settings: a secret form, or the machine source reading the audience it mints its identity token for. | Use the broker's `https` address. |
| `the settings file …/config can be written by its group or by others (mode …) …` (exit 2), `the settings file …/config is owned by uid …, not by this user …` (exit 2), or `the settings file …/config is not a regular file …` (exit 2) | `~/.config/agent-secrets/config` names the broker this machine proves its identity to, and someone other than its user (or root) could change it, or the path is a directory, a FIFO or another file that is not a regular one. Nothing in it was read. | Make it a regular file the user owns (`chown`), then `chmod go-w ~/.config/agent-secrets/config`. |
| `NOT_ENROLLED: this session is not enrolled with the broker yet` | The session registered, but the helper has not enrolled it yet: it was started without `--wait`, or the broker was unreachable. | Start sessions with `--wait 10`. If it persists, check the helper's log and that `AGENT_SECRETS_URL` reaches the broker. |
| `agent-secrets register: the broker refuses to enroll this session, and the helper asks no more: broker 403 RESTRICTED_MEMBER_ENROLLS_NOTHING: …` (exit 1), `agent-secrets register: the broker refuses to enroll this session, and the helper asks no more (…); launching anyway, with no secrets access` (`register --exec`), or `NOT_ENROLLED: the broker refuses to enroll this session, and the helper asks no more: …` | The machine login's person is someone Dispatch calls a restricted member: a person an access list admitted from outside the deployment's sign-in domain. The broker enrolls no session under such a login and releases no secret to that person's agents, whoever approved the login, so the helper made one enroll call for the session and stopped. The session's state reads `refused`. A `register` made after the refusal, or one given `--wait`, exits 1 naming it; the first `register` without `--wait` can answer before the helper's call and exit 0. `register --exec` launches its command all the same, with no secrets access, and says so. | Nothing to retry. The session stays refused until it is relaunched: a later machine login on the same machine, another person's included, does not enroll it, so relaunch the session after that login. A restricted member's agents reach Envoy and Dispatch with the token their device login trades for, and take no secret from the broker. |
| `… (MEMBER_KIND_UNCHECKABLE)`, or `broker 503 MEMBER_KIND_UNCHECKABLE: whether Dispatch calls … a restricted member cannot be read: …`, from an enrollment, a request or a release, or on Dispatch's pages from a dismissal, a deny of a service's machine login or a grant's revoke | The broker asks Dispatch what kind of member a person is (`BROKER_PROJECT_ACCESS_URL`), and could not get an answer, as the message's last words say: `the broker could not ask Dispatch` (Dispatch did not answer, or the request ended first), `Dispatch refused the broker's own account`, `Dispatch answered a member kind this broker does not know`, or `Dispatch answered what the broker cannot read` (another status or code, a body that does not decode, a certificate that does not verify, a name that does not resolve). A check that cannot decide refuses, so nothing was enrolled, decided, released, dismissed or revoked. A dismissal asks only when it would act as the record's approver, a deny only for a service's login, and a grant's revoke only when it would act as the grant's approver, since a restricted member is no approver of a secret or of a service's machine login. While Dispatch does not answer at all (a timeout, a failed connection, a gateway's `502`, `503` or `504`, Dispatch's own `DATABASE_UNAVAILABLE` or `OIDC_ISSUER_UNAVAILABLE`, or a `500` that names no code or names `INTERNAL`, which is how Dispatch answers while its database fails), only the person a grant names as its approver ends it through the broker as an approver, since a revoke only takes access away; every revoke through a group or as anyone is refused then, whatever session holds the grant. A grant on your own session you still end as its operator, asking nothing; a grant on a session that acts for no person (a service's pod, a person's pod `BROKER_POD_OPERATORS` no longer maps, or a machine's own session) nobody but its named approver ends through the broker until Dispatch answers, and what remains meanwhile is cluster access: delete the pod. The machine-login page and its revoke never answer this: while the kind cannot be read they hold you to your own machine logins, which you can still end. The broker waits at most 2 seconds for the member-kind answer, so a Dispatch that does not answer gives this refusal and not a timeout. | Ask again: the helper enrolls again on its own, and a command can be run again. If the message names the broker's own account, or it keeps happening, tell whoever runs the broker. |
| `this machine's agent-secrets-helper holds no credential at the secrets broker; not an agent session (the helper: no machine credential; run: agent-secrets machine login, and have a human approve it)` | The helper holds no machine credential: the machine was never logged in, its login lapsed or was revoked, or its machine file (`AGENT_SECRETS_MACHINE_FILE`) is gone. A helper in identity mode (`AGENT_SECRETS_MACHINE_IDENTITY`) says instead that its trade loop is trading this machine's identity for a new credential: its broker refused or did not answer its trades for longer than the credential lives. | [Log the machine in](/legion/broker/guides/log-a-machine-in/). In identity mode, wait for the trade loop, and read the helper's log for the broker's refusal. |
| `… (the helper: no machine credential; the helper stopped trading this machine's identity, and its log gives the reason; restart agent-secrets-helper once that is fixed)`, from any command or `machine login-status` | A helper in identity mode whose trade ended in a way no retry cures: the broker refused this machine (a machine no entry of the deployment lists, say), or it answered a token with no launcher credential in it. Its trade loop stopped, and no credential comes until the helper restarts. A login does not cure it. While the credential it last traded for is still live, sessions keep enrolling and `machine login-status` is `issued`, saying that nothing renews it and that no session enrols under this machine's credential after it lapses; a person signed in on the machine still enrols sessions under their own sign-in. | Read the helper's ERROR line `the helper stopped trading this machine's identity: nothing renews its launcher credential, …`, whose `error` gives the reason, fix what it names in the deployment, then restart `agent-secrets-helper`. |
| The helper's log: `the helper could not keep the machine login's refresh on disk; removed the machine file …` (ERROR) | A refresh rotated the login's token, but the machine file could not be written: a full disk or an exceeded quota. The helper removes the machine file at once, since it names a token the broker rotated away and a restart presenting that token past its five-minute grace would revoke the machine. It holds the new login in memory, keeps working, and retries only the save every 15 s, with no further token request. A save that lands writes the file back. | Free space; the next save writes the file back. A restart before the next good save holds no login: [log the machine in](/legion/broker/guides/log-a-machine-in/) again. |
| The helper's log: `… nor remove the machine file: a restart before the disk is writable again presents a token the broker has rotated away …` (ERROR) | The filesystem refuses even the removal (read-only). The file still names the rotated-away token. | Do not restart the helper until the filesystem is writable again: a restart before then presents that token, and the broker revokes the machine as a reuse, ending every session it enrolled. Once it is writable, the next save keeps the login. |
| `agent-secrets: helper unreachable at …` | The helper is not running, or the socket path is wrong. | Start `agent-secrets-helper`, or point `AGENT_SECRETS_HELPER_SOCK` at its socket. |
| `agent-secrets enroll: ENROLL_FAILED: timed out waiting for <person>'s sign-in on this machine, which another call holds while it trades…`, or the same line from `unenroll` (`UNENROLL_FAILED`) | The helper was trading the sign-in of the person signed in on the box for another call, and that trade did not end within the 20 seconds the helper gives the command. `enroll` made no enrollment and `unenroll` ended none: the helper had sent the broker nothing for this command, or, for `enroll`, the broker had refused its first try under that person's sign-in (the line then goes on `, to drop the credential the broker refused (…)`). | Check that the broker is up and that the helper's `AGENT_SECRETS_URL` reaches it, then run the command again. |
| `agent-secrets register: AGENT_SECRETS_HELPER_SOCK is unset and no helper socket is at … (machine sessions only; an agent box has a key dir instead)` (exit 2) | No helper listens on the default socket, `$XDG_RUNTIME_DIR/agent-secrets/helper.sock`, and `AGENT_SECRETS_HELPER_SOCK` names none. | Start `agent-secrets-helper`, or set `AGENT_SECRETS_HELPER_SOCK` to the socket it listens on. |
| `agent-secrets register: NOT_A_SESSION: pid … is in no registered session and no session launcher (omp) is an ancestor of it, so a session registered for it would end with this command; relaunch the session under agent-secrets register --exec -- omp …` (exit 1) | `register` without `--exec`, with or without `--session-id`, was run from a process that is in no registered session and has no `omp` session launcher above it. A session rooted at that process would end with the command, so the helper refuses it. | Run it from inside a session launched by `agent-secrets register --exec -- omp …` (or `--exec` for the command that starts the session), which is where a launcher learns the session id to register. |
| `agent-secrets register: BAD_REQUEST: pid … is above the live session rooted at pid …, so a session rooted at it would hold that session's processes too; …` or `BAD_REQUEST: pid … is "…", not a session launcher (omp): …` (exit 1) | `register` without `--exec` named, as the root to pin, a process that is above another live session, or one that is no `omp` launcher (a tmux server, a login shell). A session rooted there would hold processes of other sessions, so the helper refuses it and changes nothing. | Run `register --session-id` from inside the session it is for, or relaunch the session under `agent-secrets register --exec -- omp …`. |
| `agent-secrets register: the agent-secrets-helper at … did not attach the session to its launcher (it is from before this fix); restart it on this release, or relaunch the session under agent-secrets register --exec -- omp …` (exit 1) | The helper running predates `register` without `--exec` attaching the session to its launcher: it names no session root in its answer, and it may have pinned the register command's own process, which has ended, so the session it enrolled is nobody's. A client of this release refuses such a helper's answer, so upgrade the helper before the client. | Upgrade the helper to this release and `agent-secrets-helper install --url …`, or relaunch the session under `agent-secrets register --exec -- omp …`. |
| `agent-secrets register: the agent-secrets-helper at … answered pid … as the session's root, which is not an ancestor of this process…` (exit 1) | The helper answered a session rooted at a process that is not above the register command, so that session is not the one the command runs in; the command prints nothing on stdout for it. | Run `agent-secrets register --session-id` again from inside the session; if it says the same, relaunch the session under `agent-secrets register --exec -- omp …`. |
| `the launcher credential reached its expiry; run: agent-secrets machine login, and have a human approve it`, `the broker refused the launcher credential (expired or revoked, …); run: agent-secrets machine login, and have a human approve it`, or `the broker refused the machine login's refresh: it was revoked, lapsed, or its refresh token was reused; run: agent-secrets machine login, and have a human approve it` (from `machine login-status`) | The credential expired or was refused: no refresh reached the broker for `BROKER_LAUNCHER_CREDENTIAL_SECONDS`, [revoked by the person who approved it](/legion/broker/guides/revoke-a-session/#end-a-machines-login), a refresh token spent twice, a clock far off the broker's, or an `AGENT_SECRETS_URL` that is not exactly the broker's public URL. A token is spent twice when a copy of the machine file refreshed it elsewhere, or when the broker's answer to a refresh was lost and the broker then stayed unreachable past its five-minute grace: the helper retries every 15 s for as long as the broker does not answer, and a retry after the grace counts as reuse, which revokes the machine and ends its sessions. A helper in identity mode (`AGENT_SECRETS_MACHINE_IDENTITY`) ends the line with `the helper's trade loop is trading this machine's identity for a new credential` instead: its credential lapsed while the broker refused or did not answer its trades. | Fix the clock or the URL if either is wrong, then log in again. In identity mode, read the helper's log for the broker's refusal, and wait for the trade loop. |
| `ENROLLMENT_NOT_LIVE` from `agent-secrets renew` (exit 76) | The session ended: it was revoked (its launcher unenrolled it, or its machine login was revoked), its lease ran out while a broker was serving, or, for a machine's own session, the machine login its Google identity traded for has ended (the row below). A lease that ran out while no broker was serving is not ended, so a broker outage alone does not cause this ([when no broker is serving](/legion/broker/concepts/#when-no-broker-is-serving)); a broker that runs but that the session cannot reach does. The renewer names the enrollment, HTTP status and code; the pod shim stops restarting the renewer, and the pod has none until it is relaunched. | Start a new session (a pod: relaunch it; a box: a new key and enrollment, [run an agent in a container](/legion/broker/guides/run-an-agent-in-a-container/)). |
| Every session on one fleet machine stops renewing at once, the broker logging `broker: machine session renewal refused: its machine login has ended enrollment=…` (WARN) and answering `ENROLLMENT_NOT_LIVE` | A machine's own session renews only while the machine login its Google identity token traded for is live. That login has ended: it was revoked, it passed the hour's expiry the identity token gave it and the machine has not traded again, or its account is no longer listed for its service in `BROKER_VM_SERVICES`. Every session of that box lapses within one `BROKER_LEASE_SECONDS`, with its grants. A person's sign-in sessions on the box, and every pod, are unaffected. | If the box should still be trading, check that it can reach the broker and still mint an identity token (`AGENT_SECRETS_MACHINE_IDENTITY` and its own variables), and that the account is in `BROKER_VM_SERVICES` and within the `BROKER_VM_PROJECTS` and `BROKER_VM_INSTANCES` pins, redeploying the broker after a settings change ([Operate](/legion/broker/operate/#what-to-run)). The sessions enrol again on their own once a trade succeeds. If the fleet was dropped on purpose, this is that change taking effect. |
| `PROOF_INVALID` | The broker refused the proof itself: its `iat` is outside `BROKER_PROOF_SKEW_SECONDS`, its key does not match the enrollment, or `AGENT_SECRETS_URL` differs from the broker's public URL. A renewer keeps retrying this code because a clock or URL correction can make the next proof valid. | Check the clock and URL; for a key mismatch, start a new session. |
| `the broker's host … does not resolve` or `… name resolution failed`, each naming `GET`/`POST` and `AGENT_SECRETS_URL` | The call never reached a broker: the address's host either resolves nowhere, or its name resolver timed out or failed. Usually a stale or mistyped `AGENT_SECRETS_URL` was inherited. It is not a refusal the broker gave. | Set `AGENT_SECRETS_URL` to the broker's current public URL in the profile your shells and agents start from, and start the session again. |
| `nothing answered at …: the connection was refused`, `nothing answered at …: no connection could be made`, or `… did not answer in time`, each naming the call and `AGENT_SECRETS_URL` | No connection to the broker was made or it did not answer: nothing listens at the address, the network or host is unreachable (a route, a firewall, a VPN or tunnel that ended), or the broker is too slow. | Check the address, the route to it, and that the broker is running. |
| `the broker at … answered but the exchange failed`, naming the call and `AGENT_SECRETS_URL` | A peer took the connection and then broke the exchange: a TLS certificate it would not trust or an HTTP server answering an `https` URL, or the stream ended or was reset after the request. It is not a broker refusal. | Check the address's scheme and port, TLS configuration and any proxy between the session and the broker. |
| `the request to the broker at … failed`, naming the call and `AGENT_SECRETS_URL` | The request failed in a way none of the rows above names; the error after the colon is the transport's own. | Read that error; it says which layer failed. |
| `the broker's address is not a valid URL`, naming the call and `AGENT_SECRETS_URL` (exit 1) | `AGENT_SECRETS_URL` is not a URL the client can build a request from, such as a bad `%` escape or a port that is not a number. Nothing was sent. | Set `AGENT_SECRETS_URL` to the broker's public URL, escaping any `%`, `@`, `/`, `?` or `#` in a user name or password. |

## An enroll or unenroll with an unknown outcome

`agent-secrets enroll --helper` and `agent-secrets unenroll --helper` ask the machine's helper,
and the helper asks the broker. When the broker's answer does not come back, nobody on the machine
knows whether the broker made, or revoked, the enrollment. These messages say so, and each exits 1.

| Message | Cause | Fix |
| --- | --- | --- |
| `ENROLL_OUTCOME_UNKNOWN: the outcome is unknown: …; the broker may have made the enrollment; run the same enroll again: it answers the enrollment the broker made, if there is one`, from `agent-secrets enroll --helper` | The enrollment request may have reached the broker, and the helper did not get a result it could read. The message then says `the request may have reached the broker, but the helper did not get its result (…)`, with the failure in the parentheses: the connection failed after the request was sent, the broker or a proxy in front of it answered with a 5xx status, or the answer could not be read. The message also comes when the enrollment did not end within the helper's 20 seconds: the failure in the parentheses then ends in `context deadline exceeded`, and the request may not have been sent in full; or the message says `the operation did not end in 20s` when the helper was still waiting to send the request. The broker may have made the enrollment, and `enroll` wrote no `enrollment` file. | Run the same command again, with the same runtime id and thumbprint. If the broker made the enrollment, it answers with that enrollment, and `enroll` writes its id. A box's launcher unenrolls only an id it recorded: if it does not run the command again, an enrollment the broker made ends only with its lease, `BROKER_LEASE_SECONDS` after the broker made it ([when the box stops](/legion/broker/guides/run-an-agent-in-a-container/#when-the-box-stops)). |
| `agent-secrets enroll: the helper gave no answer (…). So it is not known if the broker made the enrollment. Run the same command again: if the broker made the enrollment, the command gets that enrollment.` | `enroll` sent its request to the helper, and the helper closed the connection or did not answer within 30 seconds. A helper older than `ENROLL_OUTCOME_UNKNOWN` gives itself only 5 seconds to write its answer, but waits up to 30 seconds for each request it sends the broker. When the broker answers after those 5 seconds, that helper cannot write the answer and closes the connection without one. When the broker takes 30 seconds or more, `enroll` stops waiting first. The broker may have made the enrollment, and `enroll` wrote no `enrollment` file. | As for `ENROLL_OUTCOME_UNKNOWN`. Run the helper on the same release as `agent-secrets`, so that it answers with the broker's outcome. |
| `UNENROLL_OUTCOME_UNKNOWN: the outcome is unknown: …; the broker may have revoked the enrollment; it is safe to run the same unenroll again`, from `agent-secrets unenroll --helper` | As for `ENROLL_OUTCOME_UNKNOWN`, for the revoke: the revoke may have reached the broker, and the helper did not get a result it could read, so the broker may have revoked the enrollment. | Run the same command again. The broker answers the revoke of an enrollment that already ended as done, so the command exits 0 once the enrollment is revoked. If no run succeeds, the enrollment ends with its lease once the box's `agent-secrets renew` stops. |
| `agent-secrets unenroll: the helper gave no answer (…). So it is not known if the broker revoked the enrollment. It is safe to run the same command again.` | As for `enroll`'s message of the same words, for the revoke. | As for `UNENROLL_OUTCOME_UNKNOWN`. |

## A pod's renewer cannot read its token

| Message | Cause | Fix |
| --- | --- | --- |
| `agent-secrets renew: ERROR: enrollment … cannot read its pod token (…); nothing was sent, so its lease lapses unless the file becomes readable` | The pod's renewer (`agent-secrets renew --pod-token-file`) could not read its projected service-account token, or read it blank, so it sent the broker nothing. The broker never hears of it, so this line in the pod's container log is the only record. The renewer does not exit 76 for it: at start it exits 2 and the worker shim starts it again 5 s later, and after a renewal it waits and reads the file again. If the file stays unreadable the enrollment's lease lapses, and its grants end with it. | Check the projected-token volume is mounted read-only at `/var/run/legion/agent-secrets-token` in the pod's container (`roles` in an issue pod), with the file `token` present and non-empty, and that the container's user can read it: the volume's mode is `0440`, readable through the pod's `fsGroup`. Once the file is readable, the next renewal succeeds. |

## The request was refused

| Message | Cause | Fix |
| --- | --- | --- |
| `request … to the broker AGENT_SECRETS_URL names … was denied` (exit 77) | The approver denied it, or one of the names is a service's secret, which only that service's sessions get. Nothing ran. | Ask the approver why, or ask for the names you may have. |
| `request … to the broker AGENT_SECRETS_URL names … was denied: <NAME>: a reason is necessary; ask again with --reason` (exit 77) | The request named a secret a person must approve — a human-tier secret, one your operator withheld from this session, or another person's agent-tier secret — and carried no reason, or only spaces. The broker asks nobody to approve work the record does not describe, so it denied the whole request. ## A request the judge decides is pending, refused, or with a person

A request for keys whose profiles' `proxy` blocks let the model judge decide is the judge's alone while it holds
it, for at most two minutes from when it was written: it carries `judge_deciding` and no page, and it
is on no person's list. The judge then grants it, refuses it for good, or hands it to its person
once, as an ordinary card ([Concepts](/legion/broker/concepts/#the-model-judge)). A refusal reads
`the model judge refused this request: <reason>. This request will not be granted. Tell whoever
gave you this work.` and `agent-secrets` exits 77. Do not send the same request again: tell
whoever gave you the work what the reason says. What the judge decided, and why, is one
`request.judged` row in the broker's `audit` table and one line in that broker's log,
`broker judge: wrote a verdict`, naming the record, the verdict, the model's reason and, where a
check stopped the run, `failed_check` and `failed_detail`; a refusal's line adds `decided=denied`
and the `refusal` its agent read.

| What you find | Cause | Fix |
| --- | --- | --- |
| A request for a judge key is on the approver's list from the start, with no row and no line | The broker that took it runs no judge (its `BROKER_JUDGE_*` settings are unset), the request also names a key a person decides, or a key is an administrator's. | The approver decides it, as before. |
| No row and no line, and the request reached the approver two minutes after it was written | The run passed its 35 seconds or the broker stopped serving under it, which logs `broker judge: the run ended before it wrote anything`. | The approver decides it. Tell whoever runs the broker if it keeps happening. |
| `a requested secret requires a shorter grant lifetime … --ttl …` when the request is written | The judge would decide the request, and its lifetime is longer than a judge key's seconds. Nothing was written and the judge was not asked. A request a person decides keeps the ordinary lifetime rules. | Ask again with the `--ttl` the message names, or less. |
| `failed_check=rules-judge` or `failed_check=lifetime` | The profiles file changed between the request and the run, so a key's profile's `proxy` block no longer gives the judge seconds, or no longer covers the lifetime. The request went to its person. | The approver decides it. Which keys the profiles file gives the judge is the deployment's own choice, changed only in that file (`BROKER_PROFILES_FILE`), which a person reviews. |
| `failed_check=policy` | The tag policy, read again at that moment, no longer answers approval for a key: its owner or tier changed, or it left the broker's policy. | `failed_check=admin` | A key was tagged as an administrator's (`admin: "true"`) after the request was written. A person approves every release of one, so the request went to its person. | That approver decides it. |

| `applied=false` | The judge's grant or refusal wrote nothing; for a grant, `not_applied` says why. Dispatch did not answer the approval's own check in time, which the broker's log also names at WARN (`the judge's approval was not applied`): it is still pending, and went to its person. | `applied=unknown` | The judge granted, the approval's answer was lost (`not_applied` names what came back), and the broker could not tell whether the approval applied (`applied_unknown` says why): the read of the approval's own row failed, or the approval was still committing when the broker's wait for it, half the time it had left to write the row, ran out. The broker's log says it at WARN (`whether the judge's approval applied could not be read`). Read the record's own state: `granted` means the approval applied. A `pending` state, read during the hold or after it, does not prove the approval did not apply, since one still committing may yet grant the request; read it again before acting on it. |

## Managing a secret

These are the messages of `agent-secrets secret`
([manage a secret](/legion/broker/guides/manage-a-secret/)). A usage error exits 2 and leaves
the store as it was. SIGHUP, Ctrl-C, Ctrl-\\ or SIGTERM at the value prompt ends the CLI by that
signal (a shell reports 129, 130, 131 or 143) and leaves the store as it was; every other failure
exits 1. On GCP, `create` makes the secret, empty and with its tags, before it asks for the value,
so a store that refuses the create asks for none. From then until the value is added, a create
that stores no value deletes that empty secret before it exits, and asks the broker to reread the
name: on a usage error, on the store's refusal of the value, and on one of those signals at any
point in between. It deletes nothing that may hold the value: after an add whose answer leaves
that open it deletes nothing at all, and every delete first checks that the secret carries its own
`agent-secrets-create` label and holds no version. Before it asks for the value it asks IAM whether
your sign-in may add one, and stops there where it may not. On GCP it reads the value for ten
minutes at most, the time the broker holds the new secret as waiting for its value, and gives up
after that; on AWS, where it makes nothing before the value, the read has no such limit.
Each store call from the create until the value is stored or the empty secret deleted has a
deadline of 60 seconds, on AWS's `CreateSecret` and each gcloud token refresh too. That bound is
per call, not per signal: a signal waits out the call in flight, and its cleanup then makes its
own calls, each with the same deadline, so a first signal against a store that answers nothing can
take a few minutes to return; a second signal while it waits ends the CLI at once, by that second
signal, after one line naming what the store may be left holding. Every command the CLI
prints for settling what a create left signs in as that create did.
