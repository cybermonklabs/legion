what-that-means: a durable step whose result never reached the journal is run again by the replacement process: Restate's guarantee for a Run block is at-least-once, and exactly-once only for a Run whose result the server recorded
state-for-a-handler-that-ran-with-its-outcome-unknown: no: the journal does hold a Run command with no result notification, so the server can see the step was begun and did not return -- but that state is not do-not-re-run, it is re-run. The next attempt executed the body again, and the side effect happened twice. Restate has no third state between 'not done' and 'done'
work-bound-to: a deployment, which is an endpoint URL: sys_invocation.pinned_deployment_id, set on the first attempt and kept
work-bound-to-a-process: no: Restate has no notion of the process behind the URL, so any process listening on that URL may be handed the work, and a process is replaceable without the server noticing
if-the-pinned-endpoint-never-comes-back: the invocation retries against that URL with an exponential backoff -- initial-interval 500ms, factor 2.0, max-interval 1m -- for max-attempts 70, and then does what on-max-attempts says, which in this server's own effective configuration is "pause"
limit: one invocation, one durable step, one kill, on a single-node server with one partition: it shows what Restate records and re-runs when the process behind a deployment dies inside a step, not how a cluster behaves, nor what happens when the server rather than the service process is the thing that fails
