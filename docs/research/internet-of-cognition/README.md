Each mode declares what it needs in one table, which `--help` prints and the mode checks before it reads or judges anything: the tools on `PATH` (`git`, `curl`, `jq`, `python3`, `uv`, `go` and the `dispatch` command, each where its mode runs it), a `git` whose `git grep -P` works for `--citations` and a `grep` whose `grep -P` works for `--replay` and `--landed`, since each reads a token an author wrote, a cited symbol, a commit or a record, as a whole token by a Perl-compatible regular expression, and a program built without PCRE would read every such token as missing, the history `--shape` and `--landed` read, the clone root, `DISPATCH_URL` and `DISPATCH_TOKEN_FILE`, the Dispatch token this pod already holds, and, for `--replay` and the `--self-test` that runs it, `IOC_DEPLOYMENT_REPO`, the deployment repository written `<owner>/<name>`, whose form the mode checks too. `--landed` needs nothing installed: the committed proof of each landed step reads the commit it names with `git show`. It clones what it needs under `$TMPDIR/ioc-clones`, one commit deep and with no tags, which is the clone the triage read.
The gate reads GitHub through `git` and the REST API and never through `gh`, which in a Legion pod is scoped to this project's owners alone: a repository's files from a clone at pinned commits, and what only the REST API answers, a pull request's reviews, times and size, with `curl`. No recorded command and no script a row runs calls `gh`, and `--admitted` refuses a row that does.
`--replay` also needs the deployment repository, which this public tree names nowhere, as `export IOC_DEPLOYMENT_REPO=<owner>/<name>`, the repository the deployment applies from, and a `git` credential helper that answers for it, as a Legion pod's `legion git-credential` does. Rows read it at pinned commits, most from a blobless clone `env.sh` fetches under `$IOC_CLONES/deployment` at the commits `sources.json` pins, whose entry names the variable and no url, and a few its pull requests through the REST API, at `https://api.github.com/repos/$IOC_DEPLOYMENT_REPO/...`. ## How a cited symbol is read

`--citations` reads the `symbol` field of each code citation by one grammar, stated in `check.sh`'s header above `resolve_symbol` with the case of `check.test.sh` that pins each form, and listed here.
A symbol is a list of parts, split at each comma and at each ` and `.
Each part is read against its file: the paths the citation's `file` field names, until a part names a file, which is its file and the file of every part after it.
"Text the file holds" means text the file holds as a whole token: `TesterVerdictRequire` does not stand in `TesterVerdictRequired`.
"A file beside the cited paths" means a cited path that is the name or ends with it, the name in a cited directory or in the directory of a cited file, or, for a name holding `/`, that path from the repository's root; a bare name is never looked for elsewhere in the repository.
A cited path names itself, each character as it is written, and every path below it where it is a directory. A glob, a path holding `*`, names each path whose elements match it, each `*`, or run of `*`, any run of characters within one path element and every other character itself, and every path below a directory it names; it is read from the root where it holds a `/`, and at any depth where it holds none, as `*.py` names every Python file. Every reading of a cited path, the search of its files' text among them, reads that one set: `notes/a[bc].md` names that file and never `notes/ab.md` (case 218), `notes/*` names `notes/deep/x.md`, `notes/**/x.md` names `notes/a/x.md` and never `notes/a/b/x.md` (case 219), and `*.cfg` names `notes/deep/x.cfg` (case 220). The repository's paths are read as git lists them with `-z`, never quoted, so `docs/café.md` and a path holding `\` or `"` are read as they are written (case 223).
Each part is in one form, decided by its text alone, in this order, and read by that form's rule alone, but for a table head (8): a part in neither 1 nor 2 that begins with `[` and ends with `]` is a table head, whatever later form its text would also fit.

1. A line or a line range, alone, after a colon or after a name and a colon: `88`, `88-97`, `:188-196`; `file:line` and `file:line-line`, as `pr-body.md:33-34`, whose name is a file beside the cited paths, which becomes the part's file; `Symbol:line`, as `askOnMessage:306`, whose name is text the file holds. The file holds that line, or the range's last line; a line is 1 or more, a range does not end before it starts, and a line read against a directory or a glob is not read.
2. A part in words, holding a space: text the file holds; else, holding a colon, a prefixed name (6), whose readings can hold it and never fail it, so where the reading of 6 that applies does not hold it, it is read on as when none applies: `deploy: the replica count` cited in a directory that holds `deploy.py` is not checked, as it is where no `deploy.py` stands (case 217); else, holding `|`, `*`, `?` or `\`, a pattern by the rules of 8, a table head where it begins with `[` and ends with `]`, else an extended regular expression or a glob; else it is not checked, and `--citations` lists it as not checked, as `[project] dependencies = []` is. A path inside it is not read as a path.
3. A quoted string with no space, as `'strict'`: text the file holds, its quotes among it.
4. A name, `Symbol`, of letters, digits, `_` and `-`, its first character no `-`: text the file holds.
5. A key path, keys joined by dots, a key being a name, a name followed by `[]` or by digits in brackets, or a string in double quotes: `Envelope.Validate`, `SKILL.md`, `scenarios[].overlays`; a key path in square brackets is a table head (8). In turn: a file's name beside the cited paths, which becomes the part's file; text the file holds; a file's name that a path at or below the cited paths ends with, and no path elsewhere in the repository; and, holding a dot, a qualified name: `file.ext.Symbol`, whose prefix is a file beside the cited paths and whose local part that file holds; `module.symbol` or `pkg.module.symbol`, whose longest leading run of components names a Python module, a `.py` file or a `.pyi` stub by its stem after the directories above it, a `.py` before a `.pyi` of its name among the files the citation names, a package's `__init__.py`, or its `__init__.pyi` stub where no `__init__.py` stands among the files the citation names, by its directory, or such a module below a cited directory, and each name after the run, a class or attribute and then the local part, stands in that file; or, for a part that does not start with a digit (below), `Namespace.Symbol`, whose local part and each component of whose prefix the file holds. A file of any other extension is never read as a module: `core.schema.load` cited in `lib` reads `lib/core/schema.py` and never `lib/core/schema.json` beside it (case 210), and `schema.load` cited in `pkg/schema.json` is read as `Namespace.Symbol`, so the file must hold `schema` too (case 211). `pkg.func` cited in `pkg/__init__.pyi` reads that stub, and `core.setup` cited in `lib` reads `lib/core/__init__.pyi` where no `lib/core/__init__.py` stands (case 222).
6. A prefixed name, `prefix:local`: text the file holds; else `file:Symbol`, `module:attr` as Python's entry points write `pkg.mod:func`, or `Namespace:Symbol` as the Turtle term `mas:sessionId`, each read as in 5, and the part fails where the one that applies does not hold it.
7. A path, holding `/`: a file beside the cited paths, which becomes the part's file; text the file holds; a file's name that a path at or below the cited paths ends with; or a path, a directory or a glob the commit holds, from the root or below a cited directory or glob, never read as a pattern over text. A glob here is read as in a `file` field, above: `src/c++/*` names `src/c++/x.h` and never `src/cc/x.h` (case 216). A part below a cited glob is read where that glob is read, so below a glob holding no `/`, at any depth: `sub/tools` cited in `pkg*` holds where `a/pkg1/sub/tools/run.sh` stands, and not where only `a/pkg1/other.py` does (case 221).
8. A pattern: a table head, a part in neither 1 nor 2 that begins with `[` and ends with `]`, and any other part holding `|`, `*`, `?` or `\`. Its text alone decides how it is read. A table head, as TOML and INI write one, holds only on a line of the file that is that head: spaces or tabs, none or more, the head, spaces or tabs, none or more, and nothing after them but a comment that begins with `#` or `;`. Its brackets are themselves and never a bracket expression, its inside is read by the glob rule below, and it is never read as text the file holds. So `[tool.*]` holds where a line is `[tool.ruff]`, and neither in a file with no head under `tool` nor in one whose only such text is `tool.x`; `[project]` holds where a line is `[project]` or `  [project]  # metadata`, and neither where the only head is `[projects]` nor where `[project]` stands inside a line, as in `# the [project] table`; and `[project.optional-dependencies]` holds where a line is that head. Any other holding `|`, `(`, `[` or `\` is an extended regular expression: text the file holds, or a line of the file it matches, read as written, as `grep -E` reads it: `consensus|majority|quorum`; `v(1)?_total` and `v[0-9]?_total`, which hold in `v1_total` and not in `vx_total`; `\bv1_total\b`, which holds in `v1_total` and not in `xv1_total`. One that begins with a bracket expression writes something before it or after it, as `^[a-z]*_total` or `[a-z]*_total$`, since a part that begins with `[` and ends with `]` is a table head. Any other, holding `*` or `?`, is a glob of names: text the file holds, or a name the file holds as a whole token that the glob covers, each `*` any run of letters, digits, `_`, `.` and `-`, the empty run among them, each `?` exactly one of them, and every other character, `.` and `_` among them, itself. So `GEN_AI_*` holds in `GEN_AI_MODEL` and not in `GEN_AIRPORT`, `gen_ai.*` in `gen_ai.request.model` and not in `gen_aix_total`, `a*_total` in `a_requests_total` and neither in `ba_requests_total` nor in `a_requests_totals`, and `v?_total` in `v1_total` and neither in `v10_total` nor in `xv1_total`. Any other `(` or `[` makes no part a pattern: `match(row)`, holding none of `|`, `*`, `?` and `\`, is in no form.

Any other part, as `match(row)`, `$row` or `Engine::match`, fails `citation-our-code` or `citation-project-code` by name as a part that is not a symbol form the gate reads, and is never read as text.
A part that starts with a digit and is no line is never read as the line its first digits name. In no form, it fails by name as no line, as `3–9` written with a dash does.
In 3 to 8, every reading of its form that reads it as a file or as text the file holds reads it: in 5, a file's name beside or below the cited paths, text the file holds, `file.ext.Symbol` and `module.symbol`; in 6, text, `file:Symbol` and `module:attr`; every reading of 7 and of 8. So, cited in `notes`, `2024-report.md` holds where `notes/deep/r/2024-report.md` stands and `2024/` where `notes/2024/` does (case 212); `2024-report.md:Title` and `2024_report.main` hold where their file or module holds the name (case 213); and `2024-*` holds where a file holds `2024-11-23` (case 214).
A namespace reading, `Namespace.Symbol` or `Namespace:Symbol`, reads such a part neither as a file nor as text, so it never holds it. Where no reading of its form applies to it, it fails by name as no line: `3.14` fails so in a file that holds `3` and `14` as words and not `3.14` (case 215). A file or module reading that applies and does not hold it fails naming that file, as for any part.
A citation whose `file` field names no path, only words, holds its symbol to no file, and each of its parts is listed as not checked.

## What the gate does not read

`--coverage` prints this list beside the assertion table, and that printing is the one this directory keeps:
whether the ranking is right, whether the reconciliation is fair, whether the reading is deep, whether a cited text supports the claim beside it, whether a candidate that cannot be argued in one page was left off the list, whether one fact is written once, and whether an engineer-day estimate is right.
The tester and the reviewer read those by reading the deliverable against the question list.
