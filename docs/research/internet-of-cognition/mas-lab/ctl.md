## What `ctl` is

`ctl` is the multi-agent command line of the stack [m-ctl-package-role].

It installs as `mas-ctl` and registers 16 commands, among them `compile`, `compose`, `validate` and `run-mas` [m-ctl-cli-commands].

A multi-agent system is a YAML document, `mas.yaml`, with `kind: MAS` [m-ctl-mas-workflow-fields].

The deployment side of a specification is a second document, `kind: InfraBundle`, which `ctl` reads into `InfraManifest` [m-ctl-infra-manifest-fields].

`InfraManifest` holds endpoints, models, proxies and tool servers only; it holds no phase, no trigger and no workflow field [m-ctl-infra-no-workflow].

The compose step turns the merged documents into an effective bind and a placement plan [m-ctl-compose-models].

## The overlay mechanism

An overlay is a patch document merged onto a base document [m-ctl-overlay-rfc7396].

The merge is RFC 7396 JSON Merge Patch with added rules for agent lists [m-ctl-overlay-rfc7396].

A patch leaf can carry an explicit operation: `replace`, `add`, `remove`, `clear` or `merge` [m-ctl-overlay-ops].

Which fields a patch may touch, and how each one merges, is read from the kind's own JSON schema through an `x-merge` annotation on the field [m-ctl-overlay-xmerge].

The `spec.workflow` field of a MAS document carries `x-merge: {strategy: replace}`, so an overlay replaces the whole workflow block and never patches one row of it [m-ctl-mas-workflow-fields].

## How `ctl` compiles a specification

`compile_manifest` loads the document, applies the overlays, attaches Controls and fills the runtime defaults [m-ctl-compile-entry].

The result is a dictionary, not a program: `fill_agent_defaults` writes default values into `spec`, for example the design pattern and its `params` [m-ctl-compile-defaults].

Compilation produces no transition table and no generated code.

## How `ctl` runs one

`execute_run_mas` composes the manifest, materializes the agents and then runs one session loop on the entry agent [m-ctl-run-entry].

The other agents are reached as tools: `wire_peer_delegation` gives each agent a delegation tool for every peer the workflow names in `delegates_to` [m-ctl-run-delegation].

The order of work inside one user turn is therefore the model's choice of tool calls, not a table [m-ctl-run-delegation].

## Our own workflow table

Our workflow is the Go value `workflow.Table` in `packages/daemon/internal/workflow/table.go` [m-ctl-our-row-struct].

A row is a struct with five fields: `From`, `Trigger`, `Guard`, `To` and `Effects` [m-ctl-our-row-struct].

I counted the rows by building the package and printing `len(workflow.Table)`.

The table holds 38 rows [m-ctl-our-row-count].

17 of them are written out in the literal [m-ctl-our-literal-rows].

The other 21 are generated by `backwardRows` from `phase.BackwardPairs` [m-ctl-our-row-count].

`TriggerKind` has 13 named values [m-ctl-our-triggers].

`EffectKind` has 4 named values [m-ctl-our-effects].

A guard is a Go function over `Snapshot`, a record of three fields [m-ctl-our-guard-snapshot].

The engine picks the first row whose `From`, `Trigger`, optional target and guard all agree [m-ctl-our-first-match].

## Question 1: can its specification format express Legion's phase workflow?

The short answer is no for the MAS manifest, and partly for one design pattern inside it.

`ctl` has three places where a flow can be written.

### Place 1: `MAS.spec.workflow`

This is the only workflow block `ctl` executes.

Its model holds two fields: `entry` and `nodes` [m-ctl-mas-workflow-fields].

A node holds `id`, `role`, `agent`, `delegates_to`, `dispatch`, `config` and `description` [m-ctl-workflow-node-fields].

There is no from-phase, no trigger, no guard and no effect field.

This block cannot hold one row of our table.

### Place 2: the standalone `kind: Workflow` manifest

This document has `spec.edges`, and an edge holds `from`, `to`, `condition` and `label` [m-ctl-workflow-v1-edges].

`from`, `to` and `condition` are a near fit for our `From`, `To` and `Guard`.

The edge has no trigger field and no effect field.

The word `edges` does not appear anywhere in the `ctl/` tree [m-ctl-edges-absent-in-ctl].

The project says itself that this manifest is a schema only and that `mas-ctl run-mas` does not execute `edges` or `condition` [m-ctl-edges-doc-claim].

So this document can hold part of a row, and nothing runs it.

### Place 3: the `state_machine@v1` design pattern

This is the only transition table in the stack.

It is a plugin of `library-standard`, not of `ctl`, and its table rides inside an agent's `spec.design_pattern.params` [m-ctl-sm-table].

The table has `states`, `start`, `vars`, `signals` and `max_steps`; each state has a `run` kind and a list of transitions under `on` [m-ctl-sm-table].

Field by field, against one of our rows:

- The from-phase maps well: a state name is the `From` of every transition listed under it [m-ctl-sm-table].

- The to-phase maps well: a transition's `goto` is the `To`, and it must name a declared state [m-ctl-sm-table].

- The guard maps partly: a transition's `when` is a mapping of path to condition, and the conditions are the 9 operators `eq`, `ne`, `in`, `not_in`, `gt`, `gte`, `lt`, `lte` and `exists` [m-ctl-sm-operators]. Our `HasOpenOrMergedPR` is a boolean of a record, so `when: {pr_open_or_merged: {eq: true}}` would hold it, but the variable must first be put in the machine's own `vars`, because the machine reads only its variables and the outcome of the state that just ran [m-ctl-sm-operators].

- The effects do not map: a transition row has exactly three keys, `when`, `set` and `goto` [m-ctl-sm-transition-keys]. `set` writes the machine's own variables and nothing else [m-ctl-sm-transition-keys]. An effect must become a state of its own, because only a state can act, and a state can only `delegate`, `react`, run another `pattern`, run `parallel` regions, call one `tool`, or `end` [m-ctl-sm-run-kinds]. Our four effects are durable outbox writes on a session and an issue; the nearest the model offers is a `tool` state [m-ctl-sm-run-kinds]. So one Legion row with two effects becomes a state plus a transition, and the table grows.

- The trigger maps badly: there is no per-row trigger field [m-ctl-sm-transition-keys]. A transition fires on the outcome of the state that just ran, not on a named outside event [m-ctl-sm-table]. The one outside event the model knows is a steer, which arrives as `signal` with four fields, `text`, `sender`, `source` and `intent` [m-ctl-sm-signal-fields]. A named trigger could be written as `when: {signal.intent: {eq: tester_passed}}`, but only under `signals`, and only while a run is in flight [m-ctl-sm-signal-fields].

- The ordering maps well: the `on` rows are tried in order and the first match wins, and the `signals` rows are tried before them [m-ctl-sm-order]. This is the same rule our engine uses [m-ctl-our-first-match].

Two further facts limit place 3.

The schema that covers `design_pattern.params` has `additionalProperties: true` and declares no `states` key, so a state table is free-form YAML to `ctl` [m-ctl-sm-params-unvalidated].

The words `state_machine` and `validate_definition` do not appear in `ctl/src`, so `mas-ctl validate` checks no state table; the plugin checks it at run time [m-ctl-sm-absent-in-ctl].

A deeper mismatch is scope.

A `state_machine` run is one turn of one agent, and its states are delegations to peers [m-ctl-sm-table].

Our phases are the states of an issue that lives for days, and our effects start and suspend whole sessions [m-ctl-our-effects].

### The answer

The specification format of `ctl` cannot express our phase workflow as a specification [m-ctl-answer-1].

`MAS.spec.workflow`, the one block that runs, holds an entry and a node list alone.

The `kind: Workflow` document holds from, to and a condition, and nothing executes it.

The `state_machine` table holds from, to, a guard and the first-match order, but no trigger field and no effect field, it is not part of `ctl`, `ctl` does not check it, and its states are agent turns rather than issue phases.
