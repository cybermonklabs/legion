# r7: a real Dispatch issue written against SCOPE's ontology

Input: dispatch://INFRA-3134, read from Dispatch on 2026-11-12.

The test is this.

Take one real issue of this deployment, write its node graph in Turtle using only SCOPE's own classes and properties, and run their SHACL shapes over it with `pyshacl`.

The graph conforms [ts-conforms-1], the validator bites when a required triple is taken away [ts-bites-content] [ts-bites-custom], and the list of what the ontology cannot hold runs to twenty-eight parts of that one issue [ts-gap-count].

No service of theirs was started; `pyshacl` and `rdflib` ran as libraries [ts-no-service].

## The shapes

`mas-shapes.ttl` is not committed; it is generated by `scripts/generate_shacl_shapes.py` and gitignored, so a reader who clones the repository has no shapes file until they run the generator [ts-shapes-generated].

The shapes graph was assembled the way their own `verification.py` assembles it: the five ontology files, the generated `mas-shapes.ttl`, and the committed `mas-shapes-custom.ttl` [ts-shapes-graph].

With every severity counted the graph does not conform: twenty-four results, all `sh:Warning`, none `sh:Violation` [ts-strict-1].

With `--allow-warnings`, which is the line their own `verification.py` draws, it conforms [ts-conforms-1].

The twenty-four warnings are all the same two: every `mas:AgentCall` is warned for having no `mas:hasToolCall` and no `mas:hasLLMCall` [ts-agentcall-warnings].

A Dispatch issue has no tool call and no model call, so that warning is the ontology saying the graph is not a trace.

## What conformance forced into the graph

Three things had to be put in the file that the issue does not contain.

`mas:containsSemanticGroup` is `sh:minCount 1` at `sh:Violation` on `mas:MAS`, and a `mas:SemanticGroup` in turn requires `mas:nSessions`, `mas:splitDistance`, `mas:embeddingModel`, `mas:nodeHash`, `mas:hasMedioidSession` and `mas:containsSession`, all at `sh:Violation`, so a conforming graph must state an embedding model and a clustering split distance that a Dispatch issue has never had [ts-forced-embedding].

`mas:executes` is its own `sh:minCount 1` shape and the ontology does no OWL inference, so asserting the subproperty `mas:executesAgent` does not satisfy it and every execution node must carry both [ts-no-entailment].

`mas:inputTo` is `sh:minCount 1` at `sh:Violation` on every `mas:State`, so the last state of a chain has to point back into a transition it did not feed, which is how the ask's answer and the final claim are written here [ts-state-closure].

## The validator bites

Taking the one mandatory `mas:content` triple off the state that holds the answer to the issue's ask makes `pyshacl` refuse: two `sh:Violation` results naming `mas:content` and the focus node `d:s-ask-answer`, `Conforms: False`, exit status 1 [ts-bites-content].

Pointing the session's initial state at a state no other execution element claims trips their own hand-written SPARQL shape `mas:SessionInitialStateSharedShape`, which prints its own message, `Conforms: False`, exit status 1 [ts-bites-custom].

## What this says for the verdict

SCOPE's ontology is a trace schema.

It holds who called what, when, for how long, and what text went in and came out, and it holds that well.

A Dispatch issue is a record of agreement: who asked, who answered, what was approved at which version, what each check proves, what blocks what.

None of that has a term here [ts-gap-count], and the two layers the shapes make mandatory — an execution span with a start, an end and a duration, and an embedding cluster over sessions — are exactly the two things an issue does not have [ts-forced-embedding] [ts-gap-event].
