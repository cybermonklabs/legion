# Anchor every criterion and every claim to a named SHA, and tell code heads from handoff heads

When a criterion names a moment the repository cannot resolve ("the branch's first push", "the same text"), the plan converts it into a derivable rule and a named handoff field that every later role reads at that SHA and nowhere else. Record it once (`firstPushSha`) and never rewrite it; keep a separate moving field (`codeSha`) for the newest code head.

Write the exact SHA you measured into the artifact that carries the claim: a proof entry, a review body, a `Look at first` or `Not proven / risk` line. Never write "at the pull request head" in a durable line; your own handoff push moves that referent before anyone reads it. If you approve the head your push creates, say in the review which SHA each measurement came from.

On a branch whose handoff pushes carry `skip-checks: true`, a handoff head has no workflow runs of its own and its green verdict is carried from the newest code head. Read CI at the code head, name its run ids, and prove the handoff head's `gh run list --commit <handoff-sha>` is empty; never present a carried verdict as measured at the handoff head.

A tester records both the head it tested and the head its own handoff push created; the daemon and the next role name the pushed one.

Cite a fact inside a file that is itself on the pull request (a handoff JSON) by file plus quoted text, not by line number: the file grows between rounds and the line moves.

Do not count pull request rounds from `pulls/<n>/reviews`: a reply through the review-comments API creates a bodyless `COMMENTED` review. Count on `state` plus a non-empty body, or on the Legion footer.

## Evidence

Pull request `sjawhar/legion-smoke#571`, issue LEGSMOKE-760. The branch's literal first push was the planner's handoff `4570f895` (no marker file, trailer, zero runs); plan decision 1 defined "first push" as the first commit touching `smoke/LEGSMOKE-760.md`, recorded as `firstPushSha = cf8054a50b7c71a5b6b6017967be53f6d6605bd5` in `implement.json` and `test.json`, and criterion 2 was read there by every role even after review round 1 appended a second line at `7150490a`.

Every handoff head measured zero runs (`b4d78c6b`, `53fd4bfc`, `26adec84`, `5ddf5e7b`: `gh api …/check-runs` → `[]`), while each code head (`cf8054a5`, `d60255ff`, `7150490a`) carried exactly four `success` runs; both workflows are unconditional on `push` and `pull_request`, so an empty list is the trailer's doing.

The approving review 5511115901 is recorded at `5ddf5e7b` and says the file decodes to the two-line reference "at the head"; the reviewer's byte read was done at `26adec84` and `5ddf5e7b` did not exist until the reviewer's own handoff push one minute earlier. `5ddf5e7b` appears in no handoff file. `test.json` names the head it tested (`b4d78c6b`) but not the head it pushed (`26adec84`), which is the one the reviewer's task line named.

Reviews 5511000773 and 5511012875 cite `implement.json:73` for a sentence that the next round's inserted proof entry moved to line 82, where `review.json` and the approval cite it. Of the seven entries in `pulls/571/reviews`, four are bodyless `COMMENTED` rows generated by thread replies, not review rounds.
